Decomp, recomp, reimplementation: one game as a case study

Legend of Legaia has been ported twice over the same months, by two separate efforts taking different routes: a static recompilation and this from-scratch engine. That makes it a rare side-by-side. This page sets out what each route gets up front, what it has to earn, and why building a new engine is a far more practical option than it used to be.

Three established routes

There are three established ways to carry a console game's logic onto new machines, and each makes something different. Matthew Stanley, whose PSXRecomp is the recompiler in this case study, writes of decompilation and recompilation that "They produce different things — infrastructure and understanding". Reimplementation produces a third thing: an engine of its own, running the original's data.

Reimplementation has a long record. OpenMW is "an entirely different game engine that does not use the original executable file in any way". OpenLoco finished reimplementing its game in C++ in December 2025. On PlayStation, Severed Chains is The Legend of Dragoon "disassembled and rewritten in Java". Legaia now lets the route be compared directly with a recompilation of the same game.

Terms on this page

A port is a result, not a method. A PC port can be built on a decompilation, a recompilation or a new engine. "Reimplementation" here means the whole game's engine; a recomp's runtime also reimplements libraries and hardware, which is a narrower thing. Engine recreations are often divided into top-down and bottom-up: built from specifications and then tuned, or rebuilt from the disassembly. This project is bottom-up in what it reads and new in what it writes.

What actually runs

The names blur, but the question that separates them is concrete: when you press Start, whose code is executing?

Legaia suits the third column unusually well. Field scripts, effects and moves are bytecode on the disc, so porting a VM carries every script written for it. The same fact is why the disc has so much for a new engine to read.

One game, two ports, the same months

Both projects started in spring 2026, within weeks of each other, so the histories can be read side by side. Dates below come from each project's commit log.

  1. The recompiler proven on the PS1 BIOS.
  2. Tomba! boots, then reaches gameplay.
  3. Widescreen and further renderer backends, framework-wide.
  4. A Legaia fork: overlay cache, then CD and XA fixes. Field, battle and summons run.
  1. First release: Rust workspace, format docs, Ghidra tooling.
  2. A walkable overworld, with collision and encounters.
  3. The disc patcher and randomizer, on the same parsers.
  4. The full-game ladder, retail corpus and soak harness.
  5. A run on pad input alone reaches the credits.
  6. Expansion packs, game modes and netplay.

Read plainly, the recomp wins on time to game by a wide margin. The Legaia branch's own commits span three days. They stand on three months of framework work, and that framework also carries Tomba! and Mega Man X6. The reimplementation needed about five months from its first release to reach the credits, and it is an engine for this one game. Nothing else on this page undoes that.

What the timeline also shows is the order value arrives. The reimplementation produced useful things long before it was a game: format docs, viewers and a disc patcher, each useful on its own before the engine could play the story. Those docs helped the other project too. The fork's README credits them, saying they "materially shortened the investigation and guided the runtime's overlay-cache fixes". And once the engine existed, what came next were things no translated binary offers cheaply, like expansion packs that name monsters and quests instead of addresses.

The last row is not a legal claim

No court has settled any of this. The nearest test, Take-Two's case over the GTA re3 and reVC projects, ended in dismissal with no ruling on the merits. A reimplementation written by people who read the disassembly is not "clean-room", and this project does not use the term; the boundary it does enforce is narrower. Whether AI assistance changes that picture is unresolved too.

The same problems, paid for differently

These come from the two Legaia ports. Each cost something on both sides, in a different place.

An item that freezes the game

Recomp

Using a Healing Leaf deadlocked. Legaia's CD callback can wait for a vblank from inside an exception handler, and the runtime scheduled none there. One fix in the hardware model also cleared Spirit actions, Hyper Arts and summons.

Reimplementation

That bug cannot exist, since no libcd runs. The cost that came with it was missing too: retail battle frames run long during a CD-XA clip, five to seven vsyncs. The engine played them at the normal rate until that was measured and modelled.

A recomp's bugs tend to be global and fixed once. A reimplementation's costs are local and found one at a time.

Code that is not in the executable

Recomp

The translator sees the boot executable. Overlays load at runtime into a reused window, so they are captured as they load and then compiled, or interpreted until they are. Jump tables need help too: the renderer's computed jr does not resolve statically.

Reimplementation

Overlays are extracted from the disc and read once, with no need to reach them in play. The price is bookkeeping: overlays share addresses, so an address alone names nothing, and these docs have been wrong about that.

The recomp's problem is finding the code. The reimplementation's is knowing whose code it is reading.

A bug no local test could see

Reimplementation

The GTE model passed its own sweep, because the sweep agreed with the model. The screen-coordinate FIFO saturates at signed 11 bits, and nothing here knew that.

Recomp

Running retail's code, it produced real input and output pairs from the GTE, which exposed the difference at once. Its value here was as a second, independent execution.

Each route makes the others better. Here, each has been the other's best instrument.

How a mistake shows up

The biggest practical difference between the routes may be what happens when somebody misreads the original.

That third row is the real historic objection to reimplementation. Without something to compare against, you can only say it feels right. It is also why this project spends so much on measurement: the retail-oracle method exists to turn that silence into a number. Even so, a score only speaks for what it sampled. A matching decompilation's proof is stronger, and nothing here replaces it.

Why reimplementation is more viable now

Reimplementation has had two standing problems: years of labour before the first reward, and that silent drift. Both have become more tractable, for connected reasons.

  • The labour is the kind coding agents do well. Reading a routine, writing the equivalent function, wiring it up, and repeating that across a whole game was the cost. By hand, that work is measured in years: OpenLoco finished reimplementing its game in C++ only in December 2025.
  • The instruments have got cheap to build. Scriptable emulators, readable save states and headless Ghidra existed already. What a small project could not afford was the software on top: state readers, scoring channels, ratchets and replay. An agent can write those too.
  • Those two fit together. An agent is a fast and confident writer, and silent drift is what a fast, confident writer produces. A reimplementation with measurement gives that writer something external to answer to.

What got cheaper

  • Reading a routine and writing its equivalent.
  • Wiring, and the sweeps nobody wants to do by hand.
  • Single-purpose tools, written for one question.
  • Docs that stay current because they are written with the change.

What did not

  • Retail captures, many of which need someone on the pad.
  • Deciding what counts as right, and which scores to trust.
  • Noticing that a green test measures nothing.
  • Standing in a community that may not want this.

This is not an argument that AI favours reimplementation alone. This project is written with Claude Code. So was the prototype of PSXRecomp, by an author with no compiler background, who adds that "the process still requires significant human oversight". Matching decompilation may have the best signal of the three, since a byte match is an unambiguous score: Chris Lewis matched one N64 game in 84 days against 596 for its sequel, with a different compiler and prior experience in the mix, and estimates it would have stalled around 89-90% without human experts. His 2025 view was that "We're a long way from 'vibe coding' being viable for matching decompilation."

The narrower claim is the one this case supports: all three routes got cheaper, and reimplementation had the most to gain, because labour was the thing that ruled it out for small teams. It need no longer be a commitment of many years. It is still a lot of careful work. Human judgment remains in the loop, and a project that skipped the measurement half would be producing exactly what its critics expect. The register of disproved readings is a public record of how plausibly wrong a reading can be.

The community cost is real

decomp.dev is sunsetting its main index, writing that AI "can expedite the decompilation process in a significant way" with the right guidance and that "the community aspect of decompilation has been broken". DarioSamo, who led Banjo: Recompiled, declined "a race to the bottom" with AI-generated ports. Severed Chains states "AI was not used to create this project", which is a useful reminder that a reimplementation has never needed it. Work built on other people's research owes those people credit, and this one tries to pay it in its acknowledgments.

Choosing a route

You want the game on modern machines, as it wasStatic recompilation, if a framework for the console exists. Nothing here competes with it on speed.
You want to know exactly what the code saysMatching decompilation, if the compiler can be pinned down.
You want the game to become more than it wasReimplementation, especially if much of the game is data, the target cannot carry its code, and you can measure against the original.
You want to play it tonightAn emulator, or an official release if there is one.

The routes also combine. This project uses a recomp as an oracle, Ghidra's output as a pointer and an emulator as the judge, and a matching decompilation of Legaia would be a better reference than any of them.

What this case cannot show

  • It is one game, and a heavily data-driven one, which flatters this route.
  • The two efforts are not equal in attention. The recomp's Legaia branch is days of work on a general framework. This repository has been about nothing else. Neither side has logged hours, so no labour comparison is possible.
  • There is no third column. As far as this project knows there is no public decompilation of Legaia, so that route is argued from other games.
  • "Reaches the credits" is not "identical to retail". Parity is measured over what the corpus has sampled, and it is still being worked on.
  • A recomp's state moves. What is described here is the Legaia branch as last published, and the framework has continued since.
  • The author has a side. This page is written by the project it argues for. The links are there so that you can check.

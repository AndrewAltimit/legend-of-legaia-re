Frame benchmark: what the engine costs a player

Two drivers measure the engine on a fixed set of scenes and on the way into them: scripts/ci/frame-bench.py on the native window and scripts/ci/frame-bench-web.mjs on the browser play page. They print tables and assert nothing. A frame-time gate on a shared machine can only flake, so the numbers belong in a before / after comparison on one machine, and not in the repo. What does gate is the cost ratchet, on counts rather than times; the proof that a browser change drew the same picture is the frame hash.

At a glance

Native

scripts/ci/frame-bench.py # every scene, both fidelities scripts/ci/frame-bench.py --scene town01 --mode enhanced --repeat 5 scripts/ci/frame-bench.py --json before.json # raw rows for a diff scripts/ci/frame-bench.py --exe new --base-exe old --repeat 5 # the two builds alternating

The driver builds legaia-engine with engine-shell’s bench-alloc feature and runs play-window tick-locked: one sim tick per drawn frame whatever the wall clock did, so every run walks the same frames and only the time varies. The audio director runs over a device-less output. It prints the fastest of --repeat runs with the spread between them, which says how far to trust a row on a busy box.

The stages are the frame profiler’s. The worst frame’s own stage breakdown goes to stderr beside each row, which is how a hitch gets a name. LEGAIA_PROFILE_ALLOC_SITES=1 on a bench-alloc binary samples allocation call stacks and prints the heaviest at the end, as [alloc-site] lines.

Entry

scripts/ci/frame-bench.py --entry --base-exe old --repeat 7 # paired against another build scripts/ci/frame-bench.py --entry --entry-scenes town01,koin1

legaia-engine entry-bench enters each scene and forces a fight from it with no window and no GPU, one [entry] <scene> <step> <ms> line per step. The first round enters through the scene picker and carries the once-per-process caches; the second, labelled scene+, is what a door back into the scene costs. What a window adds past these steps (surface, pipelines, mesh upload, draw lists) is the frame table’s startup row.

Browser

scripts/ci/build-wasm.sh # or point --site at a scratch copy scripts/ci/frame-bench-web.mjs --scene town01,battle --profile scripts/ci/frame-bench-web.mjs --site /path/to/other/site --json out.json scripts/ci/frame-bench-web.mjs --paths --vsync # the player's ways in; at the display's rate scripts/ci/frame-bench-web.mjs --cpu-throttle 6 # a proxy, labelled one

It serves a site/ directory itself, loads the disc named by LEGAIA_DISC_BIN through the page’s own file input, and enters each scene through the page’s own scene list. Each row reports the page’s frame function as a main-thread cost, every wasm export’s time, calls and returned bytes per frame, GL calls per frame, long tasks, and the scene-entry time.

--pathsA New Game and a card load, each on a fresh page; --card and --card-block pick the save.
--cpu-throttle nSlows the renderer’s main thread. A proxy, and the output says so: it shows which costs scale with the CPU and says nothing of a device. Read it with --vsync: uncapped, the page queues GPU work until a backpressure block of over a second, which no capped page builds.

The summary line reports the head of the disc’s read, the disc-load export (load_disc_spans) and the module’s memory size. A bundle built with web-viewer’s bench-alloc feature adds wasm allocations per frame. A wasm profile names its functions by index; wasm-bindgen --keep-debug over the cargo artifact gives a file whose name section resolves them.

What the frame function leaves out

Each browser scene row carries these beside it, so one run answers where a weak device pays.

A battle row waits for the page’s battle scene, not a frame count: the intro runs on sim ticks, so on a page drawing faster than the sim ticks a frame count ends inside it. The second_fight scene plays a first fight to its end, results included, then forces the fight the row times, which is where a memo would show.

Cost ratchet

scripts/ci/cost-ratchet.py --check # the gate, against scripts/ci/cost-baseline.json scripts/ci/cost-ratchet.py --measure --runs 10 # the spread between runs, nothing compared scripts/ci/cost-ratchet.py --write-baseline # after a real change, with its ledger entry

Times flake and counts should not, so this ratchets counts, each from a tick-locked run that walks the same frames every time. It is the cost-ratchet gate in full-gate.py. A rise past a count’s room fails; raising the baseline is a loosening, which check-baseline-loosening.py sends to the ledger with its reason.

What the numbers have shown

These are shapes that recur, not measurements.

  • A posed body re-parses its TMD every frame. Both hosts’ posed builders walk every primitive, which is why a primitive’s corner streams are held inline rather than as four heap lists each.
  • A per-tick copy can live in one host only. An owned read of a whole PROT entry in a browser export’s tick path is invisible on the native window, which holds its own copy. The per-export table is what shows the difference.
  • Shadow layers multiply the draw count. A draw wholly outside a lamp’s frustum writes no depth to that layer, so both hosts test each mesh’s box per light.
  • A first entry pays for what a scene never reads. The 64 cast modules parse on a module’s first read, the fog ground on the first tick with the toggle up, and a scene load asks for an entry’s class without the byte statistics a report carries. Each deferred value is a pure function of what the load captured, so its reader gets what it would have had.
  • Whole-disc copies cost at the wasm boundary. A wasm memory never shrinks. The page’s image stays on its side of the boundary and load_disc_spans copies across only the files the runtime keeps.
  • A page need not read what it may never play. The image is the largest read on the way in, and two thirds of it is movies and XA, which reach the page behind the engine (the disc image).
  • The scene picker’s first pick walks every scene. The arrival catalog reads each scene’s MAN and .MAP to find its doors, once per process. A door, a New Game and a card load do not build it.
  • The capture frame’s cost is the GPU, not the bytes. readPixels on the battle transition’s arming frame waits for that frame to finish, and the wait does not shrink with the size of the read. An asynchronous read would land the capture frames later, which moves the transition.
  • The worst battle-edge frame is the stage, not the capture. Where the transition hands over, one play_frame_ticks builds the battle stage and party forms.

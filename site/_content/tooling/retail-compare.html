Retail comparison corpus

How far is the port from retail, and where? The retail comparison corpus answers that for every captured moment at once. For each retail save state in the library that the engine can be put into, it seeds the engine into the same situation, lets it settle, and scores what the engine shows against what retail showed - channel by channel, state by state - then ranks the states worst first and holds the scores to a ratcheted baseline. It is the breadth sibling of the single-mechanism oracles: those pin one subsystem exactly, this one measures the whole port at every moment someone captured.

How it works

Nothing here runs an emulator. A save state’s RAM holds every retail observable the corpus compares, and its VRAM holds the frame that was on the TV - the display registers say which rectangle - so retail’s side is read offline. The engine’s side is a real session seeded through the port’s own card-load path and ticked forward.

The driver builds legaia-engine first (--no-build skips it) and exits cleanly with a [skip] line when the save-state library or the extracted disc is missing. Both are gitignored, per-machine data: the library is your own captures of your own disc.

Reading the report

report.md opens with the channel means over the seeded states and the class counts, then lists every seeded state worst first, each channel with both sides’ values and, when the frame ran, a side-by-side image. The unseeded states close it, each with its reason; report.json carries the same rows for scripts.

The worst states are the product. For each, decide first whether the divergence is the instrument’s - a seeding gap - or the engine’s:

  • a camera channel at 1 beside a bad image is a rendering question;
  • a camera channel far off on a state whose label names a cutscene is script progress;
  • a bgm miss on an arrival state is capture timing - a door caught before the new scene’s field init ran.

Trace switches (LEGAIA_RC_CAM_TRACE, _POS_TRACE, _DRIVE_TRACE, _FX_TRACE, _SEED_TRACE) open a battle state up further: which component of a camera framing misses its endpoint and which input put it there, how the combatants got where they stand, and which seeding stream the battle search tried.

The side-by-side PNGs are retail pixels

The report directory holds frames from your disc. It stays under the gitignored captures/ tree and is never committed.

The ratchet

The baseline file holds, per state label, each measured channel’s score and the state’s class. The disc-gated test re-runs the corpus and fails when:

  • any state’s channel falls below its baselined score (beyond a JSON round-trip slack);
  • a baselined channel of a state the run did seed goes unmeasured;
  • a seedable state fails to seed, or no state seeds at all.

A rise is allowed and is folded in by a reviewed --bless, which merges: a state outside the filter or one the run could not seed keeps its baselined channels, and a run without a display keeps each image score. A channel that no longer applies to a re-classed state leaves the file rather than failing every later check.

States the manifest tags as made on a patched disc replay a modified executable, so their RAM and frame are not retail’s. They stay in the corpus - some are the only capture of their scene - but sit outside the headline means and the ratchet; a drop there prints as [patched-drift] for review. A difference on such a state is a lead to confirm against a retail capture, not a measured engine defect.

The corpus

Every scenario in scripts/scenarios.toml whose backup fingerprint resolves to a library save state is one corpus state. Each is classed by the game-mode word and the scene label:

A field state is named by the scene it is running, which is not always its label. A walked door writes the destination label frames before the field init loads the block, so a capture in that window shows the outgoing scene under the incoming label; the corpus scores it as the scene actually loaded and records the label as pending.

The live game-state window is byte for byte the front of a save block - the save composer copies exactly these bytes - so the corpus pads it to a block and lifts it through the same parse a memory-card load uses. Party, story flags, bag and gold therefore come out in the engine’s own schema on both sides. Both emulators’ states crop the displayed frame by one rule: display start and mode from the GPU’s last GP1 writes.

The seeding model

  1. Resume. The engine opens the state’s scene through its own card-load path over the lifted save: story flags first (retail’s order, so an entry script reads the saved story), then the scene entry, then party, flags, bag and gold.
  2. Seat. The player stands on retail’s (X, Z) with the floor-sampled height, as a warp landing. The walk-on dispatcher’s last-tile pair is stamped with the seat tile, because a player standing on a trigger tile has already fired it.
  3. Camera. The arrival snap composes from the state’s own camera parameter block - whichever region record was installed last, which is walk history a tile re-query cannot recover.
  4. Frame step. The step retail was running at is rebuilt from its frame-time ring and handed over; it decides which script waits can complete.
  5. Settle. The session ticks a fixed window with no input - or, for a mid-script, battle or menu state, runs to that state’s phase.

The image channel is rendered by play-window, the real renderer, run as a child process seeded the same way (a scratch save resumed with --resume-save, then seated) and screenshotted at a fixed world tick. A --scene door entry is deliberately not used: it runs the scene’s arrival from the picker’s seat, so the frame would score the arrival rather than the scene.

What seeding does not carry

Each of these is an instrument limit, not an engine verdict:

  • Script progress outside a running record the phase gate reaches.
  • Actor state - NPC positions, animation phases, open doors, live effects - is whatever the engine’s own entry produces.
  • Timing. Retail’s frame is one instant; the engine’s is a fixed tick after entry. Some history is held through the warm-up instead of run as game time - the field VM’s script counters and the BIOS rand() seed, so every warm-up draw is the one retail would make next - and a few phases are aligned explicitly: the field HUD’s idle countdown and the palette the ambient colour cyclers write. Ambient animation and water palette walks cannot be phase-aligned.

Mid-script states

A field capture taken while a spawned script record runs holds that record’s context on retail’s actor lists: its script base, program counter, record index and wait accumulator, plus the cutscene camera mover’s progress. Such a state is not sampled a fixed window after entry. The engine runs until its own context for the same record - matched by the record’s first bytes - holds retail’s PC with at least retail’s wait and at most retail’s glide left, or has just executed the op retail is parked on.

Dialogue is met on the frame the capture shows: a box that has typed its page and waits for the press, or - for a capture caught mid-typing - the same row with the reveal counter at least the capture’s. A gate the run never meets within its deadline falls back to the settle-window sample, and the script detail says which happened.

Battle states

A battle capture carries its whole encounter in RAM: party and monster counts, the command-flow byte and action-state cursor, the monster ids, the scripted-fight bit, the present party and every combatant’s HP and MP. The seed replays the fight from a running field, as retail entered it, and then places it at the capture’s phase. Each step exists because leaving it out moves a channel for a reason that is not a port defect:

  1. Enter the fight with the captured formation, party and stage variant.
  2. Pin the random stream at the entry, searched over, since the capture holds the stream at the capture rather than at the entry.
  3. Stand the combatants on their captured ground positions and headings, taking back pushes the capture already holds.
  4. Land the HUD glides and each body’s animation keyframe the capture had already reached.
  5. Take back hits already landed this action, rewards already granted and turns already spent.
  6. Place the phase - drive the engine’s own command surfaces, one press every other tick, to the captured command-flow state, action state and acting seat; a replayed cast runs to its gate.

Fields a capture probe wrote into RAM after battle init, and fields on a patched-disc state, are listed in the detail but left unscored.

Menu states

A menu capture names its screen in the menu overlay’s sub-screen word. The pause menu’s screens - Items, Magic, Equip (and its slot browse and candidate list), Status, Options, Load, Save - are seeded: the field seed runs, then the pause menu is driven through its own pad path, Start, Down onto the row, Cross. The menu channel is 1 when the engine holds the same sub-screen. Title, boot and script-entered screens (the casino prize exchange) stay in the report as classified limits.

Channels

Each channel scores in [0, 1]; a state’s score is the mean of its measured channels. Distances score 1 inside a tolerance and fall linearly to 0 at a cut-off, so a near miss and a far one read differently.

party, flags and inventory are seeded straight from retail, so on their own they check the seeding and whatever the settle window changed - an entry script that grants an item, a flag the save round trip does not carry.

The image channel

Retail draws a 320 × 224 area, so the compared frame is the top 224 rows of the display crop. The port keeps a 320 × 240 logical screen whose rows line up with retail’s draw rows, rendered at an integer scale and box-filtered back down.

within (the score)
the fraction of 8 × 8 blocks whose mean colour is within a fixed tolerance of retail’s on every channel
mae
mean absolute error per channel per pixel, for reference

Block means rather than pixels: the engine rasterises at its own resolution with its own filtering, so a per-pixel test would mostly score dither and sub-pixel edges. A block test moves on a wrong camera, missing or extra geometry, wrong palettes and wrong overlays. A retail frame dark enough to be a fade is not scored - a dark engine frame would match it and say nothing.

The child runs at retail framing with every enhancement off: retail camera distance, no enhanced lighting, no ground fog, no see-through-walls fade, no entry pulse, no photosensitivity slew. It is also tick-locked - exactly one world tick per redraw - so a fogged scene’s frame does not move with machine load.

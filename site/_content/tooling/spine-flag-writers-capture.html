Capturing the chapter-1 spine story-flag writers

Legaia records story progress as story flags - single bits in a RAM bitmap that scene scripts check to decide what happens next: whether a door is open, whether a boss has been beaten, whether the mist walls around Drake Castle have fallen. The "spine" is the chain of mandatory chapter-1 story beats, and the question this page answers is: which code sets each spine flag? The writes happen inside overlays (code the game loads into RAM on demand), so static analysis of the executable alone cannot name the writer. This runbook is the dynamic answer - one interactive PCSX-Redux play-forward session, human at the controls, that arms watchpoints on every spine write at once and logs each writer's return address (ra - i.e. who called the flag-setter). It is maintainer infrastructure, kept as a worked example of a live writer hunt.

What problem this solves, and when to reach for it

A story flag is set by one line of one script somewhere on the disc, and a bare save-state diff only tells you the bit flipped - not who flipped it. The trick this runbook uses is to put an execution breakpoint on the game's own flag-setter function (FUN_8003CE08, SCUS-resident) filtered by the flag index in its a0 argument register. Every hit names the calling code directly, and that return address is what gets attributed to an overlay and then to a script carrier. Reach for this pattern when:

  • a story gate is unexplained - a scene checks a flag whose writer is in no static image;
  • you want to bracket a story beat with catalogued save states for later oracles;
  • you need the whole flag-provenance stream of a play segment, not one flag (the firehose variant below).

At a glance

  • Emulator: PCSX-Redux in interpreter + debugger mode. Never --fast - Lua breakpoints do not fire under the recompiler.
  • Probe: scripts/pcsx-redux/autorun_spine_flag_writers.lua (three targets) or autorun_flag_firehose.lua (every flag write). Neither self-quits; wrap the launch in timeout.
  • Where to start: the chapter-1 ladder memory card, loaded by name on the in-game load screen.
  • The result so far: story flags in chapter 1 are written exclusively by the field-VM's 0x5x/0x6x script ops; flag 0x142 is caught and closed to a script byte in the rikuroa MAN; flags 0x482 and 549 remain the standing capture targets.

Quick start

Localise first, then hunt. The exec-breakpoint watches force the interpreter (~10 fps), so a --fast dynarec run of autorun_state_poll.lua (the two-tier model) first logs which scene each flag changes in at full speed; then point the interpreter session there. Both probes share the USA-build version guard (lib/probe/version.lua).

Card-save play (the primary mode). Configure PCSX-Redux to use the ladder .mcr as memory card 1 (persisted in its GUI settings, or copied into the emulator's memcards dir before launch), cold-boot, load the slot from the in-game load screen, and play forward:

LEGAIA_NO_SSTATE=1 xvfb-run -a timeout --kill-after=15s 1800s bash scripts/pcsx-redux/run_probe.sh --lua scripts/pcsx-redux/autorun_spine_flag_writers.lua

Drop xvfb-run -a to see the window and drive it yourself; raise the 1800s budget for a long forward run. If you already hold a .sstate near a beat, skip LEGAIA_NO_SSTATE and seed from it instead:

LEGAIA_SSTATE=/path/to/pre-zeto.sstate xvfb-run -a timeout --kill-after=15s 900s bash scripts/pcsx-redux/run_probe.sh --lua scripts/pcsx-redux/autorun_spine_flag_writers.lua

Output lands under captures/spine_flag_writers/<run-ts>/; a caught write is a CSV row with a non-zero ra (see below).

What gets watched

Two watch methods: a plain write-watch on a RAM address, and an execution breakpoint on the flag-setter 0x8003CE08 filtered by a0 - the latter names the calling code directly. The probe installs a bare Vsync listener with no self-quit (this is a human-at-the-controls session), arms the watches once the game settles into field mode, and streams every hit to a CSV.

The Zeto row is kept only because the probe still arms it. Zeto (0x4B, byte-confirmed name in PROT 867) fights in scene garmel, and its formation [0x4B,0,0,0] is installed by the FUN_801DA51C actor[+0x94] record path - not the DAT_8007b7fc battle-id path, which reads 0 everywhere and may be vestigial. Derived watch addresses

Flag-bank geometry (SCUS-resident): base 0x80085758, byte = base + (idx >> 3), mask = 0x80 >> (idx & 7).

The exec-bp path is preferred: it isolates the exact flag and names the writer ra directly, which a raw byte watch can't (eight flags share one bank byte). Set LEGAIA_FLAG_FALLBACK=1 to additionally arm the raw byte watches if a flag write is somehow missed by the setter breakpoint (then decode the ra by hand).

Which emulator

PCSX-Redux, not mednafen. These are live watchpoints, which need the interpreter + debugger. run_probe.sh sets -interpreter -debugger by default; do not pass --fast - Lua breakpoints do not fire under the recompiler. The mednafen toolkit answers the offline half (which bytes changed between two states) but cannot name a writer.

Which card slot for which beat

The chapter-1 ladder card saves/library/cards/playthrough-ladder-pro00-14.mcr holds 15 active slots (PRO-00..14, blocks 1..15). Story-flag state is read directly from each SC block's bitmap (block offset 0x14C0, mirroring RAM 0x80085600). Load the slot nearest the beat you want, then play forward:

Load saves by name on the in-game load screen, never by block position: the card's physical block order does not follow the PRO numbering (verify with save-tool saves <card>; e.g. PRO-01 sits mid-card, after PRO-03/04/05). PRO-00 is a viable single start for a forward run past the Caruban beat.

Mist-wall caveat. Flag 0x482 is unset across every slot of this card. It is not bracketable from this card: keep the watch armed and play forward past the Zeto beat to the Drake mist-wall story event (chapter2_garmel_pre_zeto brackets it), or source a different card that sits nearer it. This is the one leg that needs fresh forward play - the others are one short walk from their load slot.

The firehose variant - capture every flag write, not just the spine

autorun_flag_firehose.lua generalizes this session: instead of filtering to the spine targets it logs every story-flag SET (FUN_8003CE08) and CLEAR (FUN_8003CE34) with the writer ra, every battle-id staging write (0x8007B7FC), and every scene-name / game-mode transition as a context timeline - one CSV (flag_firehose.csv: tick,kind,value,pc,ra,mode,scene,count).

Per-key repeat suppression (first 8 of each (kind,flag,ra), then every 64th with a running count) keeps hot per-tick callers from flooding the file; a long session stays in the hundreds of KB. Prefer it for any play-forward longer than a single beat: the same session that catches the spine writers also banks the full flag-provenance stream for later analysis, so nothing needs re-capturing. Same launch shape, same emulator constraints, same attribute_overlay_hits.py post-pass per row.

Beat order for one full session

With PRO-00 loaded (or the tightest slot per beat), the flags fall in story order, so a single armed session can sweep several:

  1. keikoku - walk the Kikoku Cliff leg (sets 0x193; not watched, but the marker that you're on the spine).
  2. rikuroa (Caruban trigger) - enter Mt. Rikuroa; Caruban is 0x142-gated. Caruban's own formation mechanism is still un-captured and worth re-checking with the firehose.
  3. Caruban victory - win the fight; the post-victory record P2[50] sets 0x142 (the write the firehose caught; the probe labels the row flag_0x142_dolk_clear).
  4. dolk dungeon - continue through to Zeto in garmel.
  5. mist-wall event - continue to the Drake mist-wall story event; the flag_0x482_mist_walls row fires (this leg needs fresh forward play; see the caveat above).

What a “caught” hit looks like

Output lands under captures/spine_flag_writers/<run-ts>/:

  • spine_flag_writers.csv - one row per hit: tick,label,addr,pc,ra,value.
  • spine_flag_writers.detail.txt - call-context (GPRs + code + stack) for the first N hits of each label (LEGAIA_MAX_DETAIL, default 8).

A caught write is a CSV row whose ra column is non-zero - that is the writer's return address, the whole point of the hunt. For the flag rows, pc is the setter 0x8003CE08, value is the flag index (322 / 1154), and ra is the game-logic caller that requested the set. That ra is what to attribute by containment (attribute_overlay_hits.py) to find the owning overlay. (For the Zeto row, value would read 75 with pc the store site - it never fires.) The [spine] HIT ... lines in pcsx.log mirror each CSV row live, so you can watch the hunt land without opening the CSV.

Attribution caveat The static field-overlay image is wrong at the writer VAs (previous-occupant strata and aliasing - see a small overlay does not clear the slot). Attribute callers by disassembling the resident bytes from a same-mode save state, not from static overlay dumps.

What the captures settled

  • Flag 0x142 - caught, then closed statically. The SET fires at the rikuroa post-Caruban beat, ra 0x801E3598 = the field-VM dispatcher's own 0x5x SET arm. The source is script bytes 51 42 in the scene's streaming variant MAN (PROT 0157_rikuroa, records P1[10..12] + the self-latching post-victory P2[50]; carrier + census in script-vm). Save-state bracket catalogued as rikuroa_pre_caruban / rikuroa_post_caruban.
  • Story-flag provenance model (capture-proven). Across every chapter-1 scene traversed, story flags are written exclusively by the 0x5x/0x6x script ops; every other setter caller is an engine system touching low indices (0/3 entity-SM staging, 0x35 battle-end victory in FUN_8004E568, 0xB/0xC/0x18 interaction locks, 0xE dispatcher spawn ops).
  • Two capture targets stand: flag 549 (0x225) and flag 0x482 (Drake mist walls) - both direct code paths. For 0x482 arm a write-watch across the post-Zeto Drake-revival beat.
History: readings this runbook once targeted
  • "DAT_8007b7fc = 0x4B is the Zeto battle-id write" - falsified live. A firehose from chapter2_garmel_pre_zeto with this exact write-watch armed at width 1 and width 4 stayed silent across three reproducible Zeto fights; Zeto is a garmel record-path fight. The earlier jou-side scoping for this write is superseded.
  • "0x142 = dolk-dungeon clear" - a mislabel; the SET is the rikuroa post-Caruban beat. The probe's row label flag_0x142_dolk_clear keeps the old name.
  • "0x1BE is a Zeto gate" - the carrier-complete census closed it statically as geremi's Jeremi-arrival one-shot.
  • "The census closed 0x482" - did not hold: every census site for 0x482 is a desynced-walker alias of SJIS text (hand-disasm-falsified per class; the census now flags decode coherence per site - GFlagSite::clean).

The project-wide list of falsified readings is do-not-re-walk.

Catalogue the missing pre-write states

Each beat boundary is also a chance to close a gap in the state library. At each boundary (pre-Zeto, pre/post-mist), save a PCSX-Redux state, then fingerprint and catalogue it so the library gains the missing brackets:

scripts/manage-states.py fingerprint
scripts/manage-states.py library

Load states by fingerprint, not slot number (slot indices are ephemeral and get overwritten). These additions are valuable regardless of what the watches catch this run.

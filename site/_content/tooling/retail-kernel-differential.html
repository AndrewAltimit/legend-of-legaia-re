The retail kernel differential: run the game's own routine beside its port

crates/retail-exec is a user-mode R3000 interpreter. Its disc-gated tests load SCUS_942.54 and any overlay off your disc, seed RAM with generated inputs, call a retail routine, and compare what it wrote with what the Rust kernel claiming to port it produces. No decompiled C and no hand reading sit between the two sides. No Sony bytes are committed; without LEGAIA_DISC_BIN the tests skip.

At a glance

cargo test -p psx-retail-exec --profile dev-fast --test integration

Where it sits among the project's other checks, and what it cannot see, is the verification ladder.

What it can run

Integer instructions, hi / lo, unaligned loads and stores, RAM and the scratchpad. A routine with no break guard can run a div by zero as the chip does (Cpu::hardware_zero_div), since that result is what ships. COP0 carries its register moves and rfe; anything else there, or a syscall, stops with Stop::Unsupported.

The GTE is psx_retail_exec::gte: both register files with their quirks, every command, the 44-bit accumulator with its overflow flags, the FLAG saturation bits, the UNR divider and the MVMVA far-colour bug. It is written from the hardware documentation, not from the engine's GTE, so a defect the two shared could not cancel. Unit tests pin hand-worked spec values; gte_capture re-runs the RTPS / RTPT / NCLIP / AVSZ commands the PCSX-Redux state library's register files hold and lands on their outputs; gte_engine holds the engine's live divide and its light-source NCCS kernel to it with no disc.

  • Cpu::hook replaces a call, which is how rand() is scripted so both sides draw one stream.
  • Cpu::calls records the calls made, which is how a test proves it reached the arm it claims.

How to add a routine

  1. Read the disassemblyFind what it reads and writes. Seed those bytes with the shapes a game reaches, including the caps and the empty cases.
  2. Compare whole regionsA write the port does not know about is exactly what this is for, and a field-by-field test cannot see one.
  3. Assert the armsHold that the run reached the interesting arms, so a seed change cannot leave the test passing on nothing.
  4. Declare the routineOpen the test with differential!(scus(VA)) or differential!(prot(ENTRY, VA)), naming every routine it compares. A test with no declaration fails the coverage gate.

Declaring what a test runs

Every test opens with differential!(..), naming the routines it compares as scus(VA) or prot(ENTRY, VA), or with not_a_differential!("why") when it compares a table and runs nothing. Each argument is a literal or a const of the test file, so the declaration reads without compiling anything.

  • The run checks the declaration. Cpu::call notes every entry it runs, with the bytes there, in a thread-local ledger. When the test passes with the disc present, the macro's guard fails it unless each declared routine was entered and its bytes are the named image's. A wrong address, or the right VA in the wrong overlay, fails the test that carries it.
  • The count needs no disc. scripts/ci/differential-coverage.py reads the declarations and the // PORT: tags and reports how many tagged addresses a differential runs; --check fails on a test with no declaration or on coverage below its baseline, in the pre-commit hook and in CI.
  • Other tools read it. The port catalog carries a differential column and a --no-differential worklist; the provenance checker counts a differential-run address as verified.
  • The declaration can be derived. --record runs the suite with the ledger written to target/ (it holds the executable's bytes, so it is never committed), --propose names each entered routine's image off extracted/, and --apply writes the missing declarations.

The credit is per address: a passing differential proves which routine ran and that the kernel the test calls computes what it wrote, not that every tag carrying the address sits on that kernel, nor that every arm was reached.

python3 scripts/ci/differential-coverage.py --check

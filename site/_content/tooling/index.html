Tooling

Two very different kinds of tools live here. Some are for you: point them at your own Legend of Legaia disc image and they extract every asset, re-roll the game from a seed, or translate its text - no reverse-engineering knowledge needed. The rest are the project's own reverse-engineering infrastructure: the instruments the format docs and the engine port are built with. This page is a map by task - pick the thing you want to do and follow the card.

Pick a task

Every tool takes a disc image you supply (the project ships no game data) and reads from the extracted/ tree the extraction pipeline produces. The groups below are ordered the way most people arrive: get the assets off the disc first, then either play with the game (patch it) or dig into how it works (Ghidra, emulator capture, measurement).

  • Extract assets - turn the disc into PNGs, meshes and audio; the starting point for everything else.
  • Patch a disc - randomizer, ROM patcher, language packs. Shipped deliverables, not side effects.
  • Dig in Ghidra - the static path: disassemble the executable, recover the RAM overlays, answer "who calls this?".
  • Capture the emulator - the dynamic path: watch the retail game run and record what the code actually does.
  • Measure the port - how much of the game is understood, how much is ported, and whether the port matches retail.
  • More tooling docs - the gate and triage pages that live only on GitHub.

Extract assets

Almost everything on the disc lives inside one archive, PROT.DAT, as containers within containers. One command unpacks the whole chain.

./legaia-extract "/path/to/Legend of Legaia (USA).bin" --out extracted
Extraction CLIs
The one-command pipeline (disc → PROT.DAT → LZS → sub-asset → PNG / OBJ / WAV) plus every per-stage binary for when you want a single step.
Guide: extracting assets
The task-oriented walkthrough for a first run - what to expect in extracted/ and where to look next.
Web asset viewer
Browse a disc's textures, meshes, dialog and sound banks in the browser - nothing is uploaded.

Patch a disc

The patcher edits a copy of your disc in place - same-size edits, sector checksums re-encoded - so the result boots on real hardware and every emulator. Nothing Sony-owned is ever committed; you bring the disc.

ROM patcher (in browser)
Run the randomizer client-side: supply your own disc image, toggle the settings, download a patched image. The patch runs in WASM in your tab.
Randomizer / disc patcher
The full CLI reference: loot, encounters, monster stats, shops, doors, arts, the starting party, tuning sliders, and the code-hook features retail has no table for.
Translation / language packs
legaia-patcher translate exports a disc's text as an editable YAML pack and applies a filled pack back as a same-size patch. Built for community translations.
Official PAL localizations
How the official French / German / Italian discs align to the USA coordinate space, and how their text is lifted onto it.

Dig in Ghidra

The static path. Ghidra runs headlessly in Docker and is driven by scripts; every FUN_80xxxxxx on this site is a function it labelled. The catch that shapes all four pages: most of Legaia's game logic is not in the executable - it lives in overlays, chunks of code the game pages into RAM on demand - so "no static caller" is a question, not an answer.

Ghidra in Docker
Setup, one-query-per-exec workflow, the script catalogue, the LUI+ADDIU workaround, and the decompiler artifacts that have produced false claims.
Static overlay pipeline
Extract each runtime overlay straight from PROT.DAT at its recovered load address, so an overlay's identity comes from the disc rather than a guess. Reproducible from any copy of the disc.
Address-reference scan
"Who calls this?" answered from the bytes: every way the game can reach an address - pointer table, split-address pair, call, jump, branch - swept across the executable, every overlay image and every archive entry at once.
Function directory
The canonical index of Ghidra-traced entry points, grouped by subsystem - where a dumped function's write-up lives.

Capture the emulator

The dynamic path. When static analysis cannot say which code runs, an emulator can: load a save state, arm a watch or breakpoint, run a few frames, and read back what happened. Two emulators are used for different strengths - PCSX-Redux has a scriptable breakpoint debugger, mednafen has cheap save states whose RAM can be diffed.

Overlay capture
Slice the RAM-resident overlays out of a save state and import them into Ghidra at the right base. The dynamic complement to the static pipeline.
PCSX-Redux automation
Closed-loop Lua probes: save-state load → arm probes → capture N VSyncs → CSV / snapshot. Quick start, the probe catalogue, and the authoring pattern.
Mednafen automation
Scriptable substitute for an interactive memory-watchpoint debugger: pairwise save-state diffs, write-transition bisection, declarative scenarios.
Spine flag-writers capture
A worked example of a live writer hunt: one PCSX-Redux session watches the chapter-1 story-progression flags and logs which code writes each one.
Super Art queue capture
Runbook + Lua capture pinning the byte-exact action queue each Super / Miracle Art combo expands to.
Playthrough coverage
Play a scripted opening segment with a breakpoint on every not-yet-understood function, and let the hits pick what to document next.

Measure the port

Three different questions, each with its own instrument: how much of the game's code is understood and reimplemented (the catalog and disc coverage), whether the reimplementation behaves like retail frame for frame (the differential oracle), and whether it behaves like itself run twice (determinism).

Port catalog
Per-function status - dumped × documented × ported × ignored - from // PORT: tags in the crates, with feature views and a regenerable open-work dashboard.
Disc coverage
The same question with the denominator taken from the disc instead of from our own citations: byte-exact coverage of each image's code, plus PROT format recognition by bytes.
Recomp differential oracle
Frame-tagged parity between the clean-room engine and a static recomp of retail: both emit the same state trace and trace_diff.py reports the first frame each channel diverges.
Determinism + replay
legaia-engine record / replay: capture your inputs to a small text file and play them back frame-perfectly. Same input twice → bit-identical state trace.

More tooling docs (on GitHub)

These pages live in docs/tooling/ and are not mirrored on the site. Most are the project's CI gates and triage ledgers - the checks that keep a measurement honest and the per-row verdicts behind the port catalog's numbers.

Worklist classification
Whether a missing-port row is a portable function entry at all (REAL / INTERIOR / SHARED_TAIL / DUPLICATE / VA_ALIASED / ...), so the worklist reads as work rather than addresses.
Live-audit triage
Per-anchor verdicts for the "undisclosed inert ports" the catalog's live audit flags, keyed by address + call site.
Stale NOT-WIRED triage
The sibling ledger: rows tagged NOT WIRED that the audit finds live, and the three call-graph shapes that put them there.
Reach triage
Verdicts for ports that are statically live but never entered by a replayed playthrough - the runtime gap the static audits are silent about.
Call-target integrity
Why a decoded jal target is a property of the bytes, not the load base - and the one dump window whose targets are therefore untrustworthy.
Dump-corpus integrity
A dump's printed addresses are a property of its load base; a filename prefix is not evidence. Census of mis-based and truncated dumps plus the re-runnable checker.
Port provenance
Nothing checks that a // PORT: address names the routine the Rust code implements. The ranked worklist for that, and the signal that was built, measured and deleted.
Phantom print index
Address by address in the 0x801C**** / 0x801D**** band: which image and VA a printed address's bytes really occupy, and whether that VA is a function entry.
Host drift
The port ships three hosts on one engine (native window, browser play page, browser minigames), so a feature wired into one is invisible in a diff. The ladder of gates that catches it.
Shipped-bundle freshness
The site's WASM bundle is uncommitted build output whose source closure is most of the workspace; a content-addressed stamp says when a local bundle is stale.
Site shell
The static site's app shell across breakpoints, the two silent CSS / JS shadowing traps, and the page layer's delivery rules.
Shell observer traps
Three shell defects where the observer sits inside what it observes: pipe exit status off the wrong stage, pkill -f matching itself, grep's no-match exit 1 read as failure.
Doc density + link gates
The two pre-commit doc checks: over-long lines and table cells, and relative links + #anchors that must resolve.
Tagged-release pipeline
Pushing a v* tag builds the workspace binaries and attaches per-target archives + SHA256SUMS to the GitHub release. Binaries and licenses only - never game data.

Disc-gated tests

Everything that touches a real .bin runs only when LEGAIA_DISC_BIN is set; CI runs without disc data and those tests skip cleanly. Release-archive users run the binaries directly; source builds live under target/release/.

LEGAIA_DISC_BIN="/path/to/Legend of Legaia (USA).bin" cargo test --workspace

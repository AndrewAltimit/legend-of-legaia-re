PSX RAM map

The PlayStation has exactly 2 MB of main RAM, and everything the running game is - its code, the party's stats, the loaded scene, the story flags, the item bag - lives somewhere in that window. This page walks it bottom to top: the executable, the save block, the heap, the two overlay slots the per-mode code is streamed into, and the stack at the very top - then the 1 KB scratchpad that sits outside the 2 MB altogether.

At a glance

Main RAM
2 MB at 0x80000000..0x801FFFFF. Nothing above it: 0x80200000+ only mirrors RAM on a retail console.
Executable
SCUS_942.54 loads at 0x80010000 and is 0x6B800 bytes (430 KB): tables, then code from main() at 0x80015E90, then data. It ends at 0x8007B800.
gp
0x8007B318 - most globals are reached as imm(gp), which an absolute-address search never sees.
Save block
0x80084140..0x80085B57, the 0x1A18 bytes a save copies: character records at 0x80084708 + n*0x414, flag bank 0x80085758, item bag 0x80085958.
Heap
0x80091800..0x801C5FFF (InitHeap(0x80091800, 0x134800)): scene bundles, models, the battle context and actor pool.
Overlays
Slot A at 0x801CE818 (field, battle, menu, minigames - one at a time); slot B at 0x801F69D8 (summon / cast modules, world-map render).
Stack
Starts at 0x801FFFF0 and grows down.

Where these boundaries come from

The executable's own header fixes the bottom half: t_addr = 0x80010000, t_size = 0x6B800, initial PC 0x80026C28, initial sp = 0x801FFFF0, and no BSS (b_addr = b_size = 0) - so nothing above the image end is cleared by the loader. The first jr ra in the image is at 0x80016228 and the last at 0x8006F178, which is what places the code between the table head and the data. main() sets the heap from DAT_8007B414 = 0x80091800 with size 0x134800 (0x200000 on the 8 MB development console), so the heap ends at 0x801C6000. The overlay bases are recovered from each image's own call graph (static overlay pipeline).

The previous version of this map split the executable at 0x80060000, gave it ~960 KB, placed a 256 KB overlay window at 0x801C0000 with a title overlay at its base and an "extended overlay region" past 0x80200000. None of that survives the header and the overlay bases: the title screen is PROT 0899 code at 0x801CE818, 0x801C0000..0x801C5FFF is heap, and there is no RAM past 0x801FFFFF.

How to read an address

  • Every address is a PSX virtual address. Main RAM starts at 0x80000000, so 0x80084708 is byte 0x84708 into the 2 MB. DAT_8007B83C is Ghidra's automatic label for data at that address, the way FUN_8003E4E8 labels a function (key functions).
  • The executable is only the bottom of the picture. Its data holds the persistent state, but most game logic lives in overlays streamed off the disc per game mode.
  • An overlay address is ambiguous on its own. Every slot-A image links at 0x801CE818 and only one is resident, so the same address means different things in field, battle and menu mode. The overlay rows below say which image they belong to.
  • A heap address is a snapshot. It depends on the allocation order; the ones listed are those that stay put across the captured states.
  • 0x1F800000 is not main RAM. It is the scratchpad, and a flag a script tests may live there.

Static work area and the save block

From the image end at 0x8007B800 to the heap base is uninitialised global storage - the executable declares no BSS, so a cell here holds only what the code stores. It holds, in order, the rest of the gp block, the actor and mesh tables, the save block and the work buffers above it.

0x8007B8C2 - the build-mode selector

Every one of its 40 read sites splits the same way: non-zero opens assets by PROT-TOC index through the in-RAM table; zero opens by filename through FUN_800608F0, whose whole body is break 0x103 - a PsyQ dev-station host trap retail hardware cannot service. main() writes the halfword once at cold boot:

80015f00  jal  0x8003F084      ; two-instruction leaf: returns 1
80015f04  nop
80015f08  sh   v0,0x5aa(gp)    ; gp = 0x8007B318, so EA = 0x8007B8C2

The store is gp-relative, which is why sweeps for the absolute lui 0x8008 form reported no writer. BSS zero-init does not establish it - the header declares no BSS. The field-VM flag ops cannot reach it either: their index window is [0x80085758, 0x80086957] and the move VM's signed operand reaches down only to 0x80084758, both above it. A from-scratch engine treats both flags as build-time constants. JP retail uses build-shifted addresses (+0x1B90 for the debug-menu enable).

The global TMD pointer table

Every populated entry [0..DAT_8007BB38] is a post-fixup Legaia TMD (magic 0x80000002, group descriptors at +0xC, stride 0x1C). The sole writer is the installer at FUN_80026B4C @ 0x80026BA8; its store through gp[+0x820] is what hides the walker counter from Ghidra's xref database. A settled field-scene snapshot (dolk) holds 143 entries: five character meshes from PROT 0874 section 0, then a contiguous 138-entry scene pack installed by the single descriptor walk. Type-0x05 slot-4 bodies never install here - only dispatcher cases 0x02 / 0x09 reach the installer. Consumers: the world-map top-view renderer, the SCUS and overlay actor allocators, the table walker and the per-party-member equipment-conditional group patch (character mesh).

Free RAM and the stack

Above the largest slot-B image nothing is loaded. The stack starts at 0x801FFFF0 and grows down; the deepest use seen across the save-state library is 0x801FE420, and 0x801FD000..0x801FE000 reads all-zero in every state - which is why the disc patcher parks injected code there (randomizer).

No code on the disc builds an address from 0x801FA9D8 up, apart from the initial stack pointer. The loader reads exactly as many sectors as the PROT table of contents gives, so a larger PROT 0900 / 0901 would carry its extra bytes into this space on every field load, and they would stay until power-off. The catch is that those two entries have no spare room on the disc, so growing them means moving every later PROT entry, which a same-size patch cannot do. In the same way, while the field or menu overlay is loaded, the range 0x801F3818..0x801F69D7 only holds leftovers from whichever image last used it.

How we know

Ghidra's reference manager does not resolve MIPS lui+addiu pairs or gp-relative stores, so most rows were pinned by a writer hunt (Ghidra tooling), a save-state diff, or a cheat code that names the cell. The region boundaries come from the executable's header and the overlays' own call graphs.

The port's crate map

The project is a Cargo workspace of small crates stacked in bands: one crate per disc format at the bottom, the format families over them, the engine's World-free kernels, the simulation, and the hosts at the top. Hover a crate to see what it uses and what uses it, click it for its scope, binaries and modules, or follow a scene from the disc to the screen.

The map

Each band uses only the bands below it, and colour marks the track a crate belongs to. The edges are the real [dependencies] of every Cargo.toml, regenerated with the page's data (how).

Three hosts, one engine

No host carries a second copy of the game. The two play hosts tick the same engine-session BootSession over the same World; the minigames page drives the World-free minigame rules engines directly. What differs is only the shell: the window, the GPU API and the audio device. Host drift covers the gates that keep a feature from landing in one host only.

How the map stays true

The page draws from site/crate-map.json, which scripts/ci/gen-crate-map.py builds out of what the workspace already states: the edges and binaries from each crate's Cargo.toml, the public modules from its src/lib.rs, the one-line scope from the crate tables in CLAUDE.md, and the kernel ranks, roles and coupling reasons from scripts/ci/crate-layering.toml. Only placement is written by hand, in scripts/ci/crate-map-layout.toml.

  • Nothing points up. The generator fails if a crate depends on a crate in a band above its own, if a crate sits in no band or two, or if a crate has no line in CLAUDE.md.
  • A stale map fails the commit. gen-crate-map.py --check runs in the pre-commit hook and in CI, so a new crate, edge or module cannot land without the page and the README diagrams being regenerated with it.
  • The kernel ranks are not drawn by hand either. They are the stack the layering gate derives from its committed table of allowed edges.

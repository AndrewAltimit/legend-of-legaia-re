Item-effect descriptor table Confirmed

What does a Healing Leaf actually do, and why is a Door of Light greyed out in battle? A small static table in SCUS_942.54 answers both: for each consumable it records the kind of effect - heal HP, restore MP, cure status, revive, raise a stat, escape a dungeon - its target shape (one ally or the whole party) and where it may be used (field menu, battle, both, neither). What it does not hold is the number: "restores 200 HP" lives in a separate tier-indexed table the apply handler reads, and the stat-up magnitudes are immediates in the handler's own code.

What it is and is not

The amounts are not here

This table holds class + tier + flags. "Healing Leaf restores 200 HP" is split in two: this table says (class = heal-HP, tier = 0), and the tier → 200 mapping is the separate, also-static heal-amount table. Stat-up and buff magnitudes (classes 5/6/7) are inline immediates in the apply handler, pinned to the disassembly.

It is the sibling of the item-name table (DAT_80074368) and the spell table: the three are contiguous static data. The lookup is double-indirected - an item id resolves to a subtype byte in its name-table record, and the subtype picks a descriptor here - so many items share one descriptor, and "key items are unusable" is not a special case at all: a key item simply resolves to a descriptor with neither usability bit set.

Flag byte (+2)

BitMeaning
0x80populated - set on every descriptor that has an effect
0x40draws its own info-panel body instead of the passive block - exactly five subtypes: the Point Card and the two summon-flute pairs; consumer is the item-info panel FUN_801D0F1C, whose Point Card arm prints the live _DAT_800845B4 bank (shop)

Healers carry 0x04 | 0x02; permanent stat-ups and field-utility items carry 0x02 only; status-cures and revive carry 0x04 only. Key items resolve to a descriptor with neither usability bit (e.g. flag 0x89), which is how the menu greys them out. The class byte is meaningful only together with the usability flags - many key items funnel to class 0 with no usability bit, so "class 0" alone is not "an HP potion".

Heal-amount table (0x8007655C)

The literal restore amounts the apply handler FUN_800402F4 reads: two contiguous u16[4] sub-tables indexed by the descriptor tier (base + tier*2); only tiers 0..=2 are read flat.

VASub-tableTier 0Tier 1Tier 2Read by
0x8007655C (file 0x66D5C)HP restore cap2008009999classes 0 / 1
0x80076564MP restore cap5020020class 2

Each restore is deficit-clamped (applied = min(max - current, table[tier])), so tier 2's 9999 is an effective full restore. Tier 3+ HP heals do not read this table - they are character-relative, scaled off the per-character 0x80084140 Seru-heal tables. Revive (class 4) is not a flat amount either: tier 0 restores max_hp×0.4 + rand()%(max_hp/8), higher tiers a full revive. Provenance: HP arm 0x800404b8, MP arm 0x80040dc0, revive arm 0x80040f58 (ghidra/scripts/funcs/800402f4.txt). Parser: heal_amounts() and restore_amount(id) → Hp / Mp / CharRelative; the disc-gated test pins Leaf 200, Flower 800, Berry full, Magic Leaf 50 MP, Magic Fruit 200 MP, Healing Shroom 200.

History: "the amounts are overlay-resident immediates"

An earlier reading placed the restore amounts in a switch of immediates inside an overlay-resident handler outside the dumped corpus. The HP / MP amounts are static tier tables read by the static FUN_800402F4; only the class 5/6/7 magnitudes are immediates. Recorded on settled threads.

Stat-up / buff items (classes 5/6/7)

These classes read no data table - their magnitudes are inline immediates in FUN_800402F4's case 5/6/7 (lines 2380-2639 of the dump), so the (class, tier) → effect mapping is pinned to the disassembly while each item's (class, tier) is parsed from the descriptor.

Indexing and the readers (Ghidra-traced)

From FUN_8003043C (ghidra/scripts/funcs/8003043c.txt):

subtype    = item_name_table[id].byte(+1)      ; DAT_80074369[id*0xC]
descriptor = (&DAT_800752C0)[subtype * 4]      ; stride-4 record
arm        = descriptor[+0]                    ; effect class / validator arm
tier       = descriptor[+1]
flags      = descriptor[+2]
  • The item record's +0 byte - its kind - is a sibling selector some callers gate on first: the pause-menu target-panel preview FUN_801D6A54 requires kind == 2 and class == 6 before mapping the tier onto a preview mode. ItemEffectTable::kind exposes it alongside subtype.
  • The & 0x20 all-party test is read in FUN_8003043C itself (selecting the all-targets call to the validator FUN_8003fb10); the 0x02 / 0x04 bits are read by the field list builder FUN_80030628; the battle item path reads class + tier straight into the actor's action context (battle overlay 0x801e3ba4).
  • The apply handler is reached through the 132-entry jump table at 0x80014FA0, but what indexes it depends on the caller: the descriptor class at 0x801d84b4 (field item use), the item record's own kind byte at 0x801d9280, and the battle actor's +0x1E8 at 0x801e40dc. One handler serves both the field menu and the battle path (branching on game_mode == 0x15).
  • Menu-usability gate. FUN_8003043C only offers an item (not greyed) when at least one eligible target would benefit: it walks the live party calling FUN_8003fb10(class, tier, target) per member (the 16-arm validator on the battle-action page). The engine equivalent inventory_use::item_has_valid_target greys a heal at full HP, a cure with no matching status, a revive with nobody fallen.

Parser + engine consumption

ItemEffectTable::from_scus resolves both tables from a SCUS_942.54 image (PSX-EXE t_addr → file-offset map, the item-name-table resolver). The engine installs the flags over its curated catalog via ItemCatalog::apply_effect_flags (usability gates + is_all_party: Healing Bloom / Fruit skip target-select and fan across every living ally), seeds the Water line via apply_stat_items, the Elixirs via apply_buff_items (the same ×6/5 ramp + revert bookkeeping as buff spells), and Fury Boost via apply_action_gauge_items (approximated as a ×7/5 raise of the slot's ApGauge::base_ap, since the engine models AP as a discrete budget). All disc-present-only - never a no-op on a disc-free build. Source of record: docs/formats/item-effect-table.md.

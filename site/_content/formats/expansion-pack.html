Expansion packs: the format

An expansion pack is a modder-authored bundle of new content for the port - custom maps, battles and bosses, a level curve, quests, dialogue, trading cards, game modes - that the engine loads beside the player's own disc. It is the port's own format, not a disc format, so nothing here is decoded from retail and the page carries no confidence labels: it is the specification. This page covers the pack's layout, the manifest, how a pack names disc content, the shareable .lxpack bundle and validation. The sections have pages of their own (battles, quests, maps); the tour is the expansion packs hub.

A pack carries no bytes from the disc. Every disc asset it uses is named by a coordinate (DiscRef) and resolved against the disc the player supplies - the same rule a shareable language pack follows. The flagship pack, Rebirth, is written with exactly the format and tooling on this page.

Layout

Paths are relative to the pack root with / separators. Every file but pack.toml is optional; an absent section file is that section's default (empty).

my-pack/
  pack.toml          manifest (required)
  battle.toml        monsters, formations, encounter overrides, bosses
  progression.toml   level curve, XP and rewards
  quests.toml        quests and challenges
  dialog.toml        dialogue lines
  cards.toml         trading cards
  modes.toml         game modes
  items.toml         items, equipment, sets and shops
  maps/
    <id>.toml        one custom map per file; the file stem is the map id
  assets/...         the modder's own files (art, models, sound, text)
  README.md  LICENSE[.md|.txt]  CHANGELOG.md

The loader reads the files above and ignores anything else; the validator reports an ignored file as a warning, so a misspelt section name does not vanish silently. maps/ is flat: maps/a/b.toml is not a map.

The whole tree is one PackFiles value (BTreeMap<path, bytes>). The directory walker, the bundle reader and the browser workbench each produce one, so a pack parses the same way whichever form it arrived in.

Content ids and namespacing

Content a section defines (a monster, a quest, a card, a map) has a local id: [a-z0-9_], at most 48 characters, unique within its kind across the whole pack. The pack id is its namespace, so tower_king in pack rebirth is rebirth:tower_king to the engine and to other packs.

  • tower_king or rebirth:tower_king (the pack's own id): must be defined somewhere in this pack.
  • other:thing: content of pack other, which must be listed in requires; the engine resolves it once that pack is loaded, not the validator.

A definition never carries a :; writing one is an error.

Disc references

refs::DiscRef is the only way a pack names disc content: a TOML inline table tagged by kind.

boss_model = { kind = "monster", id = 77 }
arena      = { kind = "scene", name = "town01" }
mesh       = { kind = "tmd", prot = 874, index = 3 }
guide      = { kind = "npc", scene = "town01", index = 12 }

PROT numbers are extraction indices, the NNNN in extracted/PROT/NNNN_*.BIN, not raw TOC indices (numbering space).

Checking happens in two halves. DiscRef::check_range needs no disc and rejects a coordinate no NA disc can satisfy. refs::DiscResolver is the disc-backed half: the engine (and the workbench) implement resolve(&DiscRef) over the player's disc - does entry 874 hold a TMD with an object 3 - and validate::validate_with runs every coordinate a section recorded through it.

Sections

Each content section is a TOML file whose type lives in its own module of legaia_expansion_format. Every key is optional, so a pack writes only what it uses.

  • battle.toml - monsters derived from a retail record (set or scaled stats, drop, steal, element, spells), formations of up to four monsters with optional waves, per-scene encounter overrides and named bosses. Formations compile to engine ids from 0xE000; a once-only boss's victory is saved.
  • progression.toml - the XP curve (retail, scaled, banded or explicit), EXP and gold multipliers, enemy level scaling and level-up item rewards.
  • quests.toml - quests (giver, prerequisites keyed to retail system flags, party level and other quests, ordered or unordered objectives, rewards, repeat rules) and challenges (rule sets over one battle with a score).
  • dialog.toml - lines in the translation markup, as rows and pages, with two- to four-option menus that set pack flags, chain a line or start a fight. Every line is compiled at validation, so text with no glyph is an error.
  • maps/<id>.toml - a tile grid with walls and floor tiers over a retail base scene, props, NPCs borrowed from retail placements, spawns, exits, trigger and encounter zones, and the entrances that lead in from the retail game.

cards.toml

Trading cards, the boosters they come in, the dealers that sell them and the rules that hand them out. Card, booster and dealer ids are the section's own (cards keep hyphenated ids such as mist-wisp, which save files key on), so the section checks them itself; it references formation and boss, and records each card's art and each monster reward source as a disc coordinate.

The validator rejects a repeated or empty id, a side outside 1..=10, a pool, starter, reward or stock naming a card or booster that does not exist, all-zero weights, a reward with neither a booster nor a card, a chance over 100 and a mode source no modes.toml instance has; it warns on a dealer stocking an unpriced booster or paying over the sell value. The runtime is on game modes.

modes.toml

Instances of the port's own game modes: the pack picks the numbers and the layout, the rules live in legaia_engine_modes (game modes). Each instance has an id (what a kind = "mode" reward source names), a name and an optional location (DiscRef).

A golf hole is one character per tile: . fairway, , rough, s sand, w water, # wall, space out of bounds, T tee, O cup, and ^ v < > fairway sloping downhill that way. The validator parses the section and runs no checks of its own on it: an instance is built when it is entered (legaia_engine_modes::active), and one whose data cannot make a session is refused there, the mode picker showing the reason.

The .lxpack bundle

The shareable form of a pack is one file: bundle::write_bundle archives a PackFiles tree and bundle::read_bundle restores it. The bundle adds no metadata of its own - the manifest is pack.toml, one of the files - and no timestamps, so the same tree always gives the same bytes. All integers are little-endian.

Header (16 bytes)

0x00magic LXPACK\x1A\n8 B
0x08version 1u16
0x0Aflags 0u16
0x0Centry countu32

Entry-table record (44 bytes + path)

+0x00path lenu16
+0x02methodu8
+0x030u8
+0x04raw lenu32
+0x08stored lenu32
+0x0CSHA-256 of raw bytes32 B
+0x2Cpath, UTF-8path len

The digest cell is drawn at a quarter of its width.

The whole file

0x00header16 B
0x10entry table, path ordercount x record
...data: stored bytes back to back, table order, no paddingsum of stored lens
end - 32trailer: SHA-256 of all before32 B
  • Method 0 is stored, 1 raw DEFLATE (RFC 1951). The writer deflates an entry only when that makes it smaller.
  • The reader trusts nothing first. It checks the magic, version, flags and trailer before the table, refuses unsorted or duplicate paths, unknown methods, a stored entry whose lengths differ and trailing bytes, inflates each entry to exactly its declared length, and checks each entry's digest.
  • Paths stay inside the output directory. Relative, /-separated, at most 255 bytes, no empty, . or .. component and none of \, : or NUL - on every host.
  • Limits. 16384 entries, 64 MiB per entry and 512 MiB in total once decompressed.

Validation

validate::validate_files checks a raw tree (paths, layout, parse errors) and then the parsed pack; validate::validate checks a parsed pack alone. Both return every issue rather than stopping at the first. An issue has a severity, its file, a dotted field path and a message. An error stops the engine loading the pack and stops asset expansion bundle; a warning does not.

Adding a section's checks

A section implements validate::SectionRules, whose two methods default to doing nothing. Validation calls declare on every section first, then check on every section, then resolves references, so a quest may name a boss from battle.toml whatever order the sections run in.

  1. Declareevery section registers the ids it defines
  2. Checkevery section checks its fields, names what it references, queues its coordinates
  3. Resolvereferences against the declared ids; coordinates through the disc resolver
Checker methodUse
declare(kind, id, field)Pass 1: register a content id the section defines.
reference(kind, id, field)Pass 2: name content of kind, resolved after both passes.
disc_ref(field, &DiscRef)Pass 2: range-check a coordinate and queue it for the resolver.
error / warning(field, msg)Report against the current file.
pack(), qualified(id)Read the whole pack; form pack:id.

The battle, progression, quest, dialogue and card sections implement the trait in their own modules, and maps in map_rules; modes.toml alone keeps the empty impl in validate.rs, since its instances are checked when they are built.

The no-disc-bytes rule

Every file under assets/ must pass all four:

  1. Allowed typeextension png, gltf, glb, ogg, wav, txt, md or toml (any case)
  2. Its type's signaturethe PNG header, glTF version 2, OggS, RIFF....WAVE, or valid UTF-8 text with no NUL (a .gltf opens with {)
  3. Not shaped like a disc formatno TIM, Legaia or Sony TMD, VAB, SEQ, VAG, PS-X executable, raw-sector sync or ISO 9660 descriptor at its start, and no PS-X EXE header or sector sync anywhere
  4. Sizeat most 8 MiB each, 64 MiB for all assets together

Anywhere in the pack, a file named like a disc file is refused: PROT.DAT, DMY.DAT, SCUS_942.54, SYSTEM.CNF, CDNAME.TXT, a disc image (.bin, .iso, .cue, .img, .ccd, .sub, .mdf, .mds, .chd, .ecm, .pbp), streamed media (.str, .xa), or a retail format's extension (.dat, .exe, .tim, .tmd, .vab, .vag, .seq, .lzs, .man, .mes, .anm, .mdt, .dpk, .spk, .pch).

Packs are made to be shared, and the disc's bytes are not the project's to share. The type allowlist does most of the work: an LZS stream, a DATA_FIELD chunk or a headerless table has no PNG or Ogg signature, so it fails rule 2 even though it has no magic of its own for rule 3 to catch. The checks guard against accidents, not a proof; text a modder pastes in from the game is still the modder's responsibility.

Tooling

asset expansion info                                   # schema, bundle version, layout
asset expansion validate packs/rebirth [--strict]      # a directory or an .lxpack
asset expansion bundle packs/rebirth -o rebirth.lxpack # refuses a pack with errors
asset expansion unbundle rebirth.lxpack -o out/        # out/ must be empty or absent
asset expansion info rebirth.lxpack [--json]

validate exits non-zero on any error, and with --strict on any warning. None of these reads a disc. The same checks run in the browser on the expansion workbench, with the visitor's disc resolving every coordinate.

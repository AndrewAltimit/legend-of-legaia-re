DATA_FIELD streaming format Confirmed

When the game loads a scene or a battle effect it usually needs several different things at once - a texture, a mesh, an animation - and it wants to read them off the disc in one go. DATA_FIELD is the container that does that: a stream of typed chunks, each a 4-byte header (what it is, how long it is) followed by raw data, read one after another until a terminator. The game hands each chunk to the asset-type dispatcher, which routes it to the right format handler.

Overview

The walker passes every chunk through the dispatcher with copy_only=1, so chunks are always uncompressed - the container trades disc space for a load path with no decompression step. Implementation: crates/asset/src/lib.rs::parse_streaming.

Scope note

This page covers the typed-chunk streaming shape that FUN_8002541C consumes - not the wider question of "what does the per-scene CDNAME block actually carry?" (a CDNAME block is the run of consecutive PROT.DAT entries that CDNAME.TXT assigns to one scene). Per-scene field bundles use multiple shapes; the slot map at the end identifies which shapes show up where.

What's in the wild

asset scan-stream strict-validates 34 PROT entries (class data_field_streaming), in two families.

Character / effect streams

The other5 run, entries 1204..1219. The common shape is three single-asset chunks:

chunk[0]: TIM   (single, magic 0x10)        - sprite atlas / texture
chunk[1]: TMD2  (single, magic 0x80000002)  - single Legaia TMD
chunk[2]: MOVE2 (single, magic 0x08)        - animation data
terminator

The two heads of the run are homogeneous instead: 1204 is five TMD2 chunks (the battle-form party meshes used by the Baka Fighter minigame and as the default-equipment sibling pack - the in-battle player meshes themselves are assembled from the PLAYER1..4 files) and 1205 is eight TIM chunks of 0x8220 bytes each (their atlases) - which is what makes the atlas stride 0x8224, chunk header included.

Scene bundles

MAN / MES / MOVE / VDF, four chunks (dolk2, rikuroa, rikuroa2, rayman, station, taiku, taiku2, doman, nilboa2, edbalden, eddoman). Shorter variants drop the trailing VDF (balden2, ropeway2) or lead with a bare TMD where a MAN would sit (balden, bubu1, edbubu). Two entries are neither family: init_data is TIM_LIST + TMD, and 0890_sound_data2 is two TIMs.

The chunk layouts are single assets in the other5 family (one TIM, one TMD2, one MOVE2), not packs. Other clusters do use pack-shaped TIM_LIST / TMD chunks; the pack format handles that case.

Trailer data

Some entries contain bytes past the streaming terminator. asset extract preserves these as _trailer.bin next to the extracted chunks. The function that consumes the trailer has not been located; tracing the caller of FUN_8002541C in the field/town overlay is the next move if a specific entry's trailer looks structured.

Related shapes

  • The scene-TMD-prefixed streaming shape is structurally similar but the leading chunk has no [u32 type_size] header and the inner content is a bare TMD instead of a TIM.
  • The scene-VAB-prefixed streaming shape uses the same chunk0-header trick but with VAB content.
  • Pack format lives inside TIM_LIST / TMD chunks when the chunk's data is a pack rather than a single asset.
  • One entry (extraction 0892) matches the data_field_truncated detector - three clean leading chunks, then an over-large fourth header - and the match is an artefact. The entry is an asset::pack (count = 2, word offsets [3, 0x208B]), and those "chunks" are the pack's own header words read as chunk headers. Mode-22 CARD INIT (FUN_8002574C) walks it as a pack and uploads each member through FUN_800198E0. See the card font pack.
History: the "truncated" scene entries

Three scene entries once cited in the truncated class - 0157_rikuroa, 0228_station, 0373_taiku - are not truncated, and neither is 1205_other5. Each scene entry is one of the four-chunk MAN / MES / MOVE / VDF bundles above; the superseded over-read entry size (toc[p+5] - toc[p+3] + 4) fell short of these entries (0157 declared 163840 bytes against a real 186368; the other two were short by 69632 and 8192), so the last chunk overran a buffer that ended early. Against their own sectors all three terminate cleanly. The "runtime extends the chunk via streaming DMA continuation" explanation that accompanied the old reading is withdrawn with it. See PROT TOC § history of the over-read.

Entry 0892 (card_data) is a pack, not a truncated stream

Extraction entry 0892 is a two-member asset::pack of 4bpp TIMs, loaded once per memory-card-screen entry. The "12 MB LZS container" figure that once stood against it came from the superseded declared span (toc[p+5] - toc[p+3] + 4 = 5977 sectors); the entry is 33 sectors, 67,584 bytes.

The entry-context selector is gp+0x7E8 (0x8007BB00): 0 skips the block, 1 takes the disc load, and any other value takes a third arm that MoveImages the same VRAM footprint back from a parked copy. Every writer of the slot stores 1 and the menu overlay clears it to 0, so no retail path reaches that third arm - but its inverse is live: the menu overlay parks (0,475) 256×1 to (0,492) and (320,256) 128×256 to (704,0) on the way into game mode 0x1A.

The content: a JIS X 0208 level-1 kanji font

The CLUT block is identical in both members and is not an ordinary palette bank. Rows 0..3 hold the index patterns 0101…, 0011…, 00001111… and 00000000 11111111 against one ink, and rows 4..7 repeat them against a darker ink - each row selects one bit of the 4bpp index. The texture is a 1bpp bitmap packed four bit-planes deep, and a draw picks its plane by CLUT row. Rows 8..15 are ordinary 16-colour palettes for other content on those rows.

Per plane the grid is a 12-pixel pitch with an 11×11 ink box: columns and rows 11, 23, …, 239 carry no ink in any plane and nothing is inked past 238. That is 20×20 = 400 cells per plane, 4 planes per member, 8 planes in all - seven full and the last inked through cell 164, for 2965 inked cells, exactly the JIS X 0208 level-1 kanji count. Plane 0 reads in level-1 ku-ten order, so a glyph's cell is plane = g / 400, row = (g % 400) / 20, col = g % 20.

Which routine samples the page is open: no image materialises the base CLUT id 0x76C0 (475 << 6), so the consumer either computes the id or reads it from a table. The upload runs on every mode-22 entry either way.

Per-scene field bundles - what's still open

The CDNAME block for a typical field/town scene (e.g. town01, bubu1) carries 8-12 PROT entries. Categorize (the sweep that classifies every archive entry by format) identifies several known shapes per block. Slots below are in the retail block frame (see CDNAME § numbering space): slot 0 is the scene's .MAP and slot 1 its v12 trigger sidecar, which is why the classes below start one or two slots later than a naive count.

What is not modelled yet:

  • Cross-entry pointers (NPC references that point into other PROT entries - the asset chain in asset loader is best-effort).
  • Which function consumes the post-terminator trailer bytes.

Two long-standing entries on that list are closed, and both closed by shrinking rather than by new machinery. The field-pack "slot semantics" were this page's own chunk format plus the pack format: the 0x01059B84 "magic" is a (TIM_LIST << 24) | size chunk header and the "97-entry schema" is that chunk's [count][word offsets] table; the "124 entries" figure came from the superseded over-reading entry size. And the per-scene asset-table indirection needs no capture: the walk is positional, and +0x04 of the header is the sum of the descriptor sizes - see scene bundles.

The categorize sweep classifies every PROT entry to something; the items above are the residual edge. See the engine page for how scene loading consumes these shapes.

History: the "scripted asset table" class

A SceneScriptedAssetTable class - a descriptor table found at a sector-aligned offset inside an entry that led with an event prescript - was an artefact of the over-read entry size: every such offset was the next entry's start LBA, i.e. the neighbour's ordinary offset-0 table. Read against their own sectors, the prescript entries classify as event scripts and the 88 bare asset tables stay where they are. See PROT TOC § history of the over-read.

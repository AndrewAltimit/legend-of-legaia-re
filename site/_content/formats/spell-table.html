Spell table Confirmed

Cast Gimard and the banner names it, 10 MP drain away, and one enemy takes the hit. All three facts - name, cost, target - come from one static table in SCUS_942.54: 190 records of 12 bytes, one shared numbering that covers unnamed enemy-attack tiers, named monster attacks, the party's Seru magic and the Ra-Seru summons. Enemies are named from the very same rows. The one thing the table does not carry is a damage number: a spell's magnitude is computed from battle state at cast time.

Table base + record layout

The table is viewed through two interleaved base pointers over the same records: DAT_800754C8 (the stats base, read for MP + class + target) and DAT_800754D0 (the same base shifted +8, read for the name pointer). Both step 0xC per spell id, so record id sits at DAT_800754C8 + id*0xC.

Why the extent matters

The 12-byte walk does not stop at record 0xBD; nothing bounds it but the reader. Any tool that sweeps "every spell id" up to 255 walks straight into the neighbouring tables, and a write at those coordinates corrupts them - a spell-cost patch that assumed 256 records would overwrite the description-pointer and arts-name tables on the patched disc. SPELL_COUNT is 190 (reading past the extent).

The Delilas arm: three ids, one body, an arithmetic cast id

0xA2, 0xA3 and 0xA4 are three consecutive jump-table slots pointing at the same arm 0x801EB7C0, which names no spell of its own - it computes one from the formation id:

801eb7cc  lbu   a0,0x28a(v0)     ; the round counter
801eb7d0  lui   v0,0xaaaa
801eb7d4  ori   v0,v0,0xaaab     ; 0xAAAAAAAB - the divide-by-3 reciprocal
801eb7d8  multu a0,v0
  ...                            ; a0 = round % 3
801eb7f8  bne   a0,v0,0x801ebdac ; fire only on round % 3 == 2
801eb800  addiu v0,v0,-0x42f4    ; DAT_8007BD0C
801eb804  addu  v0,s7,v0         ; + the formation slot
801eb808  sb    a0,0x1de(s4)     ; actor[+0x1DE] = 2, the Magic category
801eb80c  lbu   v0,0x0(v0)       ; the formation monster id
801eb814  addiu v0,v0,-0x29      ; the whole mapping
801eb81c  _sb   v0,0x1df(s4)     ; actor[+0x1DF] = id - 0x29

Monsters 162 / 163 / 164 resolve to spells 0x79 / 0x7A / 0x7B, and the entire mapping is one literal, 0x2442FFD7 at PROT 0898 file offset 0x1CFFC (VA 0x801EB814). Which cast fires is a function of the id the formation seats; the banner name then comes from this table at that id.

History: the 0965 attribution

0965 was once read as a shifted sibling of the battle-tutorial overlay 0967 - an entry-size over-read artifact (entry size is the gap to the next entry; see PROT). The corrected entries share no content. Catalogued on do-not-re-walk.

Target shape (+2)

Two independent bits over a side/scope pair: bit 0x02 = ally side (clear = enemy side; equivalently the low nibble is _4 for enemy, _6 for ally), bit 0x20 = all targets on that side (clear = single).

ValueShape
0x44one enemy
0x64all enemies
0x06one ally
0x26all allies

The model holds across the whole named player block and the six offensive Ra-Seru summons. One documented exception: the revive Ra-Seru Horn ("Resurrector", 0x9C) carries an enemy-side 0x24 byte even though it revives all allies - the summon projects toward the enemy field and the revive is special-cased by spell id. Decoded by SpellEntry::target_shape; the legaia-gamedata magic_vs_disc oracle joins the curated chart by name and verifies MP (byte-exact for all 21 Seru + 7 Ra-Seru; it corrected one curated target, Mushura / "Crazy Driver" = single-enemy) plus target shape, checking the Horn exception explicitly.

History: the "bit 0x40 = enemies" reading

Equivalent for the four player-block values but misclassifies the internal enemy-attack tiers, whose byte is 0x04: 0x40 clear yet enemy-targeting. The 0x02-bit / low-nibble reading classifies 0x04 as enemy-side, matching their role.

Description index (+4) and the name field

The pause menu's spell info window (FUN_801D2E74, menu overlay - field menu) reads the +4 byte and indexes a flat u32 string_ptr[] array at 0x80075DB0; index 0 means no description. The strings use the MES 0x7C line-break; the player block's shape is a title line then an effect line. Parser SpellEntry::desc.

The +8 name pointer names a string followed by a run of NUL bytes before the next object - the record's whole edit budget, and it is word alignment, not a fixed slot: every extent is 4 * ceil((len + 1) / 4), so a 13-byte name has three spare bytes and a 15-byte name one. spell_names::name_field measures the run and returns (file_offset, len, budget). Reaching a name through its record's pointer is the only safe way to rewrite one - these names nest (a text search for one name finds the longer name that contains it), so a search-and-replace is one row away from corrupting a neighbour. legaia_art::arts_table::name_field is the same accessor for the arts-name table, since a rename that must stay consistent across party and enemy paths touches both.

History: "+4 is an animation id"

The +4 byte was once recorded as an animation id. The summon effect / animation is dispatched by spell_id - 0x81, and the menu decompile pins +4 as the description index.

Reading past the extent

An id above 0xBD resolves into whatever static data follows, and on the retail disc that is two known tables:

IdsWhat the walk lands in
0xBE..=0xD4the description-pointer table 0x80075DB0
0xD5..the arts-name table 0x80075EC4

Both boundaries fall on exact multiples of the stride (0x80075DB0 − 0x800754C8 = 0xBE × 0xC, 0x80075EC4 − 0x800754C8 = 0xD5 × 0xC), so an over-read reads whole neighbouring words. The arts table's stride is 0x14 with its name pointer at +0xC, which coincides with the spell record's +8 whenever the arts index is 1 mod 3 - so spell 0xD7's name-pointer word and arts record 1's are the same four bytes at 0x80075EE4 (Burning Flare; spell 0xDC / arts record 4 is the next pair, Cyclone). A rename through either coordinate is one write, not two - a trap for anything that enumerates every id up to 255. asset spell-names still sweeps 256 ids for inspection, so the aliased rows (Tactical Art names read through the wrong table) appear above 0xD4; the table's own extent is SPELL_COUNT = 190, and the patcher's spell-cost edits stop there.

No per-spell power scalar

The table carries no magic-power field - bytes +5..+8 are zero on every record, state 0x28 of the action SM reads only +3 (MP), +0 (the 'c' flag) and the name pointer, and the static attack-vs-defence kernel FUN_801ec3e4 is melee / arts only (it returns early unless the queue head is in 0xC..=0x1F). Summon magnitude is battle-state-derived, applied by the paired stager overlays (PROT 0903..0915) in the same function that spawns the summon body parts:

  • Damage summons (PROT 0904 / 0912 / 0914, plus 0915's second arm) roll via the shared kernel FUN_801dd0ac: attacker rand % (summon_AGL + 1) + summon_HP + caster_AGL×2 against a defender roll, then element-affinity (the 8×8 matrix at 0x801F53E8) / status-weaken / magic-power scaling in FUN_801dd864, and the finisher FUN_801ddb30 (resistance bits, rand % 9 + 8 floor, 9999 cap, gauge fill, popup, MP drain). Stages 1-2 are ported as pure kernels in engine-vm::battle_formulas.
  • Heal summons (PROT 0903 / 0905 / 0910 / 0911 / 0913, plus 0915's first arm) compute (power_byte << 5) + 0xE0 inline, with power_byte fetched from the caster's character record (spell-id match at +0x705, power byte at +0x729).
  • The per-summon effect / animation is dispatched by (spell_id - 0x81): state 0x29 indexes PTR_s_re_check_801f6734 and calls func_0x8003ec70(spell_id - 0x79, 0).
  • The genuine per-move power scalar that does exist - the 26-byte-stride table at overlay VA 0x801F4F5C, reached through the 128-byte id → index map at 0x801F4E63 - feeds the arts / physical branch and shares this table's id space: power records for move ids 0x25..=0x74 are the named monster special-attacks, 0x04..=0x1F the unnamed tiers. See the move-power table.

The base_power figures in engine-core::retail_magic stay MP-scaled placeholders until the summon roll is wired into a live battle context.

History: the summon jump-table hypothesis

"The magnitude is in the summon jump table" is falsified: the JT at 0x801F69D8 (FUN_801f2d68, state < 7) resolves into the resident render overlay (PROT 0900) - staggered entry points into one per-frame routine that lerps anim banks and emits GPU packets, with no multiply, no HP write, no power read. The 0xC5 MES substitution table at DAT_80075EC4, once mistaken for a spell-name source, is the Tactical Arts name table. See do-not-re-walk.

Parser + engine consumption

legaia_asset::spell_names resolves the table from a SCUS_942.54 image (PSX-EXE t_addr → file-offset map); CLI asset spell-names <SCUS> [--json]. The engine sources the player Seru-magic catalog's MP + target from the user's executable via engine-core::retail_magic::seru_magic_catalog_from_scus, falling back to the pinned retail_seru_magic_catalog on disc-free builds; the disc-gated spell_catalog_disc test confirms all 11 pinned targets + MP byte-for-byte. The spell-cost slider edits the +3 byte in place across the 190 records. Source of record: docs/formats/spell-table.md.

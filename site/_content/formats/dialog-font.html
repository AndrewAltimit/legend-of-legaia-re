Dialog font (proportional Latin) Confirmed

Every line an NPC speaks, every menu label and every "learned a new Art" banner is drawn one letter at a time from a single 256-cell glyph sheet. It is a proportional sans-serif - an "i" is 3 pixels wide, a "W" is 9 - and its pixel widths - not byte counts - decide whether a translated line fits its box. The sheet lives in video memory at runtime; the widths and escape codes live in the executable.

Three pieces of data

  • The glyph sheet - 4bpp tiles in VRAM at (896, 0)..(960, 256), one 16×16 cell per character byte.
  • The width table - 256 bytes in the executable, one advance per character byte.
  • The escape table - 38 four-byte entries in the executable, selected by the byte after a 0xCE escape; they draw controller-button and UI icons, or print a script counter.

Glyph sheet

The sheet is a 4bpp TIM (4 bits per pixel, 16 colours), 64 halfwords wide × 256 tall = 256×256 pixels, framebuffer destination (896, 0). Cell c for character byte c in 0x20..=0xFF:

U = (c & 0x0F) * 16
V = (c & 0xF0) - 0x20

The drawn region in each cell is 14 × 15 pixels; the remaining 2 × 1 pixels are guard space. Bytes 0x00..=0x1F are control codes and have no glyph. The TIM uses three palette indices: 0 transparent, 14 the (32,32,32) drop shadow, 15 the glyph fill.

The TIM sits in the unindexed head gap of PROT.DAT - after the table of contents, before the first numbered entry - which is why a per-entry walk never sees it. The font is therefore decodable straight from the disc, no save state required.

Palettes

Sixteen 16-colour palettes (CLUTs) sit end-to-end on VRAM row 510 from x = 96, one every 16 pixels. The colour-change escape 0xCF n sets the palette index; the CLUT word in each glyph packet is index + 0x7F86, and 0x7F86 decodes as (96, 510). Palette 0 is the white-on-transparent dialog palette; the others are the coloured variants for status text and system prompts.

Width table

256 bytes indexed by character byte. The advance for c is widths[c] + pad + 1: +1 is the fixed inter-character gap, and pad is a per-call override that resets to zero after each render call. Menus and battle draw with pad = 0; the field dialog pager sets it to 1 before every row, so dialogue runs one pixel wider per glyph than the same text in a menu.

Every byte reaches the advance except the four control bytes; a space takes its advance without emitting a sprite. A line's pixel width is exactly the sum of its per-byte advances, with no per-line term - the save screen's memory-card warning line measures 164 px.

Before drawing, a preprocessor expands the string into a line buffer: authoring-time ^X becomes 0xCE (X - 0x2D), and the substitution tokens 0xC1..=0xC5 / 0xC7 are replaced by the text they name (a party member's name, an item, spell or arts name). The renderer only ever sees the expanded string.

Escape table

38 four-byte entries at SCUS 0x80074050, indices 0x00..=0x25; an index past 0x25 reads whatever follows the table.

+0x00sprite_id (0 = number)i16
+0x02advance pxu8
+0x03y_offset / counteri8

A non-zero first field is not a string: it is a UI-icon sprite id into the 12-byte sprite records at 0x800732A4, drawn untinted from the system-UI sheet at VRAM (896, 256) at y + y_offset. A zero first field prints a number instead: the signed halfword at script-counter slot y_offset (the field VM's counter table, written by 4C CA/CB/CC), at 8 px per digit.

Line width: nothing wraps

No retail text surface wraps. Every line break is an authored 0x7C or a new dialog line; an over-long line is drawn in full, over the box frame and off it. The renderer has no clip and no length test, and none of its callers measure a line first. That is why a translation has to fit the box by pixels, not only its byte slot.

Typewriter pacing

Dialogue types in. The pager keeps a reveal counter per row, and the draw shows only that many units. A unit is a glyph, a 0x7C or a whole 0xCE escape; a colour change costs nothing, and a substitution costs the length of what it splices in. The counter gains one unit per vsync. A row shorter than 0x22 units then holds for a moment before the next starts, so short lines do not flash past; the last row of a page never holds. Confirm while a row types completes the page. Rows scroll inside the box rather than clearing per page - see MES dialog.

Rendering pipeline

  1. ExpandPreprocessor: ^X → 0xCE escapes, substitution tokens → their text.
  2. CountGlyph count for the typewriter reveal - a unit count, not a pixel width.
  3. Draw lineWalk bytes, dispatch escapes, emit one GP0 0x64 sprite per glyph, apply the advance.
  4. PagerThe field dialog pager draws each row at the box's x with pad 1, capped at the reveal counter.

A separate pixel measurer (the same expansion, then the widest 0x7C-separated line) exists for the few surfaces that size themselves to their text, such as the battle name plaque.

Accented Latin cells

The sheet indexes every byte 0x20..=0xFF, so the cells above 0x7E are ordinary glyph cells. Whether one draws needs two things at once: ink in the cell and a non-zero width.

  • USA page. 32 of the 128 high cells carry accented Latin letters, mostly at their IBM CP437 positions (0x80..=0x90, 0x95..=0x9A, œ at 0x9C, a run one cell below CP437 at 0xA0..=0xAC). The width table gives 26 of them a zero advance, so they draw and the next letter overprints them. Retail English text barely touches them.
  • PAL pages (French / German / Italian). A different, smaller drawing of every glyph, with CP437 accents plus accented capitals and ß mostly at CP850 positions. The French preprocessor alone folds oe / OE to the ligature cells at draw time.
  • Byte range limits. 0xC0..=0xCF are two-byte dialog opcodes, never glyphs, so those cells are unreachable from text.

The translation tools share one byte-to-character layout (CP437 for the lowercase block, CP850 for the rest, so text lifted from a PAL disc and text typed by hand land on the same cells). Their accent font rebuilds every layout cell on the user's own disc at patch time: it copies the base letter from the same page, paints a small diacritic mask in the page's two ink indices, and sets the width to the base letter's advance. It is two same-size in-place edits (the font TIM rows in PROT.DAT and the SCUS width table), and no glyph pixels are committed - the recipes run against the disc being patched.

What does not fit: Latin letters with no cell in the layout (Polish ł, Czech č) fold to ASCII, and Cyrillic, Greek and CJK need more cells than the 224-cell sheet has - a second glyph bank plus a multi-byte encoding in the renderer.

How we know

The tables, packet shape and escape handling are read off the single-line renderer's disassembly; the disc TIM byte-matches the font page in live save-state VRAM, and line widths decoded from it match the drawn display lists.

Open questions
  • The upload routine. The boot-time routine that issues the GPU LoadImage of the head-gap TIM to (896, 0) is not named; it sits between the PROT TOC loader and the first dialog open.
  • Description lines. Item and spell description lines have no pinned width; the 144 px info window bounds them only by inference.
History: the "carrier never found" search

A per-entry search of every PROT entry (direct slice, glyph-row signature, both again over LZS-decompressed bytes) returned zero hits - correctly, because the font lives in the gap between the TOC and the first entry. The flat sector scan behind the TIM catalog is what found it.

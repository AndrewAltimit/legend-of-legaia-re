Art Data - Tactical Arts records Inferred

Legaia's battles are famous for their fighting-game input system: tap the right d-pad sequence and your character performs a Tactical Art combo. This page is the data behind it. Each playable character (Vahn, Noa, Gala) has a per-character table of art records describing damage, animation, hit timing, status effects, and Super/Miracle Art trigger metadata; these records drive the battle action system. The mechanics hiding in the data are the fun part: a Miracle Art is a literal secret input string that, when matched exactly, wipes the whole action queue and substitutes its own (below), and Super Arts trigger by a find-and-replace pass over the tail of the queue (below). Implementation: crates/art.

The button combos live in TWO places

The matcher - what actually fires an art - reads the player-file record copy: the 1=L,2=R,3=D,4=U byte run at record +0. The menu draws the arrows from the SCUS arts-name table's +8 glyph string. Editing the glyphs changes what the menu shows but the art still fires on the old combo (proven in two emulator playtests), so a faithful edit changes both - which is what the arts randomizer does.

Art record layout

The layout is schema-then-walk: each record begins with a fixed prefix (commands, action constant, anim index), and the remainder is a sequence of variable-width fields whose presence depends on the art. The external RE work this schema derives from captured field positions but did not pin every byte - this page documents the schema; crates/art ships a strict parser for the prefix and surfaces the unparsed tail for downstream tooling.

Damage power byte - pinned to record0 +0x24

The power bytes are Confirmed on disc. Each 0xD0-stride record carries its 1-4 per-strike power bytes as a contiguous run at a fixed offset +0x24 (after the fixed-width name slot, not name-relative). The read chain: the arts / melee damage kernel FUN_801EC3E4 (overlay 0898) reads the current strike's power byte as param_2[actor+0x1F4], where param_2 = actor[+0x4C] (the materialised art record) and actor+0x1F4 is a strike cursor starting at 0 and incrementing per hit (0x801EECE8); FUN_8004AD80 materialises an art (staged id >= 0x10) into actor[+0x4C] = *(DAT_801C9360[char] + slot*4), the runtime copy of record0. Byte-validation across all three player files: every art the name table lists resolves to one record whose +0x24 holds power bytes matching its damage tier (weak arts 1 byte, Hyper / Super 4 ascending bytes; Gala's spirit-only Miracle carries none). There is no display copy of the power. Editor: legaia_patcher::arts_power.

Art records are indexed by action constant

The array is not a packed list of inputtable arts - it is indexed by action constant: record_off = art_block_base + (c - 0x10) * 0xD0. Constants 0x19 / 0x1A (the two Art Starters) land on the two records named "Starter", 0x1B on the character's Miracle Art, and the regular arts follow at 0x1B + display index. The mapping comes off the queue-builder FUN_801EED1C, which emits a matched art's constant as its row + 0x18 (0x801EF6F0). Three consequences:

  • Super Art finishers have records here too, at 0x2B..0x2F (Vahn, Gala) and 0x2E..0x32 (Noa), named for the Super Art and carrying real power tiers - so a Super Art's damage is ordinary art-record data (legaia_patcher::super_art_power).
  • A Super Art record has no combo - its +0 field is a one-byte stub, which is why a combo-keyed lookup never lands on one.
  • Some records are reachable by neither route: Vahn's and Gala's 0x2A, Noa's 0x2C/0x2D carry named records with power bytes but no name-table row and no combo.

Runtime cue playout

The hit sparks, damage numbers and impact freezes you see during an art are not decoded up front - a per-frame driver in the battle overlay (PROT 0898) walks the record's hit run as the animation reaches each frame, with a per-actor cue cursor at actor[+0x1F5].

  • FUN_801dea50 - the per-frame hit-cue + damage-marker playout. Reads the hit run at art_record + cursor*8 + 0x14 (8-byte entries: +0 timing, +1 cue code, +2/+4/+6 XYZ offsets), places each cue from the actor's position rotated by its facing, and dispatches on the code: high bit set spawns an efect.dat billboard (& 0x7F via FUN_801dfdf0); a plain code selects a 3D move-VM prototype from 0x801F6324. On the terminator entry it materialises the move-power record for actor[+0x1DF]. ghidra/scripts/funcs/overlay_battle_action_801dea50.txt.
  • FUN_801e22c8 - a lighter impact-cue emitter for a single art / anim id, reading the per-art cue table at 0x801F6470 (5-byte stride: count, then codes).
  • FUN_801e09f8 - the special-attack sibling of FUN_801dea50; same machinery, damage routed through the summon / move-power kernel FUN_801dd0ac.
  • FUN_801e6d84 - raises the caster and target banners for a committed action (keys on +0x1DD target, +0x1DE category, +0x1DF id; nothing for Run / Defend). FUN_801d8de8 is the HUD-element raiser, not a camera command.

Impact-effect class (entry +0x7A)

Entry +0x7A carries a 1..=5 selector (0 = none), bounded by FUN_801ec3e4's sltiu v0,v0,6, stored at actor[+0x21F] with its 0x801F53D4 row at actor[+0x04]. Two renderers read those and neither consults the cue records: FUN_8004998c streams an element spark along the swing path (efect.dat sprite 0x0B for selector 1, 0x10 for 2), and FUN_80049348 draws fading afterimage copies of the character mesh tinted from the per-character table at 0x80076908. So this byte, not the cue script, is what makes an art read as its owner's element - of the three 50-AP Hyper Arts only Vahn's Burning Flare sets it (1); Gala's Thunder Punch is 2. The afterimage table's channel order is not settled.

No battle effect id plays a sound. A party Tactical Art's audio is entirely the CD-XA layer - the per-swing cue, the shout pool and the Hyper fanfare fired by FUN_8004AD80 (audio). A cue code's high bit is the "spawn a digit" flag, and a plain code past 0x3C reads past the prototype table - the spreadsheet's 0x4C "hit effect" constant stages a part from a NULL record and names no sound and no authored effect. Per-code specials are tabulated on battle-action.

History: 0x801F6418 as an SFX table

0x801F6418 was long documented as an SFX id issuing a "0x1DC sound packet". The routine the six readers end in is FUN_80058490, whose materialised string is MoveImage, and the 8-byte "packet" is a PsyQ RECT (x = table[code], y = 0x1DC, w = 0x10, h = 1) - a palette copy, not a cue. No SPU-cue call appears inside FUN_801DEA50 or FUN_801E22C8. See do-not-re-walk.

Learned Art Constant

A separate per-character byte (0x8008488D Vahn, 0x80084CA1 Noa, 0x8008506C Gala) tracks the highest learned art slot. Slot indices 0..=0x10 resolve to action constants through a per-character indirection table - and that table has holes: Noa skips slots 0x02 and 0x03 because her Hurricane Kick covers all three on-disc levels through a single learned slot.

Miracle Arts

Each character has one Miracle Art. When the player enters the exact command sequence for that art, the runtime clears the entire action queue and writes the art's replacement string instead.

Character Art RAM PROT Command sequence
Vahn Vahn's Craze 0x64F4 0x0CDC R D L U L U R D L
Noa Noa's Ark 0x6504 0x0CEC L U R D U L U D R
Gala Biron Rage 0x6514 0x0CFC R R D U D U D L L

Each replacement string follows the shape [L, R, D, U, SpecialStarter, art1, art2, ...] where the four leading directionals are the on-disc MSB-set bytes (0x8C/0x8D/0x8E/0x8F), masked to 0x0C/0x0D/0x0E/0x0F at copy time. The full table is in crates/art/src/miracle.rs.

Super Arts

Super Arts are not invoked by direct command-string match. Instead, after each art finishes, the runtime walks the full action queue and looks for a registered Find pattern. If a Find pattern matches the tail of the queue and all participating arts paid AP, the matched bytes are replaced by a Replace tail that ends with the Super Art's finisher action constant.

Example - Vahn's Tri-Somersault (0x2B):

Find:    19 27 0F 19 1F 0E 19 27
         (Starter Somersault Up Starter Cyclone Down Starter Somersault)
Replace: 19 27 0F 19 1F 0E 1A 2B 2B 2B
         (… SpecialStarter, Tri-Somersault × 3 hits)

Triggers:

  1. The last art of the Find string must be the last action in the queue.
  2. All arts in the Find string must be non-NEW (their AP cost is paid).
  3. Super Arts themselves do not consume AP - the chain arts pay it.

Full per-character tables (5 entries each for Vahn / Noa / Gala = 15 total) are in crates/art/src/super_art.rs.

The interleaved connector direction after each art (the 0F / 0E above) is not typed between the arts - it is what the retail tokenizer leaves behind. FUN_801EED1C's normalisation loop (0x801EF2EC..0x801EF858, read off the disassembly) writes 0x19 over the last arrow of a matched art, inserts the art constant after it, and keeps the leading arrows in place; it walks tail-first and restarts after every match, so an arrow can belong to two arts. ↑↓↑ alone becomes 0F 0E 19 27. So a Super's Find pattern is what its physical input tokenizes to: Tri-Somersault's 19 27 0F 19 1F 0E 19 27 is ↑↓↑↑↑↓↑ - seven arrows, Somersault, Cyclone and Somersault overlapping - and the in-the-wild capture's resident queue is exactly that input tokenized then tail-replaced. Laying the three arts end to end tokenizes to four arts and does not trigger. Port + derivation: legaia_art::tokenize.

Arts-name table (DAT_80075EC4)

The display names + AP costs of every Tactical Art live in a static table in SCUS_942.54 at DAT_80075EC4. It's the table the MES interpreter's 0xC5 substitution code reads (see MES bytecode encoding) - the 0xC5 operand XX keys it as (character = XX>>6, art index = XX&0x3F).

The expander (FUN_80036514) scans 20-byte (0x14) records sorted by character, matching (record[+0], record[+1]) against the key, and returns the +0xC name pointer ((&PTR_DAT_80075ED0)[match_index * 5]).

A (99, 99) record named "End" terminates the table. Each character's index 0 entry is the Miracle Art (AP byte 99; the name string opens with a 0xCE 0x09 character-name-substitution control, e.g. "&'s Ark" / Gala's "Biron Rage").

The AP costs are byte-exact against the curated gamedata arts table (every matched art agrees), which makes this the on-disc provenance for that table's ap column + the canonical art display order.

The AP byte is a display mirror

The +2 byte is not the value the battle engine spends. Its one reader is lbu a0,0x2(s2) at 0x801D4524 inside the menu overlay's status-panel renderer FUN_801D33D8 (PROT 0899). The battle path computes the cost as multiplier x command_count, the multiplier taken from three code immediates keyed on the art's position in its character's list; retail keeps the two consistent by authoring (all 45 arts agree). A patcher that changes an art's cost has to move both - see arts command gauge.

Command-glyph string (+8)

The +8 pointer is the command-input display string - the arrow sequence shown in the arts menu, and an independent on-disc source for each art's directional command (the PROT 0x05C4 art-record command bytes are a best-effort parse pending a watchpoint). Encoding: [count u8] then count two-byte glyph codes. A one-off 0xFF XX marker separates the sequence (0xFF06 for regular arts, 0xFF09 for Miracle arts) and is not a direction. The arrow glyphs map to physical d-pad directions:

Glyph Direction dir code
0x81A9Left1
0x81A8Right2
0x81ABDown3
0x81AAUp4

The string stores the physical direction; the logical action (Arms / Ra-Seru) depends on the character's handedness (Noa's Arms / Ra-Seru are swapped). The codes match the Left=1 / Right=2 / Down=3 / Up=4 encoding the PROT records use. Cross-checking against gamedata surfaces at least one walkthrough error (Vahn's Hyper Elbow is L R L on disc, not Arms / Ra-Seru / High). Decoded by legaia_art::arts_table::parse_from_scus; dump it with art arts-table.

Validation oracle

Because the glyph string is byte-exact ground truth, it serves as the validation oracle for the two derived command sources:

  • The best-effort PROT 0x05C4 parser (legaia_art::parse_record). legaia_art::ArtsOracle::by_command(character, &commands) resolves a decoded command sequence back to a named art; the disc-gated contract test crates/art/tests/arts_table_real.rs runs every art's canonical record bytes through parse_record and asserts the decode round-trips through the oracle. This pins the parser's 1=L,2=R,3=D,4=U command-byte decode against the executable without needing the (still-unpinned) full record stride.
  • The curated legaia-gamedata arts.toml ap + directions columns. The disc-gated test crates/gamedata/tests/arts_scus_oracle.rs matches each curated art to its SCUS row by name and asserts AP + directions agree, with a small explicit allowlist for documented walkthrough errors (only Hyper Elbow). A new undocumented divergence fails the test.

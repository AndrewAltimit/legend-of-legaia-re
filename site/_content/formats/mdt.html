MDT - the MOVE buffer (animation clip bank) Confirmed

When a scene tells an actor to "do move 12" - a villager's wave, a door swinging, a scripted stumble - the frames come from the scene's move table: the buffer the engine keeps in RAM at the MOVE base, one record per move id. Despite the name, that buffer is the scene's ANM clip bank: byte-equality against the live bank in a field save state shows the type-0x05 payload is an ANM container, and its records are per-bone keyframes, not move-VM bytecode. Every scene ships its own bank inside its asset bundle; there is no single global one. And a naming trap for anyone browsing an extracted disc: the files literally named move_program_no.BIN are not move tables at all (below).

How a move is found

  1. Script asks for a moveThe field VM's 0x22 EXEC_MOVE stores a move_id in the actor's +0x5C and calls the clip driver (script VM).
  2. Pick a bufferActor flag 0x01000000 set → alternate base _DAT_8007B75C; else MOVE for ids < 0x400, MOVE2 for >= 0x400.
  3. Offset tableThe driver reads word move_id & 0x3FF of the container head: word 0 is the record count, word d is offsets[d-1].
  4. Record headerClamp the playhead, pick the frame divisor, find the per-frame data (layout).
  5. Pose the frameThe per-frame data is one 8-byte (bone, frame) entry per bone, decoded to a rigid transform per TMD object (ANM).

Layout the consumer reads

The driver masks the move id to 10 bits, so a table is addressable up to 1024 words; a real bank is an ANM container holding far fewer records (69-72 in the field scenes), with the record bodies packed right after its offset table:

+0x000countu32
+0x004byte_offsets[count] - word move_id of the head is readu32 × count
offsets[0]records, back to backvaries

Each record is an ANM clip (the field names this page used before the ANM reading in brackets):

+0x00bonesu8
+0x01scale [flags]u8
+0x02frames [max_position_x16]u16
+0x04marker_1 = 0x080Cu16
+0x06flag; low byte = divisoru16
+0x08per-frame data: one 8-byte entry per (bone, frame)8 × bones × frames
  • Scale bit 0 = "use frame divisor" (and blend adjacent frames); the divisor is consulted only when it is set.
  • frames clamps the playhead at (frames * 16) - 1: the cursor is in 1/16-frame units.

FUN_800204F8 clamps actor[0x68] (the playhead) to [0, frames * 16), advances it by actor[0x6A] (frame delta) optionally scaled by the divisor at record[6], and binds the clip for the renderer to pose. This is ANM clip playback itself, not a sibling format sharing its frame cursor.

On-disc source - per-scene scene_asset_table slot 4

(PROT.DAT is the disc's single big archive; CDNAME is the name map that groups consecutive entries into per-scene blocks.) The MOVE base is populated per scene during area transitions, not from a boot-time entry. Every scene block's second PROT entry - the one classified scene_asset_table - carries an Asset(0x05) = Move descriptor whose payload is that scene's runtime table.

+0x00count = 7u32
+0x04total decompressed size (never read)u32
+0x087 × (u32 type_size, u32 data_offset); descriptor[4] type 0x05 = Move7 × 8
data_offsetpayloads, each its own LZS stream decoding to exactly size bytesvaries

The descriptor's data_offset is measured from the start of the bundle entry, and the payload lies inside that entry's own sectors (an entry's size is the sector gap to the next TOC entry). In the port, engine-scene::scene_bundle::extract_move_payload slices and decodes it, and scene_asset_table::move_descriptor is the typed slot accessor:

let s = legaia_scene_formats::scene_asset_table::detect(&prot_bytes)?;
let move_descriptor = s.move_descriptor()?; // type_byte = 0x05

The MOVE2 base (_DAT_8007B840) is zero across every observed save state, and no Move2 payload has been observed in a retail scene bundle - the alternate table is rare or unused. (The scene_scripted_asset_table that once looked like its carrier was an entry-size over-read; see PROT.DAT.)

The move_program_no name

The extraction files named 0972 / 0973 move_program_no.BIN are not move tables. Under the +2 CDNAME numbering shift they sit in the other_game block: 0972 is the fishing minigame overlay (dev other1) and 0973 the 1-sector OTHER2 dev module. The move_program_no define actually covers extraction 0970..0971 - a \DATA\MOV*.STR FMV program / path table (the block names MOVie program numbers; see the STR FMV table), not Tactical-Arts moves. mdt classify correctly reports that neither file matches the runtime layout above.

Caveat: MoveBuffer::parse over-reads the offset table

Real per-scene buffers have offset tables far shorter than the 1024-word mask and pack record data densely right after the real table end, so MoveBuffer::parse keeps reading record bytes as offsets. Most of those point past the buffer and are counted as bogus_offsets, which makes the strict fitness() score (used - 2*bogus) strongly negative for valid retail data. Use MoveBuffer::looks_like_move_buffer() instead - it requires records.len() > 0 && used > bogus, which real per-scene buffers pass while random data fails - and classify()'s OffsetTableLayout verdict routes through it, so the CLI reports the same shape the engine accepts.

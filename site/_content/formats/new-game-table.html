New-game starting-party table Confirmed

Pick NEW GAME on the title screen and Vahn wakes up in Rim Elm at level 1 with 180 HP, five Healing Leaves and 500 gold. Where does that come from? The stats and names are a tiny static table in SCUS_942.54 - four 26-byte rows, one each for Vahn, Noa, Gala and Terra - that the seed routine expands into the live per-character records; the starting inventory and the gold are not table data at all but literals baked into the seed code. Both matter to modders: the starting-level and starting-bag randomizer options edit exactly these bytes.

The +4 stat reads as agility because of the per-character archetypes (Vahn 100, Noa 120, Gala 80). The neighbouring cap cells (+0x10C current, +0x120 max) are not fed from it: the seed routine writes the literal 100 into both for every roster slot (800561b8 li v0,0x64 / sh v0,0x6d4(s0) / sh v0,0x6e8(s0), inside the four-iteration loop). Vahn's +4 is also 100, so a Vahn-only cross-validation cannot separate the literal from the template field - Noa and Gala can.

History: the "+4 seeds the cap" reading

An earlier reading had the +4 field fanning out to the stat-cap constant and the spirit-gauge value as well as agility, because a Vahn-only save state shows 100 in all of them. The disassembly of the seed loop separates the literal from the template field; the cap is a literal. See the cap constant.

Starting inventory (code-built, not a table)

The new-game data-init FUN_80034A6C writes a single slot into the live owned-item array at 0x80085958 (= save-context base 0x80084140 + 0x1818; 2 bytes per slot [id: u8][count: u8], id-0 terminator):

0x80034b0c  addiu $v0, $zero, 0x77    ; item id  = Healing Leaf
0x80034b10  sb    $v0, 0x1818($s0)    ; inventory[0].id   ($s0 = SC base)
0x80034b14  addiu $v0, $zero, 5       ; count    = 5
0x80034b18  sb    $v0, 0x1819($s0)    ; inventory[0].count

A vanilla New Game starts with Healing Leaf ×5 and nothing else. A 6-instruction loop right after (0x80034b04.., 0x80034b1c..0x80034b2b) zeroes the 512 bytes below the inventory, but both callers of FUN_80034A6C (FUN_8001DCF8's new-game branch, guarded by the flag at 0x8007b7ac, and FUN_8001FFA4) memset the whole SC[0..0x1a18) region first, so that loop is redundant - the reclaimable seed region is the 10 instructions at 0x80034b04 (40 bytes).

The array at +0x1818 is a single ordered (id, count) list shared by every item category - the inventory menu only filters it into Items / Goods / Key tabs by id (verified against a real end-game save: consumables, equipment and accessories all sit in this one list, running to a (0, 0) terminator). A seeded slot can therefore hold any id, which is how the randomizer's starting-bag toggles seed Door of Wind / Incense and the Speed Chain / Chicken Heart / Good Luck Bell accessories. The bag's runtime bounds are on the inventory page.

legaia_asset::new_game::StartingInventory decodes the region by replaying its $v0-source stores into an SC-offset → byte map, so it reads back either the vanilla sb pair or the randomizer's packed sh halfword (id | (count << 8) in one instruction):

Starting level / XP seed

The seed routine FUN_800560B4 also initialises each live record's progression fields (offsets on the save record):

Record offsetFieldVanilla seed
+0x0 (u32)cumulative experience0
+0x4 (u32)next-level XP threshold (the status screen's "next")reach(L2): Vahn/Terra 121, Noa 102, Gala 140
+0x130 (u8)displayed character level ("LV"; the applier maintains it +1 per level-up event)1
+0x131 (u8)second per-character byte the seed inits (magic-rank candidate, unconfirmed)1

+0x100 stays zero and is unrelated to the level (the engine port uses it as its own internal cell). The shown level is read from +0x130 directly, not re-derived from experience - confirmed live: a record with level-10 experience and stats but +0x130 == 1 still shows LV 1. The per-character +0x4 values differ because of the small per-slot FUN_801E9504 correction, not because the XP curve is per-character (level-up).

How the starting-level randomizer retargets the seed

The routine seeds +0x4 for each slot by storing one $v0 literal and reloading it twice for the per-character values; the patch controls that one register and reclaims the reload sites, seeding the whole growth-capable party (Vahn / Noa / Gala) at level N with same-size edits:

  • Level - the loop's level literal + stores set +0x130 = N for every record (packed addiu $v0, (1<<8)|N; sh $v0, 0x6f8($s0); nop at 0x800561C4/C8/CC, keeping +0x131 at 1).
  • Experience - each growth slot's +0x0 gets an in-band level-N value (midpoint of reach(N)..reach(N+1)) via one addiu $t0 preload at 0x800560FC feeding three sw $t0 stores (Vahn 0x5c8, Noa 0x9dc, Gala 0xdf0) written at 0x80056100, 0x80056108 and 0x80056118 (a redundant second lui $at).
  • Next threshold - the literal at 0x800560F0 loads reach(N+1) into $v0; with the two reloads gone, all three sw $v0 stores take the same threshold, and the applier re-applies the per-slot correction on the first post-seed level-up.
  • Stats - each growth slot's template stats are recomputed to level N.

Seeding only slot 0 would leave Noa with an experience readout of 0 and Gala with a stale level-1 threshold of 140 (a spurious early level-up); seeding all three keeps the visible roster coherent.

World-state seed (code literals, not a table)

Before FUN_80034A6C calls the template expander it writes a fixed set of save-context cells from immediates in its own instruction stream. It holds the SC base in $s0 for the whole routine (lui $s0, 0x8008 / addiu $s0, $s0, 0x4140), so every seed write is an sb or sw at $s0 + off:

Three further sws are absolute rather than SC-relative and not part of this set: 0x80073EF4 = 0xE40, 0x80073EF8 = 0x2DC0, 0x80073EFC = 0. After the expander returns, the routine writes the starting-item pair at SC + 0x1818 and then clears SC + 0x1618..0x1817 - 0x200 bytes of story flags, walked downward by sb $zero, 0x1618($v1). The Door-of-Wind warp bitmask at SC + 0x161C sits inside that range, which is why any warp preset must be applied after the clear.

Widths come from the opcodes, not from Ghidra's naming. The decompiled body renders these as DAT_ / _DAT_ globals - a prefix with no width meaning that also hides that the two item stores are $s0-relative. legaia_asset::new_game::new_game_seed_words mirrors the table, and the disc-gated new_game_seed_disc test re-decodes the routine out of the user's own executable and fails on any offset, value or width the port gets wrong.

Parser + provenance

The table base + stride are pinned by byte-search of SCUS_942.54 for Vahn's ATK..INT stat run followed by his name, with every field cross-validated against the live record at 0x80084708 lifted from an early town01 save state. legaia_asset::new_game::StartingParty parses the table from a SCUS_942.54 image at runtime (PSX-EXE t_addr → file-offset map, the same resolver as the item-name table), so the engine seeds a faithful New Game from the user's own disc without committing any Sony bytes. seed_live_records ports the seed routine's halfword stores and the engine's record builder (engine-core::new_game::starting_record) applies them, so the two cannot drift. The disc-gated new_game_real test pins the four rows against the real executable. CLI: asset new-game <SCUS> [--json]. Source of record: docs/formats/new-game-table.md.

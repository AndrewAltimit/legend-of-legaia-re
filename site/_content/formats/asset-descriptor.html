Asset descriptor format Confirmed

When a town loads, the game pulls one compressed bundle off the disc and has to find the pieces inside it - the meshes, textures and animations that become the scene. This little table of contents is how it does that: a count, then a list of (type_size, data_offset) pairs, each pointing at one asset in the buffer and saying what kind it is. The walker is FUN_80020224, and the interesting part is that nothing in the executable calls it - it is reached only from a runtime overlay. Implementation: crates/asset/src/lib.rs::parse_player_lzs.

At a glance

Parser

Confidence
Confirmed - the walker is disassembled and its overlay caller is traced; the second header word's purpose is still Unknown.

Layout

The table is a flat array of 8-byte pairs after two header words. data_offset is byte-relative to the buffer start, and type_size packs the asset-type byte (the 8-bit tag saying TIM / TMD / MES / …) in its high byte with the payload size in the low 24 bits. Each payload is an LZS stream when the container is a player.lzs-style chain.

+0x08 + 8i4type_size_i(type << 24) | size: asset-type byte in the high byte, size in the low 24 bits.
+0x0C + 8i4data_offset_iByte offset of asset i from the buffer start.

How FUN_80020224 is reached

Static analysis of SCUS_942.54 (the game's main executable) finds zero cross-references to the walker - which looks like dead code until you follow the overlays. FUN_801D6704 (the town overlay's MAIN_INIT) calls FUN_80020224 at 0x801D6B0C with a0 = 0, and the result is stored at 0x80087AF8. So the format is exercised by every field scene load - through a runtime overlay rather than the executable's static call graph. This “zero static callers but alive via overlay” pattern recurs across the whole codebase; treat a zero-xref result as “needs an overlay sweep”, never as “dead”.

The same walk is what installs the field-form character meshes: FUN_80020224 → FUN_8001F05C case 2 → FUN_80026B4C registers PROT 0874 §0's five TMDs into DAT_8007C018[0..=4].

Strict-scan against the disc

Strictly scanning all 1233 PROT entries (the numbered slots of PROT.DAT, the disc's main asset archive) against this shape as a top-level entry finds zero hits: the table only exists once an LZS chain such as player.lzs has been opened, and the DATA_FIELD streaming format carries descriptor-shaped chunks under its own header instead. The parser is kept for the buffers that do carry it.

Note on naming

The Rust function is named parse_player_lzs for historical reasons - the format was first encountered while investigating player.lzs chains. The format itself is not player-specific.

Asset descriptor format Confirmed

When a town loads, the game pulls one compressed bundle off the disc and has to find the pieces inside it - the meshes, textures and animations that become the scene. The asset descriptor is that bundle's table of contents: a count, then a list of (type_size, data_offset) pairs, each pointing at one asset in the buffer and saying what kind it is.

At a glance

Confirmed - walker disassembled, overlay caller traced, and the second header word measured across every carrier on the disc.

Layout

Two header words, then a flat array of 8-byte pairs. data_offset is byte-relative to the buffer start; type_size packs the asset-type byte (the 8-bit tag saying TIM / TMD / MES / …) in its high byte with the payload size in the low 24 bits. Each payload is an LZS stream when the container is a player.lzs-style chain.

OffsetSizeFieldMeaning
+0x004countNumber of descriptor pairs that follow.
+0x044total_decompressed_sizeThe sum of the descriptors' decompressed sizes - see the second header word. Retail never reads it, and editors must keep it consistent.
+0x08 + 8i4type_size_i(type << 24) | size: asset-type byte in the high byte, size in the low 24 bits.
+0x0C + 8i4data_offset_iByte offset of asset i from the buffer start.

The second header word

The word at +0x04 is the container's total decompressed size: the sum of every descriptor's size field. Across the 105 carriers on the disc the identity holds 105 times out of 105, and in all 105 the sum is larger than the PROT entry that carries it - which is what rules out reading it as a file size or a sector count. It is where the last asset ends once the container has been unpacked into the runtime buffer, not a position inside the entry.

Retail never reads it. The walker takes its loop count from +0x00 and steps descriptor pairs from +0x08, so +0x04 is never addressed. Sweeping the executable and all 83 extracted overlays for every dereference of the table-base pointer - including the lui+load and materialised-base forms an absolute-address scan cannot see - turns up 69 access sites: one store that publishes the buffer base, and four that dereference the pointer, every one of them at displacement 0x0.

Inert at runtime is not the same as free to change. The word is an authoring total, so an editor that rewrites a descriptor's size has to keep it consistent; the Rust side checks it with SceneAssetTable::total_size_is_consistent.

Where it appears

  • On the disc, at the top level. A structural sweep of all 1233 PROT entries (the numbered slots of PROT.DAT, the disc's main asset archive) finds 105 entries wearing this header at offset 0 - the scene bundles, the player.lzs-style character and effect containers, and the minigame art container. An earlier reading of "zero hits" came from a detector that demanded a fixed descriptor count; the count word varies (80 carriers use 7, the rest 1, 3, 4, 5 or 6).
  • Reached only through an overlay. The executable's static call graph never touches the walker - it looks like dead code until the town overlay's init is followed (how we know). This "zero static callers but alive via overlay" pattern recurs across the whole codebase; treat a zero-xref result as "needs an overlay sweep", never as "dead".
  • Installs the party's field meshes. The same walk registers PROT 0874 §0's five TMDs into the model slots the field-form character meshes draw from.

The Rust parser is named parse_player_lzs after the container it was first read through; the format itself is not player-specific.

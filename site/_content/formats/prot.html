PROT.DAT / DMY.DAT TOC Confirmed

PROT.DAT is the disc's one big asset archive. Nearly everything you see and hear in the game - every texture, 3D model, sound bank, dialogue container, animation set, scene script and even the chunks of engine code that load on demand - is one of its 1233 numbered entries. Only the movies, the streamed voice audio and the main executable live outside it. This page is about its table of contents (TOC): the short index at the front of the file that says where each entry starts and how big it is.

Overview

An "entry" (or "slot") is one numbered region of the archive - the unit the game requests when it loads assets for a scene, a battle or a menu. The TOC measures everything in sectors and LBAs: a sector is the disc's 2048-byte block (see disc geometry), and here an LBA is a sector number counting from the start of PROT.DAT itself, not from the start of the disc. Three things to hold onto:

  • One word per entry. The TOC stores only each entry's start LBA. An entry's size is the gap to the next entry's start - which is exactly how the game computes it.
  • The entries tile the archive. Starts ascend, each entry ends where the next begins, and the sizes sum to the whole file. That property is what makes the reading self-checking.
  • Two index spaces, off by 2. The game's in-RAM copy of the TOC counts from the file's first word, this project's extraction counts from the first entry word. Every index recovered from game code is 2 higher than the matching extracted/PROT/NNNN_*.BIN file, and CDNAME.TXT's numbers are authored in the game's space.

DMY.DAT is a sibling archive at the disc root with the same TOC shape. Its content turns out to be developer fixtures (a memory-bus test pattern plus paired random blobs), not game data - see DMY.DAT.

Header (8 bytes at offset 0x000 OR 0x800)

OffsetSizeFieldMeaning
+0x00u32unusedzero in both retail archives
+0x04u32lba_row_count - 1number of TOC rows minus one: PROT.DAT 1235, DMY.DAT 15
+0x08u32header_sectorsheader + TOC size in 0x800-byte sectors - and this word is toc[0]

The header proper is the first two words: the toc[] array starts at +0x08, so the sector-count word doubles as toc[0]. Both readings hold at once by construction - the TOC's first LBA row is the first content sector, which is the sector immediately after the TOC. The detector takes the word as a sector count to size its TOC read; retail's resolver indexes from toc[2] upwards and never reads it as a size.

lba_row_count counts TOC rows, not entries. PROT.DAT's 1236 rows are toc[0] and toc[1] (the two boot-UI regions), 1233 entry start LBAs, and one end terminator (toc[1235] = 59206, the archive's sector count). DMY.DAT's 16 rows resolve to 13 entries the same way.

The detector tries offset 0x000 first, then 0x800, accepting whichever yields plausible values. Both retail archives use 0x000.

TOC (immediately after header)

The TOC is a flat array of u32 words (toc[] below - word 0 is the first u32 after the 8-byte header). p is the 0-based entry index (the extraction index). Each entry contributes exactly one word - its start LBA at toc[p+2] - and its size is the gap to the next entry:

start_lba     = toc[p + 2]                  // LBA relative to PROT.DAT
size_sectors  = toc[p + 3] - toc[p + 2]     // the gap to entry p+1
byte_offset   = start_lba * 0x800
size_bytes    = size_sectors * 0x800

That subtraction is retail's own routine: FUN_8003E68C is twelve instructions long and returns TABLE[i+3] - TABLE[i+2], and the loader passes its result straight to the sector read. Implementation: legaia_prot::runtime_toc, called once by Archive so the arithmetic exists in one place.

The TOC LBAs are PROT.DAT-relative, not absolute disc LBAs. byte_offset is an offset into PROT.DAT, and the in-RAM TOC is raw PROT.DAT bytes, so the values are independent of where PROT.DAT sits on the disc. Verified by diffing USA against the PAL discs: entry 0's start LBA is identical on every disc although PROT.DAT lives at a different disc LBA per region. This is what makes whole-sector entry growth tractable - growing an interior entry needs only a shift of the later entries' start-LBA words (at PROT.DAT byte 8 + (j+2)*4), not a disc-wide cascade. See disc § full-ISO relayout.

The entries tile the archive

The sizes above partition PROT.DAT: start LBAs strictly ascending, every entry ending where the next begins, and the sizes summing to exactly the span from entry 0's start (LBA 121) to the archive's last sector (LBA 59206) - no gaps, no overlaps. The two words below entry 0, toc[0] and toc[1], tile the rest: the boot-resident system-UI region runs from LBA 3, immediately after the 3-sector TOC.

A partition with that property is the entry layout, which is what makes the reading self-defending rather than merely plausible. legaia_prot::tiling states it as a checkable measurement; crates/prot/tests/archive_tiling_real.rs runs it against a real disc.

Six further lines of evidence pin the gap as the size, none of which relies on the definition itself (the "entry p ends where p+1 starts" check would be a tautology and is deliberately not cited):

  1. The tiling above. No partition of a file can exceed the file.
  2. The runtime uses the gap. FUN_8003E8A8 returns TABLE[idx+3] - TABLE[idx+2], and byindex_sync_loader (FUN_8003EB98) passes that straight to the sector read. See In-RAM TOC.
  3. Known-length files agree with it. readef.DAT is exactly 78 × 0x10800 and summon.dat exactly 103 × 0x10800 (summon-readef); every field map (DATA\FIELD\<scene>.MAP) is exactly 0x12000, the sum of its four regions; bse.dat is 2 sectors, which is what fits the 0x1800-byte buffer its loader allocates.
  4. A capture-pinned boundary. Each of the six Cort mid-cast save states holds a summon stager byte-resident in the slot-B buffer, matching its file exactly up to the sector gap and diverging after it - stale bytes of the previous occupant. The battle-action overlay's RAM-verified clean-copy prefix, 0x28800, is likewise exactly PROT 0898's 81 sectors.
  5. Every asset table lands at offset 0. Reading each entry's own sectors, all 88 scene-asset tables sit at offset 0 of their entry with every descriptor payload inside it.
  6. The one apparent counter-example is not one. PROT 899 is 74 sectors, the last 60 of which are the title-screen overlay code (see boot) - all its own, not a "trailing overlay" past its end.
History: the over-read entry size

toc[p+5] - toc[p+3] + 4 is not an entry's size

This project long used indexed_size_sectors = toc[p+5] - toc[p+3] + 4 as the entry's "TOC-declared payload", taking max() of it and the sector gap. Since every entry contributes one word, toc[p+3] is entry p+1's start LBA and toc[p+5] is entry p+3's, so the expression expands to size(p+1) + size(p+2) + 4 - the two entries that follow p. It exceeds the real size for 931 of the 1233 entries (the declared spans total about 2.5× the whole file) and falls short for the rest. Under the max() reading most entries were parsed over a buffer that ran into their neighbours' sectors. The "+4" expression gives readef.DAT a non-multiple of its record size, stops inside summon.dat's object table, and hands bse.dat a 43× buffer overrun.

The "trailing-overlay sectors" reading (that ~24% of entries were read past the size the TOC declares) was the same thing seen from the other side: entry 899's payload is not "14 indexed sectors plus 60 trailing overlay sectors", it is 74 sectors, all its own. Archive::read_entry returns exactly those and nothing a neighbour owns; Entry::declared_span_sectors and read_entry_declared_span keep the old value for diagnostics only (prot-extract list prints it in the decl_span column with an OVR flag where it overshoots). Nothing parses against it.

What reading the neighbours produced

  • The "prescript-prefixed asset table" was an over-read. A scene_scripted_asset_table was a descriptor table found at a 0x800-aligned offset inside an entry that led with an event prescript. Every such offset is the next entry's start LBA - the neighbour's ordinary offset-0 table seen through the over-read. Reading each entry's own sectors leaves the 88 bare tables and zero scripted ones; the carriers classify as event-script prescripts. The 0x1000 variant aliases the entry two rows later (scene-v12-table records two cases).
  • Overlay identity by pointer resolution was inflated. A longer window widens the acceptance range and adds a neighbour's code, so both halves of the self-pointer ratio were borrowed. On its own sectors PROT 0901 carries three such pairs, not nine.
  • "Shifted copy" claims between adjacent entries. 0900[0x2800:0x5000] == 0901[0x0:0x2800] says only that entry 0901's bytes equal entry 0901's bytes: PROT 0900 is 0x2800 bytes and 0901 begins exactly there.
  • A detector calibrated on the wrong length. The init.pak parser required >= 0x30000 bytes - PROT 0895's old declared span. The entry is 75 sectors (0x25800), so the floor rejected the real file; all four publisher-logo TIMs sit inside it.

A (entry, offset) pair is only a coordinate if the offset is inside the entry

The over-read's longest-lived legacy is a naming one, and it is the family to check first when an asset stops resolving. Any constant of the form "asset X lives at PROT N offset K" was measured inside the old window, so whenever K ran past entry N's real end the pair named a real place on the disc - just not the entry it claimed. Re-keying it to the entry whose own sectors hold those bytes changes no byte and fixes the read:

Two properties make a corrected coordinate checkable, and the disc-gated tests for those modules assert both: the offset plus the asset's length must fit inside the entry, and the payload's own framing (a streaming chunk chain, a descriptor count in the header) must terminate inside it rather than run to the buffer's end. A constant that needs a wider buffer than its entry is naming the wrong entry.

Older still

  • An early Python proof-of-concept used start_lba = toc[p+5] - toc[p+2]. That subtraction computes a size in sectors; read as a start LBA it collapsed ~80% of PROT entries onto the same few low-LBA byte ranges. Anything derived from that formula's outputs is artefacted; trust only start_lba = toc[p+2] extractions.
  • "The boot loader transforms the TOC into a different in-RAM layout" - falsified; the in-RAM copy is raw PROT.DAT from byte 0, and only the index space differs (by 2).

The full catalogue of falsified readings lives in do-not-re-walk.

In-RAM TOC + the two index spaces

At boot the game copies the front of PROT.DAT into RAM and resolves every later asset request against that copy. SCUS_942.54 keeps it at 0x801C70F0; the resolver is FUN_8003E8A8 (FUN_80xxxxxx names are Ghidra-traced function addresses in the executable):

start_lba    = TABLE[(idx + 2) * 4 + 0x801C70F0]
end_lba      = TABLE[(idx + 3) * 4 + 0x801C70F0]
size_sectors = end_lba - start_lba

The routine returns the span, not the LBA: it stores start_lba at gp+0x8f0 and folds it into the CD position the read consumes (msf_to_lba(base) + start_lba, back through lba_to_msf), leaving size_sectors in v0. That is why FUN_8003EB98 can hand its return value straight to FUN_8003E800 as a sector count.

The in-RAM copy is raw PROT.DAT from byte 0 - FUN_8003E4E8 reads the first three sectors of PROT.DAT into 0x801C70F0, header words included (byte-verified against a live save state's RAM). There is no transformation. But the extraction (crates/prot, and the NNNN in extracted/PROT/NNNN_*.BIN) builds its toc[] array after the two file-header words, so the two sides count from different origins:

The canonical rule: raw TOC index = extraction index + 2. Any PROT index recovered from a FUN_8003E8A8 argument must subtract 2 to land in extraction space (byte-verified for the battle side-band files: raw TOC indices 0x37F/0x380 resolve to extraction entries 893/894, see summon-readef). CDNAME.TXT's #define numbers are authored in the raw-TOC space, so the extractor's filename labels are shifted +2 relative to the content the defines name - see cdname § numbering space.

Raw-TOC entries 0 and 1 cover the boot-UI region (LBA 3..120) that extraction indexing leaves unindexed: two TIM-packs holding the boot-resident system-UI bundle (menu-glyph atlas, sprite sheets, cursor parts; uploaded once at boot by FUN_800198E0 with flat-strip CLUT semantics, parser legaia_asset::system_ui_bundle) - see tim-pack § boot-resident system-UI instance.

Resolving entries by name vs by index

Game code asks for an entry in one of two ways:

  • FUN_8003E8A8 - index-based (consumed directly by the streaming loader and the dev-build sound branch).
  • FUN_8003E6BC - path-based; resolves dev paths like data\battle\efect.dat or h:\PROT\FIELD\<scene>\… into an index via the CDNAME-driven name map, then delegates to the LBA resolver. Most retail-build code paths land here.

Names come from CDNAME.TXT, which lives at the top level of the disc.

Overlay loaders (parallel slots)

Much of the game's logic is not in the executable at all: the field, battle and menu engines are overlays - code entries in PROT.DAT that the game loads into RAM when it switches mode. Two paired wrappers over FUN_8003E8A8 + FUN_8003E800 (the async LBA-based loader) manage two independently swappable overlay slots. Both call FUN_8003E8A8(param + 0x381) - which, per the index-space rule above, is extraction entry param + 0x37F (param 2 → 0897 field, 3 → 0898 battle, 4 → 0899 menu):

Two overlays can therefore be RAM-resident at once (a title-overlay code blob in slot A and a sister asset blob in slot B); mode-init handlers use one or the other depending on what they load. The CD-read API stack behind these is on boot.

FUN_8003E360 shows a dual-mode loader pattern: in retail (_DAT_8007B8C2 != 0, the value retail boots with) it loads via the PROT TOC index; in dev (_DAT_8007B8C2 == 0) it opens an h:\ path through FUN_800608F0 / FUN_80060944, where FUN_800608F0 is a break 0x103 dev-station host trap. Only the retail branch runs on a real disc.

MES dialog format Confirmed

MES is the container for Legaia's dialog text - every line an NPC speaks lives in one. The text is not ASCII: each byte names a tile in the dialog font, and a few prefix bytes splice in live data - the hero's name, an item, an art - at display time. Two on-disc variants share an offset table + bytecode tail, and unusually the interpreter is in the main executable rather than an overlay.

Anatomy of a line

lead0x1Fu8
glyphsfont tile indices1 byte each
escape0xC1 XX = hero's name2 bytes
glyphs… 0xCE XX = spacing1-2 bytes each
end0x00u8
control0x24 / 0x25 / 0x27..after the page

A line is glyph indices with 2-byte escapes. Consecutive lines fill a three-row box; the control byte after the page says what the button press does - next page, close, or open a choice menu.

The Records variant has no fixed header: the parser finds record boundaries by scanning for 0x44 0x78 markers (at least four). Its per-record structure is Unknown.

Bytecode encoding

Most bytes are glyphs. Prefix bytes 0xC0..0xCF (plus two aliases) take a data byte and either name a wide glyph, insert spacing, or substitute a string from one of the game's name tables. All four interpreter functions share this classification; only the action per byte differs.

ByteStrideMeaning
0x00..0x1E1Line terminator; walkers stop here
0x1F..0x5D, 0x5F..0xBF, 0xD0..0xFE1Glyph (font tile index); 0x1F is also the line lead
0x5E XX2Alias, rewritten to 0xCE (XX - 0x2D)
0xC0 XX, 0xC6 XX, 0xC8..0xCD XX2Wide glyph, no substitution
0xC1 XX2Character name from the save record XX; 99 = current party leader
0xC2 XX, 0xC4 XX2Item name (item table); two consumer sites, one table
0xC3 XX2Magic name (spell table)
0xC5 XX2Tactical Art name (arts-name table), key (character = XX >> 6, art = XX & 0x3F)
0xC7 XX2Terrain / quest name (8-byte stride table)
0xCE XX2Spacing: XX is a horizontal offset
0xCF XX2Passthrough: XX renders alone
0xFF1Alias, rewritten to 0xCF

The substitution gate is the integer test (byte + 0x40) < 8, catching 0xC0..0xC7; 0xC0 and 0xC6 fall through to "no substitution" at 2-byte stride.

Japanese build: count-led Shift-JIS lines

The table above is the Latin builds' encoding (USA and PAL). The Japanese disc frames the same script positions differently, measured from its scene MANs:

Latin buildsJapanese build

Both satisfy the pager's line test (b & 0x7F) < 0x20, which is why the Latin builds kept 0x1F - the Japanese build's longest count - as their lead byte. Three Latin-build scene MANs still carry Japanese-framed lines that no Latin script reaches.

The four interpreters

  • Stride walker - 16 instructions returning the glyph count to the next terminator; the pager uses it for line lengths.
  • Glyph counter - the same walk plus substitution dispatch, counting the substituted name's glyphs too. It returns a count, not a pixel width (it never reads the font width table): the count paces the typewriter reveal. Nothing wraps text at run time - line breaks are authored (dialog font).
  • Substitution expander - normalises the two aliases, then inlines each substituted name byte by byte into a working buffer.
  • Renderer - expands first, then emits glyphs into the text-actor buffer and forwards spacing ops to the cursor.

The dialog window pager

Above the byte-level interpreter sits the per-frame state machine that opens the speech box, scrolls lines in, waits for a button press, and turns the page. It lives in the dialog overlay: 26 states covering load / scroll / drain / wait / done, with per-line bytecode pointers in a 16-line buffer. In the port: engine-core's dialog_window (rows, scroll, confirm) and dialog_pacing (the typewriter).

Box packing

  • The window shows 3 rows; three box-open states each pin the limit to 3. It is a window height, not a page length.
  • Consecutive 0x1F lines are one page: a line right after a line's 0x00 means "same page, next row". A fourth line scrolls the window up a row with no button press; the page ends only at a control byte.
  • A 0xC? escape whose argument falls in 0x00..0x1E (e.g. 0xC1 0x00) does not end the line; the advance loop consumes the argument as part of the token.
  • Multi-page speech is several pages chained by 0x24. dialog_box::pack_page decodes a page; pack_box / pack_boxes cut the same lines into window-sized chunks. The Rim Elm sparring partner's narration packs into three full pages then a 2-row box opening a 4-option menu.

Row window and scrolling

The row table is a scrolling window. State 0x0B types the last row; a line after a full window scrolls it (0x0C, 15 px per row at 0x24 * dt sixteenths a call); at a page end, rows the previous page left above scroll away (0x0F) before the page waits (0x19). A 0x24 page turn keeps the rows and types the next page beneath them. A confirm press while a row types or holds latches 0x25 and completes the page (0x0D, then 0x0E for overflow). The text is clipped to the box's rows band; the frame does not scroll. A town01 emulator trace pins every arm.

Post-page control byte

When the page is full and the player confirms, the pager reads the next control byte (masked & 0x7F) and picks the follow-on state:

Control bytePager statesEffect
0x243 → 4Next line, same box (rows preserved)
0x489 → 0xABox reset, open animation - a fresh box
0x250 → 1Box reset, row buffer cleared (teardown)
0x4C 0xFF6 → 7Box reset, row buffer cleared (teardown)
0x2A0x11 → 0x122-option menu in a small top-right box that slides in from the right edge
0x270x13 → 0x142-option Yes / No menu; the box slides up from the bottom edge
0x280x15 → 0x163-option menu, same slide
0x290x17 → 0x184-option menu, same slide

The pager decides the box, not the conversation: teardown clears rows and stops. Whether the dialogue session ends is decided by the actor dialog SM and the field VM.

No menu takes input on the press that opens it. The box slides from off screen to its place over a span of 24 frame-step units - twelve pager calls at the field's 30 fps, 10 px a call for the inn's top-right box - and the option hand appears on the call where it lands, with input read from the call after. A capture of an inn's stay offer measures 26 vsyncs from the press to a usable menu. Tetsu's 4-option list in Rim Elm rises the same way from below the screen, y 240 to 148 at 8, 8, 7 px a call, with the same 26 vsyncs to input.

Choice menus (pickers)

Four open bytes - 0x27, 0x28, 0x29 and 0x2A - open a menu. Relative to the open byte at index O:

before O0x1F prompt … 0x00box text
Oopen0x27..0x2A
O+1N jump entriesi16 LE × N
O+2N+1continuation0x24/0x25/0x48/0x4C FF, or absent
thenN × [0x1F label 0x00]option labels
  • Each jump entry is a signed 16-bit relative jump applied on confirm: new_pc = (O + 1 + index*2) + entry[index], relative to that option's own entry.
  • Labels are ordinary 0x1F segments after the continuation byte, drawn under the prompt at a 15-px row pitch.
  • Two continuation forms exist: a dispatch byte before the labels (the izumi book menu) or the first label's 0x1F directly (Rim Elm's spar menu). The parser accepts both.
  • 0x2A is a real 2-option picker whose cursor clamps instead of wrapping. Every inn's Yes / No offer is one (inn); a decoder that stops at 0x29 finds no inn menus.

In the port: legaia_mes::picker decodes the menus; engine-core::inline_dialogue runs the whole interaction script through the field VM (flag tests, scene changes) and pauses only at each 0x1F segment, applying the picked jump on confirm.

Box geometry and render

The three box-open init arms (states 0, 6, 9) are near-copies differing in one word: the successor state each writes (1, 7, 0xA). States 1 and 7 clear the 16-entry row buffer; state 4 (from 0x24) returns early and preserves it; state 0xA ramps _DAT_801F274C to 0x1000, which the draw reads as the box collapsing to its centre line, then hides the box for 0x18 steps and drops into state 1.

Picker box rect: x = 0x26, y = 0x94 + ((4-N)*0xF)/2, w = 0xF4, h = 0x38 - (4-N)*0xF - 244 wide, shrinking 15 px per absent option. The main reading box is emitted as (ctx+0x12, ctx+0x14 + d, 0xF4, lines*0xF - 3) with skin 0x61, where d moves only with the 0x48 collapse animation - the rows scroll, the frame does not.

The box emitter composes a 9-slice gold frame from the system-UI sheet plus an interior fill of two identical semi-transparent gouraud quads (mode B/2 + F/2, top RGB (0x18,0x18,0x28), bottom (0x40,0x40,0xA0)), which composes to 0.25 back + 0.75 gradient. The engine bakes the gradient at alpha 191/255 and draws it once. The page-advance hand draws at (0x10A, box_y + lines*0xF - 0x13); the picker hand at (box_x - 6, box_y + cursor*0xF); labels render CLUT 7 at box_x + 0x10.

Field dialogue has no dedicated opcode: it is the actor's inline interaction-script text, triggered by the touch / button-press interaction rather than an opcode (op 0x3E with op0 < 100 is the scripted-battle install). Op 0x3F is the scene change, not a dialog op.

VAB sound bank Confirmed

Every instrument you hear in Legaia's music - the strings under the world map, the drums in a battle theme - and every sound effect is a sampled sound stored in a VAB bank. A VAB is Sony's standard PlayStation instrument bank: a set of programs (instruments) made of tones (key-range variants) that point into compressed sample bodies the sound chip plays. The bank is one half of the music; the note data that plays against it is the other half, the SEQ.

What trips up a stock VAB reader

The format itself is documented in the PsyQ SDK, so this page only covers the parts that are Legaia-specific - the things that make a generic VAB extractor return nonsense on this disc.

  • The bank is usually wrapped. The dominant on-disc carrier is the scene-VAB-prefixed streaming shape: a 4-byte chunk header, then the VAB body, then a second chunk header and the SEQ. So the VABp magic is not at offset 0 of the entry; crates/vab::parse_header(buf, offset) takes a starting offset for that reason.
  • Don't trust the filename. Extraction filename labels carry the +2 CDNAME numbering shift, so a block name is a hint, not a verdict. Trust the VABp magic and the loader constant.
  • Program numbers are not tone-page indices. The tone pages are packed by used program, so a program resolves to its page by rank. Details in the next section - it is the single most consequential fact on this page.
  • The VAG size table is 1-indexed. Its slot 0 is a spacer that is 0 in every retail bank; it is not a pitch or sample-rate field.
  • Sample rate lives in center. A body recorded at 22.05 kHz is authored with its center key an octave above where it should sound. A port that also multiplies by 22050/44100 plays everything an octave low.

Layout

A bank is a fixed 32-byte header, a 128-slot program table, a packed run of 16-tone pages, a 256-entry sample-size table, and then the sample bodies.

Program slots vs packed tone pages

A SEQ ProgramChange (or an SFX descriptor) names a program number, which indexes the 128-slot ProgAtr table directly. But the tone pages that follow are packed: there is one 16-tone page per program whose tones byte is non-zero, ps pages in total, in slot order. A program therefore finds its page by its rank among the used slots, not by its own number.

Retail builds that rank map once, at bank open: FUN_80068D94 (SsVabOpenHead) walks the whole ProgAtr table writing the running used-program count into each entry's +8 reserved word, and the program-change handler FUN_80068B98 reads it back as the page index. The open also stashes each VAG's SPU address >>3 into the +0xC / +0xE reserved slots.

This matters on this disc: 66 of the 218 wrapped PROT-entry banks - 43 of the 77 music_01 banks - use sparse program sets, so indexing pages with the raw program number mis-tones or silently drops most of their instruments. The engine expands pages into slot space at upload (VabBank::upload); the law is asserted corpus-wide by engine-audio/tests/real_vab_program_mapping.rs.

The unused-slot alias

Retail stores the rank counter before the used check increments it, so a program-change to an unused slot borrows the next used slot's page (keeping its own mvol/mpan). Real BGM exercises this - music_01 PROT 868 program 5 and PROT 996 program 19 select gap slots retail plays via the alias - and the engine reproduces it (real_seq_program_change_coverage.rs pins the census). The one case not reproduced is a change past the last used slot, where retail reads garbage beyond the tone region: the engine leaves those silent.

Tone attributes: which fields retail actually uses

Each 32-byte tone (VagAtr) carries the standard Sony fields. A disc-wide census of every tone (real_vab_tone_attributes.rs) fixes which of them the retail data populates:

  • Used by playback: vol/pan (mix), center/shift (key to pitch), min/max (note range picks the tone), adsr1/adsr2 (envelope), and pbmin/pbmax - the per-tone pitch-bend range in semitones. The common value is 2 (the GM default), with a few tones at 4/12/24/40; a (0, 0) tone does not bend. The sequencer scales a 0xEn wheel event by the sounding tone's range (VabBank::pitch_bend_range).
  • Always zero in retail: vibrato (vibw/vibt) and portamento (porw/port), so the clean-room voice model needs no LFO.

center / shift are the whole of the pitch, sample rate included

center is the key at which the tone plays at unity - SPU pitch 0x1000, 44.1 kHz - and shift raises it by shift/128 of a semitone. The header carries no per-sample rate and the size table's spacer is not one either, so a 22.05 kHz body is authored with center twelve semitones above the key it should sound at. The full key-on law is in audio § key-on pitch law. crates/vab's WAV writer hard-codes 22050 for the standalone-extraction case, which is a separate question from playback.

The VAG size table is 1-indexed

The trailing table is 256 × u16; vag_table[1..=vs] hold each sample's size in 8-byte units, so vag_table[0] is a leading spacer. It is 0 in all 424 retail banks (disc-gated corpus_vag_spacer), and no pitch offset is derived from it - VabReport::vag_table_spacer surfaces the raw byte only.

History: the "three multi-bank archives" and the 1191-header count

Earlier corpus figures - 1191 VABp headers across 239 entries, with 0889_sound_data2 (207 banks) and 0890_sound_data2 (203) alongside 0891 as multi-bank archives, and 120 vab_01 carriers - were counted through the superseded over-read entry window (prot § History). That window spans the two small entries into 0891's 6 MB archive; on their own sectors 0889 and 0890 hold one and zero banks. Exactly one multi-bank archive exists. The old-window numbers reproduce only under the old formula. See do-not-re-walk.

Field-pack format Confirmed

Rim Elm is the first town a player walks around, and the entries that carry it on the disc are unusual: a handful of them open with a scene-shaped script table, then a magic number, then a 97-slot offset table (the "schema") and the ~91 KB block it indexes. That block turns out to be byte-identical in every file that carries it - a shared template, not per-scene data - and the magic itself is decorative: nothing in the game's code ever checks it. The real per-scene payload is the preamble in front of the block. This page is as much about what the format is not as what it is; the detector is solid, the interpretation is bracketed. Detector + dispatch: crates/asset/src/field_pack.rs.

What varies and what does not

Scope from a raw PROT scan, pinned by crates/asset/tests/field_pack_real.rs: the magic appears raw in exactly four PROT entries, the 97-entry schema signature in eight (the other four carry it without the magic prefix), and the ~91 KB schema-indexed region is byte-identical across town01 and town0c. Two facts fall out:

  • The ~91 KB region is a global constant. A block that is byte-identical across unrelated scenes is a shared template / default asset, not the scene's own field data. (0002 and 0020 carry only a ~5.7 KB head of it.)
  • The magic is decorative. The identical block ships with the magic in town01 and without it in town0c; combined with the word having zero runtime references, 0x01059B84 is a build-tool stamp, not a parser anchor. 0005/0023 are the same "template-only" entry, one stamped and one not.

The per-scene payload is the preamble

What actually varies per scene is the preamble before the block. In 0003_town01 it opens with a record count (0x3F = 63) + an ascending u16 offset table (0x80, 0x380, 0x3c2, ...) + variable-length records - exactly the scene_event_scripts prescript shape. Record 0 is a fixed 768-byte dispatch table; records 1.. are word-aligned actor/event command records (0xFFFF 0x0000 header sentinel, 0x0008 terminator) - not field-VM bytecode. The town0b/town0c field files that carry no field-pack block at all (0012_town0b, ...) open with the same prescript, confirming the preamble - not the constant block - is the scene's field data.

History: "124 entries, slots filled per scene"

The earlier reading - "124 PROT entries share the schema, the preamble fills the slots per-scene" - does not survive a byte scan of the corpus, and the long-open "preamble to schema-slot mapping" question rested on a false premise: the slots are a fixed template, there is nothing per-scene to project into them, and the per-scene structure is the already-parsed scene_event_scripts prescript. Retired readings are collected on do not re-walk.

Why the magic isn't load-bearing

A scan of SCUS_942.54 (the game's main executable) and every captured overlay (chunks of MIPS code the game loads into RAM on demand - dialog, town, battle action, menu, the 0896 / 0897 / battle-action clusters) for either the LUI+ADDIU/ORI immediate pair that synthesises 0x01059B84 or the byte sequence 84 9B 05 01 returns zero hits. The runtime never compares against this magic.

That rules out a magic-checked format loader. The most likely interpretation is that field-pack is a build-time layout artefact - the schema describes the in-RAM shape that per-scene code reads at hard-coded slot offsets, and the magic is a sanity marker the disc mastering left behind (or the dev tooling stamped) rather than a runtime parser anchor.

Per-slot interpretation therefore depends on locating the consumer - per-scene code in a field/town overlay that reads from the slot offsets. See ghidra/scripts/find_field_pack_magic.py for the scan that established the magic isn't referenced, and ghidra/scripts/find_field_pack_consumers.py for the consumer-search complement.

Loader chain

Tracing a town01 field capture (CDNAME town01, scene 0x03) through the captured overlays + SCUS_942.54 pins the runtime path that brings a field-pack file into RAM:

1FUN_8001FD44(scene_name, sub_index)Scene change requested: copies the new name into 0x80084548, the previous name into 0x80084558, sets the 0x40 pending-transition bit in _DAT_1F800394SCUS 2FUN_801D6704Scene-transition orchestrator; calls the loader with a0 = _DAT_1F8003EC, a1 = 0x80084548, a2 = _DAT_80084540 (801d6ae8)overlay 0897 3FUN_8001F7C0Builds DATA\FIELD\<scene>, loads it via FUN_8003E6BC; builds h:\PROT\FIELD\<scene>\efect.dat, loads it at buffer + 0x12800 and stores that address in _DAT_8007B8D0SCUS 4FUN_80020224 → FUN_8001F05CDescriptor-pair walker (801d6b0c) iterates the asset descriptor table at _DAT_8007B85C and dispatches each entry through the asset-type dispatcherSCUS

Dialog-overlay handlers like FUN_801D1344 call FUN_8001FD44 directly when a story event needs to warp - e.g. the town01 warp requires _DAT_1F800394 & 0x04000000 != 0 plus a couple of menu-state flags. buffer_ptr is read from scratchpad cell 0x1F8003EC (the heap-resident scene asset buffer pointer); per-scene values vary because the loader allocates from a pool. The asset descriptor table at _DAT_8007B85C = 0x8015CBD0 is statically allocated and identical across captured saves; its entries point into the per-scene region.

The 97-slot field-pack data is consumed at static offsets - there is no slot-iteration loop in the captured code. The byte-identical schema confirms it: the consumer treats the buffer as a fixed in-RAM layout template and reads NPC/event/collision slots by hard-coded index, not by walking the offset table. Per-NPC and per-event slot handlers are called indirectly through the descriptor table; their specific entry points require capturing a full scene-init execution trace (not yet available in the overlay dumps).

Per-scene runtime RAM base

The active field-file RAM base is recoverable from any save by reading _DAT_8007B8D0 and subtracting 0x12800. The constants and a recover_base() helper live in crates/engine-core/src/capture_observations.rs under field_pack_load.

The 75 KB region between the base and _DAT_8007B8D0 (base..base + 0x12800) holds the loaded field asset, and efect.dat lands immediately after.

Loader order-of-operations

A save captured mid-transition between town01 (intro Rim Elm) and town0c (Rim Elm normal entry) pins the loader's order-of-operations. The mid-transition snapshot has these properties simultaneously:

  • The scene-bundle pool at 0x80084540 already carries the destination scene name (town0c) - both pool slots +0x08 and +0x18 flip together.
  • _DAT_8007B8D0 still reads the previous scene's value (0x8014BD30, town01's efect.dat base).
  • The destination scene's region at the canonical town0c base (0x800A25F0..0x800B4DF0) is partially populated.
  • The previous scene's region at 0x80139530 is zeroed.
  • The static asset descriptor table at 0x8015CBD0 is bit-identical between the pre- and mid-transition snapshots (4 KB SHA-256 match).

That sequencing pins the loader as: (1) write new scene name into the bundle pool, (2) zero the previous region, (3) populate the destination region at its canonical base, (4) flip _DAT_8007B8D0 last. Mid-transition, the engine can detect a scene swap is in flight by checking that the pool slot's CDNAME label disagrees with the base implied by _DAT_8007B8D0: legaia_engine_core::capture_observations::field_pack_intra_transition::detect_mid_transition(main_ram).

History: the "runtime layout differs from on-disc schema" reading

Reading the town capture at base + 0x60 - where on-disc slot 0 was assumed to sit - yields post-processed GP0 GPU primitive packets rather than the raw records the disc bytes encode, and an earlier section concluded that the loader transforms per-scene preamble bytes into the runtime slots. That premise does not hold: the schema-indexed region is a disc-side global constant, so there is nothing per-scene to project into it; and base is the field-file buffer base, while the loader places the field-asset region at buffer + 0x12000, so base + 0x60 is the field file's own object/primitive region, not schema slot 0. The GP0 packets are most likely the scene's primitive scratch. The runtime-projection claim is unresolved and not worth re-walking without a mid-load capture.

Save-state diff observations

A save-state diff over the engine RAM range 0x801C0000..0x80200000 lights up a 9 KB region at 0x801F69D8..0x801F8F02 that toggles between two different MIPS-code overlays - different scenes load different per-area code into the same slot. The first 16 bytes match the standard PSX function-prologue shape (addiu sp,sp,-N, sw s1,N(sp), lui s1,0x801F, ori s1,s1,...), confirming the slot is a MIPS overlay rather than a data buffer (the slot-B stager window on the overlay pointer-table page).

Rust API

legaia_asset::field_pack::FieldPack exposes typed accessors over a parsed file:

// Classify a slot by index.
let kind: Option<SlotKind> = fp.slot_kind(i);

// Iterate all 97 slots with structural classification + bytes.
// Bytes are non-empty only when magic_offset == 0 (entry 0005_town01).
for (kind, bytes) in fp.iter_slots(buf) {
    // kind: SlotKind::{TypeFlag, TimPage, NpcRecord, EventTrigger,
    //                   CollisionBox, CompactRecord, MediumRecord,
    //                   SingleRecord, LastSlot}
}

For static schema enumeration without holding a file:

use legaia_asset::field_pack::{CANONICAL_SCHEMA, canonical_slot, iter_canonical_slots};

// 97-element static array of u32 LE schema offsets.
assert_eq!(CANONICAL_SCHEMA[0], 0x60);

// Per-slot accessor: returns (offset, size) where size is None for slot 96.
let (off, size) = canonical_slot(5).unwrap();

// Iterate (index, kind, offset, size) over the canonical schema.
for (i, kind, off, size) in iter_canonical_slots() { /* ... */ }

SlotKind is derived from the slot's byte size and covers the major structural clusters identified in the size table above. legaia_engine_core::capture_observations::field_pack_load::recover_base(main_ram) pins the heap-allocated RAM base from a saved main-RAM image. The detector is reliable for classification; per-slot interpretation beyond size-clustering is bracketed by the cluster table and pending a per-scene loader trace.

Field-pack Confirmed

There is no field-pack format. The entries named after the magic 0x01059B84 are ordinary DATA_FIELD streams whose single chunk is an asset::pack of PSX TIMs or Legaia TMDs - a scene's texture or mesh pack. The "magic" is that chunk's (type << 24) | size header, the "97-entry schema" is the pack's own [count][word offsets] table, and the "byte-identical 91 KB constant block" is two Rim Elm scenes sharing their leading textures.

At a glance

What it really is
One DATA_FIELD chunk wrapping one asset::pack - two formats this site already documents
Where
Raw-TOC offset +4 of a scene's CDNAME block (extraction index #define + 2). 23 blocks carry one; the rest reserve the slot with a pochi filler
The "magic"
0x01059B84 = (TIM_LIST << 24) | 0x059B84. The low 24 bits are that carrier's payload length, so the word differs per file - it occurs exactly once in the whole archive
Two forms
18 carriers lead with the chunk header; 5 carry the bare pack at offset 0. The bundle's Flag descriptor picks which
Parser
legaia_asset::field_pack::scene_pack (corrected reader); detect / CANONICAL_SCHEMA kept for the classifier and the asset field-pack CLI
Confidence
Confirmed - loader disassembly plus a whole-archive byte sweep, disc-gated in field_pack_real.rs
Used by
scene bundles, asset loader

Where a carrier sits

Every scene's CDNAME block seats the same slots at the same offsets from its #define, in raw-TOC space:

Block offsetContent
+0<scene>.MAP - the per-scene field map, 0x12000 bytes
+1<scene>.PCH - the walk-on trigger sidecar, 0x800 bytes
+2efect.dat - the move-VM stager prescript
+3the scene asset table
+4this page - the streamed TIM / TMD pack, or a pochi filler
+5…the battle-stage backdrop meshes

The first three names come from the loader's own path literals; the +4 position is what the loader's by-index branch computes directly, FUN_8003EB98(scene_index + 4, …) with the scene index equal to the block's #define value.

How it reaches RAM

FUN_800255B8 loads one streamed file into the scene asset buffer and returns its sector count, choosing the path by a mode argument; FUN_8002541C then reads the buffer with the reader that mode selects.

ModePathReader
0x0Ah:\PROT\FIELD\<scene>\tim.datBare pack: count = base[0], then LoadImage at base + word_offset[i] * 4 per member
0x0Fh:\PROT\FIELD\<scene>\move.mdtMove table
0x14DATA\FIELD\<scene>.pacDATA_FIELD chunk walk into the asset-type dispatcher

Nothing else picks the mode: it comes out of the scene's own asset table. The dispatcher handles type bytes 0x0A / 0x0F / 0x14 by returning (case << 8) and nothing else; the descriptor walker ORs every return into one status word, and the field init shifts that right by 8 and hands it to FUN_8002541C. So a Flag descriptor in the bundle is a request to stream the block's +4 entry.

Bundle carriesBlock +4 holdsBlocks
Flag(0x14)a chunk-headered single-chunk pack16
Flag(0x14)a multi-chunk DATA_FIELD stream12
Flag(0x0A)a bare pack4
no Flaga one-sector pochi filler64

Two blocks break the pattern in the harmless direction - opurud and other7 carry a pack with no Flag descriptor to reach it. Flag(0x0F) appears in no retail bundle, consistent with the move table being a descriptor inside the bundle rather than a streamed file.

The RAM base this page used to name

_DAT_8007B8D0 - 0x12800 recovers the field-file scratch base - the buffer holding <scene>.MAP at +0 and <scene>.PCH at +0x12000. It is not a field-pack base, and the GP0 packets an earlier reading found at base + 0x60 are that buffer's primitive scratch, not a transformed schema slot. The scene's own asset buffer is a separate 0x62C00-byte allocation.

History: "124 entries, slots filled per scene"

An earlier reading had 124 PROT entries sharing a schema with a per-scene preamble filling its slots; a later correction cut that to eight carriers and a shared template. Both were reading neighbouring entries through the superseded entry-size expression, and both took a pack offset table for a schema. See do not re-walk.

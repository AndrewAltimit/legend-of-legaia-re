SEQ - PsyQ sequenced-music format Confirmed

SEQ is the sheet music. Every tune in Legaia - the town themes, the battle loop, the world-map fanfare - is stored not as recorded audio but as a list of notes and timings that the console plays live against a VAB instrument bank. It is the PlayStation SDK's sequenced-music format: essentially a single-track MIDI file, close enough to MIDI that generic tools almost work and different enough that they fail in two specific, diagnosable ways.

Why your MIDI tool chokes

Two divergences from the PsyQ documentation
  1. Legaia's header has a u32 big-endian version field where the PsyQ documentation says u16, shifting every later field by two bytes. A parser using the documented 13-byte layout reads the wrong PPQN and tempo.
  2. PSX SEQ meta events carry no MIDI length byte. A Standard MIDI File writes a tempo change as FF 51 03 tt tt tt; SEQ writes FF 51 tt tt tt. Reading a phantom length byte silently drops the first tempo override - and because every retail track ships a 240 BPM placeholder header tempo that the first body event corrects, the audible symptom is everything plays ~3x too fast.

Both are detailed below. The format is a publicly-documented PsyQ SDK shape (header layout + event encoding); this page describes byte order, the meaning of every header field, and how Sony's SsAPI sequencer consumes the event stream - no Sony bytes appear here.

Header

Two header shapes coexist in the wild:

Standard PsyQ shape (13 bytes)

OffsetSizeFieldMeaning
+0x004magicpQES
+0x04u16 BEversiontypically 1
+0x06u16 BEresolutionPPQN - ticks per quarter note
+0x08u24 BEtempoinitial tempo, microseconds per quarter note
+0x0Bu8time-sig nume.g. 4
+0x0Cu8time-sig denompower of 2 (2 means /4, 3 means /8)
+0x0D-eventsevent stream

Legaia variant (15 bytes)

Every retail Legaia SEQ examined uses a u32 BE version field rather than the u16 BE PsyQ-doc form, with two reserved zero bytes between the magic and the version word. The remaining fields shift by two bytes:

OffsetSizeFieldMeaning
+0x004magicpQES
+0x04u32 BEversionalways 1 in retail - the two extra bytes are what shifts everything below
+0x08u16 BEresolutionPPQN - always 480 in retail
+0x0Au24 BEtempoinitial tempo; a 240 BPM placeholder the first body event overrides
+0x0Du8time-sig num
+0x0Eu8time-sig denompower of 2
+0x0F-eventsevent stream

crates/seq::parse_header accepts both shapes - it probes u32 BE at +4..+8 == 1 and dispatches accordingly. HEADER_LEN is the standard length; HEADER_LEN_LEGAIA is the variant length.

version is verified by the SsAPI loader (FUN_80062410 in SCUS, see audio stack). Files with version != 1 emit s_This_is_an_old_SEQ_Data_Format_*.

Event stream

Each event is a delta-time (variable-length integer) followed by a status byte and zero or more data bytes - the standard MIDI encoding. Running status applies: if the first byte of an event is < 0x80, reuse the previous status byte and treat that byte as data.

Status range Event Data bytes
0x80..=0x8F Note Off 2 (key, velocity)
0x90..=0x9F Note On 2 (key, velocity) - velocity == 0 ≡ NoteOff
0xA0..=0xAF Poly Aftertouch 2
0xB0..=0xBF Control Change 2 (controller, value)
0xC0..=0xCF Program Change 1 (program)
0xD0..=0xDF Channel Aftertouch 1
0xE0..=0xEF Pitch Bend 2 (LSB, MSB; both 7-bit)
0xFF NN Meta event fixed length per type (see below)

Channel index is the low nibble of the status byte (0..=15). Retail data only uses 0x90 / 0xB0 / 0xC0 / 0xE0 (Note Off is 0x90 with velocity == 0).

A disc-wide sweep of every SEQ-bearing PROT entry (numbered entry in PROT.DAT, the disc's single big archive) pins exactly what the score emits, and the engine Sequencer acts on all of it: pitch bend (0xE0) is used heavily (thousands of events across a handful of music banks) and is applied by scaling each sounding voice's pitch over the tone's own pbmin/pbmax range; channel volume (CC7) and pan (CC10) are the busiest controllers and are dynamic (the music swells and pans voices mid-note), re-derived per change from a channel-free per-note base. Channel/poly aftertouch (0xD0/0xA0) and expression/reverb controllers never appear, so the per-cue reverb-enable for BGM is not carried in the sequence data.

Variable-length quantity (VLQ)

A VLQ is a big-endian sequence of 7-bit groups; the high bit of each byte is 1 for "more bytes follow", 0 for the final group. Maximum 4 bytes per delta. SEQ uses VLQ for delta-times only - meta events carry no length field (below). See legaia_seq::read_vlq.

Meta events

PSX SEQ meta events have no MIDI variable-length length field. This is the one place the format diverges sharply from a Standard MIDI File: the SsAPI sequencer reads a meta-type byte and then a fixed number of payload bytes determined by the type. The two meta types that appear in retail data:

Kind Bytes after type Meaning
0x51 3 Set Tempo (u24 BE microseconds per quarter note). The 3 tempo bytes follow 0x51 directly - there is no 0x03 length prefix. An SMF would write FF 51 03 tt tt tt; PSX SEQ writes FF 51 tt tt tt.
0x2F 0 End-of-Track. Two bytes total (FF 2F), no 0x00 payload. Required; terminates parsing.

Any other meta type has an undefined fixed length, so the parser cannot safely skip it and stops the track there (the reference SsAPI reader behaves the same way).

The tempo gotcha

Reading a phantom MIDI length byte mis-decodes every tempo event: 0x51 would consume the first tempo byte as a "length", then swallow the following note events as a bogus payload, and the override would be dropped. Retail tracks ship a 240 BPM (250000 µs/qn) init-placeholder header tempo that the first body 0xFF 0x51 event immediately overrides to the real musical tempo (e.g. FF 51 0B 71 B0 = 750000 µs/qn = 80 BPM). Dropping that override pins playback at the 240 BPM placeholder - a constant ~3x-too-fast rate. Every retail SEQ has ppqn = 480.

Loop markers

PSX SEQ encodes looping through NRPN-style control changes on 0xB0: controller 0x63 (99) value 20 = Loop Start, value 30 = Loop Forever (jump back to the last Loop Start). 88 of 92 retail SEQ tracks carry these markers.

The parser surfaces them as ordinary ControlChange events (the bytes really are a CC), and the engine Sequencer interprets them at playback time: a Loop Start records the position immediately after the marker, and a later Loop Forever - or an end-of-track that follows a Loop Start - rewinds there rather than to event 0. The rewind lands on the event after the marker, so it neither re-fires the marker nor re-applies its delta, and the integer sample-clock is reset so the looped body re-fires on the same sample offset every pass. Sequencer::set_loop_to remains an external fallback for the four tracks that carry no markers.

ProgramChange to an unused VAB slot

A 0xCn ProgramChange names a ProgAtr slot in the paired VAB. Retail's bank-open (FUN_80068D94) writes a running used-program counter into each slot's +8 word and the program-change consumer reads it back as the tone-page index, so a change to an unused slot aliases onto the next used slot's page (and past the last used slot it reads garbage beyond the tone region).

A disc sweep of every in-container [VAB][SEQ] pair (engine-audio/tests/real_seq_program_change_coverage.rs) finds eight such ProgramChanges across four entries. Two are audible (PROT 868 program 5, PROT 996 program 19 - retail aliases to a valid page and notes follow); the rest are benign (retail's own index runs past the tone region, PROT 994 program 42, or no notes follow, PROT 988 program 127). The engine reproduces the alias for the audible cases and leaves the past-the-end case silent rather than replaying undefined bytes.

Stream termination and truncation

A well-formed stream ends on its own FF 2F marker. Retail always writes a trailing 00 after it, which the parser never reads. Two things the parser cannot size stop it early - a meta type other than 0x51 / 0x2F, and a system-common / SysEx status byte (0xF0..=0xFE) - and in both cases it appends a synthetic EndOfTrack so the event list stays well-formed. That synthetic marker looks identical to a real one from the events alone, so anything that needs a whole track (a player, a parity oracle, a corpus sweep) must check Seq::termination / Seq::is_complete.

The corpus is almost entirely clean (real_seq_stream_integrity.rs pins the count of non-clean streams). The one outlier is PROT entry 1045, and its cause is pinned: the stream is a valid, complete track, but a few notes before its real end the parser drifts by exactly one byte inside a dense run of running-status notes (near stream offset ~4900, next to a non-round-BPM tempo event). Latched one byte ahead, it reads the closing fade's volume CCs as deltas plus note data, walks through the real FF 2F 00, and halts on a 0xF4 eleven bytes past the true end. That 0xF4 is dead post-track tail, not a skippable event; "skip it and continue" would decode ~124 KB of container bytes as bogus music. real_seq_1045_truncation.rs proves both halves, and the parser is deliberately left stopping there.

Tempo math

tempo is microseconds per quarter note; ppqn is ticks per quarter note (always 480 in retail data). Per-tick duration is tempo / ppqn microseconds, and the runtime accumulates real-world time against this rate. A mid-stream SetTempo overrides for future events only - events that already fired at the previous tempo are unaffected.

The three tempo bytes are read raw, with no length byte between FF 51 and the payload. The evidence is arithmetic rather than structural: read that way, every retail tempo event lands on a round BPM (65, 70, 80, 128, 130, 140, 150, 160, 170). Consuming a phantom length byte first would scatter those into nonsense, so the reading is self-verifying - real_seq_stream_integrity.rs asserts the roundness.

legaia_seq::us_per_tick(tempo, ppqn) returns the per-tick duration as f64 for inspection. The engine playback clock (Sequencer) does not use this float: it accumulates time as an exact integer in units of sample × ppqn × 1_000_000 and fires an event of delta d ticks once the accumulator reaches d × tempo_us × 44100, which keeps every term integer and the timebase free of long-track drift.

Where the data lives

SEQ payloads are loaded by the PsyQ libsnd SsSeqOpen family - see the audio stack page ("Public SEQ API"). On-disc, SEQ data lives inside the same scene-VAB-prefixed streaming containers described in scene-bundles.md - which means the SEQ bytes sit at a non-zero offset behind a wrapper, not at the start of the file. The _DAT_8007BAC8 slot the field VM writes (opcode 0x35) is consumed by FUN_800243F0, which resolves a SEQ payload through the CDNAME per-scene block and hands it to FUN_80062340 (SsSeqOpen) for playback.

Tooling

crates/seq (binary seq) parses SEQ files end-to-end:

seq info    <PATH>    # header summary + event-type histogram
seq events  <PATH>    # disassemble every event in source order
seq json    <PATH>    # full parse as JSON

Playback is the engine side: legaia_engine_audio::Sequencer consumes a parsed Seq + a loaded VabBank and drives the clean-room SPU model. See audio stack ("Engine-audio model").

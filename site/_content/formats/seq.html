SEQ - PsyQ sequenced-music format Confirmed

SEQ is the sheet music. Every tune in Legaia - the town themes, the battle loop, the world-map fanfare - is stored not as recorded audio but as a list of notes and timings that the console plays live against a VAB instrument bank. It is the PlayStation SDK's sequenced-music format: essentially a single-track MIDI file, close enough to MIDI that generic tools almost work and different enough that they fail in two specific, diagnosable ways.

Why your MIDI tool chokes

Two divergences from the PsyQ documentation
  1. The version field is a u32 big-endian where the documentation says u16, shifting every later field by two bytes. A 13-byte-header parser reads the wrong PPQN and tempo.
  2. Meta events carry no length byte. MIDI writes a tempo change as FF 51 03 tt tt tt; SEQ writes FF 51 tt tt tt. Read a phantom length byte and the first tempo override is lost - and since every retail track ships a 240 BPM placeholder header tempo that the first body event corrects, everything plays ~3x too fast.

The meta-event difference, byte for byte:

+151Set Tempo

Header

Every retail track uses the 15-byte Legaia layout; crates/seq::parse_header also accepts the documented 13-byte PsyQ layout, dispatching on whether the u32 at +4 reads 1.

+0x00magic pQES4 B
+0x04version = 1u32 BE
+0x08PPQN = 480u16 BE
+0x0Atempou24 BE
+0x0Dts numu8
+0x0Ets denu8
FieldMeaning
versionAlways 1 in retail. It is a u32 where the PsyQ documentation has a u16 at +4; the two extra bytes shift every field below.
PPQNTicks per quarter note - always 480.
tempoMicroseconds per quarter note. A 240 BPM placeholder that the first body event overrides.
time signatureNumerator (e.g. 4) and a power-of-two denominator (2 = /4, 3 = /8).

The event stream starts at +0x0F.

The retail loader checks version and rejects any other value as an old SEQ format.

Event stream

Each event is a variable-length delta time, a status byte and its data - standard MIDI encoding, with running status (a first byte below 0x80 reuses the previous status). Channel is the low nibble.

A meta is a running status too. The retail decoder (FUN_80063CEC) latches 0xFF as the channel's running status when it reads a meta, so a data byte after a meta is the next meta's kind: FF 51 t t t <delta> 51 t t t is two tempo events, and a channel event after a meta needs its own status byte. A parser that keeps the previous channel status across a meta falls one byte out of phase on the one track that relies on this.

Any other meta type has an unknown fixed length, so the parser (like the retail reader) cannot skip it and ends the track there.

Loop markers

Looping is encoded as ordinary control changes: controller 99 value 20 = Loop Start, value 30 = Loop Forever (jump back to the last Loop Start). 88 of 92 tracks carry them. The engine Sequencer rewinds to the event after the marker and resets its sample clock, so the loop re-fires on the same sample offset every pass; an end-of-track after a Loop Start also rewinds.

Tempo math

Per-tick duration is tempo / ppqn microseconds as written. The engine clock keeps every term integer - it accumulates in units of sample × ppqn × 1 000 000 and fires a delta-d event once the accumulator reaches d × tempo × 44100 - so long tracks never drift. legaia_seq::us_per_tick returns the float form for inspection only.

Retail does not play the written tempo exactly: its driver turns each tempo into an integer BPM and a per-vsync tick budget rounded to tenths of a tick, so a track runs at the rate that budget implies - 80 BPM plays at 80.25, and the slow closing tempos drift furthest. The engine Sequencer plays that retail rate by default and the written score behind set_exact_tempo(true); the audio internals page has the derivation.

Edge cases the engine reproduces

  • Program change to an unused VAB slot. Retail's bank-open writes a running used-program counter into each slot, so a change to an unused slot aliases onto the next used slot's tone page (see VAB). Eight such changes exist across four entries; two are audible (PROT 868 program 5, PROT 996 program 19) and the engine aliases them the same way. Past the last used slot retail reads garbage; the engine stays silent there.
  • Truncation. An unknown meta type or a system status byte (0xF0..=0xFE) stops parsing; the parser appends a synthetic End of Track and marks the track truncated so players and parity oracles can tell it from a clean end.
Details: the track that needs the meta latch (PROT 1045)

Every stream in the corpus parses to a clean end. PROT 1045 (sound test 57, the "sorrowful event" requiem) closes on a ritardando written with the meta latch: FF 51 0E C4 3E (62 BPM), then 51 0F 42 40 (60 BPM) with no second FF. Read 51 0F 42 as a note instead and the parser falls one byte out of phase, reads the closing volume fade (B5 07 nn / B6 07 nn) as long deltas and notes, walks through the real FF 2F 00 and halts on a 0xF4 eleven bytes past it - the last bars garbled and the loop never reached. That was once recorded as a one-byte desync in an otherwise valid stream.

Where the data lives and how it is played

SEQ payloads ride behind a VAB inside the scene streaming containers (scene bundles), so the bytes sit at a non-zero offset. The field VM's BGM opcode (0x35) writes a slot that the BGM loader resolves through the CDNAME map to the containing entry; playback goes through the PsyQ SsSeqOpen family (audio stack).

In the port

seq info <PATH>
seq events <PATH>
seq json <PATH>

info prints the header plus an event-type histogram, events disassembles every event, json dumps the full parse. The engine side is legaia_engine_audio::Sequencer: a parsed Seq plus a loaded VabBank driving the from-scratch SPU model.

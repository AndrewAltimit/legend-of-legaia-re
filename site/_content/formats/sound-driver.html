Sound-driver path-string cluster Confirmed

When a scene starts and its music and sound effects load, the game builds a file path out of a small set of extensions its developers' sound tools used - .dpk, .spk, .MAP, .PCH - still sitting in the executable. This page decodes that cluster and answers the question it raises: are these exotic sound formats to reverse? Mostly no. The per-scene .dpk sound pack is an ordinary VAB + SEQ pair in a chunked wrapper, and the .MAP / .PCH intermediates never made it onto the retail disc.

The .dpk / sound_data2 payload is a VAB + SEQ bundle

This is the answer most readers want first. A per-scene sound pack is a VAB followed by a SEQ in a streaming-chunk container - not a novel .MAP / .PCH / .spk layout:

Chunk typePayloadMagic
0VAB header sectionpBAV (0x5641_4270 LE)
1VAB sample section (SPU-ADPCM / VAG waveform pool)- (raw samples)
2SEQ (the stream terminator)pQES

The decisive invariant: type-0 + type-1 reconstitute one contiguous VAB whose header total_size (+0x0C) equals chunk[0].size + chunk[1].size. Byte-verified across 0877–0885 (e.g. 0877: 0x2820 + 0x1BA90 == 0x1E2B0); the reconstituted VAB parses with legaia_vab and the terminator SEQ with legaia_seq. The content shape matches the scene_vab_stream BGM wrapper; only the container differs.

The type-1 payload depends on the consumer: on the graphics battle-init walk, FUN_8001FE70's type-1 handler is the TIM/CLUT upload (FUN_800198E0); in a sound pack it is the VAB's sample pool. The .MAP (sample-address map) and .PCH (patch / program data) PsyQ SoundArtist intermediates are the dev-side inputs that produce this VAB; the retail disc does not carry them, so a crates/sound companion to crates/vab is not warranted.

History: the bare-VAG-container reading

An interim trace labelled the .dpk a bare VAG-record container. That is falsified: the VAG samples are the type-1 section of a VAB, indexed by the type-0 header, not a header-less stream. Falsified readings are catalogued in do-not-re-walk.

.dpk is a streaming-chunk container

FUN_8001FA88 loads the per-scene .dpk into the caller's buffer and does not read it; the consumer is FUN_8001FE70, which FUN_800513F0 calls on that same buffer right after the load (ghidra/scripts/funcs/800513f0.txt). FUN_8001FE70 (ghidra/scripts/funcs/8001fe70.txt) is the generic streaming-chunk walker the asset dispatcher already models: [u32 (type << 24) | (size & 0xFFFFFF)][size bytes, 4-padded] chunks, advance by (size & ~3) + 4.

The one difference from the DATA_FIELD walker is the terminator: FUN_8001FE70 ends on a type-0x02 chunk (whose size is non-zero), whereas FUN_8002541C ends on a zero-size header - so the DATA_FIELD parser mis-reads a .dpk. PROT 0877 walks cleanly as [type 0: 0x2820][type 1: 0x1BA90][type 2: terminator]; the disc-gated sound_pack_stream_real test pins it.

Consumers

Two SCUS functions touch the cluster (located via ghidra/scripts/find_sound_path_builders.py):

Function Role Touch points
FUN_8001FA88 Sound subsystem init / .dpk loader. Allocates a 0x1800-byte buffer at _DAT_8007B8D0. Loads bse.dat. Then assembles h:\main\bg\domepack\<name>.dpk (template at 0x800105C8 + extension at 0x8007B3B4) and opens it. 0x8007B3AC (bse.dat), 0x8007B3B4 (.dpk)

See character-mesh.

bse.dat master-bank header

FUN_8001FA88 (ghidra/scripts/funcs/8001fa88.txt) loads bse.dat into the 0x1800-byte buffer at _DAT_8007B8D0, then derives a second pointer from a single u16 at offset +2:

count     = *(u16 *)(bse_base + 2)
gp[0x678] = bse_base + (count & ~1)        ; (count/2)*2 - an even byte offset

So bse.dat leads with [u16 @0][u16 @2 = even byte offset to a second section][section A ...][section B]. The value is a byte offset splitting the once-loaded master bank into two sections (the >>1 ... *2 is a round-to-even, not a division) and it indexes the master bank, not the per-scene .dpk.

Dev-build vs retail-build paths

Both FUN_8001FA88 and FUN_8001FC00 carry a _DAT_8007B8C2 (debug-flag) carve-out:

  • Retail branch (_DAT_8007B8C2 != 0, the value retail boots with) loads sound data via PROT indices. FUN_8001FA88's retail branch loads index 0x37A (= sound_data2) plus param_1 + 5 for per-scene variations, via the index-based loader (FUN_8003EB98).
  • Dev branch (_DAT_8007B8C2 == 0) opens an h:\ path through FUN_8003E6BC. That helper does no name resolution - it is strcpy, then FUN_800608F0 (break 0x103, a dev-station host trap), then fseek/fread/fclose. Retail hardware cannot service it.

Only the retail branch runs on a real disc; the dev branch is a build-time artefact whose paths are not in the filesystem. The same split appears in FUN_800255B8, so it is a pattern that repeats across asset-loading subsystems.

Sound-driver path-string cluster Confirmed

When a scene starts and its music and sound effects load, the game builds a file path out of a small set of extensions its developers' sound tools used - .dpk, .spk, .MAP, .PCH - still sitting in the executable. Are these exotic sound formats to reverse? Mostly no. The per-scene .dpk sound pack is an ordinary VAB + SEQ pair in a chunked wrapper, and the .MAP / .PCH intermediates never made it onto the retail disc.

The .dpk sound pack is a VAB + SEQ bundle

A per-scene sound pack is a VAB followed by a SEQ in a streaming-chunk container - not a novel .MAP / .PCH / .spk layout. Each chunk is [u32 (type << 24) | size][payload, 4-padded]; the walk ends on the type-2 chunk, which is itself the SEQ.

+0size (low 24 bits)u24
+3typeu8
+4payload, padded to 4size
Chunk typePayloadMagic
0VAB header sectionpBAV (0x5641_4270 LE)
1VAB sample section (SPU-ADPCM / VAG waveform pool)- (raw samples)
2SEQ (the stream terminator)pQES
  • Decisive invariant: type-0 + type-1 reconstitute one contiguous VAB whose header total_size equals chunk[0].size + chunk[1].size. Holds across 0877–0885 (PROT 0877: 0x2820 + 0x1BA90 = 0x1E2B0).
  • Same walker, different terminator. The chunk walker is the one the DATA_FIELD dispatcher models, but it ends on a type-0x02 chunk (non-zero size) where DATA_FIELD ends on a zero-size header - so the DATA_FIELD parser mis-reads a .dpk. Use StreamTerminator::TypeTwo.
  • Type-1 depends on the consumer. On the graphics battle-init walk, the type-1 handler is the TIM/CLUT upload; in a sound pack it is the VAB's sample pool.
  • The content shape matches the scene_vab_stream BGM wrapper; only the container differs. The .MAP (sample-address map) and .PCH (patch data) are the PsyQ SoundArtist dev-side inputs that produce this VAB - the retail disc does not carry them, so no dedicated parser is warranted.

bse.dat master-bank header

Battle init loads bse.dat into a 0x1800-byte buffer and parks the record-table pointer at gp+0x678 (0x8007B990); the buffer slot itself is repointed at every field load. A single u16 at offset +2, rounded down to even, is the byte offset of a second section:

+0tagu16
+2table offset (rounded even) = 4u16
+48-byte SFX descriptor records ...n × 8

The loader computes gp[0x678] = base + (word@2 & ~1) - a round-to-even byte offset, not a record-count divisor.

Reading that split as two sections overstates it: @2 is 4 in both retail carriers, so the "second section" is simply the record table and nothing precedes it but the header. What follows the table in entry 888 belongs to a different file - a foreign VAB tone table left in the sector. The pointer indexes the battle-loaded bank, not the per-scene .dpk. The records use the SFX descriptor columns, for cue ids ≥ 0x200.

Dev-build vs retail-build paths

Both path builders carry a debug-flag carve-out (_DAT_8007B8C2):

  • Retail branch (flag non-zero, the value retail boots with) loads sound data by PROT index via the index-based loader: raw TOC 0x37A = extraction 888, which is bse.dat rather than the .dpk, plus param_1 + 5 for the per-set pack.
  • Dev branch (flag zero) opens an h:\main\bg\domepack\<name>.dpk path through a helper that is strcpy, a dev-station host trap (break 0x103), then fseek/fread/fclose. Retail hardware cannot service it.

Only the retail branch runs on a real disc; the dev branch is a build-time artefact whose paths are not in the filesystem. The same split appears in the asset loader, so it is a pattern that repeats across loading subsystems.

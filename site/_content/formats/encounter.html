Encounter record format Confirmed

Walk a few steps in a dungeon and the screen shatters into a fight; talk to the sparring partner in Rim Elm and the same thing happens on purpose. Both kinds of battle - the random ones and the scripted bosses - reach the battle engine through one tiny structure: the encounter record, three header bytes, a monster count, and up to four monster ids. Whatever arms a fight simply points a field actor at one of these records; a single reader copies the ids into the global formation cell the battle loader reads. This page covers the record itself, the reader, the two ways a record gets armed (script and random roll), and the per-scene MAN tables the records live in on the disc.

The record

A record is a count followed by the monster ids, with three bytes in front that the formation copy never reads. The reader copies monster_ids[0..count] into the global formation cell at 0x8007BD0C..0x8007BD0F (a 4-byte array, one byte per slot). Slots beyond count stay zeroed, and a count of 0 clears the cell entirely (no monsters spawn this round).

OffsetSizeFieldMeaning
+0x001header / scripted-fight predicateNot copied. Non-zero raises the "scripted fight" bit 0x80 in the per-battle flags byte (below). For an inline arm this byte is the install opcode; for a MAN row it is authored per row.
+0x012reservedNot consumed by the formation copy (operand bytes of the install opcode, or scratch on a MAN row).
+0x031monster_count0..=4.
+0x04countmonster_ids[]Each id indexes the monster catalog (the monster archive, PROT 867). Anything after the ids is not consumed by the copy.

Reader

FUN_801DA51C is the per-frame tick for world-map / field entities - live objects carrying a 5-state state machine at entity[+0x8A] (see the world-map subsystem). When an entity's SM reaches its encounter-confirm state, the body at 0x801DA620..0x801DA678 performs the copy:

801da620  lui v0,0x8008
801da624  addiu s0,v0,-0x42f4   ; s0 = formation_cell_base = 0x8007BD0C
801da628  sb zero,0x3(s0)        ; clear monster slot 3 (0x8007BD0F)
801da62c  sb zero,0x2(s0)        ; clear monster slot 2 (0x8007BD0E)
801da630  sb zero,0x1(s0)        ; clear monster slot 1 (0x8007BD0D)
801da634  jal 0x801de190         ; helper (effect / sound trigger)
801da638  _sb zero,-0x42f4(v0)   ; clear monster slot 0 (0x8007BD0C)
801da63c  lw v0,0x94(s1)         ; v0 = encounter_record_ptr = actor[+0x94]
801da640  nop
801da644  lbu a1,0x3(v0)         ; a1 = monster_count = record[+0x3]
801da648  nop
801da64c  beq a1,zero,0x801da67c  ; nothing to copy: skip loop
801da650  _clear a0
801da654  move a2,s0             ; a2 = formation cell base
801da658  lw v0,0x94(s1)         ; re-read record pointer (volatile)
801da65c  addu v1,a0,a2          ; v1 = &formation[a0]
801da660  addu v0,a0,v0          ; v0 = record + a0
801da664  lbu v0,0x4(v0)         ; v0 = record[+0x4 + a0] = monster_ids[a0]
801da668  addiu a0,a0,0x1
801da66c  sb v0,0x0(v1)          ; formation[a0-1] = monster_ids[a0-1]
801da670  slt v0,a0,a1
801da674  bne v0,zero,0x801da658  ; loop until a0 == monster_count
801da678  _nop

s1 is the entity record (the caller's a0); +0x94 is the record-pointer slot. After the copy the reader clears entity[+0x94] and advances the SM (entity[+0x8A]++), so the copy fires exactly once per arm. The reader does not check which flag bit armed the record, so one reader serves both the scripted and the random path.

The per-battle flags byte (DAT_8007BD60) and the +0 predicate

Just before the copy (0x801DA5F8..0x801DA61C) the reader loads record[+0] and, when it is non-zero, ORs bit 0x80 into the per-battle flags byte at 0x8007BD60:

801da5f8  lw v0,0x94(s1)         ; v0 = encounter_record_ptr = actor[+0x94]
801da600  lbu v0,0x0(v0)         ; v0 = record[+0]
801da608  beq v0,zero,0x801da620  ; zero: leave the flags byte alone
801da60c  _lui v1,0x8008
801da610  lbu v0,-0x42a0(v1)      ; 0x8007BD60, the per-battle flags byte
801da618  ori v0,v0,0x80
801da61c  sb v0,-0x42a0(v1)

One byte carries two unrelated things, written by the two halves of the same path:

  • Low bits - the stage id. The random roll (FUN_801D9E1C) overwrites the whole byte with region[+8] & 0x1F; the backdrop picker reads it back as word[0x80084540] + (byte[0x8007BD60] & 0x7F) to select the battle stage (legaia_asset::battle_backdrop).
  • Bit 0x80 - "this fight is scripted". Raised by the confirm state when the armed record's +0 is non-zero. The roll writes first and the confirm ORs after, so they never race: a random roll leaves the bit clear unless the row it landed on carries a non-zero header byte. An inline-script arm points at the bytecode overlaying the install opcode, so +0 is the opcode - non-zero by construction. A MAN-row arm (3E FF <row> or the random roll) reads the row's own header byte: in rikuroa the two scripted rows 16 and 17 (the Caruban fight) read 01 00 00, all sixteen random rows read 00 00 00.
Consumer of bit 0x80Effect when set

How a record gets armed

Nothing in the field VM is called "encounter". A record is armed by pointing an entity's +0x94 at it, and there are three shapes of pointer:

1
Random roll
FUN_801D9E1C picks a MAN formation row from the player's current region and points +0x94 at it (flag bit 0x80000).
region_encounter
2
Scripted, by row
The interact op 3E FF <row> sets entity[+0x8A] = 1 and points +0x94 at MAN formation row row. This is how retail's bosses are cued (garmel rows 8/9 = Songi / Zeto, rikuroa row 17 = Caruban).
World::trigger_scripted_battle
3
Scripted, inline
A generic halt-acquire opcode (0x37/0x41, 0x38, 0x43, 0x47, 0x4C) points +0x94 at its own bytecode, so [count][ids] are the trailing operand bytes (flag bit 0x400).
engine-vm field VM
4
Confirm + copy
The entity SM reaches its confirm state; FUN_801DA51C copies the ids into 0x8007BD0C, clears +0x94, and the battle loads.
World

What turns a halt into an encounter is the consumer: only entities ticked by FUN_801DA51C ever read their +0x94 as a formation record, and only once the SM reaches the confirm state. Which shape a given fight uses is a per-scene bytecode fact.

Inline install sites in the script VM

The dispatcher FUN_801DE840 (script VM) installs the pointer with the pattern at 0x801DEEDC..0x801DEEEC:

801deedc  lw v0,0x10(s5)
801deee0  sw s0,0x94(s5)         ; actor[+0x94] = s0 (encounter record pointer)
801deee4  sh zero,0x54(s5)       ; reset actor sub-state
801deee8  ori v0,v0,0x400        ; raise "encounter armed" flag (state[0x400])
801deeec  sw v0,0x10(s5)

s0 is set once in the prologue (addu s0, a0, s8 at 0x801DE858, i.e. bytecode_buffer + pc_offset) and is the current opcode pointer; Ghidra's C renders it as pbVar43 = (byte *)(param_1 + param_2). s5 is the resolved target actor - frequently the player context _DAT_8007C364; when bit 7 of the opcode byte is set, byte +1 routes through the system-channel resolver FUN_8003C83C.

All install paths share one pre-install gate: the actor already has a record (re-arm) or it is the player context; and the armed flag is clear or the scene allows re-arm:

if (actor[+0x94] != 0  ||  actor == _DAT_8007C364) &&
   ((actor[+0x10] & 0x400) == 0  ||  *_DAT_801C6EA4[+8] != 0)

Two other writes to actor[+0x94] live in the dispatcher (case 0x34: pbVar47 + 0xe and pbVar47 + 3). They do not raise 0x400, pair with actor[+0x9c]/[+0x9e] zero-writes, and are a separate callback pattern - not encounter arms.

Engine port. The clean-room field VM mirrors the split: the bare arm op asks the host is_scripted_encounter_armed() and, only when armed, hands install_scripted_encounter() the bounded window overlaying the opcode ([opcode][op1][op2][count][≤4 ids]). World parses it as an EncounterRecord, registers the formation and forces the next field-step roll; a successful install disarms (fire-once, matching the retail +0x94 clear). A scripted formation always overrides the region roll: on_field_step checks a scripted_formation_pending flag before the region path, which is what lets the Tetsu fight start in a town whose random rate is 0.

The random roll (FUN_801D9E1C)

The roll lives in the world-map overlay (also paged in by the dance / fishing / slot-machine / cutscene / dialog / debug-menu overlays - same bytes each time) and runs once per movement update:

  • Run the condition walk to pick which slice of the scene's region table is live.
  • Match the player's (x, y) tile against each live region's AABB (region[0..3]); the hit supplies a per-step rate increment (region[4]) and a formation slice (region[6] base, region[7] count).
  • Scale the rate by the setting byte and four modifiers (0x801da1b8..0x801da200): High Encounter passive (bit 0x3B, Bad Luck Bell / Nemesis Gem) << 2; Low Encounter passive (0x3C, Good Luck Bell / Evil Talisman) >> 1; system flags 0x1D / 0x1E << 1 / >> 1.
  • Subtract the scaled rate from the step counter at _DAT_8007B5FC; when it reaches ≤ 0, two RNG draws pick a formation in [base, base + count) and the roll installs the row.
*(short *)(actor + 0x88) = formation_id;
*(short *)(actor + 0x8a) += 1;
*(uint  *)(actor + 0x94) = formation_table_base + 1 + formation_id * stride;
*(uint  *)(_DAT_8007c364 + 0x10) |= 0x80000;
_DAT_8007b5fc = (RNG % 0x1e7) - ((RNG % 0x1e7) - 0x3ce);

Same +0x94 slot as the scripted path, different flag bit (0x80000, not 0x400).

The condition array: story-flag-gated region groups

The region array is not one flat list. The condition array partitions it into consecutive groups, one per story state, and exactly one group is live at a time. Each 4-byte condition is [u16 flag_id][s16 region_count]; the walk (0x801d9f30..0x801d9fd8) starts a region cursor at 0 and steps through the conditions in order:

  • flag_id == 0xFFFF - stop; this group is the unconditional default.
  • FUN_8003CE64(flag_id) non-zero (story flag set) - stop; this group wins.
  • otherwise advance the cursor by region_count and continue.

Running off the end of the list returns without rolling - "no encounter this step", not a fallback to the whole array. Two corpus-wide invariants hold in every retail MAN that decodes: the group lengths tile the region array exactly, and the list ends with exactly one 0xFFFF. Runtime states agree with the disc bytes (the three _DAT_801C6EA4 pointers reproduce the carve; in Drake Castle the 0x0142-gated leading group is skipped and the 14-region unconditional tail is live). A group commonly ends with a whole-map rate 0 catch-all, and a gated group is often nothing but such a row - which is how a scene is silent in one story state and noisy in another. Reading the array flat lands on group 0's placeholder row, which is what makes most scenes look encounter-free. asset man --with-encounter prints regions under the group that owns them.

The no-trigger path consumes zero RNG (replay-safe). Overworld and field scenes both route through it (set_world_map_regions / set_field_regions); a MAN with no region section (towns) falls back to the mean-rate session.

Worked example: the Rim Elm training fight

The opening battle in town01 is a scripted single-monster fight against archive id 0x4F (Tetsu). The cell is 00 00 00 00 in the pre-battle field and 4F 00 00 00 from battle-load (game_mode 0x15) onward. The id is not an inline script literal - it is a per-scene formation index. Two independent surveys of town01's bytecode find no [1][0x4F] install operand: the scene_event_scripts prescript (PROT entry 3) carries none, and an opcode-aware walk of the MAN partition-1 field-VM scripts (53 records, 71 yield sites) finds zero. Every window that a naive byte-scan "decodes" is a count=0 artifact of stepping into embedded dialog text - the false positive the opcode-aware walk exists to reject (disc-gated test town01_p1_arm_sites.rs; survey CLI legaia-engine man-scripts).

Instead the lone-0x4F formation is town01 MAN formation index 4. The scene's formations load into a contiguous 8-byte-stride table, and the live "Come at me!" save state reads seven rows - byte-identical to the engine's MAN parse (legaia_asset::man_section → encounter_man::scene_encounter_from_man), with row 4 = [count 1][0x4F]. The carrier selects the row by index and FUN_801DA51C copies it on the dialogue-accept. The engine reaches the fight the same way: World::install_man_formation(RIM_ELM_TRAINING_FORMATION_ID = 4) installs the existing row, so the scene's merged stats stand (Tetsu's HP 999).

The carrier entity

town01 partition-1 holds exactly one placement at tile (76, 65) with model byte 0x6A whose interaction record carries a long multi-page dialog block - the sparring talk-menu and its battle branch; every other village NPC is one or two lines. It is pinned as RIM_ELM_SPARRING_CARRIER_TILE / _MODEL in encounter_record.rs. The carrier is identified by its dialog block, not an opcode-decoded selector: message text aliases field-VM opcodes (a literal > is 0x3E, punctuation hits the 0x37/0x41 yield bytes), so linear disassembly desyncs inside it; the text is recovered structurally as 0x1F-lead / 0x00-terminated segments (man_field_scripts::first_inline_dialog_offset).

The engine derives its carrier set from the MAN itself (man_field_scripts::derive_field_carriers): the sparring partner becomes a ScriptedEncounter for formation 4, every other talk NPC a plain Npc. Engagement is driven by the field-VM dialogue-accept (interact op 0x3E opens the dialogue, the dismiss 0x4C n5 sub-4 engages), so the bytecode drives the fight. Still open: the Yes/No box-selection logic of the sparring dialogue (the engine treats the accept as the dismiss; the fight is forced, so there is no decline path to gate), and a mid-interaction RAM capture confirming the accept → +0x94 install on this specific entity.

Open - does any retail battle write DAT_8007b7fc? History: how the boss fights were attributed

Earlier mid-cast Zeto save states pinned the id 0x4B but not the mechanism, and attributed the fight to scene jou; the live forward-play superseded both (the runtime scene buffer 0x8007050C reads garmel throughout). The plan to catch a DAT_8007b7fc writer with a write-watch at the Zeto trigger was falsified by the same capture - that trigger never writes the global. Caruban's "re-verify the mechanism" caveat was settled statically once the 3E FF arm was decoded. Falsified readings are collected on do-not-re-walk.

Where the records live: the MAN encounter section

The per-scene encounter data is section 0 of the scene's Man asset (type 0x03, descriptor index 2 of the 7-asset scene_asset_table bundle). The dispatcher FUN_8001F05C LZS-decompresses it into a heap buffer at _DAT_8007B898; the MAN walker FUN_8003AEB0 (from FUN_801D6704 and the family scene loaders) walks the multi-section header and writes the encounter-section pointer into the control block before calling FUN_8003A110 ("Mesworks set encount group table").

Random vs scripted formations

Scripted and boss formations live in the same formation array as the random ones; what separates them is reachability. A region with rate_increment == 0 never advances the counter, so it can list formations without ever rolling them. A formation is a random encounter iff some rate > 0 region reaches it. In town01 the rate-0 regions cover formations 2..=4 but the only rate>0 regions reach 0..=2, so the Tetsu row at index 4 is scripted-only. The encounter randomizer relies on this to leave boss fights untouched (legaia_patcher::encounter::random_formation_mask); its optional solo-strong pass thins only random formations, setting count to 1 and zeroing the dropped ids within the fixed stride.

MAN section 3: the camera-region table

Section 3 is the per-scene camera-region table: [u8 count] then count × 18-byte records. The per-tile query FUN_801DBA20 walks it (tile = (player_pos - 0x40) >> 7, first match wins). The field camera arrival handler FUN_801DBE9C hands the hit to the loader FUN_801DBC20, which splits bytes[5..17] into the camera-parameter globals at 0x8007B607..0x8007B627; the builder FUN_801DAB90 folds those into the same staging-struct slots the script-VM Camera Configure op 0x45 writes (pitch +0x02, yaw +0x06, eye-space +0x0E/+0x12/+0x16, GTE H +0x26; see cutscene). A zone record is a per-region camera preset in the op-0x45 parameter space.

Provenance: ghidra/scripts/funcs/overlay_fishing_801dbc20.txt (byte-identical across the fishing / dance / debug_menu / slot_machine captures; the overlay_0897 and overlay_baka_fighter captures alias different bytes at this VA); consumers overlay_cutscene_dialogue_801dab90.txt and _801dbe9c.txt.

Record header (bytes[0..5]): +0x00 kind - 0 = anchor (rec[1], rec[2]) and the player tile both inside the scratch attribute box, 1 = inclusive tile-bbox match, 2..=0x1F = region-type mask bit vs _DAT_8007B8F4; +0x01..+0x04 = tile bbox [minX, minZ, maxX, maxZ] (kind 1) / anchor (kind 0). For mask kinds with byte[1] != 0, the loader side-copies bytes[3],[4],[1],[2] to scratchpad 0x1F8003E8..EB and mirrors 0x801F2778/80/7C/84 - the writes are Confirmed, the consumer Unknown.

Camera payload bytes[5..17] - byte[5] is stored whole to the mode byte DAT_8007B607; its high nibble selects both the loader split and the build branch (low nibble = strength). Mode 6 = keep current camera (the loader writes nothing).

Global roles (consumer FUN_801DAB90 unless noted; angles in the 4096 = 360° space, one tile = 0x80 world units):

  • B607 - mode byte. High nibble 1/2: anchor-follow with a position-proportional yaw sweep - yaw = B610 ± (B607 & 0xF) · lerp(player X across the zone attribute box at 0x1F800384/386), sign by nibble. 3 = look-at anchor, 4 = pad-analog yaw (pitch B60C, depth B614), 5 = fixed scripted shot, 6 = keep current.
  • B608 - pitch sweep: high nibble 1/2 = sweep sign about the box Z midpoint (pitch = B60C ± (B608 & 0xF) · lerp(player Z)); other values pin pitch to 0x1B8.
  • B609 - depth sweep: high nibble n ∈ 1..=5 anchors the sweep (n−1)/4 of the Z span from the box max (depth = B614 + (B609 & 0xF) · lerp(player Z)); else depth = B614.
  • B60A - heading-coupled pitch adjust: high nibble 1..=4 → pitch += (B60A & 0xF) · heading / 4; 5 → / 8 plus sin/cos-LUT (dy, depth) compensation from the player facing +0x16. Heading = func_0x80019278(anchor).
  • B60B - high nibble 1..=0xB: eye-space dy = 0x200 − heading · (B60B & 0xF); else dy = 0x200. The same nibble is the per-frame ease-damping shift in the follow-ease FUN_801DB510 (srav by B60B >> 4).
  • B610 / B60C - base yaw / base pitch (staging struct +0x06 / +0x02).
  • B614 - eye-space depth (staging struct +0x16). Mode 3 treats it as a bias: depth = (dist3D(anchor, player) · ((B607 & 0xF) + 1) · 6 >> 10) + B614 − 0x4000.
  • B618 - GTE H (projection focal length, staging struct +0x26) in every mode.
  • B61C / B624 - anchor/focus tile X / Z. Mode 3: look-at target is world (B61C·0x80+0x40, B620·0x20, B624·0x80+0x40). Mode 5: the focus tile - FUN_801DB8EC writes focus −(tile << 7) − 0x40 and FUN_801DB510 smooth-scrolls toward it.
  • B620 - mode 3: anchor height (× 0x20 world units). Mode 5: s8 height offset rotated by pitch into (dy, depth) via the sin/cos LUTs (_DAT_8007B7F8 / _DAT_8007B81C).

Query-miss defaults (FUN_801DBE9C): B607 = 0x10, B608 = 0x10, B609 = 0x30, B60A = 0x51, B60B = 0x20, B610 = 0, B60C = 0x1B8, B614 = 0x4000, B618 = 0x300.

Confidence: the three byte splits and the global routing are Confirmed (disassembly + the builder's consumption); the mask-kind scratchpad side-write consumer is Unknown.

What this doesn't tell us

  • Per-opcode encoding of the header bytes. Each inline install opcode packs its first 3 bytes differently (target selector / sub-op / flags); the count + ids at +0x3.. are fixed by the reader, but the header needs a per-case decode to read as "encounter from script X at PC Y".
  • Sibling section roles (1, 2, 4). The walker pins offsets and lengths for every section in all 80 scene bundles, and section 3 is decoded, but the interior layout of sections 1, 2 and 4 beyond what is noted above is open. The lengths cluster small (often 1 byte), suggesting per-scene callbacks / inline state rather than record arrays.
  • The pre-encounter live-pointer state. No save state in the scenario corpus captures an entity with +0x94 mid-armed; byte-level verification of "the bytes at the live actor[+0x94] match the parsed MAN row" needs a capture in the one-frame window between roll and consumption.
History: readings this page replaced

Summary tables restated the MAN header as "four s16 section offsets at +0x22..+0x28" and four sections; the byte-level block above (three s16 counts, one u24, six sections) is the one traced through the walker. An earlier reading held that there is "no separate on-disc encounter-record array" and every record is inline in bytecode; the Rim Elm survey showed the scripted fights select MAN formation rows by index, and inline windows are one of two carriers. The Zeto / Caruban attribution history is in the battle-id section. The falsified-reading catalogue is do-not-re-walk.

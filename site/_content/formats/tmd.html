Legaia TMD (3D mesh) Confirmed

Every solid thing in Legend of Legaia - Vahn and his Ra-Seru arm, every monster, the houses of Rim Elm, the Genesis Trees, the props on a shop counter - is a small 3D mesh: a list of points, and a list of triangles and quads that connect them and say which texture (or which flat colour) to paint on each. The container is TMD, the PlayStation SDK's standard model format, but Legaia ships a custom variant: point a stock PSX TMD tool at these files and it will reject them or draw garbage. This page documents the variant byte-for-byte, including the two habits that took longest to pin - how a primitive's vertex indices are found, and the fact that the game never lights a mesh from its normals.

Not stock PSX TMD

The tell is the very first word: Legaia's magic is 0x80000002 instead of the standard 0x00000041. Beyond the magic, the differences run deeper:

  • Custom primitive grouping - primitives are batched into groups behind an 8-byte group header instead of the stock per-primitive packet stream.
  • Offset pointers - the object table's pointer fields are byte-relative offsets that the runtime patches to absolute RAM addresses on load.
  • A fixed scale word - the per-object scale field is always 0x00808080, a Legaia-custom value where standard PSX TMD stores a signed log2 scale.

Implementation: crates/tmd/src/lib.rs + crates/tmd/src/legaia_prims.rs. Reverser context (decompiled-function dumps from Ghidra - FUN_80xxxxxx names are addresses of traced functions in SCUS_942.54, the game's main executable): ghidra/scripts/funcs/{80026B4C, 800268DC, 8001F05C, 8002735C}.txt.

Header (12 bytes)

OffsetSizeFieldMeaning
+0x004idAlways 0x80000002. Bit 31 = FLIST_BIT (pointers are byte offsets relative to the header end); low byte 0x02 = "Legaia TMD format version 2"
+0x044flags0 on disc; the runtime sets it to 1 after pointer fixup (the relocation sentinel, below)
+0x084nobjNumber of objects

The 0x80000002 magic is confirmed by the version check in FUN_80026B4C - the registration function bails with a "model version" diagnostic when *tmd != 0x80000002.

The flags word is the relocation sentinel

FUN_800268DC early-returns when flags == 1, and sets flags = 1 before walking the object table, so re-registering an already-relocated TMD is a no-op rather than a double-relocation. Retail depends on this: an actor's per-object render table can be rebuilt from a TMD that may or may not have been relocated yet (FUN_80024D78), and the guard is what makes that safe. Two implications:

  • A static tool must never write flags - a 1 on disc would make the runtime skip a relocation the mesh still needs.
  • A clean-room port that parses to typed offsets instead of patching pointers in place is structurally immune to the whole failure mode, so it should not reimplement the relocation.

Object table (28 bytes per object x nobj)

A TMD holds one or more objects - independent sub-meshes (a character's limbs, a scene's props). Each gets a 28-byte descriptor:

OffsetSizeFieldMeaning
+0x004vert_topByte offset of the vertex array from the end of the header (0x0C)
+0x044n_vertVertex count
+0x084normal_topByte offset of the normal array from the end of the header
+0x0C4n_normalNormal count
+0x104prim_topByte offset of the primitive section from the end of the header
+0x144n_primitiveSum of every group's count in the object's primitive section
+0x184scaleAlways 0x00808080 in Legaia (stock PSX TMD stores a signed log2 scale here)

After FUN_800268DC runs at load time, vert_top / normal_top / prim_top are patched in-place to absolute RAM addresses. Static tools should NOT do this patch - they should use the offsets as (ptr_base + offset) where ptr_base = 12 (HEADER_SIZE).

Vertex / normal data

Both are arrays of SVECTOR { i16 x, y, z, pad } = 8 bytes each - 16-bit integer coordinates, the native input format of the PSX's GTE (the console's geometry co-processor).

pub struct Vector { pub x: i16, pub y: i16, pub z: i16, pub _pad: i16 }

Primitive section

This is where Legaia departs furthest from stock TMD. The primitive section is a sequence of groups: each group has an 8-byte header followed by a fixed-stride array of primitives (a “prim” being one triangle or quad to draw).

OffsetSizeFieldMeaning
+02countPrimitives in this group
+22flagsSelects the row of the per-mode shape table (below)
+41olenPSX SDK "output length" (packet word count)
+51ilenPSX SDK "input length" - per-prim word stride; byte stride = ilen * 4
+61flagPSX SDK flag byte (lighting / shading)
+71modePSX SDK mode byte (FT3 / FT4 / GT3 / GT4 ...)
+8count * ilen * 4prim datacount records of ilen u32 words each; no per-prim sub-headers

The shape table

The per-prim layout depends on the prim type, and the runtime resolves it through a lookup table rather than the stock TMD mode byte. The renderer (FUN_8002735C) treats the 8-byte-stride table at 0x8007326C as a packed {u32 first; u32 second} per row, selects row = ((flags >> 1) - 8) >> 1, and reads exactly two fields (8002735c.txt:80027460..80027500): byte3 = first >> 24 (the shape selector) and byte4 = second & 0xFF (the base vertex-index offset in u16 units). Each row covers four flags values - a tri/quad pair for each of two adjacent flags; the low bit is not consumed.

row flags (tri / quad) raw 8 bytes byte3 (shape) byte4 (vtx off) family
00x10,11 / 0x12,1304 00 00 05 07 00 00 000x050x07FT, lit
10x14,15 / 0x16,1709 00 00 07 06 00 00 000x070x06GT, lit
20x18,19 / 0x1A,1B04 00 00 00 02 00 00 000x000x02F
30x1C,1D / 0x1E,1F06 00 00 02 06 00 00 000x020x06G
40x20,21 / 0x22,2307 03 00 01 07 00 00 000x010x07FT, baked
50x24,25 / 0x26,2709 03 00 03 0B 00 00 000x030x0BGT, baked

byte3 & 3 is the shading / texture family (0 = F flat untextured, 1 = FT flat textured, 2 = G gouraud untextured, 3 = GT gouraud textured); the quad bit (flags >> 1) & 1 picks tri vs quad. So flags 0x1B is row 2, byte3 0x00, an F4 (flat quad); 0x1D is row 3, byte3 0x02, a G3; 0x1F a G4. The crate's legaia_tmd::descriptor::TABLE is authoritative.

Vertex-index offset

The per-prim byte stride is ilen * 4; the vertex-index read offset comes from byte4 plus a per-byte3 quad adjustment. Triangles read byte4 (in u16 units) directly. Quads take a per-byte3 chain - and the two retail renderers that walk this table do not agree on it:

They agree everywhere except the lit textured rows 0/1, where FUN_8002735c's byte4 + 2 fallback reads past the vertex indices and into the normal-index block that trails them. The on-disc packets put the four vertex indices of a lit textured quad at byte 12 for both rows, so legaia_tmd::descriptor resolves 6 (u16 units) for both - which is what FUN_80029888 computes for row 1, and the one place its row-0 arithmetic (byte4 = 7, byte 14) parts company with the data. Pinned across every field/town env pack: offset 12 is the only candidate with zero out-of-range indices, and it leaves the quads planar (0.78 units mean out-of-plane, vs 65-166 for 14/16/18). Guarded by crates/engine-core/tests/env_mesh_prims_disc.rs.

Reading rows 0/1 quads at the FUN_8002735c offset makes their indices exceed the object's vertex count, so every mesh builder drops those prims - the visible symptom is a town house rendering as a shredded pile (Rim Elm object 137 keeps 58 of its 163 prims).

Per-prim colour / texture block

The bytes from the prim's start up to the vertex-index offset hold either a texture block (FT*/GT*) or a per-vertex colour block (F*/G*), selected by the byte3 shape (low 2 bits 1 / 3 are textured, 0 / 2 flat / gouraud). legaia_tmd::descriptor resolves the shape and the vertex_offset per group.

Textured prims

The texture block (legaia_prims::extract_textures) is [u0, v0, cba_lo, cba_hi, u1, v1, tsb_lo, tsb_hi, u2, v2 (, u3, v3)] - cba is the CLUT-base address naming which palette row in video memory to use, tsb the texture-page selector naming which VRAM region the UVs index into. Its start is Descriptor::texture_block_offset, resolved from the table entry's byte 1 (the renderer's per-vertex colour base at sp+0xb9):

  • byte1 = 0 (rows 0/1, flags 0x10..0x17): the light-source-lit variant. The texture block sits at offset 0, ahead of the vertices; per-vertex data trails the vertex indices. Rim Elm env-mesh pack 36 FT4/GT3/GT4 prims carry cba = 0x7ac? (CLUT row 491) at prim byte 2.
  • byte1 = 3 (rows 4/5, flags 0x20..0x27): baked per-vertex colours precede the block - one colour word for flat FT* (block at byte 4), n_vertices words for gouraud GT* (block at byte 12 for GT3, 16 for GT4). Here the block does end at the vertex-index offset.

Colour block and the untextured records

Every row except the lit rows 0/1 carries a per-vertex RGB colour block: the PSX [R, G, B, code] word, whose 4th byte is the SDK GP0 command code, not colour (0x20/0x24/0x28/0x2C/0x30/0x34/0x38/0x3C, optionally | 2 for the semi-transparent variant, and only on the leading word of a gouraud packet). Flat shapes store one colour word at prim offset 0, shared by all corners; gouraud shapes store one per corner at a 4-byte stride. On a textured prim this block is what pushes the texture block off offset 0. Pinned byte-exact from the renderer + real town01 props (pack 31 obj 315, pack 109 obj 114):

ShapeflagsilenRecord
F40x1B3 (12 B)[0..4) one colour word broadcast to all 4 verts; [4..12) 4 x u16 vertex byte-offsets (÷ 8 = index), winding [0,1,3,2]
G30x1D5 (20 B)[0..12) v0 / v1 / v2 colour; [12..18) 3 x u16 vertex offsets; [18..20) pad
G40x1F6 (24 B)[0..16) 4 colour words read in winding order [0,1,3,2] via DAT_8007b410; [16..24) 4 x u16 vertex offsets

The quad winding-remap table DAT_8007b410 = 00 01 03 02 reorders both the colour slots and the vertex indices for quads, so colour[i] pairs with vertex[i] after the remap.

Lit textured records (rows 0/1)

The baked rows carry their shading in the colour block. The lit rows carry it in normal indices that trail the vertex indices, and the texture block is a fixed 12 bytes for both tris and quads - the quad packs u3/v3 into the half-word the tri layout leaves as padding:

ShapeflagsilenRecord
GT30x14/156 (24 B)[0..12) [u0 v0][cba][u1 v1][tsb][u2 v2][pad]; [12..18) 3 x u16 vertex offsets; [18..24) 3 x u16 normal offsets (one per corner)
GT40x16/177 (28 B)[0..12) [u0 v0][cba][u1 v1][tsb][u2 v2][u3 v3]; [12..20) 4 x u16 vertex offsets; [20..28) 4 x u16 normal offsets
FT40x12/136 (24 B)[0..12) texture block; [12..20) 4 x u16 vertex offsets; [20..22) 1 x u16 normal offset (flat: one per face); [22..24) pad

The object header's n_normal confirms the block: it is exactly 1 x FT4 + 3 x GT3 + 4 x GT4 summed over the object's lit groups (Rim Elm env pack slot 36 object 0: 8 + 44*3 + 100*4 = 540, its declared normal count). The tri of row 0 (FT3, flags 0x10/11) is the one shape that puts its single normal before the vertices - [12-byte texture block][n0][v0 v1 v2] - which is what row 0's byte4 (7, byte 14) encodes.

Neither renderer lights from the normals

A surprise for anyone expecting PSX-style light sources: FUN_8002735c reads only the prim pointer (param_1[4]), the vertex base (param_1[0]) and the loop count (param_1[5]) - never the object header's normal table. FUN_80029888, the sibling that handles the lit rows (the only other function in SCUS_942.54 that reads the descriptor table), issues no NC* op either: between them the two renderers run exactly one GTE colour op, DPCS (cop2 0x780010, the depth cue). So the lit rows' normals are authored but never transformed, and shading is the stored colour word modulating the texel on the GPU (texel * colour / 128). This is the field's entire lighting signal - see renderer § Lighting. The engine port re-derives smooth normals from the geometry, so it decodes the indices only to know where the vertex block ends. legaia_tmd::legaia_prims decodes the colours into Prim::colors for every prim, and legaia_tmd::mesh::tmd_to_vram_mesh_field_hybrid surfaces textured UVs + untextured colours together for a hybrid render (see character mesh § hybrid render).

History: the two mis-reads this section replaced

An earlier walker assumed block_start = vertex_offset - block_len for the texture block, which only holds for the byte1 = 3 rows; the byte1 = 0 rows then read (cba, tsb) from geometry bytes and rendered as rainbow garbage (the Rim Elm decorative-plant props). texture_block_offset fixes this while leaving rows 4/5 byte-identical. Separately, mis-reading an untextured colour block as a texture block yields bogus (cba, tsb) and samples a random VRAM page - the historic "flat green tint / transparent hole". Both are catalogued with the rest of the retired readings on do not re-walk.

TMD pointer table

At runtime the game keeps a global registry of loaded models. FUN_80026B4C writes registered TMDs to *(int **)(idx * 4 + 0x8007C018). Confirmed readers in retail (4 functions, all setup-not-render):

Function Role
FUN_80021B04Actor-spawn helper; builds per-actor OBJECT pointer table at actor[0x44]+4
FUN_80024D78Per-actor OBJECT-table rebuild (safe on relocated or unrelocated TMDs thanks to the flags sentinel)
FUN_8001EBECPer-frame OBJECT[10/11] swap (pose select for player TMDs)
FUN_8001E890“DATA_FIELD player loader” - calls FUN_8003eb98(0x36C, …) (PROT 876 = player_data) and names the dev paths data\field\player.lzs / h:\prot\all\data\field\player.lz. The retail bytes it reads (PROT 876 = streaming-format VAB+TIM_LIST+SEQ; the dev player.lzs file is absent from the ISO9660 walk) do not carry the [0..4] character TMDs - those come from PROT 0874 (befect_data) section 0, see world-map overlay § disc-side source of [0..4]. What this function does do that is still consumed at DAT_8007C018[0..2] is the post-install group-count cap (entry[+0x08] = 10) and the equipment-conditional patch dispatch into FUN_8001EBEC.

The per-actor OBJECT[i] is a 28-byte struct copied into actor[0x44][i+1] from tmd + 12 + i*28 - sizeof(OBJECT) = 28.

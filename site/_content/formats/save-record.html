Per-character save record Confirmed

Open the status screen and everything you see about Vahn - level, HP, the eight stats, his learned magic, what he is wearing - is one block of RAM: a 0x414-byte record per party member, four of them side by side. Level-ups write into it, equipping writes into it, and saving to a memory card copies it out verbatim. Its field offsets are pinned by an unusually good ground-truth source: a GameShark cheat labelled "Max ATK" that pokes one address is a free field label for that offset.

The display name sits at +0x2A7 (9 bytes, NUL-padded), bounded by the active-spell table at +0x2B0. Slot 3's footprint runs into the global story-flag bitmap (RAM 0x80085600, record offset +0x2BC) and the inventory, so only its leading fields (name, live stats, record stats) are exclusive; the tail aliases the globals. This is benign - Terra is never saved as an active member.

On the memory card

The save block is a verbatim dump of this resident region: record n's base is block + 0x5C8 + n×0x414 (game_data + 0x3C8), so the name surfaces at block + 0x86F + n×0x414. "Verbatim" is true of the bytes, not of the whole block: editing a record also invalidates the additive checksum at block + 0x1FFC, which retail compares before it will accept the save - a stale word captions the slot "Damaged data." and the record never reaches RAM. legaia_save::card::restamp_sc_block_checksum is the fix-up, applied by write_retail_char_records; see the save screen.

Field notes

+0x12E is the battle status word

The halfword mirrors battle actor +0x16E, the packed ailment flags. FUN_80047430 copies it verbatim every frame a party actor ticks (lhu 0x16e(actor) then sh at 0x80047680 and 0x80048040), so the record carries the live in-battle condition. The battle HUD reads the same halfword through a second base: the status element selector FUN_8002C2E4 indexes 0x80084140 + slot × 0x414, and 0x80084140 + 0x5C8 == 0x80084708, so its +0x6F6 is this +0x12E, its +0x6CE is +0x106 and its +0x6F8 is +0x130. The per-bit map and the accessory-guard clear masks are on the accessory-passive page; engine mirror engine-vm::status_effects::display_flags.

+0x130 is the displayed character level

The status screen reads +0x130 as "LV" and the Level 99 cheat sets it to 0x63. Boot-confirmed via the starting-level randomizer: a New Game record with level-10 experience, level-10 stats and the right threshold but +0x130 == 1 still displays LV 1, and +0x130 = 10 displays LV 10 - the shown level is read from this byte, not re-derived from XP. The level-up applier maintains it by incrementing +1 per level-up event (the captured Noa / Gala four-level jumps bumped it once), so it can momentarily lag after a rare multi-level jump; for single-level play and the new-game seed it equals the level. Whether a separate magic-rank byte lives at +0x131 is unconfirmed. The accessor legaia_save::CharacterRecord::magic_rank() reads +0x130 - the level byte under a legacy name; level() reads +0x100, always zero in retail (the engine's own internal cell).

+0x000 is cumulative XP; +0x004 is the next-level threshold

+0x000 is the "Max Exp" target, the "Experience" readout and the value the applier compares; +0x004 is the "next" readout. Confirmed live: a randomized ROM that wrote a level-10 XP value into +0x004 showed "next level: 11195" while experience stayed 0 - so the starting-level randomizer seeds +0x000, not +0x004. The u16 that appeared to move by an XP-shaped delta at +0x004 in the Noa / Gala level-up triplets is the low half of the threshold word, which the applier rewrites on every level change. CharacterRecord::cumulative_xp reads the u32 at +0x000; no xp_low_word_alt field exists.

+0x13C is the learned-spell count - which is why the cheat works

The database calls it "Magic Slot Activator" and prescribes writing 0x24, which reads as an enable byte. Two menu-overlay readers say it is a plain length: the per-character list screen FUN_801DA2A0 reads +0x13C as the Ra-Seru-gated learned-spell count before walking the ids, and the window-7 character prompt substitutes record[+0x13D + sel] - the sel-th entry of that list (field menu). "Activating" the list is just declaring it 36 entries long. Treat +0x13C as a count when writing it: a value past the real id run displays uninitialised slots rather than granting spells.

+0x161..+0x178 is the summon-level array, not spell levels

The All Summons Level 9 cheat stamps 0x09 into 16 bytes at +0x161..+0x178 - one per summon id, not per spell. Any per-spell levels sit in the magic-group window at +0x13D..+0x160 where the database has 12 named modifiers. The accessor is summon_levels(); the older SpellList::levels is preserved for compatibility only.

The +0x120 cap constant

Across every captured save, +0x120 reads as 100; the level-up overlay writes it on every level-up event regardless of character or stat, and the new-game seed writes the same literal into +0x10C and +0x120 for every roster slot. It is the hard ceiling the record-side stats clamp against; the runtime then re-projects through FUN_80042558's 0x3E7 clamp on the live copy, so equipment and buffs can push past it up to 999 in battle. Accessors: stat_cap() / set_stat_cap() (the same field as RecordStats::cap_constant).

History: superseded readings
  • "+0x130 is Magic Rank, not character level" - reconciled the per-event +1 tick with the Level 99 cheat the wrong way round; falsified by the starting-level boot test. If a magic-rank byte exists it is the unconfirmed +0x131.
  • "The level-up logic reads +0x004 as cumulative XP" - conflated the threshold the applier reads with the XP it compares against.
  • "+0x161..+0x184 is a parallel spell-level array" - it is the 16-summon level array.

The falsified-reading catalogue is do-not-re-walk.

Parser + provenance

Offsets are pinned by a fusion of three sources: decompiled function dumps under ghidra/scripts/funcs/ (notably FUN_80042558, FUN_800431D0, FUN_80042DBC and the level-up overlay applier); captured save-state observations in engine_core::capture_observations::char_level_up and the levelup::observations::{noa,gala}_4_level_jump triplets; and the GameShark database, whose every effect is a labelled (addr, value) write. legaia_save::character::CharacterRecord is the typed accessor + round-trip layer; Party::from_retail_sc_block lifts a real SC block into a typed party. Source of record: docs/formats/save-record.md.

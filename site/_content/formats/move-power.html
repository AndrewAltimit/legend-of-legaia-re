Move-power / parameter table Confirmed

When an enemy uses a named special attack - Fire Breath, Tail Fire - how hard it hits, how it homes in on its target, what sound plays and which effects burst on contact all come from one 26-byte record in this table. It is the enemy special-attack power table: a party member's Tactical Art takes its power from the art record instead, and plain physical attacks never look here. Technically it is static data inside the battle-action overlay (PROT entry 0898), indexed through a 128-byte id→index map by the same move id the spell-name table uses. One record survives for an attack no enemy can cast - the dummied-out "Freeze Thunder".

What indexes it - power_table[map[move_id]]

(FUN_80xxxxxx names are Ghidra-traced functions labelled by RAM address.) The record index is not the move id. The setup site reads the actor's move id at actor[+0x1df], looks it up in the 128-byte id→index map, and indexes the table with the result; a map byte of 0x00 or 0xFF means "no record". The move id is the same id space as the SCUS spell-name table, so joining the two labels every record:

  • records 0x10..=0x2b (move ids 0x25..=0x74) are the named monster special attacks - their power, separate from the name the spell table carries;
  • records 0x01..=0x0f (move ids 0x04..=0x1f) are the spell table's unnamed internal enemy-attack tiers (escalating-power triplets);
  • record 0 is an all-zero unused slot.

Special-attack-only

The map covers exactly 44 ids (internal tiers 0x04..=0x07 / 0x12..=0x1F + named attacks 0x25..=0x74). The basic-attack and Tactical-Art bands 0x08..=0x11 and 0x16..=0x18 are unmapped: a live capture shows Vahn's queued Somersault carrying move id 0x0F and a Gobu Gobu basic attack 0x09, both resolving to record 0. Cross-checked against the enemy roster

Of the 29 mapped named ids (≥0x25), 28 are exactly the special attacks enemies cast (monster record +0x21..=+0x23). The table is a subset: across 186 monsters, 46 distinct attack ids appear and only 28 are here; the other 18 (0x2E / 0x2F / 0x3C / 0x4A..=0x6E, and 0xA7 / 0xB8 beyond the map) are the magic / elemental casts, whose damage is caster-state-derived - consistent with this being the physical/arts table. 95 of 186 monsters carry no magic attack at all.

The one mapped named record with no caster (move id 0x2C, record 22) is the unused Freeze Thunder enemy spell: its power record survived (power 37, cue 0x4A) but its effect lists are empty and no formation casts it. Community testing shows that forcing it crashes on a missing asset.

Record layout (26 bytes)

Three functions consume the record. The damage kernel FUN_801dd0ac reads only +0x00. FUN_801dea50 computes the record address once and stashes it at ctx+0x1014; the per-frame tick FUN_801e09f8 dereferences that pointer ~25 times for the residual fields. Corpus-wide, the offsets any consumer touches are exactly +0x00, 02, 04, 06, 08, 09, 0a, 0b, 0d, 0e, 12, 16 - never +0x0c.

Table extent, independently: 0x801F4F5C + 44*26 = 0x801F53D4, exactly where the +0x0a impact-config table begins, so the record count is pinned by the next referenced address in the overlay.

Worked example

Record 3 (move id 0x06, the third internal-tier attack) decodes as a homing physical strike: power 1500, approach speed 0x20, a 480-frame strike phase, Y offset 250, impact effect 1, cue 0x4d, designer tag C, one effect list on launch and a different one on contact.

The four power shifts

FUN_801dd0ac reads +0x00 at three load sites and derives four shifts from them. They are not a full / half / quarter ladder: two bound a random roll, two are summed straight into the damage accumulator.

LoadShiftSiteRole
0x801dd1c0>> 20x801dd1ccroll modulus, div at 0x801dd1d4
0x801dd1c0>> 00x801dd240additive damage term
0x801dd38c>> 10x801dd39cadditive threshold term
0x801dd3cc>> 30x801dd3d8roll modulus, div at 0x801dd3e0
0x801dd3cc>> 10x801dd448additive damage term

Both moduli are used as rand % (x + 1), so power < 4 rolls a constant 0 on the >> 2 branch and < 8 on >> 3. The half and eighth scales appear only in the retry arm, which re-floors a too-low attacker score. The branch split is on param_2: bne a1,0x7 at 0x801dd104 takes the non-summon path; when param_2 == 7 no table read happens. This roll is then scaled by the element-affinity matrix FUN_801dd864, a sibling table in the same overlay (battle formulas).

Where it lives and how it is read

The whole 0x801F4F5C..0x801F69D8 window is loaded with the overlay image, not built per battle - it is byte-identical across unrelated battle save states, and the raw PROT 0898 bytes match. The "runtime VA" is the fixed RAM address the overlay occupies once loaded (slot-A base 0x801CE818, file 0x25178), which is why the parser can read the same bytes straight off the disc.

ThingValue
PROT entry0898 (battle-action overlay; CDNAME overlay_battle_action)

Both halves of the index expression are disassembly-pinned. The map lookup at the call site in FUN_801e09f8 materialises 0x801F4E64 and reads lbu a0,-0x1(v1) - the odd 0x801F4E63 base is that addiu 0x4e64 / lbu -0x1 pair, so the constant 0x4e63 appears nowhere in the code. The base is materialised at three sites corpus-wide: 0x801dd1a0 and 0x801dd36c (both in the kernel) and 0x801df27c (setup).

The second of those is the one a linear lui+addiu matcher misses: its lui a0,0x801f sits in the branch delay slot at 0x801dd2f8 and the addiu is the branch target, 0x74 bytes later with a0 clobbered in between. Any sweep folding pairs must follow branch targets, not adjacency.

History: 0x801F3990 and the mis-based dumps

Dumps labelled overlay_0897_* / overlay_magic_* / overlay_muscle_dome_* carry the same battle-overlay bytes as overlay_battle_action_* but were produced at a wrong load base, so their printed VAs are off by a constant. That produced a claim that 0x801F3990 was a second damage kernel reading this table; at the real runtime VA it is a distinct function - the cast audio-cue dispatcher, reached by one jal at 0x801E3E04 - and it reads no field of the record. Take addresses from the extracted overlay image, never from an overlay_0897_* dump. Details in do-not-re-walk and the battle action SM page.

The +0x0c no-reader sweep

A negative is only as good as the coverage it names. This one is swept over bytes, not dumps: SCUS_942.54 plus all 25 overlay images in static-overlays.toml, every 4-byte word decoded independently, sound for every valid R3000 load / store and for j / jal targets (not for COP2, which cannot address a record). Access shapes modelled: absolute constants (lui+addiu/ori pairs folded and tested against [table, table + 44*26)), base-folded displacements, ×26-indexed registers, pointer-relative reads through lw rD, 0x1014(rB), straddling loads, and data-resident pointers. Result: no reference lands at a shifted offset, no data word holds an in-table address, and PROT 0898's five byte-width loads at literal displacement 0xc all sit on unrelated RAM structs. PROT 0896 / 0965 / 0971 are unswept but are slot-A entries that can never be co-resident with the battle-action overlay.

Effect-id lists (+0x12 / +0x16)

Both lists are up to four ids, dispatched identically by FUN_801e09f8 - the only difference is when they fire (contact vs launch). Each byte multiplexes two id spaces by bit 7:

History: "0x801f6418 is the SFX byte" and the split pairing

An earlier reading paired +0x12 with 0x801f6324 and +0x16 with 0x801f6418, and read the second table as a per-effect sound id. Each list uses both tables, and the byte is a CLUT source-x handed to the image copier (see art data for the cue tables). A "~0x20-byte struct" reading of the prototype table was likewise a coincidence of record 0x27's size.

Effect-list framing - two consumers disagree

  • FUN_801DEA50 (setup) walks one contiguous run from +0x0E, stopping only on a zero byte. 0xFF is not a terminator there: it has bit 7 set and routes to the 2D path with id 0x7F.
  • FUN_801E09F8 (tick) reads +0x12 and +0x16 as two separate 4-byte lists and treats +0x0E == 0xFF as a broadcast to all four arms.

Ids 0x0A, 0x2D and 0x2E additionally latch the spawned handle into ctx+0x1028 and seed the per-frame delta triple at ctx+0x1184, which is what makes their effect follow the actor.

The cue-group table 0x801F6470

A third region of the same data band, indexed by group id rather than effect id. The cue expander FUN_801E22C8 reads it (addiu v1, v0, 0x6470 at 0x801E2374) one record per call:

OffsetSizeFieldMeaning
+0x001cue count0..=4; zero spawns nothing
+0x014cue idsOnly the first count are read. Bit 0x80 = an actor cue (FUN_801DFDF0(id & 0x7F, pos, yaw), the strike pose); any other id indexes both effect tables above

Stride 5, 13 records: on disc they fill 0x801F6470..0x801F64B5 followed by padding and the summon.DAT path literal, and retail's callers never index past 0xC. The table has exactly one consumer - a reference scan of SCUS plus every base-mapped overlay finds 0x801F6470 materialised once, inside FUN_801E22C8 itself - while its two sibling tables are reached from five sites each, always in pairs. The caller is the damage-application primitive FUN_800402F4 (eleven branches, group ids 5..0xC literal or computed). The port has the kernel (legaia_engine_vm::battle_cue_group::expand_cue_group) and both tables but not that dispatch.

Effect → triggering-move inverse index

The join from a spawned effect back to the moves that trigger it is fully disc-derivable: walk every mapped record, classify each list byte, and invert. The index is keyed on (space, id) because the lists multiplex two spaces - Proto3D(id), Efect2D(id), plus the Flash singleton. The +0x0a impact selector is a separate config space and stays out. There is no symbolic effect-name table, so id → move is the achievable join; move_power::effect_trigger_index builds it and asset move-power --effect-index emits it.

Effect-prototype records - the spawn path

A 0x01..=0x63 byte spawns the move-VM record 0x801f6324[id] points at. The tick calls FUN_80050ed4(world_pos, src_pos, 0x801f6324[id], 0x1000), a 0x60-slot allocator that tail-calls the shared stager FUN_80021B04 (the disassembly preserves a0..a3; the C decomp drops them), which:

  • reads the record's +0x00 model_sel; < 0 / 0x4000 / 0x4001 are transform-node / render-mode sentinels, else the mesh is DAT_8007C018[model_sel + gp[0x754]];
  • allocates an actor (FUN_80020de0), stores the record as the actor's move-VM buffer (+0x48) and forces the PC to u16-index 2 (+0x70 = 2, bytecode at record+4);
  • drives it through the move VM (FUN_80023070).

So each record is byte-identical to a summon part record (+0x00 i16 model_sel, +0x02 u16 flags, +0x04 move-VM bytecode) and reuses the same stager, VM and TMD-pool bridge as legaia_asset::summon_overlay. move_power::parse_effect_proto_records decodes the whole table; all 54 unique records execute cleanly through the ported move VM (disc-gated move_fx_records_vm_exec_disc, ~20 distinct ops). A live capture seats one: the Gimard "Fire Tail" mid-cast holds a part-actor whose +0x48 is 0x801F5484 (proto entries 0 / 0x30 / 0x31).

model_sel base semantics

gp[0x754] (global 0x8007BA6C) is party_count + 2 in battle, save-corpus-pinned: 0 when no effect-model library is resident, 3 for the 1-member training party, 5 for the full party. The two fixed pool slots plus the live party meshes precede the effect-model library, so model_sel is library-relative and there is no per-summon base. A PCSX-Redux exec breakpoint on FUN_80021B04 during a move-FX spawn pinned the chain FUN_801e09f8 → FUN_80050ed4 → FUN_80021B04 with the prototype base and list id live in registers (model_library_base_tracks_party_size).

Engine wiring

MovePowerCatalog pairs the table with the id→index map on World::move_power and resolves a move id to a full MoveFx descriptor (every behavioural field, the impact-config join, each list byte as an EffectListEntry with its prototype and CLUT row). The monster special-attack damage path rolls +0x00 through the arts/physical kernel (battle formulas).

Move-FX scene-graph render

World::spawn_move_fx parses a move's spawn records, stages them as a SummonScene at the fixed library base (global_tmd_pool[3..=32], the PROT 0871 effect-model library) and drives each part through the ported move VM (tick_move_fx; play-window H cycles the moves MovePowerCatalog::spawnable_move_ids() enumerates). In the live loop the shared cast path (World::cast_spell_on_slots, used by player casts and the monster-AI special path) requests the spawn for any non-summon move with a spawnable entry; the host drains take_pending_move_fx_spawn(). Player Seru-magic ids 0x81..=0x8b route to the summon-creature path; plain physical attacks carry no move id. AltEffect entries spawn through the 2D pool (World::try_spawn_effect / spawn_by_ui_id) whether or not a 3D scene stages.

Presentation fields

A spawn also surfaces the trail texpage (+0x0b → 0x7700 + id) via World::active_move_fx_trail_texpage() - the afterimage streak draw FUN_801e1ab0 is ported as legaia_engine_render::afterimage::build_afterimage_quad (jittered semi-transparent POLY_FT4), with the camera-coupled corner projection FUN_800195a8 as billboard::project_billboard - and the sound cue (+0x0d) via World::take_pending_move_fx_cue(), routed through the ported FUN_8004fcc8 decode (legaia_engine_audio::classify_cue) into the SFX ring.

Summon exception

The summon arm of FUN_801dd0ac (attacker slot 7) never reads this table; a summon's magnitude is caster / summon-state-derived (spell table, and the open per-spell-power thread in open RE threads).

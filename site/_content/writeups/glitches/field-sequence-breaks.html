Incense, doors and the Door of Light

Four ways Legend of Legaia lets a player go where the story is not ready for them: an Incense notice that swallows a cutscene trigger, an Incense effect that outlives its save file, a boss-room door that opens to one button press from beside its guards, and one patch of floor in Nivora Ravine where a Door of Light works. Each is traced to the code and scene data on the USA disc.

How to read this page
Everything here is read from the disassembly of the game program and its field overlay (PROT entry 0897, load base 0x801CE818) and from the scene files. The Juggernaut Room door is also captured on an emulator, and its section says how each capture was set up; so is one reading in the carry-over section. The rest is static: where those sections say what a debugger shows, that is a prediction from the code. The player's movement lock is bit 0x80000 of player[+0x10], with the player actor at *0x8007C364; a tile is 128 units, and the player's tile is its position shifted right by 7.

Incense trigger bypass

Reported as
When the notice that the Incense has worn off appears on the step that would have entered a cutscene trigger or loading zone, the notice wins and the trigger never fires (community report).
Cause
The Incense expiry sets the movement lock mid-frame; the player still steps onto the trigger tile, and a locked crossing is recorded without running.
Where
Field overlay, PROT 0897: FUN_801D0B90 (walk tick) and FUN_801D1EC4 (walk-on dispatcher)
Affects
Walk-on records and intra-scene teleports that are one tile deep on the line walked; Jette and the three Uru Mais dreams match on the disc
Status
explained - read from the disc, not captured on an emulator

The trigger code never looks at the Incense. What the two share is the movement lock, the bit that tells the game a script or window owns the player.

Each frame the game asks once whether the player is free. If so it runs the walk tick, then moves the player, then compares the player's tile with the last one to see whether a trigger tile was entered. When the Incense runs out, the walk tick raises the lock so its notice window can take the pad. That happens after the frame's question and before the move, and the player still moves that frame.

If that move crosses onto a trigger tile, the trigger test finds a new tile and a locked player. Its rule for that case is to write the tile down as handled and do nothing else. Once the notice is dismissed the player is standing on the trigger tile, and only a fresh crossing fires a trigger. The trigger is spent without running.

The Incense drains by time spent moving: one use is 0x40 walk ticks of 0x20 vsyncs each, about 34 seconds of walking, capped at 0x100 ticks (about 137 seconds). That is why a fixed walking route reproduces the skip. This is read from the code; it has not been captured on an emulator.

Mechanism

  1. 0x801D1694Gate: the per-frame player routine tests the lock once. A free player continues.
  2. 0x801D0D14Walk tick: the Incense window goes from 1 to 0, the notice record is installed and the movement lock is set.
  3. 0x801D01F0Mover: its own lock test only skips the menu-button block, so the player still moves and can cross a tile edge.
  4. 0x801D2158Trigger test: new tile plus locked player takes the exit that stores the tile and performs no lookup.
  5. 0x8007BDC8After the notice the last tile equals the current tile, so nothing fires until another crossing.

Scope

Between the gate and the mover call the only code is the walk tick, and the Incense edge is its only lock write, so Incense is the only source of this on the walking path. The kingdom overworld runs the same routine. The skip lasts one pass: the record never ran, so its one-shot flag is not set and a later crossing of the same tile fires it.

Related pages: field locomotion, the walk-on trigger sidecar, the pause menu.

Verifying it

Break on 0x801D0D14. On the hit, note the player position, run to 0x801D2068 in the same frame and compare the new tile against 0x8007BDC8 / 0x8007BDCC. To force the case, write 1 to 0x8007B600 and 0x21 to 0x801F2274 on the frame before the player's centre crosses into chitei2 tile (18, 14). Prediction: the branch at 0x801D2158 is taken, 0x8003BDE0 is not called from 0x801D2184, and flag 0x470 stays clear.

  • The community reports that the Jette skip costs the Door of Light for the rest of the game; that is not traced. A capture of 0x1F800394 after the skip, and of whether FUN_801D9E1C still reaches 0x801DA058, would settle it.
  • The routine that releases the lock after the notice is not traced.
  • The out-of-bounds uses in the community reports are not matched to specific tiles.

Incense carry-over into a new game

Reported as
Use Incense, then load a different save or start a New Game without resetting the console, and the no-encounter effect is still running. Speedrunners call the trick the Incense File Transfer and name the categories that use it New Game+ (community report).
Cause
The Incense window is one number in the program's own memory, outside the block that is saved, loaded or rebuilt for a new game.
Where
RAM 0x8007B600, inside the SCUS_942.54 load image
Affects
The Incense window only, up to 0x100 ticks (about 137 seconds of walking)
Status
explained - read from the disc; the carry-over itself is not captured on an emulator

"New Game+" is the community's name for this glitch, not a carry-over mode of the kind other games ship. The only thing that transfers is the remaining Incense steps. The name stuck because the trick splits the speedrun categories: a run that starts with Incense already burning skips the early random battles, and it also has the trigger bypass available from the first minutes, long before the item can be bought, so the route looks completely different from a run without it.

The window is a single number kept in the game program's own memory rather than in the block that goes to the memory card. Loading a file does not restore it and starting a new game does not clear it, so whatever was left keeps draining as the party walks. Only a reset or power cycle, which reloads the program, returns it to zero.

Two consequences follow. Saving, using Incense and reloading keeps both the effect and the item. And because the wear-off notice still appears, the trigger bypass becomes available in a file that owns no Incense.

Mechanism

  1. 0x8007B600The window sits inside the program image, which ends at 0x8007B800; its value in the file is zero.
  2. 0x80084140The save block is a 0x1A18-byte copy of the live window further up in memory.
  3. 0x80046870Seven instructions on the disc touch the window: the top-up, the validator, the drain and the encounter test. None stores a constant.
  4. FUN_8001DCF8The mode-entry reset writes a fixed list of globals; the Incense window is not on it.

Scope

The most that can be carried is the cap, 0x100 ticks. Any other global kept outside 0x80084140..0x80085B58 and off the reset list behaves the same way.

The encounter step counter 0x8007B5FC is another number outside the saved window. Its value in the program file is 0x3CE (974), and that is what it holds after a power-on and a memory-card load; this one is a capture, on an unmodified played save loaded from a cold boot. The first battle after a cold load in a room with encounter rate 18 therefore comes on step 55, every time. Whether the counter is on the reset list is not checked here.

Related page: the save screen.

Verifying it

Write 0x100 to 0x8007B600, reach the title screen without resetting the console (a Game Over does it), start a New Game and read the address on the first frame of free walking. Prediction: 0x100 less the ticks walked. After a reset it reads zero.

Juggernaut's Room door

Reported as
The two guards in front of the Juggernaut Room in Ratayu castle, who stand aside only for a party at level 99, can be beaten early: "you come at it from the side", stand at an exact spot beside one guard, and one press of the interact button opens the door (community report; the method is shown in this community video).
Cause
From a strip beside a guard, one interact press lands in his talk box and the door's box at once; he makes it a talk, and the door, later in the actor list, gets it.
Where
Scene retockin (Ratayu interior), door to jagaroom; interact probe FUN_801CF9F4 in the field overlay, PROT 0897
Affects
This door, in both story states that have the guards, from either side; the same last-hit rule applies wherever an NPC and a prop share an interact point
Status
explained - traced in the disassembly and captured on an emulator; the player was placed by poked coordinates and then driven by pad

Nothing gets past the guards. The door has no lock of its own while they stand there; the guards are the lock. Standing beside one of them, a single press of the interact button reaches a point that is inside the guard's talk box and the door's box at the same time. The guard makes the press count as a talk; the door, which comes later in the game's list of actors, is the one that receives it. The door opens and its own script walks the party through.

The spot is narrow. Along the outer side of each guard there is a strip about eight units wide where he does not stop a player walking up. Stand in that strip level with the guard, face diagonally toward the door and press: the game checks one point 64 units across and 64 units up, and from the strip that point is close enough to both the guard and the door.

A little too low and the guard just talks. A little too high and nothing happens. At the very top of the strip, against the wall, the guard talks without any button press, which is the sign players use to know they are in the right column.

The door is unlocked for a story reason. It is the route to the boss on the first trip through the castle, so its script opens on touch, and the room is closed before and after that by standing two guards in front of it. A party that reaches level 99 and talks to Saryu gets the guards removed and a key, and only then does the door ask for the key.

Behind the door, once the Saryu story is done, the chest gives the Evil Talisman and asks for no key. Before that the room is empty. Nothing is duplicated and nothing locks: the room's exit puts the party back in front of the guards, and reaching level 99 later still gives the key, which then opens a room whose chest is already taken.

Mechanism

  1. retockin P0[0] +0x16Door prop, centre (3584, 7424): flag 0x650 set opens it; flag 0x64F set asks for key item 0xBF; with neither set the script jumps straight to open and leave, and writes no flag.
  2. 0x801F2254The interact button tests one point 64 units out on a compass of eight. At heading 0xA00 it is (x + 64, z + 64); at 0x600 it is (x - 64, z + 64).
  3. 0x801CFB40The box test walks the whole actor list with no early exit. Every hit overwrites the player's partner slot; a talk-class actor (within 72 units) adds result bit 1, a static prop (within 80) adds bit 4.
  4. 0x801D0860The caller tests bit 1 only, then posts the touch event to the partner slot: the last actor hit, not the one that supplied the bit.
  5. 0x8003B8D4Scene init creates the scripted actors before the placed props and the list is appended at the tail, so the door (list index 46) is after both guards (21, 22).
  6. (3444, 7288)From x 3442..3448, z 7282..7302 the point is inside the left guard's box and the door's box. The mirror is x 3720..3726 at heading 0x600.

Why a player can stand there at all: a guard does not keep the player out of a square around him. A step is refused only when one of three leading points, 63 or 64 units ahead, comes within 40 units of the guard, and only along the axis of that step.

The tile behind them, (27, 57), carries an ungated walk-on exit to the room, but an exhaustive flood of every position reachable in 2-unit steps finds none on that tile while the guards are present. It is not how players get in.

The guard's unprompted talk at the top of the strip is the same rule pointing the other way. With right held at z 7314, one leading point is inside the door's box and two are inside the guard, who is hit last; a prop contact auto-posts to the partner slot, and the slot holds the guard.

Scope

The trick works in both guarded states and on either side of the door. The ending's copy of the scene, edretoin, carries the same door record and walk-on record. Noa's sigil and the Door of Light in Nivora

Reported as
In Nivora Ravine, where the Door of Light is greyed out, standing on the glowing crest on Noa's route makes it usable (community report).
Cause
The crest stands inside a nine-by-nine map rectangle marked Door of Light allowed, listed ahead of the tunnel rectangles that forbid it.
Where
Scene nilboa region table; FUN_801D9E1C (PROT 0897) and FUN_80030628 (SCUS)
Affects
Tiles x 46..54, z 60..68 of Nivora Ravine; no other scene has such a pocket
Status
explained - read from the disc, not captured on an emulator

The crest does nothing to the Door. It stands inside a small rectangle of the map that is marked Door of Light allowed, surrounded by tunnels that are marked not allowed.

Every dungeon map is divided into rectangles that set the random encounters for that area. Each rectangle also carries one bit saying whether a Door of Light may be used there. Every time the player steps onto a new tile the game finds the first rectangle that contains it and copies that bit into a flag; the item menu greys the Door when the flag says no.

In Nivora the tunnel rectangles say no. A nine-by-nine box over the ravine's two-level crossing says yes, and it comes earlier in the list, so it wins wherever it overlaps. The crest sits on the east edge of that box. Step onto it and the flag flips; one tile further east it flips back.

Any walkable tile of the box has the same effect; the crest is the landmark that happens to be in it. Leaving this way during the party split skips the prompt that regroups the party; what the game does next in that state is not traced.

Mechanism

  1. 0x8003093CThe item menu dims the Door of Light when bit 0x100000 of the transient flag word is set.
  2. 0x801D9FE8On every tile step the region reader takes the first record whose tile box contains the player.
  3. 0x801DA064It sets both Door bits, then clears the Door of Light bit only if the record's byte +8 has bit 7.
  4. nilboa region recordsNivora's tunnel records carry +8 = 0x20; records 1 and 20, the box at 46..54, 60..68, carry 0x80 and come first.
  5. nilboa P1[0] +0x4D4The crest's test area is tiles 53..55, 62..64; columns 53 and 54 are inside the box.

Scope

Across every scene's bundle MAN, nilboa is the only scene where a live story group mixes allowed and blocked records so as to leave a walk-in pocket (7 of 19 allowed, in both groups). The one other mixed group is rikuroa's default group, with a single blocked record among eleven. The per-scene variant MANs are not part of this scan. No field script changes the Door bits: ops 2E / 2F appear only with bit numbers 0, 16 to 19, 22 and 24 to 27.

Related pages: encounter and region tables, the field script VM.

Verifying it

In nilboa during the split, watch bit 20 of 0x1F800394. Prediction: it reads 1 in the tunnels and drops to 0 on the step that brings the player's tile to x 46..54, z 60..68. A breakpoint at 0x801DA0C8 stops on the clear, with s2 pointing at the matched record.

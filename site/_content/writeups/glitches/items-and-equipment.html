Items, stats and equipment

Five reported oversights in how Legend of Legaia handles items, stat boosts and equipment, each followed through the game's own code on the USA disc: a stat boost that is said to overflow, story events that take equipment without telling the rest of the game, a Point Card that can freeze a battle, a coin vendor that sells a hundredth item, and a prize that can be announced and never handed over.

How to read this page
Everything here is read from the instructions and data on the disc. None of it was captured on a running game. Where a section says something "should" happen, that is a prediction that follows from the code and is marked as untested. Each glitch has an address table so another reader with a debugger can check it.

Stat boost overflow

Reported as
Using permanent stat-boost items past a stat's limit overflows the stat (community report)
Cause
Not found for the permanent items: every one adds and then clamps. The one-battle boosts next door do saturate or wrap.
Where
Item applier FUN_800402F4 in SCUS_942.54; turn-order key FUN_801DA780 in PROT 0898
Affects
Candidates: Elixir stacking, the Speed-derived turn order, the enemy cast Jugger Power
Status
Not confirmed for the Waters and Honey; the in-battle sites are candidates, read from the code

The permanent stat items - the six Waters, Honey and Miracle Water - cannot overflow anything on the USA disc. Each adds a small fixed amount to a 16-bit number and immediately compares the result with a ceiling, writing the ceiling back if it was passed. The largest value that ever exists before the compare is 1003 (10015 for HP). A 16-bit number holds up to 65535, so there is no room for a wrap.

The boosts that last one battle are a different story. Elixirs multiply a battle stat by 1.2 and can be stacked without limit until the stat pins at 65535. The number that decides turn order is built from Speed and stored in 16 bits with no ceiling, so a hugely boosted Speed can wrap it to a small value and the character acts late. And one enemy self-buff, Jugger Power, has no ceiling at all. These are the places a "stat boost overflow" can really happen, offered as candidates for what the report saw.

Three numbers are easy to mix up. The stored stat is what the items write. The live stat is the stored one plus accessory percentages, capped again. Equipment is in neither: the menu adds it into a total for display, so a figure above 999 on the status screen is a sum on screen, not a stored value.

The instructions

Class 6 (permanent stat-up) is arm 0x8004112C of the applier; the tier byte picks one of seven arms through the table at 0x800151B0. All seven have this shape:

800411e8  lhu v0,0x6ec(v1)      ; stored ATK (record +0x124)
800411f0  addiu v0,v0,0x4
800411f4  sh v0,0x6ec(v1)
800411fc  sltiu v0,v0,0x3e8     ; below 1000?
80041200  bne v0,zero,<exit>
8004120c  _sh v0,0x6ec(v1)      ; otherwise store 999

The item menu then rebuilds the live stats (jal 0x80042558 at 0x801D8540, PROT 0899), and that routine clamps again at 0x80042C0C..0x80042CE0. The Elixir arm (class 7, 0x80041464) computes stat + stat/5 and stores 0xFFFF when the sum is larger (0x800414D8..0x80041510 for Speed). The turn-order key is SPD + rand() % (SPD/2 + 1) + 1, stored by sh a0,0x16c(a1) at 0x801DA84C. Jugger Power (cast 0xBA, PROT 0945) adds a quarter to ten stat halfwords at 0x801F6DA0..0x801F6E34 with no compare.

A sweep for sign-extending loads of the battle stats finds none for ATK, defence, SPD or INT, so a pinned value does not turn negative.

Verifying it

Set Vahn's stored ATK (0x8008482C) to 0x03E6 and use a Power Water: it reads back 0x03E7, and at that value the menu refuses the item. For the turn order, write 0xFFFF to a party actor's +0x164 and +0x166 in battle and break at 0x801DA84C: the value stored is below 0x8000 and that character acts late.

What would settle the report itself: the stored stat halfword before and after the item use that appeared to overflow. No USA code path wraps there. Related reference: item-effect table, character record, battle formulas.

Story equipment removal skips the re-check

Reported as
When the plot takes a piece of equipment, its bonus keeps working until something else re-checks equipment (community report)
Cause
The script's take-item instruction empties the equipment slot but never calls the routine that turns slots into bonuses
Where
Field script instruction 4C 52 at 0x801E1ABC (PROT 0897) and FUN_800430AC in SCUS_942.54
Affects
Nine story hand-overs of a wearable item, listed below, when the item is equipped at that moment
Status
Explained - the mechanism and the nine sites; how long the stale bonus lasts is only partly traced

An accessory's effect is not looked up when it is needed. One routine "bakes" it into each character: it reads the eight equipment slots and writes out a set of ability bits and a block of live stats. Battle, the random-encounter roll and the menus all read the baked copy, never the slots.

When the story takes an item, the script instruction first tries the bag. If the item is not there because it is being worn, it clears the equipment slot directly - and stops. It does not run the bake, so the baked copy still says the item is on.

The game does have a script instruction that writes an equipment slot and re-bakes; it is the one that grows the Ra-Seru. The take-item fallback simply does not use it.

How long it lasts

Until the next event that re-bakes. Entering any scene always does. So do using an item or magic from the menu, equipping or removing anything, Best Equipment, and buying-and-equipping in a shop. The field scene is reloaded after a battle, which would limit the stale bonus to a single battle fought before leaving the room; that part rests on the engine documentation and was not re-read. The in-field save screen does not re-bake. Whether simply closing the pause menu does is not traced.

801e1adc  bne v0,v1,0x801e00b8      ; found in the bag: done

FUN_800430AC walks each party member's three accessory slots (record +0x19B..+0x19D), zeroes the first match with sb zero,0x196(v1) at 0x80043108 and returns. It has one caller on the disc.

The rebuild FUN_80042558 zeroes the ability words at 0x800425EC, walks the slots at 0x80042620..0x8004270C, applies the percentage boosts and clamps. Every reference to it on the disc is a call, and none is in the battle program. The instruction that does it properly is 0x3B at 0x801E07DC: jal 0x80042558 at 0x801E0810 with the slot store sb v1,0x75e(v0) in its delay slot.

Point Card softlock

Reported as
Using the Point Card in battle on one of your own characters hangs the battle (community report)
Cause
The target cursor can step onto an ally, and the Point Card's damage skips the HP-counter bookkeeping the end of the action waits on
Where
Item window at 0x801D18F8 and the action state machine in PROT 0898; discharge arm 0x8004209C in SCUS_942.54
Affects
Any party member as the target, as long as the Point Card holds points
Status
Explained - from the instructions; not run

Two separate mistakes line up.

The cursor can reach an ally. The Point Card is meant for enemies. When you pick it, the game builds a ring of targets that starts from whoever this character aimed at last. It builds the ring first and only afterwards checks that the last target was an enemy. If the last thing this character did was aimed at an ally - any healing item or Elixir, whose cursor starts on the user - that ally is already in the ring. The cursor is moved to an enemy, but one press of Left steps back onto the ally.

The hit breaks the HP display. The Point Card's damage routine subtracts HP and does nothing else. Every other routine that changes a party member's HP also notes how far the on-screen number still has to count. At the end of an action the game waits until on-screen HP equals real HP. Here they differ and nothing is counting, so it waits forever while the camera circles.

This is the same end state as the first of the two known battle softlocks - the HP-counter wait - reached a new way, from the controller on an unmodified disc. It is not the approach softlock described in the endless camera orbit.

  1. Aim at an allyA healing item or Elixir leaves an ally seat in the actor's target byte +0x1DD.
  2. Pick the Point CardThe ring is built at 0x801D18F8; the enemy check comes after, at 0x801D1918.
  3. Press LeftThe cycler FUN_801D8D00 returns the ring head: the ally.
  4. The hit landsArm 0x8004209C lowers HP and seeds no countdown.
  5. The waitState 0x51 asks FUN_801E7250 every frame and is always told "not settled".

Predictions from the code, none of them tested: it hangs on any party target, not only the user; it hangs whether or not the hit is lethal; with an empty Point Card nothing is written and the battle continues; aimed at a monster it is harmless.

The instructions

801d1918  lbu v0,0x1dd(v0)     ; only now read the stored target
801d1924  sltiu v0,v0,5        ; a monster seat (3..7)?
801d1930  jal 0x801db8b4       ; if not: first living monster

The Magic window runs the same two steps in the right order (check at 0x801D1C8C, build at 0x801D1CC0). The builder stores the unchecked target as the ring head with sb v0,0x245(v1) at 0x801D8B30. The picker stores the cycler's answer at 0x801D2630 and its confirm path never re-checks it.

It writes neither the countdown at actor +0x10 nor the displayed HP at +0x172; the heal and revive arms of the same routine do, at 0x800408FC, 0x80040D28 and 0x800410BC. Coin vendor purchases past 99 (Japanese release)

Reported as
On the Japanese release a coin vendor sells an item while 99 are held; the coins go and the count stays 99 (community report)
Cause
The bag silently trims a stack to 99, and the purchase never checks whether its item fitted; only a check before the confirm box prevents the loss
Where
Prize session FUN_801DC1CC in PROT 0899; bag add FUN_800421D4 in SCUS_942.54
Affects
Every coin prize row on the Japanese release (inferred)
Status
Partially explained - USA paths read; the Japanese difference is inferred

Only the USA disc was read. On it, the coin counter has one check before the Yes / No box - "do you hold fewer than 99?" - and after that it adds the item and takes the coins with no further test. The bag's add routine never refuses anything: it adds, then quietly trims the stack back to 99.

With the front check in place the trim never matters. Without it you get exactly the report: the coins go, the item is added and trimmed off again. So the Japanese build must be missing that one check. The reverse idea - check present, trim missing - would produce stacks above 99, which is not what is reported.

The USA disc has a relative of this fault. Stackable shop items go through a quantity screen capped at 99 - held, but equipment does not: the buy confirm tests only gold, and the "to the bag" row adds the item and debits gold with no held-count read between them. Buying a hundredth copy of one piece of equipment should take the gold and leave 99. That is inferred from the instructions and untested.

War God Icon can be missed for good

Reported as
The War God Icon is lost for good if the Muscle Dome Expert Course is beaten before defeating Jette (community report)
Cause
The item and its "already awarded" flag are handed out by two different pieces of code that disagree about what clearing the course means
Where
Arena settlement FUN_801D0F60 in PROT 0977; lobby victory scene, record P2[9] of scene koin1 (PROT 543)
Affects
The Master course - not Expert as reported - won while it is still shortened
Status
Explained - from the instructions and the scene script; not run
Correction to the report
The dome's three courses are Beginner, Expert and Master. The Icon belongs to Master. Nothing in the script or the arena program ties it to the Expert course.

The prize is split in two. The item is added by the arena program, and only when the contest ended on its thirteenth fight and an "already awarded" flag is clear. The flag is set by the lobby's victory scene, which only asks: was this a Master contest, and was it won?

Early in the story the Master course is cut short to 8, 11 or 12 fights. Winning the shortened course is still a win as far as the victory scene is concerned, so it sets the flag and plays the presentation - the announcer names the Icon. But the arena saw fewer than thirteen fights and added nothing. From then on the flag is set, and the arena skips the item every time, including after a full thirteen-fight win.

The last of the three story flags that lengthen the course is set inside Jette's Fortress. That is where "before defeating Jette" comes from.

The tests overwrite one another in order, so the last missing flag decides: with all three missing the course runs 12 fights.

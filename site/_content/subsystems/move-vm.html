Move-table opcode VM

A tiny per-actor animation engine. Every actor - a party member mid-art, a summon's body part, a swinging door, a looping torch flame, a spell's beam - owns a "move buffer" and a program counter into it, and every frame the actor tick runs opcodes out of that buffer until one of them stops. It is what turns a move record into motion, pose and animation-bank changes, tween setup and per-actor flag writes, and it lives in the always-resident main executable.

How a frame runs

The u16 trap

Operands, sizes and the PC all count in 16-bit units. The other Legaia VMs use byte streams, so a disassembler that assumes bytes here decodes garbage from the second instruction on. Handlers that look like no-ops in decompiled C still advance the PC - the increment hides in a branch-delay slot.

Every record starts [i16 model_sel][u16 reserved] before its bytecode: −1 makes a transform node, 0x4000 / 0x4001 a render-mode node, ≥ 0 a library mesh. Bytecode ends at op 0x08.

The loop pair, the child spawn and the render-mode-4 emitters

Loops. 0x18 latches its own PC into +0x88 and a count into +0x8C; 0x19 decrements and jumps back to the body start (past the 0x18) until the count underflows, so a count of N runs the body N + 1 times. A count with bit 0x4000 never decrements - the infinite loop ambient effects idle on. 0x1A / 0x1B are the same on a second register pair, so programs can nest two loops.

Child spawn. 0x25 seats a child part from the per-scene prescript stager table at the parent's world position and render slots - how one move program spawns another as a sub-actor.

Render-mode-4. 0x42 sets render mode 4 with selector 0x2000 (the random-walk ribbon: lightning, beams, whips) and fills the ribbon's inputs; 0x23 is the 0x4000 sprite sibling; 0x13 the default emitter. On the disc, 0x42 appears only in slot-B cast / summon images (effect VM).

The field extension (opcode 0x2F)

Op 0x2F reads a 16-bit sub-opcode and dispatches through a 61-entry jump table in the field overlay (FUN_801D362C, table 0x801CE868). The sub-opcode is bounds-checked before the jump, so there is no out-of-bounds path. Only the field overlay carries this dispatcher, so battle-side move records cannot reach it. Every in-range sub-op has its own width (2 to 16 words); there is no size-1 arm. The widths sit in branch-delay slots, so the decompiled C reports the bounds-check default for every arm - the reason an earlier reading of the HSV ramps as a "size-1 density trick" was wrong. Per-sub-op detail: move-vm-overlay-ext.md.

A sibling that is not the move VM: puzzle rooms run a discrete tile-board mode in the same overlay, a byte-cell grid where each d-pad press moves exactly one cell. It is not town locomotion (that is field locomotion).

Screen-effect widgets (PROT 0900)

The resident slot-B overlay PROT 0900 hosts four 2D screen widgets - the presentation layer of iris wipes, letterboxes and tweened panels. They are ordinary actors on the effect list with a per-frame handler, and all share one four-mode interpolator.

KindHandlerPer-frame behaviour

panelFUN_801F849CFive-channel tween, one or two textured quads
letterboxFUN_801F8A34Two black bands plus two gradient feather strips

On the disc only the ten ending-sequence (ed*) scenes invoke the family, through field-VM op 0x43 sub-ops 0x10..0x15. The mask widget was once read as a summon-part renderer; a live capture of a Gimard cast showed the summon draws as an ordinary battle actor through the rigid-keyframe pipeline (battle action).

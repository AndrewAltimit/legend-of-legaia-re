Renderer (Legaia TMD)

How Legaia puts 3D on screen. Every town, cave and battle arena you see is a set of meshes in a custom variant of Sony's TMD model format, pushed through the PS1's geometry coprocessor by the game's own drawing routine and painted by the GPU into 1 MB of video memory. This page explains that path, what "lighting" actually is in Legaia (a colour baked into every polygon - there is no light source), and how the clean-room Rust port reproduces the look over wgpu.

How it works

When you stand in a town, the picture is a few hundred small meshes - houses, fences, terrain tiles, the party - each a list of triangles and quads. The game walks each mesh one primitive group at a time, asks the GTE to rotate, translate and project the corner points to screen space, wraps the result in a GPU packet, and drops that packet into an ordering table bucket chosen by its depth. When the frame is done, the GPU walks the table from far to near and paints. Textures and palettes live as rectangles inside video memory, addressed by their top-left corner.

Legaia's TMDs are almost the standard format Sony documented, but with a custom primitive-group header layout and a custom renderer. Each primitive group has an 8-byte header [u16 count, u16 flags, u8 olen, u8 ilen, u8 flag, u8 mode] followed by count × ilen*4 bytes of per-prim data. The vertex-index byte offset within each prim isn't a fixed field - it's looked up from a 6-entry descriptor table indexed by ((flags >> 1) - 8) >> 1. The descriptor table also encodes which OT-packet shape the renderer emits.

The clean-room engine port emulates PSX VRAM as a 1024×512 R16Uint texture. The fragment shader reads the texture coordinates and CLUT base from the per-primitive bind, decodes 4/8/15bpp, indexes the CLUT, and outputs the final colour. That gives the same per-prim mode-switching the PSX hardware does, but in a single GPU draw call.

Per-mode descriptor table

A mesh can mix flat and smooth-shaded, textured and plain-coloured polygons. Instead of a switch statement, the renderer reads a tiny six-row table that says, for each primitive flavour, how the bytes are laid out and which GPU packet to build. Getting this table right is what makes every mesh on the disc parse.

The renderer treats the 8-byte-stride table at 0x8007326C as a packed {u32 first; u32 second} per row, selects row = ((flags >> 1) - 8) >> 1, and reads byte3 = first >> 24 (the shape selector, & 3 = F/FT/G/GT) and byte4 = second & 0xFF (the base vertex-index offset in u16 units):

flagsrowraw 8 bytesbyte3 (shape)byte4 (vtx off)
0x10/11004 00 00 05 07 00 00 000x050x07
0x12/13109 00 00 07 06 00 00 000x070x06
0x14/15204 00 00 00 02 00 00 000x000x02
0x16/17306 00 00 02 06 00 00 000x020x06
0x18/19407 03 00 01 07 00 00 000x010x07
0x1A/1B509 03 00 03 0B 00 00 000x030x0B
0x20-27(re-uses rows 0-5 via the same (flags>>1)-8 math)

The low 2 bits of byte3 select the OT packet shape (0 = flat untextured, 1 = flat textured, 2 = gouraud untextured, 3 = gouraud textured); the quad bit (flags>>1)&1 picks tri vs quad. Byte1 of first is the per-vertex colour base: 0 = light-source-lit prim (no baked colours - the texture block sits at offset 0 and per-vertex normals trail the vertex indices), 3 = baked per-vertex colours precede the texture block. See formats/tmd for the full per-mode record layout, and Lighting below for what the colour block is for.

The same table is exposed as a typed lookup at crates/tmd/src/descriptor.rs: Descriptor::for_flags(flags) returns the resolved PacketShape (F3 / FT3 / G3 / GT3 / F4 / FT4 / G4 / GT4) and the per-prim vertex-index offset, with the shading mode and texture flag as typed fields so consumers don't re-derive the bit math.

Lighting

Legaia's towns look lit - shadowed alleys, bright plazas, a warm glow around lamps - but none of that is computed at run time. The artists painted a brightness into every polygon when the mesh was authored, and the console just multiplies the texture by it. There is no sun, no lamp, no light direction anywhere on the field path. This matters for the port because any "helpful" light added by a renderer makes the game look wrong (banded skies, washed-out interiors).

Retail runs no light source on the field path. SCUS_942.54 has two TMD renderers over this table - FUN_8002735C and its light-source sibling FUN_80029888 - and between them they issue exactly one GTE colour op: DPCS (cop2 0x780010; real command 0x10, sf = 1), the depth cue. Neither ever issues NCDS / NCDT / NCS / NCT / NCCS / NCCT / CDP / CC, so no light matrix is consulted and no vertex normal is transformed. The GTE light matrix L (cr8-12) and light-colour matrix LC (cr16-20) are populated (FUN_8005B648 = SetLightMatrix, FUN_8005B678 = SetColorMatrix), but the only functions that consume them - via NCCS/NCCT - are the world-map slot-4 mesh handlers FUN_8004409C / FUN_8004423C / FUN_80044434 / FUN_800445B0.

Field shading is instead baked into the TMD. Every primitive carries a colour word [R][G][B][GP0 code], the code byte being one of 0x20 (F3), 0x24 (FT3), 0x28 (F4), 0x2C (FT4), 0x30 (G3), 0x34 (GT3), 0x38 (G4), 0x3C (GT4), each optionally | 2 for the semi-transparent variant. A flat prim stores one word; a gouraud prim one per corner (only the leading word carries the command byte). The renderer loads it into the GTE's RGBC, runs DPCS, and hands the result to the GPU as the packet colour, which the GPU blends with the texel:

out = texel * colour / 128

0x80 is therefore the neutral colour (texel unchanged), below darkens, and above brightens - up to 255/128 ≈ 2×. That factor-of-two headroom is why retail's field has more contrast than an unlit render: across the field scenes' environment packs, roughly four fifths of colour components sit below 0x80, with the rest at or above it. An untextured prim has no texel and is simply filled with the colour.

DPCS blends that colour toward the far colour (RFC/GFC/BFC, cr21-23) by IR0: out = c + (fc - c) * IR0. Both are staged per drawn object, and by FUN_80043390, which also stages the ambient / background colour (RBK/GBK/BBK, cr13-15 - consumed only by the NC* ops, so inert on the field path). An unfogged field scene passes IR0 = 0, making the depth cue the identity: a retail town0c capture's GTE register file shows a GT3 prim's three baked corner colours come out of the depth-cue op byte-unchanged.

The trap that keeps a synthetic light alive in a port: an unbound colour attribute defaults to white, and white is texel × 255/128 - so a missing colour stream reads as "too bright", not as "unlit". The site's WebGL shaders upload the per-vertex packet colour on both their paths for exactly this reason. Host-to-host drift of this kind is tracked on the tooling pages (docs/tooling/host-drift.md).

Frame setup and the screen

Before any mesh is drawn the game sets up its scratch buffers, tells the GTE where the centre of the screen is, and picks which of two draw environments this frame paints into. The numbers here are the ones a port has to copy exactly, or the 3D and the 2D menus stop lining up.

The screen the GTE projects onto is 320×224, not 320×240

QuantityRetail valueWhere it is read

Draw offset(0, 4) / (0, 244)GPU OffsX/OffsY, alternating buffers

All five hold across a save-state corpus spanning field, battle, battle load and the dance minigame, on both halves of the double buffer; H is the counter-example that makes the constancy a finding (it is written per phase - 256 in battle, 512 in the field). So OFY = 114 is not an off-centre offset in retail's own frame - it is 228 / 2, dead centre of the display window and two rows below the centre of the 224-row drawing area. It reads as "six pixels above centre" only against a 240-row frame, which retail never draws.

What the port does with that. Both hosts keep a 320×240 logical screen because every 2D rect (HUD panels, dialog boxes, menu windows) is a retail draw-area coordinate copied verbatim. The projection therefore puts the GTE origin on row 114 of the port's frame too, as a constant w-scaled term on clip y, GTE_OFY_NDC_BIAS = (120 - OFY) / 120, in both battle_vp (shared with the browser play page) and psx_camera_mvp (native window). The residual is the frame height itself: retail's picture occupies 224 / 240 of the port's vertical extent, so everything reads about 7% smaller - closing that is a screen-convention change, not a projection one. Oracle: crates/mednafen/tests/gte_projection_real.rs.

Graphics scratch + the "present" that isn't

  • FUN_800271A8 - graphics-scratch init. Allocates two 0x8000-byte buffers into 0x8007BB04 / 0x8007BB08, fills the second with a 0x4000-entry u16 depth ramp, then resets the GTE / primitive buffers. Runs once before any emitter has a buffer to write into (ghidra/scripts/funcs/800271a8.txt).
  • FUN_8003DAA8 is not a present driver despite the counters it advances: it is the CD load-kick / completion driver the asset queue drains through, and the four routines it calls are the libcd family (LBA→BCD-MSF, the CdControl retry wrapper, the ready / sync callback installers). See boot for the CD-read API.

The battle backdrop is drawn twice

The arena shell behind a fight is one TMD that retail draws twice, the second copy under a per-stage transform (legaia_asset::battle_backdrop). Both hosts append the second copy at build time (VramMesh::append_scaled), so a single draws.push is not evidence the shell is drawn once. The two hosts use different mesh builders for it (native: tmd_to_vram_mesh + a separate colour-mesh draw; browser: tmd_to_vram_mesh_field_hybrid with the untextured half folded in as a flat RGBA channel) - a real split, but not a shading divergence, since both carry the same per-vertex colours and ABE bit. The browser host reaches any formation directly through the wasm debug_force_battle(row) mirror of native --battle <ROW>.

TMD pointer table

Loaded meshes are registered in a small pointer table so that actors can be spawned from them by index - the party's five field meshes sit in the first slots. Four retail functions read the table, and all of them are setup, not drawing.

FUN_80026B4C writes registered TMDs to *(int **)(idx * 4 + 0x8007C018). Consumers in retail:

FunctionRole
FUN_80021B04Actor-spawn helper, builds per-actor OBJECT pointer table.

FUN_8001EBECPer-frame OBJECT[10/11] swap (pose select for player TMDs).
FUN_8001E890"DATA_FIELD player loader" - but it does not load the player meshes. Its retail-PROT branch targets PROT 876 (player_data), a streaming VAB + TIM_LIST + SEQ payload. What it writes into DAT_8007C018[0..2] is the post-install group-count cap (entry[+0x08] = 10) and the equipment-conditional patch dispatch into FUN_8001EBEC. The character TMDs themselves come from PROT 0874 (befect_data) section 0 - see character-mesh.

The per-actor OBJECT[i] is a 28-byte struct copied into actor[0x44][i+1] from tmd + 12 + i*28 - sizeof(OBJECT) = 28.

Field meshes are one thing; battle player meshes are another. In battle each character is assembled from the equipment-id sections of the player battle files (PLAYER1..4, extraction 863..866), not loaded whole from PROT 0874 or 1203. See battle-data-pack.

VRAM emulation in the engine port

The PS1 keeps every texture and every palette in one shared 1 MB image. A polygon doesn't say "use texture X" - it says "read pixels from this rectangle and look them up in the palette at that row". If two textures land on the same rows you get rainbow noise, and Legaia's palettes are scattered across many PROT entries. Most of the port's VRAM work is deciding which bytes to upload so a scene looks like retail rather than a kaleidoscope.

crates/engine-render emulates a 1024×512 R16Uint VRAM page so the per-prim CBA/TSB selectors (CBA = the prim's CLUT base address, TSB = its texture-page selector) plus 4/8/15bpp + CLUT decoding can happen in a fragment shader. The viewer uploads every sibling TIM (a TIM is the PS1's standard texture-image format, carrying its own VRAM destination coordinates) so multi-page meshes render correctly.

CLUT data scatters across the entries of PROT.DAT (the disc's single big archive; nearly all game data lives in its 1233 numbered entries) - many character meshes reference CLUT rows that live in different PROT entries from their TMD source. Engine-side scene loads resolve it from the disc: SceneResources::build_targeted walks the scene's own entries plus the shared and boot-resident blocks, with no hand-supplied directory. The asset-viewer's --vram-extra-dir is a viewer flag for browsing extracted tim_scan/ dirs that are not tied to a CDNAME scene; it is not on the engine's scene-load path. See Asset loader.

Targeted VRAM upload

The TIM corpus on a single PROT entry can run into the hundreds. Uploading every TIM into the 1 MB VRAM clobbers regions a different mesh references as its CLUT row, and the paletted decode reads image pixels as palette entries (rainbow noise). The asset viewer and the tmd CLI both go through legaia_tmd::vram_targeted::build_vram_targeted: for every TIM, the image block and CLUT block are decided independently against the prim-target rectangles for the current TMD - a TIM can contribute one block, both, or neither.

legaia_tim::vram::Vram::prim_texture_status then classifies each prim's (cba, tsb, uv) lookup as Ok / MissingClut / ClutDepthMismatch { populated_width, expected_width } / MissingTexturePage so the viewer can drop bad prims at mesh-build time and the CLI can explain why a prim was dropped (the most common case is a 4bpp prim referencing a CLUT row that's been populated as a 256-entry 8bpp palette by a different TIM). The same filter is wired into engine-side scene loads through ResolvedTmd::build_filtered_vram_mesh, so battle / field actor meshes inherit the same cleanup.

Engine-side targeted upload + shared blocks

SceneResources::build_targeted is the engine-side mirror of the asset-viewer's targeted-upload path: it parses every TMD in a scene, collects the union of all prim-target rectangles (CLUT rows + texture-page UV bboxes), then walks every TIM and decides per-block whether to write it. This matches what the retail field loader does - DMA only the texture bytes the current scene's meshes need - and avoids the CLUT-row collisions that drop most textured prims under the naive "upload every TIM" path.

build_targeted also accepts a list of shared CDNAME blocks via the FIELD_SHARED_BLOCKS constant (init_data + player_data) - the blocks the retail engine keeps resident across field-scene transitions. player_data (PROT 876) is a streaming file - VAB + an empty TIM_LIST + a SEQ trailer - and carries neither the character meshes nor the player textures. Both come from PROT 0874: §0 is the 5-TMD character mesh pack that populates DAT_8007C018[0..4], and §2 is the field-character texture pack whose entries 1/2/3 are the Vahn/Noa/Gala atlas pages at texpage (832, 256) with per-character CLUTs on row 478. See character-mesh § Textures. init_data (PROT 0) holds shared UI / sprite tiles. The shared blocks are uploaded first, so scene-local TIMs win any slot collision (mirrors the retail boot-then-scene order).

SceneHost::enter_field_scene calls build_targeted with the field shared blocks by default; the legacy SceneResources::build / build_with_shared paths remain for tests and engines that want the unfiltered upload for diagnostic purposes.

Render vs parity: targeted vs DMA-every-TIM. The targeted upload is a render optimisation. The retail field loader DMAs every scene TIM to VRAM regardless of which prim samples it, so for the VRAM parity oracle BuildOptions { upload_all_tims: true } switches build_targeted to build_vram_full_from_buffers: every parseable collected TIM is written to its header destination (images first as sequential DMA, then CLUTs with merge-zeros to preserve the row-479 palette split). The flag defaults false, so the render path is unchanged. The TIM scan walks both raw entry bytes and any LZS-decompressed sections (legaia_asset::tim_scan::scan_entry), so battle / level-up bundles that pack their character TIMs inside an LZS container need no raw-byte fallback.

History: the player atlas was once placed in PROT 876

An earlier reading placed the player texture atlas in PROT 876 at fb=(768, 0) with CLUT (0, 500). That is falsified: PROT 876 is the streaming player_data file and holds no character TIM. Don't re-derive it - see do-not-re-walk.

Two-pass upload ordering

Inside build_vram_targeted_from_buffers the targeted upload runs in two passes:

  1. Image pass writes every useful TIM image block (image overlaps a mesh's tex page region AND does NOT overlap another mesh's CLUT row).
  2. CLUT pass writes every useful TIM CLUT block (CLUT overlaps a mesh's CLUT row), unconditionally with respect to image-page collisions.

The ordering matters: a per-prim clut_collides_page suppression heuristic drops legitimate palette rows whenever any mesh's UV bbox happens to brush the CLUT row's y-coordinate - the town01 character TMDs' 256-pixel-wide palette at y=479 overlaps a separate scene mesh's texture-page rectangle. The image-then-CLUT pass order keeps the palette rows that PSX games place on the bottom of texture pages coherent without any per-prim heuristic.

Field colour-mesh pipeline (untextured prims)

Not every polygon has a texture; fences, crates and many props are plain painted colour. Untextured TMD prims (flat / gouraud per-vertex-colour primitives, no UVs) don't go through the VRAM-textured mesh builder. The per-prim colour block is decoded (F4/G3/G4 layouts + the 00 01 03 02 quad winding remap; no per-prim normal), legaia_tmd::mesh::tmd_to_color_mesh builds a ColorMesh, and the renderer's vertex-colour pipeline (scene_color_mesh_pipeline, Renderer::upload_color_mesh, Scene::color_draws) draws them. A mixed mesh renders both halves at the same placement: textured prims through the VRAM pipeline, untextured through the colour pipeline.

One further case goes through the textured pipeline with a flat-material trick: a mesh sampling texpage (960, 256) + CLUT (64, 510), whose source is the boot-resident system-UI TIM bundle (the prot::timpack at raw PROT TOC entry 0, below the extraction index space; the atlas at PROT.DAT[0x11218] supplies the page and, via FUN_800198E0's flat-strip CLUT semantics, the 256-entry strip on row 510). The pre-pass uploads the whole pack (legaia_asset::system_ui_bundle, underlaid beneath scene uploads). The same CBA/texpage pattern recurs in other scenes' env packs (rikuroa env slots 50/51/63, town01 slots 21/26/74); the prims sample a constant mid-grey texel patch. See row-510/511 strip band.

Diagnostics: CLUT-trace, VRAM oracle, depth mismatch

Two legaia-engine subcommands surface where the engine's loader still has gaps against a captured runtime VRAM. Both work straight off PROT.DAT + CDNAME.TXT, no pre-extracted tim_scan/ tree.

  • legaia-engine clut-trace --scene <name> --disc <bin> [--runtime-vram <bin>] walks every dropping MissingClut prim, groups by (cba, depth), and reports which PROT entries carry a TIM whose CLUT block covers each missing row by rectangle containment (PSX TIMs commonly pack 16 distinct 16-entry palettes into one 256-wide CLUT block). --runtime-vram distinguishes an engine loader gap from a row absent at runtime too.
  • legaia-engine vram-oracle --scene <name> --disc <bin> --runtime-vram <bin> [--diff-png <path>] [--tiles] rebuilds the scene's engine VRAM and reports per-band overlap counts plus an optional 64x64-tile breakdown. The standalone build picks its load kind via oracle_load_kind, mirroring the live enter_field_scene choice, so world-map scenes (map\d\d) get the kingdom slot-0 terrain atlas instead of a phantom gap.
  • legaia-engine info --scene <name> --tmd-stats reports per-TMD kept / miss_clut / depth_mm / miss_page counts; --vram-png / --vram-bin dump the engine VRAM; --runtime-vram + --vram-diff-png write a colour-coded diff (red = runtime has, engine missing; green = engine extras; blue = both populated but different).

CLUT-depth-mismatch threshold. Vram::prim_texture_status flags ClutDepthMismatch when a CLUT row is populated past what the prim's colour depth could legitimately fill: for 4bpp prims the threshold is 16 * 16 = 256 entries (16 packed 16-entry palettes, picked by the prim's CBA low 6 bits - the standard Legaia character-TIM layout); for 8bpp it's 2 * 256. Anything past that indicates another TIM's image bytes have spilled onto the CLUT row. The targeted-upload path prevents this spillage, so engine-side scenes hit the threshold only when a regression breaks the per-TIM block arbitration.

Texture-window register (GP0 0xE2)

Renderer::set_texture_window(mask_x, mask_y, off_x, off_y) maps to GP0(0xE2) "Texture Window setting": four 5-bit values in 8-pixel steps that clamp / wrap texture-coordinate sampling to a smaller window inside the texture page. Default is all-zero (no-op). Retail Legaia leaves the register at zero almost everywhere; the API is wired so future runtime LoadImage / DMA-to-VRAM trace work can replay the register state faithfully. The fragment shader applies coord = (coord & ~(mask*8)) | ((offset & mask)*8) before texture-page lookup.

Full-scene colour grade

The opening prologue plays in gold sepia and every scene entry fades up from black. Both are colour grades applied over the whole frame, and both ride the same staging in the port.

Renderer::set_color_grade(gold, strength) stages a per-frame (gold_rgb, strength) into every field MeshUniforms; the textured / VRAM / colour mesh shaders' apply_grade cross-fades each shaded pixel toward rgb · gold by strength (0 = no-op; text/UI overlays are never graded). For the prologue's gold sepia (opdeene / opstati / opurud) the multiply is superseded by the palette-collapse mode (Renderer::set_palette_grade): retail applies the grade to the loaded assets - every uploaded CLUT entry rewritten to L = max(r, g, b) → (L, max(L−1, 0), L >> 1) and the loaded TMD colour words collapsed to gold · max(rgb) - and the engine's shaders apply the identical law per decoded texel / packet colour. The gold coefficients (1.0, 0.94, 0.43) are the measured amber-family ratio (see cutscene for the capture that pins it). Driven by World::scene_color_grade; every non-prologue scene renders bit-identical to the ungraded pipeline.

The scripted screen fade (field-VM op 0x4C 0x12 global tint) reuses this staging: the host multiplies the fade tint into the staged grade gold and into the depth-cue far colour, so both branches of the shaders' cue mix carry it. A neutral tint stages the identity values. See cutscene.

Retail's per-render-node depth cue additionally crushes far-field blue. Renderer::set_depth_cue_ramp(far, near_z, far_z, max_ir0) stages that pull as a view-depth IR0 ramp - ir0 = clamp((z − near_z) / (far_z − near_z), 0, 1) · max_ir0 - blended in retail's order (DPCS on the packet colour before the GPU texel multiply). Driven by World::scene_depth_cue on the same prologue gate; cleared everywhere else.

Colour space: PSX framebuffer values end to end

Every colour the engine handles - texels, CLUT entries, vertex colours, menu inks, grade coefficients - is a PSX framebuffer value: display-referred, exactly what the console clocks out to the display. Nothing on the path converts colour spaces, and nothing may.

  • The swapchain is presented through a UNORM view (choose_surface_format), never sRGB. An sRGB attachment treats the shader's output as linear and applies the linear→sRGB transfer on store, lifting every midtone: retail's mid-grey (5-bit 16 → byte 132) would present as 190 - a visible, global wash-out.
  • Sampled RGBA textures (TIM-decoded uploads, the font atlas) are Rgba8Unorm for the same reason.
  • The last stage of every 3D shader is psx_dither, which quantises to 5 bits and expands with (c5 << 3) | (c5 >> 2). That quantisation only reaches the screen if the attachment stores the byte unmodified.
  • PSX semi-transparency (psx_blend) blends raw 5-bit values on retail, so the fixed-function blend must run in the same display-referred space.

Pinned by tests::color_space: the attachment is never sRGB for any surface the adapter might offer, and a known BGR555 texel presents at the byte retail puts on the wire.

Coplanar surfaces: retail's ordering model, the port's depth policy

A PS1 game never asks "which pixel is in front?" - it sorts whole polygons by average depth and paints far-to-near. Legaia's artists leaned on that freely: decals lying exactly on walls, floor tiles overlapping their neighbours, and walls modelled once per visible side. A modern depth-tested renderer turns each of those into flickering "z-fighting" as the camera moves, so the port has to reproduce the painter's outcome without the painter's algorithm.

Retail has no depth buffer. Every primitive is inserted into the ordering table by its mean GTE Z and the table is drawn back-to-front, so coplanar surfaces resolve painter-style: a small decal on a large base surface usually lands in a nearer bucket than the base (its mean Z is local; the base's mean averages a deeper span); prims in the same bucket resolve by insertion order (AddPrim is a head insertion, so the earliest-emitted prim draws last, on top); and double-sided prims never conflict at all, because the per-prim NCLIP test rasterises only the camera-facing copy.

The port resolves each class at the level it occurs, shared by the native renderer and the site's WebGL viewers: double-sided pairs are marked at mesh build (legaia_tmd::mesh::mark_double_sided_pairs) so only the facing copy draws; in-mesh decals and cross-draw overlaps get a non-commensurate depth lift so the retail winner stays the winner. A disc census over town01 / rikuroa / jou finds a couple of hundred double-sided pairs per cave/town environment pack, dozens of exactly-coplanar decal prims inside single meshes, and hundreds of overlapping terrain-tile pairs - the scene data is full of them. Full policy in docs/subsystems/renderer.md § Coplanar surfaces.

The port is not one program: the same engine draws through the native window, the browser play page and the browser field/minigame viewers. A rendering fix that lands on one of them and not the others is invisible in a code diff, which is why the surfaces are enumerated here.

engine-render links wgpu, so the browser crate cannot depend on it: every kernel that lives there is native-only as code, and a browser twin has to be a second implementation in GLSL or JS. Kernels living in engine-core, engine-vm or legaia-tmd are one implementation all five surfaces can call - and those are the ones a checker can pair by name. Not every asymmetry is a defect: set_psx_mode and dynamic lighting are opt-in and default off, so a browser with no toggle renders the same default the native window does.

Placement rotation is three angles on every surface

A .MAP object record carries three authored angles (+0x08 pitch, +0x0A yaw, +0x0C roll) and retail composes all three as Rx * Ry * Rz. The yaw-only builders take a negated yaw because their inline Ry is transposed and the two negations cancel - a cancellation specific to Ry, so a tilted placement cannot go through them at all and has to be handed a whole model matrix. A minority of placements carry a nonzero pitch or roll, lumpily distributed (juui1 tilts all nine of its by a quarter turn about X), and terrain cells tilt more often than the placed layer. A surface that reads only the yaw loses the scene on those maps, not a curiosity.

Rendering knobs: what is faithful, what is a choice

If you play the port next to a real PS1, what should look identical and what is allowed to look better? The rule is short: the game's shading - which polygon is which colour - is retail by default, and the PS1's rasterisation artefacts - wobbling vertices, the dither pattern - are off by default but one switch away.

Simulation is faithful, with no opt-out. Shading defaults to retail; rasterisation defaults to clean. "Faithful" and "default" are not the same axis, so each toggle is listed with both:

Two things routinely get mis-stated about this table. Lighting is not a psx_mode knob, and the default is already faithful - the field/town meshes go through the VRAM-mesh and vertex-colour pipelines, which draw the TMD's baked colour words with no light source at all, exactly as retail does (see Lighting). And affine UVs are not gated either - they are always on: @interpolate(linear) is a static qualifier on the vertex-output struct, not a uniform-driven branch.

set_psx_mode - vertex snap + dither

Renderer::set_psx_mode(true) enables the two strict-PS1 rasterisation artefacts that are not on by default. In legaia-engine play-window, opt in with LEGAIA_PSX_RENDER=1.

  • Sub-pixel vertex snap ("vertex jitter"). Clip-space x / y are snapped to integer pixel positions inside the vertex shader (NDC → pixel grid → NDC round-trip). Reproduces the GTE's per-vertex sub-pixel-truncation jitter that gives PSX rendering its characteristic shimmer on slow-moving geometry.
  • 15-bit ordered dithering. Packing the 24-bit shaded colour into the 15-bit (BGR555) framebuffer, the PSX GPU adds a signed 4×4 ordered-dither offset per pixel before truncating each channel to 5 bits. The shader helper PSX_DITHER_WGSL (prepended to every shaded 3D shader) reproduces it and mirrors the unit-tested CPU psx_dither module; the composed shaders are naga-validated in the test suite.

Retail law: dither is on at boot and script-controlled. The GPU's dtd bit lives in the DRAWENV byte at +0x2A of each of the two draw environments the frame-begin driver swaps; the initialiser stamps it 0, but the per-frame refresh overwrites it from a global that boots at 1, and a scene script can flip it at will. Port default: off, by choice. That is a project decision about the default look, not a reading of the executable - the retail bit is what the toggle reproduces when you turn it on.

Affine UV interpolation (always on)

Per-vertex UVs interpolate linearly in screen space, with no perspective-correct division, on every path in every mode. This reproduces the texture warping you see on retail surfaces with steep depth gradients: GP0(0x24)-class triangle commands transmit only (u, v) per vertex, and the rasteriser does not divide by 1/w. WGSL @interpolate(linear) gives the same behaviour; the baked per-prim colour carries the same qualifier, because PSX gouraud interpolation is affine in screen space too. Texture page (tsb) and CLUT base (cba) stay @interpolate(flat) - per-primitive in retail because GP0(0x24) sets them once per draw call.

Lighting: baked by default, dynamic by opt-in

PSX texture blending is the lighting. Each vertex carries the TMD prim's baked colour word, and the fragment shader modulates the texel by it exactly as the GPU does - texel * colour / 128 - then applies the DPCS depth cue. Helpers psx_modulate / psx_depth_cue live in the shared shader prelude and are mirrored, and pinned, by the CPU psx_light module.

Renderer::set_dynamic_lighting is the one lighting knob, and it is off by default - off is retail: the disabled path is pixel-identical to the faithful baked-shading render. Enabled (--dynamic-lighting), the VRAM / colour mesh shaders layer a soft warm directional light (off the smoothed per-vertex normals) plus a screen-centred light pool over the baked colours, gain capped at ~1.3×. Its sub-toggle set_dyn_shadows (default on while lighting is on; --no-dyn-shadows / Y key) adds real point lights with shadow maps at the scene's own light-emitting props - derived from the mesh data itself, since what a player reads as a candle or wall lamp is an additive-blended flame prim or a bright, warm-modulated lamp mesh (crates/engine-render/src/scene_lights.rs). Both are explicitly non-retail enhancements.

Camera-occlusion fade (see-through walls)

Retail never has a wall between you and your character because every scene's camera was placed by hand. The port's single follow camera does, so Renderer::set_occlusion_fade dissolves scene fragments that would bury the character into a screen-door dither whenever the host stages a focus (set_occlusion_focus, the player's clip-space position). The renderer default is off (off is retail, pixel-identical); play-window turns it on by default as the clearly better experience (--no-occlusion-fade or F4 restores authored-framing-only). The dither reads naturally next to the PSX ordered dither, needs no CPU sorting, and keeps depth writes intact.

set_semi_blend - semi-transparency (ABE / STP / ABR)

Water, glass, glows and magic effects are drawn see-through on the PS1 by blending the new pixel with what's already on screen. Independent of psx_mode, and on by default. Retail's GPU always blends ABE prims, so field water (e.g. the Hunter's Spring fountain), glass and additive effects composite correctly in the clean render too. Turning it off draws every ABE prim fully opaque - the harsh-edged "solid water" look.

A prim is semi-transparent when its packet ABE bit is set (TMD group mode byte bit 1; packed into bit 15 of the per-vertex TSB attribute). The blend equation comes from the texpage ABR bits (TSB bits 5..=6): mode 0 0.5B + 0.5F, 1 B + F, 2 B - F, 3 B + 0.25F. For textured prims the choice is per texel via the BGR555 STP bit, so the engine runs an opaque pass (discarding STP texels of semi prims) plus a per-ABR-mode blend pass over re-drawn semi triangles; untextured ABE prims blend all pixels via a per-vertex blend word (psx_blend::pack_blend_word). Blend ordering is per primitive, far-to-near on the clip-space w depth key (psx_blend::prim_depth_key - the GTE avg-Z the retail OT bins on), with equal keys drawing later-submitted-first (the retail LIFO OT-bucket order). Full detail in docs/subsystems/renderer.md.

GTE math module + cop2 register-state emulator

The GTE is the PS1's fixed-point geometry chip, and its rounding and saturation quirks are what make retail vertices land where they do. The port carries a bit-exact software model of it - not on the hot render path (that is f32 wgpu math) but as the oracle the render path is measured against.

A fixed-point GTE math module at crates/engine-render/src/gte.rs mirrors the retail accumulator shape (q3.12 rotation matrices, q19.12 translation vectors, i64-widened multiply-add) and exposes the higher-level primitives - a Camera bundle running RTPT end-to-end with PSX-correct saturation, nclip back-face rejection, avsz3 / avsz4 OT-bucket selection, and a small CPU rasteriser scaffold for validating captured traces.

The same module ships a register-state emulator Gte mirroring the PSX cop2 register file: V0..V2 input vectors, MAC0..MAC3 wide accumulators, IR0..IR3 saturated shorts, the SXY / SZ / RGB FIFOs (3 / 4 / 3-deep), OTZ, and the FLAG sticky-saturation register with hardware-matching bit positions (gte::flag_bits). Control registers cover the rotation / light / light-colour matrices, translation, H, OFX/OFY, ZSF3/ZSF4, DQA/DQB, and the back_color / far_color triplets. Each op charges its hardware cycle count into Gte::cycles.

Trace capture & replay harness

crates/engine-render/src/gte_trace.rs turns the cop2 emulator into a regression-test harness. GteSnapshot::capture serialises the entire register file to a plain struct that round-trips through restore; diff returns a typed list of per-field divergences. TraceRecorder wraps a live Gte and pushes one TraceStep per cop2 op (before / after snapshots). Traces serialise to JSON and Cop2Trace::replay runs each step against a fresh emulator, surfacing any divergence as a StepMismatch. legaia-engine gte-replay --trace FILE drives this from the CLI against a captured retail RAM trace.

No distance culling: every loaded body is drawn

The PS1 had to be stingy about what it drew each frame. The port doesn't: a town is a few hundred draws of a few thousand triangles, so it simply draws all of it, always, and sizes the camera's clip volume to hold a whole scene from any vantage.

There is no frustum cull, no draw-distance heuristic, no per-object radius test, and no LOD: the field draw lists (field_placement_draws, field_terrain_draws, the ground heightfield, the posed props, the NPCs) are resolved once at scene load and submitted whole on every frame. The one thing that can still remove geometry is the projection's own clip volume:

  • window::SCENE_FAR = 1e6 for every camera. A field map is 256 × 256 tiles of 128 units (~23k units on the diagonal), and the overworld walk camera composes a 6× world scale onto psx_camera_mvp, so eye-space depth there runs to ~140k. Raising the far plane costs no depth precision - the near plane sets the resolution.
  • window::scene_clip_planes(distance) gives the orbit-family cameras a near plane of distance * 0.005 clamped into [0.05, 8] - a few units in front of the lens on any scene-sized framing, small enough that a wall or floor body the camera sweeps over is never clipped, while the asset-viewer's unit-radius TMD previews keep a sub-unit plane.

Both are pinned by camera_tests in window.rs. The site play page (site/js/play-app.js) draws the whole scene every frame too - OCCLUDER_CULL = false. A per-frame occlusion cull exists in the code but is deliberately disabled: even the exact segment-vs-world-AABB form culls legitimate bodies, because placement boxes are axis-aligned over whole terrain tiles, walls and buildings, so the lens-to-player segment sweeps through a neighbour's box and blinks it out. (The see-through problem is solved per-fragment by the occlusion fade instead.)

History: the "stage geometry" detector

A "12-byte fixed prefix repeated at 20-byte stride" detector lives at crates/asset/src/stage_geom.rs. It is not real stage geometry - it matches Legaia TMD primitive data from a lit textured triangle group (descriptor rows 0/1, whose byte1 = 0 puts the texture block at prim offset 0): the "fixed prefix" is the prim's 12-byte leading texture block and the 20-byte stride is the group's ilen = 5 prim size. It is preserved as an exploration signal ("this buffer contains a TMD with effect-style primitives"); for geometry use the TMD parser (crates/tmd::legaia_prims).

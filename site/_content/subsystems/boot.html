Boot path

What the game does between disc-spin and the moment you press NEW GAME. The PlayStation logo fades, four publisher screens go by, the title wordmark appears, and behind that the game has read its archive directory, wired up its asset loader, streamed its first code overlay and entered a top-level "what mode am I in" state machine that runs for the rest of the session. This page follows that ladder, then the title screen itself, then what NEW GAME actually launches.

How it works

Everything below comes from tracing the game's code with a disassembler (Ghidra); the game shipped without symbols, so functions are named FUN_80xxxxxx after their RAM addresses in that trace.

Almost every PSX game has a built-in archive that bundles the small files together so the disc can stream them efficiently. Legaia's archive is PROT.DAT, and it has its own table of contents (TOC) - a list saying "entry N starts at sector S". Before the game can do anything, it has to read that table into RAM. That's job one.

Job two is wiring up a small asset-type dispatcher. The PROT entries don't all hold the same kind of data - some are textures, some are 3D meshes, some are dialog blobs, some are animation containers. Each entry's first byte is a type tag, and there's a single function that reads that tag and routes the bytes to the right per-format parser. Once the dispatcher's helper tables are populated, every later "load this entry" call works.

Job three: the boot code reaches a top-level game-mode state machine. This is a table where each slot is a function pointer for one major mode of the game - field, battle, world map, menu, cutscene, and so on. The mode index changes whenever the game transitions; the per-frame loop just calls "whatever the current mode's handler says". The title-screen overlay is loaded next, and its own little state machine runs the attract loop until you press a button.

One important quirk: the interpreter that drives every running script - the field VM - is not in the main executable. It lives in a RAM overlay (a chunk of MIPS code the game streams from the disc into RAM on demand) loaded when you enter a town or field map. That's why the boot path here is so short: most of the gameplay code isn't in SCUS_942.54 (the game's main executable on the disc) at all. Zero static callers in the executable therefore never means "dead code" - it means "the caller is in an overlay".

The main loop

Once the console has booted the executable, one function runs for the rest of the session. It sets up the hardware, primes a few tables, then spins: "call the current mode's handler; if the handler asked for a different mode, do the housekeeping and switch". That loop is the spine every other subsystem hangs from.

Init sequence

Each stage is bracketed by a dev-checkpoint print through the dev-string formatter FUN_800567A8 - compiled in but inert in retail.

  1. GPU / display - display-mode reset FUN_80057C44, SetDispMask off, a full-frame ClearImage (FUN_80058298) and queue flush.
  2. CD + XA - FUN_8003EE7C(0), FUN_8003F024, and the region / console probe FUN_8002B92C whose result (gp+0x550) selects the heap size.
  3. Sound - libsnd init FUN_80062310 + FUN_800644C0 over the sound-driver work area (see audio).
  4. Heap - FUN_8002B3D4(2, DAT_8007B414, size) with size = 0x134800 retail, 0x200000 when the probe reports an expanded-RAM dev console.
  5. Boot-scene name + CDNAME - the default scene string is opdeene; the build-mode halfword at gp+0x5AA (= _DAT_8007B8C2, see debug flags) is stored here, its only writer anywhere in the binary. FUN_8001D8FC then primes the CDNAME name table at 0x80088758 - a copy loop with no bound and no terminator, so long names come back mangled rather than truncated (CDNAME).
  6. Display env + mode machine - FUN_8001DAF8(0x400) (DISPENV / DRAWENV pair), FUN_8001DCF8(10) (the boot mode-init), FUN_8001E3B8(0xC800) (primitive-packet + ordering-table allocator), one priming frame pass, SetDispMask(1), then the overlay loader family (FUN_8003EBE4) streams the first overlay pair.

Master loop

While the current-mode register gp[0x524] is non-negative: call FUN_8003D254 with the frame counter, then dispatch (*(0x8007078C + mode*0x18 + 0x10))() - the handler word of the mode table. When a handler wrote a new mode index (gp[0x524] != gp[0x494]), the loop runs the transition housekeeping before the next dispatch: XA/CD stop (FUN_8003DE7C / FUN_8003ED04), GPU-queue flush, pad re-read (FUN_8001822C), and clearing the held-input / frame-state globals (gp+0x3D8, gp+0x538, _DAT_8007B938, gp+0x55C) before latching the new mode into gp[0x564] / gp[0x494]. A negative mode index exits the loop - a dev quit path retail never takes.

TOC loader

The archive directory is tiny - three sectors - and the game reads it exactly once. After that, "give me entry N" is a table lookup, and "give me h:\PROT\FIELD\town01\..." is a name lookup followed by the same table lookup.

Asset-type dispatcher

Every texture, mesh, dialog blob and animation the game ever loads passes through one function. It reads a type byte, looks up a handler in a jump table, and calls it. The boot path doesn't call it itself - it just makes sure the buffer pointers the handlers write to are valid before anything else runs.

Game-mode state machine

Walking around a town, fighting a battle, browsing the pause menu, watching a movie - to the game these are modes, and exactly one is active at a time. A mode has an INIT handler (runs for one frame, usually loading an overlay) and a per-frame handler. Switching modes is just writing a new index into one global (_DAT_8007B83C) and letting the main loop pick it up.

The 28-entry table at 0x8007078C is the dispatcher. Each 24-byte entry is a (name_ptr, …, handler_ptr, param) tuple; modes come in INIT / per-frame pairs (even index = init, odd = per-frame).

What the table tells you

  • Field gameplay is modes 2/3, not the world map. "MAPDSIP" (12/13, misspelled on the disc) is the world-map display mode. Its INIT FUN_80025DA0 is a transient sub-overlay swap: it saves the field overlay's slot-A head (0x801CE818, 0x4000 bytes), loads PROT 981 over it, calls its init 0x801CF4AC, and restores 0897's head on exit. PROT 981 seeds the scratchpad display list 0x1F800314 and runs a 21-state display SM that reads the still-resident 0897 body; the world-map controller proper (FUN_801E76D4) stays in 0897. See world map.
  • 12 of 14 per-frame handlers are one shared tick (0x80025EEC), parameterised by +0x14. Only mode 13 (world map) and mode 23 (menu) carry their own.
  • The pause menu runs under CARD (mode 23), not field mode 3. Every menu-open capture in the save library - equipment / status / options, field and town - holds game_mode = 0x17. The "CARD" dev label covers the whole menu / memory-card overlay surface (the field menu carries the Save flow). The engine mirrors this: BootSession holds the world in SceneMode::Menu while the menu is open, and the mode-trace oracle asserts 0x17 against the retail snapshot.
  • Three INIT handlers stage nothing. Modes 4, 16 and 20 skip the "reset, wait, load slot A, jump in" wrapper shape. Mode 4's whole body writes master mode 0 and returns (it bounces back to the debug menu). Mode 16 jals 0x801CE9C0 without loading anything - that address is a function entry in no image on the disc, so it executes whatever sits at slot A + 0x1A8 at the time: a retail-stripped dev path. Mode 20 is the live one: FUN_80055B6C is the battle scene setup and is resident in SCUS_942.54, so battle needs no overlay swap. Mirrored as engine_core::mode::mode_init_bare beside mode_init_stage.

Mode 23 runs no frame driver at all

Open the pause menu and the world stops - not because the menu asks it to, but because the menu's per-frame handler substitutes the whole frame. FUN_80025F74 calls the frame-begin pass, then FUN_80017978 where every other handler calls the master frame driver FUN_80016444, then the frame-end pass. FUN_80017978 is eighteen instructions carrying three jals - a debug chord inert on a shipped disc, an indirect call through the CARD actor's own tick handler, and a dev readout HUD - and none of them is 0x80016444. Since the master driver is where the actor tick passes live, retail advances no actor, no effect, no move VM and no animation while the pause menu is up, and draws nothing but what the CARD actor's handler draws. The port mirrors this in the engine rather than in its hosts: World::tick suspends the same passes whenever the mode table says the current mode skips the master driver - and keeps the frame-begin / frame-end passes (timed sound release, frame-cadence resolver) running underneath, as retail does.

The mode word does not determine the scene

Modes 24/25 OTHER host all five warp minigames, and the word says nothing about which one. Retail's discriminator is a second register, the signed halfword _DAT_8007BA34: the field VM's op-0x3E door-warp arm writes sub_id = op0 - 100 there in the delay slot of the same instruction pair that sets the mode word to 0x18, and the mode-24 init reads it twice to pick the overlay and its entry point. That init's last act sets the mode word to 0x19 and leaves the sub-id standing, so the pair stays readable for every frame the minigame runs. Two traps follow for anything translating the retail mode word into a higher-level state: the pair is the key, not the word (0x19 alone cannot tell fishing from dance), and 0x18 is the init half, which runs for a single frame - keying a live minigame on it never observes one. Full warp chain on the asset-loader page.

Next-mode field

Each table entry also carries an i16 next-mode field at +0x0A: -1 = the mode manages its own transitions, 0 = fall back to mode 0 on completion (the only two retail values). The word at +0x08 reads 0xFFFF0000 on self-managed modes - that is the -1 over a zero low half, not a sentinel constant. legaia_asset::mode_table::ModeEntry::next_mode decodes it, and the engine's transcribed table is cross-checked field-by-field against the executable by the disc-gated mode_table_reconcile test.

Which mode loads which overlay

The INIT handlers stream their overlays through the two parallel loaders FUN_8003EBE4 / FUN_8003EC70, both calling FUN_8003E8A8(param + 0x381) - in extraction index space that is entry param + 0x37F, two below the raw + 0x381, because the resolver indexes the raw in-RAM TOC (PROT § In-RAM TOC).

History: off-by-2 loader arithmetic
  • An earlier + 0x381-arithmetic reading placed the mode-0 overlay at 973 and took the slot-machine text in 973's over-read tail for its content. 973 is the 1-sector OTHER2 dev module (mode-24 warp sub-id 1); the casino slot machine is 975; the mode-0 overlay is 0971.
  • "Mode 2 loads 899, the field/town/menu overlay" was the same off-by-2: mode 2 loads 0897 (field); 0899 is the menu overlay, loaded by mode 22.
  • "Mode 24 loads PROT 0896" is refuted - 0896's bytes appear nowhere in RAM across the entry window; mode 24 loads the per-sub-id minigame slots.
  • General rule: CDNAME #define numbers are raw in-RAM TOC indices, so extraction filename labels shift +2. Always cross-validate against the loader-call constant or the file's magic bytes; see CDNAME § numbering space and do-not-re-walk.

Every load on this page eventually turns into "seek the drive to a sector, DMA some bytes into RAM". Legaia does that with its own layered CD driver - hardware-register and callback code rather than the PsyQ libcd BIOS path - so the stack is documented, not ported; the engine reads a disc image directly. Dev vs retail: the dual-mode loader

FUN_8003E360 shows the pattern every loader on this page repeats, keyed on the dev/retail flag _DAT_8007B8C2: the non-zero (retail) branch takes the PROT TOC index path (FUN_8003E8A8(0x3D5,1) + FUN_8003E800), while the zero (dev) fall-through opens a path through FUN_800608F0 - break 0x103, a dev-station host trap - then FUN_80060920 / FUN_80060944. Only the retail branch runs on real hardware.

Publisher-logo boot screens (PROT 0895 init.pak)

The first thing you see after the PlayStation logo: PROKION, Contrail, "SCEA Presents", then the epilepsy warning, each fading in, holding, and fading out. All four are plain PSX textures in one small bundle.

PROT entry 0895 (filename label bat_back_dat) is the boot-time init.pak bundle. The label is the +2 filename shift, not dev mislabeling: in the define map, raw 897 (= extraction 0895) is the first xxx_dat slot, while bat_back_dat truly names the battle side-band summon.dat / readef.DAT files at extraction 893 / 894. The bundle contains four uncompressed TIMs (the PS1's standard texture-image format) that the boot sequence uploads to VRAM and fades through:

Two of the four TIMs (PROKION, SCEA) are vertically-packed sprite atlases - the decoded bitmap stacks several smaller strips that retail unfolds into a horizontal / grid layout via multiple GPU quads. Blitting the whole TIM as one quad shows the packed layout (PROKION as PROK over KION, SCEA as four wrapped text rows) rather than the on-screen logo. The exact on-screen layout retail uses still has to be RE'd from the title-overlay tick body - the STRIP_GRID constants are fit to the visible content, not pinned to specific GPU draw commands.

There is no single title.pak bundle entry. The h:\prot\field\title\title.pak string in init.pak's pool is only a debug-print referent. The dev-tree title.pak content is split across two retail PROT entries, both confirmed by the init.pak fingerprint method against the title_screen_new_game save state: the title wordmark TIM is PROT 0890 (parsed by legaia_asset::title_pak; the big-logo RAM TIM at 0x80170DF8 fingerprint-matches it), and the options / config-menu bundle is PROT 0899 (xxx_dat), whose indexed payload opens with the config-menu string pool followed by the small config-screen TIMs (CLUTs byte-matched at offsets 0x169DC and 0x1F91C+). The title-overlay code is the tail of that same entry 899 (below).

Pre-init_data system-UI gap (menu-glyph atlas + boot cursors)

The tiny small-caps font the menus use, the boot cursor and a few ornamental sprite strips live in a place no PROT entry names: the space between the archive's directory and its first indexed entry.

A 236 KB / 118-sector unindexed region sits between the TOC and the first indexed entry (init_data at LBA 121). The TOC ends at PROT.DAT offset 0x1800 (3 sectors); the first indexed payload starts at 0x3C800 (sector 121). The gap is a packed bundle of system-UI TIMs. All are 4bpp + CLUT (a CLUT is a 16- or 256-colour palette stored as a row of framebuffer pixels) and target the bottom-right corner of PSX VRAM (fb_x >= 640).

Menu-glyph atlas

The TIM at PROT.DAT[0x11218…0x11218 + 33312] (256×256 @ 4bpp + 16×16 CLUT bank) is the small-caps glyph atlas the in-game menu UI (shop / inventory / status panels) samples. Confirmed by pinning the in-RAM copy at vaddr 0x80106478 (live title-menu state) against PROT.DAT - byte-equal modulo the runtime CLUT relocation. The atlas does NOT appear in any extracted PROT entry; it's strictly in this pre-init_data gap.

  • Alphabet row: atlas y=224…238, 26 cells × 8 px wide on an 8 px pitch starting at x=8.
  • Digits row: atlas y=209…220, 10 cells with the same pitch.
  • Non-glyph debug content (a demo-build row, a dev string, a palette bar) is present but ignored by the engine.

CLUT row 0 renders the alphabet in solid red with magenta highlights; retail switches CLUT rows per context to read white / gold / dim. The clean-room engine sidesteps the CLUT-switching logic by decoding once to a stencil (pixel-index 0 → transparent, indices 1…15 → opaque white) and applying a SpriteDraw::color tint at draw time. The atlas builder lives in crates/asset/src/menu_glyph_atlas.rs (source pin + per-character rect helper) and crates/engine-core/src/menu_glyph_atlas.rs (RGBA8 stencil decode). Extraction reads PROT.DAT directly via ProtIndex::prot_dat_raw_bytes(byte_offset, len); the per-entry paths walk TOC indices and never visit this gap.

The title screen's own "NEW GAME" / "CONTINUE" rows are not rendered from this atlas - retail samples a pre-rendered band at y=227..237 inside the title TIM itself (PROT 0890; TITLE_BAND_MENU_NEW_GAME / TITLE_BAND_MENU_CONTINUE in legaia_asset::title_pak). The band packs both strings into one 128×10 strip; the engine emits two SpriteDraws sampling the left half (x=0..65) and right half (x=65..127). Selection is colour-coded - bright for the cursor row, dim otherwise - there is no arrow cursor mark in retail.

Where the title overlay lives on disc

The code that runs the title screen is the tail of PROT entry 899 - the same entry whose head is the options-menu bundle. It's streamed raw, uncompressed, straight into the overlay window.

The title-overlay code (function FUN_801DD35C, the captured overlay_title.bin 256-KiB window) lives inside PROT entry 899, and the per-entry extractor emits it: 0899_xxx_dat.BIN is 151 552 bytes = 74 sectors. The tick body's source is at PROT.DAT offset 0x5C4C344 = entry-899 offset +0xEB44, byte-identical.

The SCUS boot sequence issues a multi-sector ReadN starting at PROT 899's LBA (47227) and reads the entry's 74 sectors. The CD-DMA primitive (FUN_8005D9A0) breaks the read into 5 sequential DMA bursts, every one landing inside entry 899:

History: the "unindexed 60-sector gap"

Earlier readings placed the title overlay in an "unindexed gap between TOC entries 899 and 900" that "the TOC misses". The TOC does not miss it. The superseded per-entry size expression toc[p+5] - toc[p+3] + 4 gave PROT 899 only 14 sectors, and the missing 60 became the "gap"; the real size is the gap to the next entry, toc[p+3] - toc[p+2] = 74 sectors, exactly what retail's own FUN_8003E68C computes. The same artifact produced every "hidden overlay in the gap after entry N" reading; a lossy-LZS brute-force scan for the overlay returned zero hits because it is not compressed at all. A "FUN_8005DA40 walks pointer table _DAT_800795B4" claim is also an artifact: 0x8005DA40 is an instruction inside FUN_8005D9A0, promoted to a fake function by Ghidra. See PROT and do-not-re-walk.

Title-screen overlay state

The title screen is a small program of its own: an attract countdown that eventually plays the opening movie, a two-row menu, a memory-card check, and the NEW GAME / CONTINUE launch. It is not one of the 28 modes - its tick is loaded by a pre-mode-dispatch boot routine, so the recurring "which mode-table row is the title screen?" question has an empty answer.

The overlay keeps its state in a struct based at 0x801F0000, with a sibling region at 0x801EF014..0x801EF200 reached via negative displacements off the same lui 0x801f. The two headline fields:

Tick function

The per-frame tick is FUN_801DD35C (12 104 bytes / 3 026 instructions, in the title overlay - not in SCUS). Pinned via a PCSX-Redux watchpoint on the countdown: the breakpoint captured pc=0x801DDCCC on the exact sw v0, -0xe94(a0) that writes the decremented value back. Full disassembly + decompile in ghidra/scripts/funcs/overlay_title_801ddccc.txt; capture pipeline scripts/pcsx-redux/autorun_countdown_trigger.lua.

lui   a0, 0x801f
lui   v1, 0x1f80
lbu   v1, 0x393(v1)     ; v1 = *_DAT_1F800393  (per-frame scalar)
lw    v0, -0xe94(a0)    ; v0 = *0x801EF16C     (countdown, u32)
nop
subu  v0, v0, v1        ; v0 -= scalar
bgez  v0, 0x801dfc3c    ; if signed >= 0, branch to "still counting"
_sw   v0, -0xe94(a0)    ; <-- captured pc: store decremented value

The "still counting" path branches to 0x801DFC3C (the normal attract loop: rendering, input, cursor logic). The "underflow" path prepares draw primitives via 0x80058490 and writes master mode _DAT_8007B83C = 0x1A, zeroing _DAT_8007BA78 (FMV id) → MV1.STR.

Sub-mode dispatcher

The first ~250 instructions of the tick fan out via a 25-entry jump table at 0x801CF244 keyed on state[+0x204]. The table, the state-struct offsets and the observed state[+0x204] = N transitions are pinned in legaia_engine_vm::title_overlay. Four modes are semantically labelled (Init, Idle, AttractIdle, AttractDelay); the other 21 carry Phase0xNN placeholders with traced-transition docstrings.

This sub-mode SM is the front-end title menu + memory-card manager + new-game / continue launcher - not an opening-narration or name-entry sequence. Sub-mode 0x10 is the menu (2-option cursor _DAT_8007B820; idle-timeout → master mode 0x1A, the attract FMV); 0x15 is the card-check poll. NEW GAME and CONTINUE both funnel menu → fade (0x16) → init_game (0x06) → master mode 2 (field). The standout pin: Phase06 writes _DAT_8007B83C = 0x02 at 0x801DFC00 - the title → main-game transition, exported as MASTER_GAME_MODE_FIELD_LAUNCH + PHASE06_LAUNCH_GAME_PC. init_game also writes the opening scene id opdeene (the prologue cutscene, CDNAME/PROT #748) into the active-scene-name buffer 0x8007050C.

Evidence: sub-mode decomp + captured opening order

The full C-decomp (a switch over DAT_801f0204, cases 0x00..0x18) is all title-menu / memory-card UI - the referenced strings are card / save prompts, and FUN_801E3EE0 / FUN_801E36C4 are the centered card-message text + box drawers. The opdeene write is verified live (opdeene at the intro save state, town01 at the Rim Elm saves), so s_opdeene is a scene id, not a display name. What NEW GAME launches

Press NEW GAME and you do not go to a name-entry screen. You go to a five-scene opening - the creation myth crawl, the Seru intro, the Mist story, a fly-in over Rim Elm - and only once you are standing in Rim Elm does "Select your name" appear. Every leg is an ordinary field scene chained by script, not a movie. A confirm press can skip the whole thing.

Title → field

The menu handler reads the live cursor (state[+0x1FC]), and on L1|Cross (pad & 0x44) stashes the chosen row at state[+0x200] and advances to sub-mode 0x14; NEW GAME is row 0 (CONTINUE routes to the save / card load path). The row-0 sub-phases reach the launch write above:

  1. Mode 2 (field INIT). _DAT_8007B83C = 2 → FUN_80025B64 loads the field overlay (FUN_8003EBE4(2), PROT 0897) and calls the per-scene initializer FUN_801D6704.
  2. Field scene init. FUN_801D6704 reads the resident map id and loads geometry + the scene's MAN (its script / event-data container) via FUN_8003AEB0 + camera + fog + BGM through the field loader FUN_8001F7C0, allocates the game-mode work buffer, then writes _DAT_8007B83C = 3.
  3. Mode 3 (field RUN). The field per-frame loop takes over. Modes 2/3 are the field / town INIT / RUN pair - not an options screen, despite the "MAIN" dev label.

Mirrored in legaia_engine_vm::title_overlay (MASTER_GAME_MODE_FIELD_RUN, FIELD_SCENE_INIT_PC, MENU_INDEX_NEW_GAME) and World::begin_new_game.

The fresh-state seed

The new-game data-init FUN_80034A6C (reached via the boot mode initializer FUN_8001DCF8) establishes what a new game starts with:

  • Gold - party gold _DAT_8008459C is set to a hard-coded 500 (a constant, not a template field). Mirror: NEW_GAME_STARTING_GOLD.
  • Story flags - a ~0x200-byte story-flag region is zeroed, so a new game starts with every flag clear.
  • Party stats - FUN_800560B4 expands the SCUS_942.54 starting-party template into the live records (stride 0x414), copying each member's default name. That default is what the downstream name-entry screen pre-fills.
  • Opening scene - set by the front-end launcher (init_game), not this seed: NEW GAME enters opdeene first.

The opening scene chain + the intro skip

The natural (zero-input) opening chains scene to scene by script execution: opdeene's timeline record P2[18] ends with a field-VM 0x3F SceneChange to opstati (Seru intro), which chains to opurud (Mist story), then to map01 (the world-map fly-in: title card + crawl over an aerial approach of Rim Elm), which scene-changes into town01 at tile (0x1D, 0x5B). Each leg's opening record spawns via op 0x44 SPAWN_RECORD in the entry script (opdeene / opstati / opurud) or the walk-on tile trigger (FUN_801D1EC4 → FUN_801D5630 → FUN_8003BDE0; map01 / town01) - live-probe-pinned (exec-BP on FUN_8003BDE0, exactly 5 hits). The narration itself plays from the timeline records: each leg's inline subtitle pages roll through the bottom-up crawl roller (FUN_80037174; engine CutsceneNarration), spawned as a child context so the camera cuts play under the scroll. See the cutscene page.

On top of that, a confirm press at any time after opdeene's timeline arms GFLAG 26 fires a name-based scene-change packet straight to town01 - the intro skip. The per-frame field / cutscene controller FUN_801D1344 issues it as a one-shot, flag- and pad-gated block:

  • The packet API. FUN_8001FD44(name_ptr) copies the target name into 0x8007050C, syncs it to the active buffer 0x80084548 (FUN_8001D7F8), and stages the load; s_ERR_CHANGE_PACKET guards re-entry. This is not the map-id door-warp (0x3E / FUN_80025980) - the door-warp handler backs up the active scene name into 0x8007BAE8, and that buffer is empty in the town01 opening saves. See asset loader § scene change.
  • The target name is the overlay literal at 0x801CE82C - which is why scanning opdeene's own data finds no town01 string. The pad bit & 0x100 is the skip press; it fires mid-narration too (the crawl is timer-driven, not confirm-paced).
  • The trigger flag (_DAT_1F800394 bit 26) is set by the field VM's generic scratchpad-bit opcode GFLAG_SET (op 0x2E, operand 0x1A). The only such write in opdeene's decoded MAN is in the last record of the MAN's third partition (partition 2, count 19; record at MAN offset 0xA47, the 2E 1A at 0xA5E) - the cutscene-timeline script arms the skip bit near its top, right after the opening colour reset, then stages the choreography and ends with the SceneChange to opstati.
  • Port. World::take_prologue_handoff mirrors the gate: while the opening chain is playing and the trigger bit (PROLOGUE_HANDOFF_FLAG = 1 << 26 in World::story_flags) is set, a confirm press clears the bit, tears down the narration, and returns town01; the host runs BootSession::enter_field_live(target). The arm fires by execution - entering opdeene installs its timeline as a spawned field-VM context and the GFLAG_SET 26 writes the bit through the same host path the main field VM uses; a static MAN-walk arm remains as fallback. Disc-gated opdeene_prologue_arm.rs pins the offset and asserts town01 carries no such arm.
History: superseded readings of the skip

The skip was first read as the required hand-off gate from the prologue into the field; the chain in fact advances by itself and the gate is a skip. An earlier guess that a 0x4C MenuCtrl sub-op in record 0 armed the bit is falsified - record 0 has no 0x2E / 0x2F byte at all.

Name-entry overlay

The "Select your name" screen runs after the field launches, as a menu overlay invoked during the town01 opening (master mode 0x03) - not a title sub-mode. The field-VM op that opens it is pinned: op 0x49 STATE_RESUME sub-op 3 at town01 partition-2 record 3 (P2[3]) body offset 0x02c6, in the opening cutscene timeline. After the establishing camera pan the script suspends on this op and op49_invoke_setup (func_0x80020de0(0x8007065c, _DAT_8007c34c)) hands off to the overlay; Vahn's scripted walk-out plays after the name commits.

Executing P2[3] through the engine field VM and correlating against the name_input_ui save state: _DAT_8007B450 (the op-0x49 state slot) holds 0x800EB297 = the 0x49 op's RAM address + 1 (record body 0x02b0 loads at RAM 0x800EB280, byte-identical), so the field script is parked precisely at this op while name entry is up. Character grid, cursor, controls

The grid lives at 0x801F29F0: a flat ASCII table, 6 rows × 17 bytes - three column-groups of five (upper / lower / digits-and-punctuation) with | (0x7C) separators. The live name buffer is at 0x801F2A6C; the committed name lands in the character record at +0x2A7 (record base 0x80084708 + n*0x414; save-block offset +0x86F for slot 0); the prompts are at 0x801CF698+.

The cursor (0x8007BB88) is a linear index over a 7-row × 17-col navigation space (0..0x77, wrapped modulo 0x77): cells 0..0x66 are the glyph rows, 0x66..0x77 the control row. D-pad deltas are -0x11 / +0x11 / +1 / -1, separators are skipped; confirm on a glyph appends it (width-capped at 0x39 = 57 px). The control row tiles the sentinel bytes 00 00 | 66×6 | 64×6 | 65×3 → Backspace (0x66) / Space (0x64) / End (0x65, gated on a non-empty name → the Yes/No confirm, whose Yes commits the name).

Renderer + state machine

FUN_801E6B34 renders the grid (skipping | / space) via glyph drawer FUN_80036888, plus the current name, the blinking caret and the box frames. FUN_801F03F0 is the state machine: substate at struct+0x54, 5-entry jump table at 0x801CF71C - init (0x801F0444) → interactive (0x801F0480) → three confirm handlers (0x801F095C / 09C0 / 097C).

Port. The whole SM is legaia_engine_core::name_entry (NameEntry + NameEntryState + Control), driven by World::open_name_entry / step_name_entry (committing into World::party_names) and rendered through legaia_engine_render::name_entry_draws_for. The town01 entry installs P2[3] as a spawned cutscene timeline (walk-on tile trigger on the natural arrival; World::install_town01_opening_timeline on the skip), which plays the establishing pan, opens the overlay at the pinned op 0x49, freezes until a name commits, then resumes with Vahn's walk-out. Sprite-emit helpers

The title tick reaches into three SCUS-side helpers to emit GPU primitives, all ported clean-room in legaia_engine_vm::title_prim:

  • FUN_80058298 (ClearImage rect-fill queue, 37 instructions) → exec_clear_image(host, rect, r, g, b).
  • FUN_80058490 (MoveImage VRAM-copy queue, 49 instructions) → exec_move_image(host, src, dst_x, dst_y) with early-out on zero extent.
  • FUN_800198E0 (sprite-descriptor dispatcher, 146 instructions) → exec_sprite_descriptor(host, &SpriteDescriptor) with full tag-0x11 + complex variant routing (alpha-OR pre-pass under flags & 8, four width-divisor variants from flags & 3).

Overlay-side helpers (FUN_801E1C1C / FUN_801E373C / FUN_801E3EE0 / FUN_801E36C4, shared across menu / battle / shop / save UI overlays) are a separate port.

History: "three multi-bank duplicates"

This page used to list three sources - 0888 @ 0x1AA28, 0889 @ 0x19A28, 0890 @ 0x14228 - as "multi-bank duplicates". A byte scan for the TIM's header signature across the whole archive returns one hit, inside 0890's own 73 sectors. The h:\prot\field\title\title.pak debug path is a dev-tree-vs-disc split, and the 0895_bat_back_dat-style label confusions are the separate +2 numbering shift.

Debug flags

Two RAM values decide whether the game behaves like the shipped disc or like a dev station. On real hardware they always read "retail" - but a cheat device can flip them, which is how the debug menu on the retail disc becomes reachable.

AddressRole
_DAT_8007B8C2Dev / retail loader-path selector. != 0 is retail (load PROT entries by constant index), == 0 is dev (open a literal h:\… path through FUN_800608F0, whose whole body is break 0x103 - a dev-station host trap real hardware cannot service). Every read is a test - all 40 read sites in SCUS_942.54 are lh at this address - and there is exactly one write: main()'s 0x80015F08 sh v0,0x5aa(gp) storing the return of FUN_8003F084, a two-instruction leaf returning 1. Retail boots with the halfword at 1 (confirmed across the save-state corpus); a 0 only ever arrives by external POKE and selects the branch that traps.
_DAT_8007B98FThe most-significant byte of the 32-bit debug-mode word _DAT_8007B98C (NA offset; JP retail uses 0x07D51F, an 0x1B90 build shift). The code reads the word: _DAT_8007B98C is the debug gate tested by FUN_8001822C (the input dispatcher) plus ~14 resident field-overlay (0897) gates, written by the shared menu / title / save-init routine. Poking the byte to 1 sets the word's MSB, so every != 0 gate reads debug mode active and SELECT+△ brings up the debug menu on the NA retail build. See docs/reference/builds.md for the debug input bindings.
History: why both flags were once read backwards

An earlier sweep reported zero writes to _DAT_8007B8C2 and concluded it was BSS-resident with 0 (= retail) at boot. The sweep searched only the absolute lui+offset form and could not see the writer, which is gp-relative (gp = 0x8007B318); and no BSS is cleared for this executable at all, since its PS-X EXE header carries b_size = 0. _DAT_8007B98F returned zero byte-granular references because the consumer reads the word - the "stripped at link time / inert" conclusion is falsified. Both are catalogued under do-not-re-walk; the gp-relative blind spot is the reason the address reference scan checks all five reference forms.

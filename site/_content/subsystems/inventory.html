Inventory - one bag, one active window

Legaia keeps the whole party’s items in a single 256-slot bag. Every read and write of that bag is fenced by an active window that shrinks to one 128-slot half whenever a character travels alone. That one rule explains the “divided” inventory players notice during solo segments - and why the folklore “72-slot” limit is a display page, not a bound.

What players see

Open the menu and the bag looks like a handful of tabbed pages. Play a segment where one character is alone and the bag seems cut in half: items the party had are gone, and what the loner picks up never shows up once everyone regroups. Both impressions come from one array and one window. The pages are views; the halves are access rules; nothing is ever physically moved.

Storage and access

Each slot is two bytes, and the array is a plain run of them inside the live game-state block, so it rides verbatim into every memory-card save:

+0item idu8, 0 = free
+1countu8, cap 99
+2 .. +0x1FFslots 1..255same shape

Chests and scripts (the field VM’s GIVE_ITEM op), battle rewards, shops and the equip swap-back all change the bag through one small helper family, passing item ids or helper-returned slot numbers. The field, battle and menu overlays also read slots directly. There is no raw-index sort or swap primitive anywhere in retail.

  • One direct write. The pause menu’s Throw Out confirm (FUN_801D8734 in PROT 0899) zeroes the selected slot’s id and count with two sb of its own (0x801D88FC / 0x801D8910).
  • Two readers ignore the window. Both are capture-class cast modules: PROT 0941 (Steal) clamps its random slot against a live count; PROT 0954 (Fatal Decision) samples all 256 slots unclamped - the only reader that reaches the key-item band without going through a window.
  • The census is closed, not sampled. The array sits 0xA640 above gp, so no gp-relative instruction can reach it; neither its base nor the block base appears as a literal word anywhere on the disc; and every one of the 125 accesses materialises the block base inline.

A new game seeds exactly one slot - five Healing Leaves - after pre-zeroing the whole range. Occupancy keys on the id alone, so a live id with a zero count survives compaction.

The active window

The helpers never see “256 slots”; they see [start, end). Window setup picks the bounds from the party roster - member count and the first roster id - every time normalize runs.

  • Consequence. A solo character has an isolated pocket of the bag: they can neither see nor spend the party’s items, and what they pick up alone never reaches the party inventory.
  • Design intent. Vahn owns the lower half because the game opens with Vahn alone - the early-game bag simply is [0, 128) until the party forms. Once two members are present the full 256 opens.
  • Bounds. end is only ever 128 or 256. Slots outside the window exist in RAM but are invisible to add, consume, capacity and normalize alike.

Why slot order matters

Because the bag is never compacted behind the player’s back, holes are real, and two consumers address it by slot rather than by item:

  • The pause item list. The selected row’s payload is a bag slot index. The list hides empty slots, and nothing compacts the bag when the menu opens (the normalize helper has one call site, a guarded field-VM arm), so the row number and the slot number part ways as soon as a hole sits above the selection. Throw Out zeroes the slot the row names.
  • The enemy Steal. PROT 0941 draws random slots over the whole array and accepts only a slot with an id, a count and a non-zero shop price - 96 of the 256 item ids are unpriced, so quest and found-only items can never be stolen. The removal, though, goes through the windowed consume helper: a steal that lands in the half the window does not cover announces an item the party keeps.

The add helper’s off-by-one

The add helper stores the item id before it bound-checks. On a completely full window the scan exits at i == end and the id byte lands one slot past the window; only the count store is guarded. This is the core of the open arbitrary-code-execution reachability thread - see How we know for the exact addresses.

Details: reaching the leak, and the probe trap

The stray id lands at 0x80085958 + end·2: 0x80085A58 when end = 128, 0x80085B58 when end = 256. Demonstrating it needs a bag genuinely filled to end (256 slots with a multi-member party) with the hit shown to land past the guard. An execution probe at pc = 0x800422BC fires on every successful add, before the guard, so a hit there is not out-of-bounds evidence by itself. The two windows fail differently: the merge pass keys on the id byte, so at most 255 distinct ids can be live and the full 256-slot window always keeps a hole. The half windows are 128 slots, and the id space does not save them - the item-name table carries 250 non-empty names over its 256 ids, so 128 distinct live ids is arithmetically reachable; what bounds the half-window case is how much of that population is obtainable while a character travels alone, which nobody has measured. Status: open RE threads.

History: the 72-slot ACE ceiling

The earlier ceiling “0x800859E8 = first key-item slot” assumed the 72-slot display page was the window. The accessors bound on end, which is only ever 128 or 256, so every out-of-bounds figure derived from a 72-slot bag is void. See do-not-re-walk.

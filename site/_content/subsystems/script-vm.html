Field / event script VM

The interpreter that makes Legaia's towns work. A villager's lines, a door that swings open, a chest that hands over an item, a cutscene, a story flag flipping so the plot can advance: each is a small bytecode script, and this one interpreter runs them all, for every actor in the scene, every frame. This page is the tour; every opcode and sub-op is on script VM internals.

At a glance

The field overlay (PROT 0897), the code the game streams into RAM whenever you walk around. The dispatcher FUN_801DE840 is one of the largest functions on the disc.

Each scene's MAN, the script-and-data bundle shipped with the scene. Nothing about a town's behaviour is in the main executable.

What a script does in a scene

A scene's MAN holds four kinds of script, and each one is started by something different. Nothing schedules them centrally: each kind waits for its own trigger.

  • NPCs. Each placement record seats an actor (model, idle clip, tile) and carries its script. A short spawn section runs at load (class flags, starting facing, flag-dependent relocation), and the rest waits for the player to touch it.
  • Doors and props. A partition-0 record bound to a map object plays the door's swing clip and, for an interior, teleports the player within the same scene grid (walking into a house).
  • Cutscenes. A partition-2 record is a timeline: it walks actors with cross-context motion ops, stages the camera, shows lines in the shared dialog box and sets the story flags that move the plot on. The narration crawl and camera mover it spawns are ordinary actors that run in parallel.
  • Gameplay hooks. Battles (3E FF row), minigames (3E with op0 ≥ 100), FMVs (4C E2), shops and the name-entry screen (0x49) are all script ops; the scene's script decides when each happens.

How a frame runs

A script runs only while its actor is engaged (bit 0x100 of the actor's flag word). While engaged it gets one slice per frame, and a slice is not one instruction: it runs instruction after instruction until something stops it.

  • Every engaged script runs every frame. The frame driver walks five actor lists; a field actor with the engaged bit runs its slice. Scripts are not time-sliced against each other.
  • A script is a series of interactions. Each one runs from where the last 0x21 left the PC to the next executed 0x21. An NPC that says one thing on the first talk and another afterwards is one record whose branches all jump back to a shared flag selector.
  • Three things engage a script. The touch post (contact or the action button), the record spawner (a new partition-2 context) and the system script's own driver. No opcode engages a placement: a cutscene that walks a villager runs on its own slice against the villager's actor, and never runs the villager's talk body.
  • The system script sits out other scenes. It starts a new pass only while no other script holds the player, and not at all while a battle is committed, so a town's per-frame loop pauses during an NPC talk or a cutscene.
  • Waits are display frames. WAIT_FRAMES adds the frame-skip factor per visit, so "wait 30" is 30 display frames whatever the logic rate. A port has to pace the VM from a display-frame clock.

The scene's own script is the readable example. Rim Elm's starts a track, clears two story-flag banks and stops the track again 32 instructions later on a first visit, all before anything is drawn; the loop after it is a 20-instruction run of player box tests choosing the camera. Stepping one instruction per frame would play half a second of music retail never lets you hear.

Where scripts live

The carrier is the scene MAN (asset type 0x03). The scene loader installs each placement record's script pointer on its actor and starts the VM on the body that follows the record header.

1[N][N×2 locals][model][anim][bx][bz]Record 0 = scene system script; records 1.. = one per NPC or trigger, script body after the header

Thirteen scenes ship a second, plain MAN inside a streaming PROT entry (the "variant MAN"); for two dungeons it is the scene's only MAN, so a story-flag writer that seems to be missing is usually there. The prescript table that precedes some scenes (scene_event_scripts) is not field-VM bytecode: it holds move-VM stager records.

The header tile is not always where the actor stands. The spawn section runs at load, and a flag-chosen arm that moves the actor (op 4C 51, or a bare 0x23) relocates it before the first frame draws - Rim Elm stages its two running kids on the standing kids' exact tiles and dispatches them across town that way.

Dispatch and targets

The interpreter is a plain function, new_pc = run(buffer, pc, ctx). Before its 43-way switch there is one prefix check: if the opcode's high bit is set, the next byte names the actor this instruction acts on, and the handler runs against that actor's context. A cutscene can say "the king walks to X" without becoming the king.

Target byteResolves to
0xF8The player
0xFBThe scene's system context (P1 record 0)
otherThe actor whose bind index matches; a halted target (flag 0x400, mid-walk) refuses the op until it lands, except the un-halt 32 0x400

That refusal is how a cutscene choreographs its cast: it starts a walk on an NPC and runs on, and its next op on that NPC waits at the dispatcher until the walk lands. Only a walk aimed at the player parks the calling script as well. The context record's fields and every target rule are on internals.

Turning to face someone

The same acquire is how a cutscene turns heads. CC <id> 85 <budget> <bind> (and its 8E / 8F siblings) hands the target actor the walk kernel's face-target leg: it turns toward the bound actor (F8 = the player) over a frame budget, zero snapping at once, and the leg's last frame clears the halt. "Noa turns to Vahn" is CC <noa> 85 <budget> F8; cutscene records issue over a thousand of these on NPCs and as many again on the Noa / Gala placements. Aimed at the player, the op parks the calling record too, so a cutscene waits for Vahn's turn before it moves on.

Outside a cutscene - a scene's entry script, a conversation - a face-at aimed at another actor still turns that actor, and in a conversation the talker's own face-at holds the record until the turn lands. Two neighbours finish the picture: 4C 3A sets the player's heading to the arrival facing a door wrote from its direction byte (a card load and New Game zero it), and 4C 45 is a look turn - a rotation the animated renderer applies to one object of the rig, in every captured case the head, ahead of its keyframe pose. The port runs all of these on both play hosts.

Story flags

"Has the player beaten this boss?" lives in a 4096-bit array at RAM 0x80085758, inside the save block. The VM reaches it through the dispatcher's default arm: any byte whose high nibble is 5, 6 or 7 is a flag op, and the opcode's low nibble plus the next byte form the flag index (bits are MSB-first within each byte).

Lead byteEffectBytes
0x5xSet flag2
0x6xClear flag2
0x7xTest flag; when set, jump by the following 16-bit offset, else fall through4

Partition-2 records gate on the same bank, so a flag set by one script is visible to the next record immediately. A beat that should play once self-latches: its script sets the very flag its gate tests. Some story-numbered flags are mechanism, not progress: the 0x527..0x531 scene-transition scratch band every entry script rewrites, the 0x00F door busy-mutex in Drake Castle, per-visit lift state. Read those as traffic. The disc-wide "who sets flag F" question is answered by legaia-engine man-scripts --system-flag-census; its caveats are on internals.

Field dialogue has no opcode

Press the action button in front of a villager and a text box opens, but there is no "show dialogue" instruction. Talking is a three-step pipeline over the NPC's own bytes.

  1. TriggerThe facing probe picks the actor in front of the player and the touch post engages its script. No opcode is involved.
  2. TextThe record carries two scripts back to back under one cursor: the spawn section, then the interaction. The interaction starts one byte past the spawn section's 0x21, and its lines are 0x1F-led glyph runs in the MES encoding.
  3. DisplayThe runner stops at the text byte and parks the context on the one shared dialog box; the pager shows it a box at a time. When the box closes, the script runs on.

The box has one owner at a time: a script that reaches text while another holds the box waits for it, while every script not on text keeps its slice. Op 0x3E is often mistaken for "talk to NPC"; with op0 < 100 it installs a scripted battle.

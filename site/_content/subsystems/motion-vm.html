Per-actor motion VMs

The interpreters that walk NPCs around. When a villager paces a patrol route, an actor turns toward you as you talk, a cutscene marches someone across the screen, or the camera glides after a character, one of two small bytecode VMs is stepping that actor, one instruction per frame. This page explains which VM does what, how an actor's facing changes, and where the bytecode comes from on the disc.

At a glance

An actor is the engine's record for one on-screen entity (the player, an NPC, a prop, a camera target). Every frame the field actor tick FUN_8003BC08 visits every actor and, depending on flag bits in the actor's word at +0x10, hands it to one of these interpreters. Function names like FUN_80xxxxxx are Ghidra's labels for routines traced at their RAM addresses; both VMs live in the main executable SCUS_942.54.

Two things catch people out. First, the NPC turning to look at you when you press the action button is neither VM - it is a single store in the dialog state machine (see talk-time facing). Second, the two VMs are ported in three places: the pursue VM is legaia_engine_vm::motion_vm; the scripted VM's static decode (which stream binds to which placement, wander pace, default moves) is legaia_engine_core::man_field_scripts::npc_motion, and its runtime facing channel is legaia_engine_vm::ambient_motion.

Both are distinct from the actor / window-widget VM and the move-table VM (Tactical Arts / battle animation); the whole family is listed on the VM family.

The driver: one tick, two arms

Before either interpreter runs, the per-actor tick decides two separate things: which way the actor should be looking this frame, and which routines get to move it. These are independently gated halves of FUN_8003BC08 (ported as field_actor_plan in legaia_engine_vm::motion_vm).

Facing arm

Runs only when the actor is live (+0x5C >= 0) and not self-frozen (+0x10 & 2 clear). It picks one facing law from the flag word: bit 0x20000000 snaps the heading to -(+0x8E); else if neither a target bit (0x20200) nor the ambient enable _DAT_8007B6A8 is set, the heading holds; else bit 0x2000 selects a per-frame clamped turn toward the target bearing (rate = pad-held * 6, a raw signed-difference clamp distinct from the frame-budget ramp below), and its absence snaps straight to the bearing (FUN_80019278).

Dispatch arm

Skipped whole when the global suppress bit _DAT_1F800394 & 0x400 is set. Otherwise four routines fire on their own guards, as in the figure. The first of them, FUN_80039B7C, is not a motion VM: it is a per-actor pump that steps a field/event-VM script (the same 0x21-terminated format the field VM reads, at *(actor+0x90) + *(actor+0x9E)) in lock-step with the global cutscene phase _DAT_801F2734, so a cutscene actor advances one authored beat per phase tick. Its helper FUN_80038050 skips the structural ops (0x21 stop; 0x24/0x25/0x48 one byte; 0x27..0x2A multi-way jump by modal depth; 0x4C two or three bytes). The motion of any actor it walks is issued by the field-VM ops inside the script, not by this function.

The pursue VM: bytecode layout

A motion script is a stream of small instructions - "walk along Y", "rotate to this angle", "move toward your target" - each addressed at an actor. Each entry is 1 + N bytes:

+0  u8 op_byte         ; bit 0x7F = opcode, bit 0x80 = "select target"
+1  u8 target_id       ; only present if bit 0x80 set in op_byte
+N  u8 operand[...]    ; opcode-specific operands

When the high bit is set, the VM resolves a target actor before applying the body. 0xF8 resolves to "this actor" (retail reads the current player pointer _DAT_8007c364), 0xFB follows a linked list at _DAT_8007c34c looking for a matching record-class signature, and any other id linearly scans the actor list at _DAT_8007c354 matching against the actor's placement bind index at +0x50 (lhu v0,0x50(v1) at 0x80037E88; +0x14 is the actor's world X, not an id).

The per-frame speed scalar is DAT_1f800393 (shared with the move VM's frame-time scratchpad): the engine updates once per frame and the VM spends that budget per opcode.

How an actor's facing changes

Watch a villager walk and you will notice they only ever face one of eight directions, yet a scripted turn during a cutscene glides smoothly. That is two different laws, and which one an NPC gets is a property of the bytecode, not of the situation. Three pursue-VM opcodes write the actor's 12-bit heading at +0x26.

Snap - walking

The tail of the 0x47 case runs on every frame the actor moved. It reduces the step to its axis signs, maps them to an index in the heading LUT at 0x80073F04, and writes the entry outright:

index01234567
direction-Z-X -Z-X-X +Z+Z+X +Z+X+X -Z

Entry i is i * 0x200, so a walking actor's facing is always one of eight compass points and never an in-between angle. There is no walk-turn interpolation anywhere in retail. A cold-boot town01 sample off the static recompilation bears this out: every on-field actor's +0x26 is a multiple of 0x200 and all eight points appear, the only exceptions being actors parked on the off-field sentinel tile.

Ramp - the two rotate ops

0x38 and 0x4C interpolate toward a target angle over a frame budget carried in their own operands, running the same arithmetic each tick:

remaining = budget - cursor                  ; cursor at actor +0x54
if remaining - speed <= 0:                   ; terminal frame
    heading = target                         ; exact snap, leg is Done
else:
    cursor += speed
    arc  = (target - heading) mod 0x1000     ; or (heading - target) when decreasing
    heading += arc * speed / remaining       ; or -=

Because the arc is measured from the live heading every tick, the step is a linear ease that lands exactly on the target, and the terminal frame snaps rather than steps so rounding can never leave the actor short. 0x38 aims at a LUT index; 0x4C re-reads the bearing to its target actor each tick, so a FaceTarget leg tracks a target that is itself moving.

Talk-time facing is not this VM

The NPC turning to look at you when you press the action button is the easiest write in the game to attribute to 0x4C FaceTarget, and it is not that op. It is one sh in the per-actor dialog SM, and the difference is observable: 0x4C ramps over a frame budget, the talk write does not ramp at all. The chain is a save / snap / restore triple:

stepsitewhat it does
saveFUN_801D5B5C 0x801D5BE4the addressed actor's heading +0x26 is copied to +0x5A
snapFUN_80039B7C 0x80039F48..0x80039F80class test, FUN_80019B28, sh v0,0x26(s2) - one instruction, one frame
restoreFUN_80039B7C 0x80039CE8 / 0x80039EBC+0x5A written back on the SM's exit paths

The snap runs only for a moving-class actor (flags & 0x420000 == 0x20000) - static props never turn. Its argument order is the load-bearing detail: 0x4C calls FUN_80019B28(self.z, self.x, tgt.z, tgt.x) and adds 0x800; this arm calls it (player.z, player.x, self.z, self.x) with no 0x800. Swapping the endpoints is the half-turn, so the two agree - a port that copies the 0x4C convention here and keeps the 0x800 faces the NPC exactly backwards. Engine side: World::face_field_npc_at_player / World::release_talk_facing, both called from the field tick so the walk-up talk and the scripted 0x3E interact behave the same.

Clean-room port

legaia_engine_vm::motion_vm (crates/engine-vm/src/motion_vm.rs) ports all six pursue-VM opcodes. Each step returns Yield (budget consumed, resume next tick) or Done; there is no fallback path. The facing law lives in heading_lut_engine (the eight compass entries, carried in the engine's 0 = +Z space - the port carries the half-turn on the LUT), walk_facing_index / walk_facing_yaw (the 0x47 sign-to-index table) and rotate_step (the shared ramp arithmetic, widened to 32-bit); engine-core's facing_index_to_engine_heading delegates to the same LUT so spawn-time and runtime facings cannot drift apart. MotionState carries a once-per-leg walk-facing latch and a per-step yaw_written signal so a heading posed by another writer (the interact bearing) is not clobbered by an idle leg's stale yaw.

Two deliberate departures: LUT indices 8..=15 are no-ops rather than reproducing retail's overread into adjacent SCUS data, and an unrecognised 0x4C sub-mode terminates the leg instead of yielding forever the way retail's inert arm does.

Camera integration

The same machinery that walks an NPC can steer the camera. The runtime Camera in engine-core::camera consumes:

  • The field-VM op-0x45 event stream (CameraConfigure / CameraSave / CameraLoad / CameraApply) for the high-level camera state.
  • The motion VM (optional) for cinematic pre-baked camera paths via Camera::tick_script.

The default mode follows a target actor slot at a configured distance + height - the same shape as the retail "follow the player" camera.

Field-NPC walking in the port

World::tick_field_npc_motions (engine-core) drives MAN-placed field NPCs through the 0x47 MoveTowardTarget pursue step, one motion-VM step per field tick, writing the live position back into World::field_npc_positions so the moving NPC's ±40-unit collision box and its interact box follow it.

Three start paths feed it:

  • Autonomous patrol routes - each placement's own pre-text 0x4C 0x51 move-to-tile ops, decoded by man_field_scripts::placement_motion_route; opt-in via play-window --live-npcs, paused while a dialogue is up.
  • Interaction-prologue runs - a record's own 0x4C 0x51 walks the interacted NPC.
  • Actor-VM start_motion glide - op 0x09, retail FUN_800358c0.

The retail speed encoding is pinned: the walk kernel's ops carry their own base-step selector ((op0>>5 & 4)|(op1>>6) for 0x37/0x41, b2 & 7 for 0x47; numerator 0x80, or 0x40 for 0x41), and the ops are the field-VM record's yield-class bytes interpreted in place from the pointer parked at actor +0x94 - see field-locomotion § NPC glide speed. Per-actor field-VM channels are not executed - the engine loops the decoded waypoint list, pacing each placement by its real decoded walk-kernel step (man_field_scripts::placement_glide_speed: the bound tail-section-1 stream's wander/step ops first, then the record's own yield ops, then the facing-nibble heuristic only for placements with no walk-kernel op at all).

The second motion VM - FUN_80038158

This is the interpreter behind a town's ambient life: villagers wandering inside an invisible box, idly turning to look around, waiting, teleporting between tiles during a scene change - and, less visibly, the story flags a scene flips as its choreography plays. It reads its stream at *(u32*)(actor+0x80) + *(u16*)(actor+0x84) and writes the system story-flag bank DAT_80085758 directly: op-7 [07, lo, hi] sets flag lo | hi << 8, op-8 clears (byte/bit math matching FUN_8003CE08).

Disc carrier - MAN tail-section 1

FUN_8003AEB0 (scene-entry map-init) walks the MAN's u24-length-prefixed tail-section chain (tail_base = MAN + 0x2B + 3*(N0+N1+N2) + u24_at_0x28) and installs section 1 at the field control block; FUN_8003A9D4 walks the body as a record chain [u8 count][s16 next_delta][count × (u8 actor_id, u8 enable)][motion stream] and binds each stream to its actor (0xF8 = player, 0xFB = the world-map entity SM node, else matched against actor+0x50 - which the placement spawner FUN_8003A1E4 writes as N0 + placement_index, N0 = the MAN's partition-0 record count, so a binding resolves to partition-1 placement actor_id - N0, not the raw index; town01: N0 = 36, binding 0x30 = placement 12). Streams open with a flag-selected variant header table re-evaluated every tick. Parser: legaia_asset::man_motion. This is the only disc source of this bytecode - all other actor+0x80 writers are eliminated.

The walk half - why a villager moves at all

"Why does nobody move" is a walk question, not a facing one. The directional steps 0x03/0x19/0x20 share one case body at 0x800383F8; the AABB wander 0x18 has its own at 0x80038B90. Two tables sit back to back at 0x80073F04: the eight-entry compass LUT the facing ops also use, and sixteen bytes later at 0x80073F14 the axis bitmask table (1 = +Z, 2 = -Z, 4 = +X, 8 = -X) every walk op reduces its heading index through before touching a coordinate - which is why diagonal indices move both axes by the same per-tick step.

Speed encoding. The walk ops step on the same 0x80 >> (2 + bits) per-frame ladder as the yield ops, with the selector in their own operands: the directional steps carry bits in operand byte 1's low nibble; the pad-echo step 0x06 and the wander 0x18 scatter a 4-bit selector over their four operand bytes' high bits ((b1&0x80)>>4 | (b2&0x80)>>5 | (b3&0x80)>>6 | b4>>7). This is the disc source of a town NPC's ambient wander pace; the engine decode is man_field_scripts::placement_wander_step → World::field_npc_glide_speeds.

What they collide with. Both walk ops probe through FUN_801cf8ac, whose only subject is the player actor - not the walkability grid and not other NPCs. The directional steps probe the single DAT_801F2254 compass point for their heading index; the wander probes the three-point fan of DAT_801F21B4 row dir through FUN_801d5a68.

The ambient VM's own facing ops

The same two laws as the pursue VM, from the same compass. The directional steps and the wander/pad-echo ops snap the heading from their operand's LUT index as they move. Ops 0x04 (in-VM ramp, case body 0x8003859C) and 0x0D (pre-unwrap + hand-off to the generic ramp scheduler, an inlined FUN_8003C5F0, case body 0x800386A4..0x80038828) ramp. Both aim at LUT[b1 & 7] and read the direction from b1 & 0x80 (set = decreasing); neither has a shortest-arc override, so an authored idle turn can deliberately take the long way round. Because the index is masked & 7, these ops cannot reach the adjacent SCUS data the sibling VM's & 0xF index can. Port: legaia_engine_vm::ambient_motion.

Op 0x17 - the per-actor default-move table

[0x17, move_id, anim_id] writes 0x801C6470[actor(+0x50) * 4] / +1, guarded +0x50 < 0x8C (0x8C is also the "unset" sentinel the variant-swap preamble reseeds a record to). The walk/anim ops reload the actor's requested-move pair +0x88/+0x5C from the record, and the interaction motion-pause kick FUN_8003C9AC (ported at legaia_engine_vm::motion_pause) sweeps the same table on the touch-event post. The engine statically harvests each stream's first 0x17 per bound placement (man_field_scripts::motion_default_move_writes → World::field_npc_default_moves).

The touch post. When two actors overlap, the field collision probe FUN_801CFC40 calls FUN_8003D038 with the touched actor's bind index; the body is one guarded store into DAT_80073F1C, the one-slot mailbox the VM's wait-for-touch arm (0x8003882C) consumes. The guard drops the post when the record's class byte is 0x8C - so a placement with no move assigned can be walked into without waking its script.

Flag census

legaia-engine man-scripts --motion-flag-census sweeps every scene MAN (v12-embedded included) for op-7/op-8 sites - the sibling of --system-flag-census (MAN field-VM ops 0x50/0x60/0x70). Disc-wide the surface is overworld walking-band choreography (map02/map03) plus one town0b clear; the spine gate flags appear in no motion stream - their writers are field-VM script bytes in the streaming variant MAN carriers (0x142/0x482/0x1BE; see script-vm) or, for the town01 opening one-shot 549, a direct code path.

History: the flag-549 carrier

An earlier reading had town01's opening one-shot flag 549 set by op-7 from its own motion bytecode. The census shows no such site; the write is a direct code path. Falsified readings are collected on do-not-re-walk.

Effect VM - battle sprite effects

Every spark, puff and spell flash in a fight is a short on-disc script that spawns a burst of sprites, animates each one for a few frames and lets it fade. This is the runtime that plays those scripts. It is called a “VM” for symmetry with its siblings, but it has no opcode table at all: it is a pool of slots driven by countdown timers, and the only data it reads are spawn records and animation frames.

Two addresses per entry

Both the spawn API and the walker begin two words ahead of their stack prologue, loading the pool-ready byte 0x8007BD58 first. Every jal on the disc names 0x801DFDF0 and 0x801E0080; dumps and pages citing 0x801DFDF8 / 0x801E0088 name the prologue word of the same routines.

How it works

Cast a spell and three things happen on screen: the caster poses, a stream of sprites flies to the target, and a hit flash plays. Internally that is one effect script: a list of spawn records, each saying “start sprite animation K at this offset, then wait N frames”. A master slot walks the record list; each record it reaches claims a child slot, which walks its own animation frames and drifts along a velocity until its last frame retires it.

What the slots read

The "state" bytes are wait counters. Every wait in the system is 5.3 fixed-point: a frame count stored << 3 and decremented by 8 per frame. The only data consumed are two record kinds.

Spawn record (effect script, 14 bytes each)

+0x00animu8
+0x01delayu8
+0x02offset ai16
+0x04heighti16
+0x06offset bi16
+0x08vel ai16
+0x0Avel yi16
+0x0Cvel bi16

The script's header is [child_count][flags][spread:i16]. The two planar legs (offsets and velocities) are rotated into world space by the master's spawn angle, so one script aims wherever the caster faces. With flag bit 0 set, the spawn API rewrites every record's two offsets in place with a random value in ±spread - the resident efect.dat buffer mutates on every randomised spawn.

Animation frame (6 bytes each)

+0atlas indexu8
+1delayu8
+2speedu8
+3unread3 B
  • Bursts. Zero-delay records spawn as one burst and zero-delay frames advance as one burst: both loops repeat while the freshly loaded wait is zero.
  • Graceful exhaustion. On a full pool the record is still consumed with no child - effects degrade rather than stall.
  • Delays wrap. The wait is stored in a byte after the << 3, so a delay of 32 frames or more wraps modulo 32.
  • Motion. Each step is pos += vel × frame.speed with the retail pool scale; each child also gets two random UV-mirror bits for variety.
  • Idle early-out. A sweep that finds no active master and no active child skips the remaining catch-up iterations.
  • Retirement overrun. Retiring a child zeroes its active flag and its wait, but the frame-advance loop tests only the wait, so retail keeps reading 6-byte strides past the batch end on the already-dead slot until it meets a non-zero delay byte. Only the dead slot is touched (the next seed rewrites it), so the port stops at retirement instead.
  • Summon side call. Spawn ids 4 and 0x13 first call the move-VM part spawner 0x80050ED4, then take the ordinary spawn path.

How a child is drawn

  • Brightness envelope. With n = frame_count >> 3, the colour ramps in over the first eighth of the animation and back out over the rest, clamped at 0x80 (neutral) and written as r = g = b.
  • Size. Atlas w/h × sprite_scale >> 8 (retail scale 0xA00, ten times the texel size) is the half-extent, applied in view space after the centre is transformed - so the battle camera's 4× world scale never touches it.
  • UVs. From the 8-byte atlas entry, corner order swapped by the child's mirror bits; CLUT from atlas +4, texture page from atlas +6.
  • Battle centres are Y-flipped. The pool integrates in raw PSX units, Y down. The battle view-projection both hosts share carries a trailing scale(1, -1, 1) that cancels the per-model Y-flip every mesh draw carries; a billboard has no model matrix, so the port flips its centre before building corners (effect_billboard::battle_billboard_centre). Without it a spark rising past an actor's head draws as far below its feet.
  • Blend. The packet's prim code 0x2E is a semi-transparent textured quad, so every effect child blends, and the page's own ABR bits pick how: pages (320,0) / (448,0) are additive (B + F), page (384,0) is B + 0.25F - why walk dust reads as almost nothing over a bright floor. Every effect the Rim Elm spar fires resolves to the (384,0) page under a dark warm-grey CLUT row, so it is faint by data, not by a bug; the bright additive pages belong to effect ids that fight never requests. The atlas stores its page in one byte, so the blend enable has nowhere to come from except the code byte; a port that copies the page alone draws the flames as opaque tan blobs.

Each host also carries a tinted billboard outline builder - a flat rectangle around each quad, faded by age. Retail draws no such rectangle; it is a diagnostic, off by default on both hosts (LEGAIA_DIAG_FX=1 on the native window, set_battle_fx_outline(true) on the play page).

The other effect primitives: render mode 4

The pool's quads are not the only way an effect actor draws. The per-actor render dispatcher's mode 4 picks one of three emitters off a selector halfword at actor+0x9E, and the move VM writes both the mode and the selector:

SelectorEmitterSet by move opWhere it appears

All three arms carry shipped content. An earlier census concluded the default arm was the only reachable one; it swept for the stores in the wrong form and missed the move VM's own. Both hosts draw every live kind-4 node of the summon, move-FX, effect-script and field ambient parts through World::active_effect_kind4_draws, composed like a mesh part.

None of the three emitters draws anything itself. Each writes a small Legaia TMD object into a scratch buffer, and the render dispatcher then draws it as the actor's own model through the ordinary TMD path.

The ribbon

Per step the ribbon writes six vertices and six packets joining them to the next step: a core strip stored twice in the core colour, two inner flares fading core to flare colour, and two outer fringes fading flare to black. Every packet samples one fixed 2×2 texel patch, so the colour words carry the look. In play the ribbon is Gilium's summon; the other carriers are not staged as scenes by the engine.

The sprite arm

The sprite arm builds one textured quad and falls into the ordinary model draw: scaled by the part's render scale +0x72 / 0x1000, turned by the rotation banks, and handed to the prim dispatcher with the colour word +0x74 and level +0x78. The scale is seated by the spawn call, not the record. Nearly every seater passes 0x1000, and the engine seats a staged part at that value unless a cast module reports the call with its own scale - PROT 0911’s group-extent calls, PROT 0913’s depth-scaled ones and the stager arms that forward a parent’s scale (SummonScene::push_parts_scaled). Its builder is main-executable code, so unlike the ribbon it draws in every mode; Baka Fighter's impact flash uses the same quad kernel.

The default arm

The default builder takes a packed count / phase argument and a parameter block (inner / outer colours, a UV rectangle, page and CLUT, inner / outer radius and height, two in-plane scales). Besides move-VM op 0x13 it is called directly by the battle ground shadow, the field battle-intro ring and Baka Fighter's floor disc. Its mode word splits three ways:

BitsSelects
mode & 3The plane the three builder axes land in; mode 1 lays a ring on the ground
(mode >> 3) & 0xFThe shape: 0 a ring or open arc of count columns (a disc when the inner radius is zero), 1..3 multi-quad and fan variants, 4..7 jittered, shifted and pivoted rings
mode >> 8The texture mode, read for shape 0 only: the ribbon's fixed patch, or the parameter block's rectangle mapped polar, as-is or turned; a page word carrying 0x4000 samples the display page itself

The captured battle states use shapes 0..3 and none of 4..7. The port's effect_default_arm transliterates the builder onto a byte buffer and is held byte-for-byte to the scratch blocks retail captures left behind, including every ground-shadow build.

Battle effect parts morph through vdf.dat

The effect-script table form stages move-VM parts like any other scene graph, and a part with op 0x0A lanes draws morphed: the lanes index the battle VDF pack vdf.dat (PROT 0872), whose sub-entry table battle init rebuilds from index 0. The Spirit charge is the visible case - two small rest meshes that VDF entry 12 grows into the aura cone.

  • Waits drain at retail's per-frame rate. The part tick subtracts the frame factor times the rate byte from the wait each frame, so a wait of v holds v frames.
  • Lanes grow from the frame after the spawn. The ramp envelope runs from the part tick's tail, which the spawn's own first VM step does not reach. Captures read the lane at exactly 0x66 per elapsed frame, so the cone takes 0x28 frames to open.
  • The model draw applies the part's scale and colour word. The aura's op 0x0C writes an additive colour word at full level; op 0x0D's level rate takes the level to 0 over 0x20 frames and back to full over the last 0x0B.

Battle effects die with the battle

Retail never tears effects down one by one. The mode initialiser calls the per-stage init FUN_8001E1B4 on every mode switch, which re-seeds the 143-slot actor free stack and re-pops the seven actor-list sentinels, unlinking every effect actor still on a list with no walk. The efect.dat pool needs no reset on the way out: its walker is battle-overlay code behind the pool-ready byte, and the battle loader re-initialises it on the way in.

The port's World outlives every mode switch and both hosts draw effect state with no mode test, so it drops the same state by name: World::teardown_battle_effects runs at battle entry, at battle exit and at every scene load, resetting the pool and every battle-scoped cast, move-FX and effect-script scene graph. A staged cast module's scene is retired earlier, when the action state machine opens the next action, because the engine runs its records as data and nothing else would halt their infinite loops.

Textures and models

Effect sprites sample two texture pools. The flame atlas etim.dat is uploaded at battle entry only (its VRAM columns hold town textures on the field), while the character texture band stays resident from the field through battle - the Gimard summon flame samples the latter. A separate 30-entry model library, etmd.dat, gives 3D effects their meshes, and effect parts morph through vdf.dat.

The player summon (Gimard’s Burning Attack, and friends) is not an effect-pool child at all: a live trace shows it posed like an enemy body, the battle per-actor draw FUN_80048A08 running in lockstep with the rigid-keyframe decoder FUN_8004998C, one call per live actor per frame. Its flame animation is geometric, not palette cycling. The summon stager images in slot B hold real move-VM part records, run by the executable’s stager, and the engine drives them as a scene graph beside the body. The enemy Gimard’s Tail Fire is a different move again: a single move-VM part actor from the move-FX module PROT 0900. The floating damage numeral is not a pool child either; it samples the third etim TIM through its own sub-palette. Read from retail's own display list, the digit run keeps its horizontal centre while each cell grows toward its 1:1 24-pixel size and the run rises to a fixed screen row; the quads are unmodulated, so the numeral never fades. Placing it is a host job - the seat is the struck actor's projected screen position - and both hosts emit the cells through one builder, battle_numerals.

History: superseded readings
  • The atlas value 0x7680 is the entry's CLUT (row 474), not a page-(0,0) 8bpp texture page - the +4 / +6 fields are CLUT then page.
  • “Flame flicker is CLUT cycling” is falsified: two animation-distinct frames carry a byte-identical CLUT band while the framebuffer differs.
  • “The summon stagers hold no move-VM records” was a wrong-link-base artifact; they recover under base 0x801F69D8.
  • “Only the default render-mode-4 emitter is reachable” is falsified (above).

The head holds the motion scale (0x1000) and the sprite scale (0xA00) the init writes. A child slot mirrors the master's shape: frame count (doubling as the active flag), mirror bits, frame cursor, wait, i16 velocity, 16.8 position and an animation cursor.

Side-band streaming: summon.dat and readef.DAT

A separate loader case streams one of two runtime-only files into 0x10800-byte slots: per-special-attack CLUT rows and 4bpp texture pages, summon-creature actor records, and the player art-animation archives. The loader consumes a raw TOC index rather than the path string, which is why the names map to extraction entries 893 / 894. Full format: summon-readef.

Spawn sources

The effect catalog (efect.dat) loads at scene entry and stays resident across field / battle transitions. Four producers feed the spawn API:

ProducerRetailPort
Animation effect armFUN_8004998C, spawning at the actor's position and facingBattleActionHost::ui_element
Per-action effect-script walkFUN_801DEA50World::route_battle_effect_spawns
Move-power effect-id listsFUN_801E09F8World::spawn_move_fx
Per-move effect-list spawnerFUN_801E22C8, called by the battle effect driver FUN_800402F4battle_cue_group::expand_cue_group
  • A spawn is seated at an actor, never the world origin: the caller copies the actor's world position, offsets it by the effect's planar legs rotated through its facing, and passes the facing as the spawn angle.
  • The effect-script walk has two record forms. Its 0x80-flagged records route into this pool; its table-form records stage a small move-VM scene graph instead (see vdf.dat morphs).
  • The last two producers share the bit-7 multiplex (effect format).
  • HUD screen-element raises do not spawn here: the HUD spawner calls no effect routine.

Naming an effect id

Effect ids are anonymous - no string table says “fireball”. To name an id, trace the call sites of the spawn API: each caller passes a literal byte, which correlates with the action that triggered it (a Tactical Art, an item use, a spell cast).

World::tick_effects runs one walker sweep per retail logic frame, and World::active_effect_sprites maps pass 2 one-for-one into billboards, which both hosts draw as camera-facing textured quads sampling the scene VRAM. It is the engine’s only per-frame effect path.

A script spawn is walked on the frame it fires

Retail spawns and walks in one frame, in that order: the per-actor anim tick steps the action effect script, whose direct arm calls the spawn API, and the walker runs afterwards from the draw tick. The engine walks the pool inside its tick and routes queued script and homing spawns in the frame tail, after the walk - so each direct spawn is caught up by the sweeps that frame’s walker gave everything else (Pool::catch_up_master: that master and the children it seeds, nothing more). Without it an effect’s first batch landed one sweep late.

  • Two port-side deltas, both invisible to retail behaviour: the retirement overrun is cut at retirement, and a dead master lane is reused as an age counter for render fades.
  • Debug spawns (the E key in play-window) live outside the pool, so the walker never sees them.
  • A faint effect is usually faint by data (see how a child is drawn). Differencing two frames with the billboard draw suppressed (LEGAIA_DIAG_NOFX=1) shows the sprites really are drawn; LEGAIA_DIAG_FX=1 logs each live sprite’s position, size, page, CLUT and VRAM residency.

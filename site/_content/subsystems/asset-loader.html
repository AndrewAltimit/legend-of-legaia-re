Asset loader

What happens between "walk through a door" and "the next room is on screen". The game gathers everything a scene needs - meshes, textures, palettes, sound banks, scripts - out of PROT.DAT, the disc's single big archive of 1233 numbered entries. Battle, field, sound and music each have their own loader, but they all share one idiom: a dev branch that loads by PROT entry number directly, and a retail branch that resolves dev-style file paths through the CDNAME name map into those same numbers.

How it works

At runtime, "load this scene" doesn't mean "load one file". A single battle scene needs character meshes, monster meshes, the active CLUTs (palettes stored as rows of framebuffer pixels), the per-monster sound bank, the visual-effect script archive, plus all the text the battle dialog box might print. They're scattered across dozens of PROT entries. (The function names on this page - FUN_8001F05C and friends - are RAM addresses in our disassembler trace of the original code; the game shipped without symbols.)

Each scene type has its own loader function whose job is to go fetch all that. They all share the same shape:

  • The loader is a small state machine with one numbered case per asset slot.
  • Each case calls the asset-type dispatcher FUN_8001F05C with the bytes for one entry.
  • Some cases also kick off async CD reads to stage things into memory while the rest of the scene is initialising.

The asset descriptor walker (FUN_80020224) is the loop that walks a per-scene asset table and calls the dispatcher per descriptor. It has zero static callers in SCUS_942.54, which would suggest "dead code" - except its sole runtime caller is in the town overlay (a chunk of code the game streams into RAM on demand), at the start of every field session. So it is exercised by retail gameplay; the call just lives in RAM.

Field / town scene loader

This is the "walk into a room" path: every town, dungeon and field map goes through it. The scene's name becomes a set of file paths, the paths become PROT entries, and the entries become the collision map, the trigger patch, the event scripts and the big asset bundle.

FUN_8001F7C0 stages the three sidecars into the per-scene buffer *(0x1F8003EC): .MAP at +0, .PCH at +0x12000 (zero-filled 0x800 when absent), and efect.dat at +0x12800 (= _DAT_8007B8D0). FUN_80020310(_, base_idx) is how a caller sizes that staging read: it returns FUN_8003E68C(base) + FUN_8003E68C(base+1) + FUN_8003E68C(base+2), where FUN_8003E68C(idx) reads the in-RAM TOC at 0x801C70F0 and returns toc[idx+3] - toc[idx+2] - entry idx's size in sectors, the same PROT TOC math. See ghidra/scripts/funcs/8001f7c0.txt and 80020310.txt.

The descriptor offsets past the first are file-relative against the loaded raw footprint (the bundle entry's whole on-disc footprint, Archive::read_entry), not relative to a decompressed working buffer: the walker hands base + data_offset to the dispatcher as the source of an independent LZS stream, which it then decompresses into a separate target. Offsets routinely run well past where a per-format view of the entry seems to end, so an offset that looks out-of-bounds usually is not.

Name-based scene change (FUN_8001FD44) + the transition streamer (FUN_80021934)

Most scene transitions - doors, stairs, town and dungeon entry from the overworld, the opening's prologue hand-off - carry a destination name. The field VM reaches this through opcode 0x3F, whose bytecode carries the name inline ([0x3F][i16 index][u8 name_len][name][entry_x][entry_z][dir]), so nearly every in-game transition has a recoverable destination.

FUN_8001FD44(name_ptr) copies the target CDNAME string into 0x8007050C, syncs it to the active buffer 0x80084548 (FUN_8001D7F8), and stages the destination index from the resolved halfword at 0x80084540 (retail arm, _DAT_8007B8C2 != 0: directly into DAT_8007B768; dev arm: _DAT_8007B9A0); s_ERR_CHANGE_PACKET guards re-entry while a packet is pending (_DAT_8007BA3C). See ghidra/scripts/funcs/8001fd44.txt.

It then spawns the scene-transition streaming actor into the system pool at _DAT_8007C34C via FUN_80020DE0(&DAT_80070734, _DAT_8007C34C) - descriptor 0x80070734 of the 24-byte spawn-descriptor family at 0x800705FC..0x80070763 (just below, and phase-misaligned with, the mode table at 0x8007078C; layout [+4 0xFFFF0000][+8 handler][+0xC flags]; see ghidra/scripts/funcs/80020de0.txt). The handler is FUN_80021934 (real entry 3 instructions before the 0x80021940 prologue), a 5-state SM over actor+0x1A (jump table 0x80010760):

Asset descriptor walker

Once the bundle is in RAM, one loop turns it into live assets. It is short, and its one surprise is that there is nothing clever in it: slot i is the i-th descriptor, full stop.

Sole runtime caller
Field overlay's FUN_801D6704 (MAIN_INIT) at 0x801D6B0C with a0 = 0
Result stored at

The chain, traced from the field init:

  1. FUN_8001E1B4 allocates a single 0x62C00-byte asset buffer once at boot and stores its base at _DAT_8007B85C.
  2. The transition streamer (above) has already streamed the destination's raw .LZS bundle wholesale into that buffer during the fade, so the count word sits at the buffer base with no relocation step.
  3. FUN_80020224 reads count = *base, then for slot in 0..count calls dispatch(base + descriptor[slot].data_offset, type_size, …), descriptors at base + 8 + slot*8, OR-ing the per-slot return codes into a status word.
  4. FUN_8001F05C splits type = type_size >> 24 and size = type_size & 0x00FF_FFFF, then jumps via the table at 0x80010638 + type*4 (type bound < 0x15).

scene_asset_table::resolve returns the table plus the base it is relative to for both the bare variant (base 0) and the prescript-prefixed scripted variant (base at a 0x800-aligned offset past the event prescript); SceneAssetTable::slots reproduces the walk and payload_range(slot, base) resolves a slot's payload span. A disc-gated corpus test (scene_asset_table_walk_real) verifies the walk against every classified entry.

The walk is what fills the mesh pool

Two dispatcher cases register into the runtime TMD pointer table DAT_8007C018, and the walk above is the only path to them: type 0x02 (TMD) decodes its payload to an asset::pack and calls FUN_80026B4C once per member; type 0x09 (TMD2) registers a single bare mesh. FUN_80026B4C stores at DAT_8007C018 + DAT_8007B774 * 4 and post-increments, so the pool is those registrations in walk order, past the resident 5-mesh head (the party meshes). A magic sweep of a scene block is not equivalent - see scene-bundles § the mesh pool is the descriptor walk. Engine side: legaia_asset::scene_asset_table::mesh_pool feeding engine-core::scene_resources.

Door warps into minigames (opcode 0x3E)

The fishing pond, the casino machines, the Baka Fighter booth, the dance floor: stepping onto those is a different kind of transition. Rather than a scene name, the script hands over a small number, the game swaps in a whole code overlay for that minigame, and remembers where you came from so it can put you back.

When the field VM executes 0x3E with op0 ≥ 100, it stores sub_id = op0 - 100 in DAT_8007BA34 and writes game mode 0x18 (24, OTHER INIT). The handler backs up the active scene name (memcpy(0x8007BAE8, 0x80084548, 8)) plus the scene-id word DAT_80084540, then loads the per-sub-id minigame code overlay via FUN_8003EBE4(sub_id + 0x4D) (sub_id ≥ 6 adds 2 first) and calls its init entry.

Only 7 distinct destinations exist (sub_ids 0..6). The loader values 0x4D..0x55 are raw loader parameters, not extraction indices - they resolve to extraction entries 0972..0980 (prot_index = param + 0x37F; fishing = 0972, slot machine = 0975, Baka Fighter = 0976, dance = 0980, plus two dev modules and the monster-roster arena). A genuine warp's op0 is therefore always 100..=106; the placement classifier uses this range (plus the absence of the 0x80 cross-context prefix) to reject text-desync phantom warps.

The op carries no destination scene name. On minigame exit the return handler restores the name (memcpy(0x80084548, 0x8007BAE8, 8)) and DAT_80084540, commits the session winnings into the casino coin bank, and hands off to mode 2 (MAIN INIT), whose per-scene initializer reloads the restored scene.

Battle bundle

A battle starts from inside a field scene, so its loader stacks on top of what's already resident: it adds the monsters, their sound banks, the effect scripts, and the side-band streams that summons and special attacks pull from mid-fight.

Two cases call FUN_8003E104(monster_idx, slot, dst_buf) to populate slots 7 and 8 with the active battle's monster sound banks - the per-monster body of h:\mpack\monster.snd. Each monster has a (start_lba, end_lba+1) entry pair in the TOC at 0x801C8980 - 0x10. See Audio → "Monster sound bank" for the loader contract. The party's own battle meshes are not loaded here: they come from the player battle files PLAYER1..4 (extraction 863..866), assembled per character from their equipment sections - see battle-data-pack and character-mesh.

The asset viewer's --bundle battle mode overlays the extraction 865..890 tim_scan window - an empirically-tuned VRAM set spanning the player battle files, the befect cluster, and the sound_data2 streams (the directory labels carry the +2 filename shift) - so character meshes have the right CLUT bindings.

Per-PROT walker (FUN_8001FE70)

One battle-scene state (in FUN_800513F0, around 0x80051A50) calls FUN_8001FA88(scene_base + slot, 0, dst_buf) to load a per-scene PROT entry into the working buffer, then FUN_8001FE70(dst_buf) to walk its chunk list. The walker is the dispatch path for the scene_tmd_stream layout - leading TMD body followed by streaming chunks - and is different from the standard FUN_8002541C streaming walker:

  • First chunk: read chunk0_header = u32 LE at offset 0. Low 24 bits = TMD body size. Round up to 32-byte alignment, allocate a buffer of that size at _DAT_8007B864, copy the TMD body in via FUN_8003D26C.
  • Loop: advance by (prev_size & ~3) + 4 to the next chunk header. If header & 0xFFFFFF == 0, exit (terminator). Type 0x01 → FUN_800198E0(payload_ptr) (LoadImage); type 0x02 → explicit terminator; other types are skipped silently.
  • Returns param_1 + 1 - a pointer just past the terminating header. The FUN_80026B4C register call that follows hooks the parsed TMD into the mesh pointer table at 0x8007C018 + idx*4.

A scene_tmd_stream entry holds exactly one [chunk0 TMD][type-0x01 TIM chunks][terminator] sub-stream, then zero padding to its sector-aligned end; the single static caller calls the walker once. This is the path that uploads the field NPC palettes to VRAM row 479 - plain PSX TIMs wrapped in type-0x01 chunks, dispatched only during battle init (npc-palette). scene_tmd_stream::sub_streams returns one block per entry and battle_tim_chunks reports every chunk as Tail; both keep a post-terminator scan as a regression detector for a buffer that spans more than one entry.

History: the "two sub-streams per entry" reading

Earlier notes described some entries as holding more than one sub-stream concatenated (0006_town01: a second sub-stream with its own leading TMD at 0x14000), "verified across the town01 / town0b / town0c clusters". That reading is falsified - an artifact of the superseded PROT entry-size expression, which over-read every entry into its successor. Entry 0006 is exactly 0x14000 bytes and the "second sub-stream" is PROT entry 0007, whose TOC start is exactly 0x14000 further on. The town0b / town0c "confirmations" were clusters of the same four-entry layout, so each over-read reproduced the artifact rather than testing it. See do-not-re-walk.

CLUT-data scattering (how the port fills VRAM)

A PS1 texture is useless without its palette, and Legaia keeps the two in different places: a character's mesh sits in one PROT entry while the palette rows it samples come from another. Retail solves this by uploading only the texture bytes the current scene's meshes need, in a fixed order. The port reproduces that policy rather than blasting every TIM into VRAM.

Engines drive this from SceneResources::build_targeted: parse every TMD in the scene's CDNAME block, collect the union of all prim-target rectangles (CLUT rows + texture-page UV boxes the meshes sample), then walk every TIM and decide per block whether to upload it - suppressing an image block when it would land on a CLUT row another mesh references, and vice-versa. That avoids the 4bpp-vs-256-wide CLUT collisions that would otherwise drop most textured prims through the prim filter. See renderer → targeted upload + shared blocks.

Field-shared CDNAME blocks

FIELD_SHARED_BLOCKS = ["init_data", "player_data"] is the set of CDNAME blocks the retail field engine keeps resident in VRAM across scene transitions. The field-form character meshes and textures both originate from PROT 0874 - the retail player.lzs container FUN_8001E890 loads by disc index 0x36c: §0 = the 5-TMD character mesh pack that populates DAT_8007C018[0..4], §1 = effect / vdf models, §2 = the field-character texture pack (eight TIMs; the three Vahn / Noa / Gala atlas pages at texpage (832, 256) with per-character CLUTs on row 478). See character-mesh. Label caveat: the extraction file named player_data is 0876 (the +2 shift) - a VAB + SEQ trailer with no TMDs. SceneHost::enter_field_scene passes both blocks to build_targeted so the player atlas survives every transition without re-upload.

Field vs battle dispatch (SceneLoadKind)

  • SceneLoadKind::Battle: uploads every TIM and parses every TMD the scanner finds, including the leading TMD + type-0x01 chunks inside scene_tmd_stream entries and every mesh embedded in the player battle files.
  • SceneLoadKind::Field: skips both. scene_tmd_stream leading TMDs go to the battle character register (_DAT_8007B864), never rendered from a field scene; the player battle files are battle-init resident, not field VRAM. Retail field saves carry row 479 fb_x=0..256 = zero, which is the dispatch boundary the engine matches.

SceneHost::enter_field_scene uses Field; BuildOptions::default stays Battle so legacy build_targeted calls keep their semantics.

Entries the sweep must never touch

Two classes in a scene's CDNAME block are not assets at all, and uploading them corrupts the scene:

  • v12 trigger sidecars (Class::SceneV12Table) - streamed through the .PCH trigger channel, never the VRAM / TMD pre-pass (the exception is a sidecar that hosts the scene's v12-embedded bundle: rikuroa / dolk2).
  • pochi-filler slots (Class::PochiFiller) - reserved-but-unused one-sector slots. Retail never dispatches a reserved slot; neither does the build. The stale character pages that once seemed to "parse out of" a pochi slot belong to the next entry, seen through the superseded over-reading entry size - uploading them clobbers the scene's ground-tile atlas on tpage 0x0C. See pochi.

Both skips apply in every SceneLoadKind. Regression: crates/engine-core/tests/field_ground_texture_pages_disc.rs.

Battle-boot pre-load (build_battle_boot_vram)

SceneResources::build_battle_boot_vram builds a VRAM blob from the player battle files (BATTLE_BOOT_BLOCKS = ["edstati3", "battle_data"] - the two extraction labels covering the retail block, extraction 863..866). It walks every record's LZS stream, uploads any standard TIM textures, and runs the descriptor-driven CLUT pass via battle_data_pack::clut_uploads. Retail performs the equivalent pre-pass via FUN_8001E890 at boot or first-battle entry so battle init has the character meshes resident before the scene-specific FUN_8001FE70 walk fires. The returned VRAM is kept separate from field VRAM - battle init merges it; field rendering does not.

Row-479 NPC CLUTs

The town01 NPC TMDs at field intersections sample CLUT row y=479, x=128..240 (CBA = 0x77C8..0x77CF). The source is the matching scene_tmd_stream entries in town01's own block, wrapped in type-0x01 chunks that FUN_8001FE70 dispatches during battle init (npc-palette). The earlier hypothesis that these palettes lived in the player battle files and reached VRAM via a boot pre-load is refuted by the byte-match corpus on battle-data-pack.

Diagnosing missing CLUTs

asset clut-finder <vram_x> <vram_y> --extracted-root extracted

walks extracted/tim_scan/<entry>/*.tim and reports every TIM whose CLUT covers the requested VRAM cell. Straight off the disc image, legaia-engine clut-trace --scene <name> --disc <bin> walks every dropping MissingClut prim in a scene, groups by (cba, depth), and reports suppliers across the whole PROT corpus by rectangle containment; --runtime-vram <bin> (a mednafen save-state VRAM dump) marks which missing rows are populated at runtime (engine loader gap) vs absent everywhere.

VRAM oracle (engine vs runtime)

legaia-engine vram-oracle --scene <name> --disc <bin> --runtime-vram <bin> rebuilds the scene's targeted VRAM and reports per-band overlap counts against the runtime ground truth. --diff-png writes a colour-coded 1024×512 diff (red = runtime-only, green = engine-only, blue = both non-zero but different, greyscale = match); --tiles adds a 64×64 breakdown. The parity policy behind it is on the engine page.

Music / SFX selection (BGM lookup)

When a scene asks for "music track 3", there is no music table to consult. The number is an offset: scene-local ids count from the scene's own CDNAME block, global ids count from the shared music bank.

// FUN_800243F0
if (bgm_id < 2000) {
    prot_idx = scene_local_base + 6 + bgm_id;     // _DAT_80084540 + 6 + bgm_id
} else {
    prot_idx = global_pool_base + (bgm_id - 2000); // _DAT_8007BC64 + bgm_id - 2000
}

The "BGM table" is the CDNAME.TXT per-scene block layout. Global id 2000+i is sound-test track i, but the music_01 bank is piecewise in extraction space - 988+i for i <= 67, 990+i for i >= 68, with a gap at 1056 / 1057 - not a flat base. Resolver engine-core::music_labels; the full cue list is on music tracks. Details under the field VM → "BGM lookup table".

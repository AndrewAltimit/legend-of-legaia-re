The browser host

What the WebAssembly bundle exports to this site: the play runtime behind the play page, the standalone minigames page, the viewer pages and the ROM patcher. Nothing is uploaded - the disc image a visitor supplies is read in their browser.

Module map

Simulation and draw are split on purpose

  • runtime is the simulation: load a disc, enter a field scene, set the pad word, set the camera azimuth so the D-pad remaps camera-relative, tick a frame, read state. It runs the ported field VM, free movement against the walkability grid, the NPC motion VMs and the dialogue runner.
  • play is what the page draws: the assembled map, the lead’s mesh posed from the world’s live pose frame, and the scene’s placed NPCs at their live positions.

The page hands each animation frame’s sim ticks to play_frame_ticks (runtime/frame_ticks.rs), which gives each tick to the owner BootSession::claim_tick names - the field, the pause menu, a shop or name entry - in the order the native window’s sim_tick uses. Menus, shops and name entry therefore step on the sim tick, not the display frame, and the whole frame body is compared state by state against the native window in engine-shell/tests/host_frame_parity.rs.

Much of a frame’s work has an answer nothing reads, since at a town’s camera most bodies are off screen. Outside PSX mode the page leaves out a draw wholly past the side of the clip volume, keeping the others in their order, and holds a posed actor or a morph’s mesh build until the camera or a light can reach it. The overlay canvas and the HUD’s text repaint only when what they show has changed. The picture stays the one the unconditional work gives, which the frame-hash oracle pins.

The map and NPC layers make the native window’s exact resolver calls. NPC clip playback runs in simulation-tick time - one clip player per placed slot, advanced once per tick - so cadence does not depend on the display’s refresh rate and scripted actors perform their cued beats.

The quality step-down

No code on the page looks at the device, so on a GPU short of the defaults the page steps its own picture down. The decision is site/js/play-quality-ladder.js, with no GL, DOM or engine in it.

  • When. Two 4-second windows in a row whose median frame gap is over 40 ms. A median means one stall cannot cause a step; a gap over a second, a paused view or a movie restarts the count; a window whose frame function already takes half the gap is left alone, because no rung relieves the main thread.
  • What, in order. Ambient occlusion off, the 3D canvas at 75%, at 50%, lamp shadows off: by what each pays under SwiftShader, where ambient occlusion and the 50% canvas are each worth about half the GPU’s frame, 75% about a fifth, lamp shadows a few percent. SwiftShader is a proxy; a tiled phone GPU may rank them otherwise.
  • Down only, and session only. Nothing steps back up on its own, and the state ends with the page.
  • It never writes an option. A rung is view-side state over the player’s option, and the boxes keep reading what the player chose.
  • A player’s choice wins. Touching a rung’s box or key takes that rung out of the ladder. “Put it back” on the note, or Reset to defaults, restores everything and disarms it for the session.
  • Retail is exempt. While Retail-faithful or PSX rasterisation holds, no rung steps and one already stepped stops counting.
  • It says so. A note under the picture names what is off for as long as it is off.

MSAA is not a rung: it is fixed when a context is created, and it is the smallest of the measured costs, so the context keeps it. ?autoquality=0 leaves the ladder unarmed. The native window has no ladder.

A capped page does not stall on a slow GPU the way an uncapped bench run does: the browser holds back requestAnimationFrame while frames are pending, so cost spreads evenly and the main thread stays free for the audio pump. Below 15 fps the world itself runs slow, since a display frame runs at most four ticks and drops the rest.

Keeping two hosts in step

The play page and the native window are two framebuffers over one engine, and the failure that costs most is quiet: a screen is wired natively and the web host drifts behind with nothing in any diff to say so.

Every screen’s geometry is a draw-list builder in engine-ui, and a host has that screen exactly when it calls the builder. So the feature surface can be derived from source, and a gate fails when a builder reaches the native window but not this crate. One-host cases live in a waiver file, each with a reason, validated in both directions so it cannot decay into a stale list.

A screen can be fully wired and connected to nothing. The gate answers “does this host call the builder”; it cannot answer “does this host feed it the same model”. The options screen was drawn on both hosts with the gate green while one of them rebuilt its session from defaults on every open and dropped the result on close.

The disc image

The play page reads a disc in three stages (js/play-disc.js), so a visitor is not waiting on movies they may never play and the wasm memory, which never shrinks, does not hold a whole image.

A consumer that polls every frame asks span(lba, sectors), which answers from what is resident or null, and prefetch on null; it installs on the first frame after the read lands. A window asked through prefetch is held until its consumer calls release, so eviction cannot take it between the read and the install. read is the form for a consumer that uses the bytes once and right away (the voice banks): it answers with the bytes themselves and keeps nothing.

span answers only from one block that covers the whole window. Neighbours are not stitched: a window across two blocks is read again, and the wider block replaces any it covers. What is left once released stays under RESIDENT_CAP, oldest use out first. The cap (32 MiB) holds the largest XA file beside the largest set of clips one scene reads ahead. A read landing with nobody waiting is dropped.

Movies. The window is read when the beat asks and dropped at the install, which copies it and demuxes once. The engine holds the world until then, bounded by INSTALL_TIMEOUT_FRAMES (600 ticks, wall time unless the page runs below about 15 fps), which is about 3 MB/s for MV1.STR. A read past it finishes the beat unplayed and the hand-off runs, as a page with no disc does.

Voice clips. A scene’s and a round’s likely lines are on play_xa_stage_requests_json before they are raised (prestage_xa_clip), so _serveXaStage reads every listed file ahead, widest span per file, and installs one row per frame, oldest first. A line whose row was served plays on the call that raises it. A line nothing listed is deferred: it plays when its row is served, a read and at least a frame after the request. Neither path reaches the simulation, which never reads the XA lane back.

Failures. A read that fails is tried three times, a quarter of a second and half a second apart. Then the window is reported failed until its release: the movie finishes unplayed, the clip’s row is installed empty and dropped. The next ask reads again. Since the bytes are not in memory, a file moved or changed on disk during a session costs every movie and clip not yet read.

A trapped engine is rebuilt by reading the head again (recoverRuntime), which goes to the Blob and not through the cap, and the voice banks are read again the same way.

While a movie is up its overlay covers the GL view, and the frame skips its GL draws: the world is held, and every pass that reads the frame (bloom, fog, ambient occlusion, the transition capture) reads one drawn earlier in the same frame. The sync with the engine still runs each frame, and the 2D overlay is still drawn.

The battle edge

The frame where the transition hands over to a fight reads a lot off the disc, and all of it is known when the transition starts: the party, its equipment and the fight’s stage. So while the encounter sits in its transition, the page runs one step per frame of the scene host’s prewarm: the entries the edge reads, each member’s battle form, the stage’s resources.

The steps fill two memos and the disc index’s cache and write nothing else, so no frame or tick can see whether they ran. A key the edge then reads differently is a miss, and builds as it would have. Both hosts and the headless drivers go through the memos; only this page prewarms.

Touch pad and the bug report

The touch pad (touch-pad.js) is an on-screen PSX pad over the picture: a D-pad, the four face buttons, the shoulders and Select / Start. It does not keep an input path of its own. Each pressed button is held through a virtual source in pad-bindings.js that joins the controller poll, so every reader of a controller press - the field tick, the menus, the title card - takes a touch press with no call site and no binding table of its own. The D-pad is one surface read by angle from its centre, with a dead zone in the middle and about a 45-degree wedge per diagonal, so a thumb rolls between directions without lifting. It shows by default where the only pointer is coarse (a phone or tablet), the Touch pad button toggles it on any device and remembers the choice, and hiding it releases whatever it held.

Checked headless. The controls step of scripts/ci/check-pages.mjs drives what only a browser has, on the built bundle: a file that is not the game is refused in words and the picker still takes the next one; on a touch-only device the pad is up, its D-pad walks the lead and lets go, START opens the pause menu and the first touch has brought sound up; a controller on the standard mapping walks by D-pad and by stick and opens and closes the menu on Start; Fullscreen presents the 4:3 picture at the screen’s height with the keyboard still on the canvas.

Copy report beside the disc picker puts on the clipboard what a bug report needs: the bundle’s version, the browser and GL renderer, the window, the input devices (pointer kind, touch points, whether the touch pad shows, each connected controller and its mapping), the disc file’s name and size, the engine’s state, the stored options and the page’s last warnings and errors. It holds no disc bytes.

The other surfaces

The minigames page holds the play hosts’ AudioDirector over one WebAudioOut, opened inside a user gesture. A tab change is that game’s mode entry: the old game’s voices and armed cues go, and the new game’s banks stage as its door warp stages them. Every cue keys a live SPU voice, so its envelope, volume, pan, reverb send and closed-slot silence are the play hosts’; a disc test renders each cue against the director and requires the same samples, and a host-drift tier rejects a cue played as a decoded buffer. Only the BGM is a buffer, an offline render at the same unity gain.

  • Viewer pages - assembled full-scene maps, the field-NPC catalog, the Tactical Arts and equipment viewers, summon and battle-stage previews - read the same format crates the extractor does.
  • NPC conversations on the NPCs page are each actor’s interaction script walked down every arm by the field kernel: pages of text, Yes / No menus and where each option leads, the story-flag and inventory tests that pick a branch, the side effects, and what the next talk runs. Text is decoded from the visitor’s disc in the browser.
  • Scene export builds a textured .glb of a scene in the browser.
  • The ROM patcher runs the randomizer and mod pipeline client-side over the visitor’s disc and hands back a patch file. See ROM patcher.
  • The translation workbench is the in-browser language-pack editor.

The browser host

What the WebAssembly bundle exports to this site: the play runtime behind the play page, the standalone minigames page, the viewer pages and the ROM patcher. Nothing is uploaded - the disc image a visitor supplies is read in their browser.

Module map

Simulation and draw are split on purpose

  • runtime is the simulation: load a disc, enter a field scene, set the pad word, set the camera azimuth so the D-pad remaps camera-relative, tick a frame, read state. It runs the ported field VM, free movement against the walkability grid, the NPC motion VMs and the dialogue runner.
  • play is what the page draws: the assembled map, the lead’s mesh posed from the world’s live pose frame, and the scene’s placed NPCs at their live positions.

The page hands each animation frame’s sim ticks to play_frame_ticks (runtime/frame_ticks.rs), which gives each tick to the owner BootSession::claim_tick names - the field, the pause menu, a shop or name entry - in the order the native window’s sim_tick uses. Menus, shops and name entry therefore step on the sim tick, not the display frame, and the whole frame body is compared state by state against the native window in engine-shell/tests/host_frame_parity.rs.

The map and NPC layers make the native window’s exact resolver calls. NPC clip playback runs in simulation-tick time - one clip player per placed slot, advanced once per tick - so cadence does not depend on the display’s refresh rate and scripted actors perform their cued beats.

Keeping two hosts in step

The play page and the native window are two framebuffers over one engine, and the failure that costs most is quiet: a screen is wired natively and the web host drifts behind with nothing in any diff to say so.

Every screen’s geometry is a draw-list builder in engine-ui, and a host has that screen exactly when it calls the builder. So the feature surface can be derived from source, and a gate fails when a builder reaches the native window but not this crate. One-host cases live in a waiver file, each with a reason, validated in both directions so it cannot decay into a stale list.

A screen can be fully wired and connected to nothing. The gate answers “does this host call the builder”; it cannot answer “does this host feed it the same model”. The options screen was drawn on both hosts with the gate green while one of them rebuilt its session from defaults on every open and dropped the result on close.

The other surfaces

  • Viewer pages - assembled full-scene maps, the field-NPC catalog, the Tactical Arts and equipment viewers, summon and battle-stage previews - read the same format crates the extractor does.
  • NPC conversations on the NPCs page are each actor’s interaction script walked down every arm by the field kernel: pages of text, Yes / No menus and where each option leads, the story-flag and inventory tests that pick a branch, the side effects, and what the next talk runs. Text is decoded from the visitor’s disc in the browser.
  • Scene export builds a textured .glb of a scene in the browser.
  • The ROM patcher runs the randomizer and mod pipeline client-side over the visitor’s disc and hands back a patch file. See ROM patcher.
  • The translation workbench is the in-browser language-pack editor.

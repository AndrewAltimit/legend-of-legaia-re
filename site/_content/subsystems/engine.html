Engine reimplementation

A from-scratch Rust port of Legend of Legaia in the ScummVM / OpenRCT2 mould: the original PlayStation code is traced with a disassembler, documented, and rewritten fresh - never recompiled. You supply your own disc image; the engine reads every asset from it and plays the game. Retail behaviour is the measured ground truth, provable against parity oracles, and enhancements ride on top as toggles with a retail-faithful mode always one flip away. This page is about how the port itself is built.

At a glance

What it is not
A recompile of SCUS_942.54, a re-authored asset set, or a build that loses the retail-faithful mode

Proof
Save-hash scenarios, VRAM diff against save-state captures, mode / audio / sim traces, record-replay determinism, a retail comparison corpus
Legal posture
Zero Sony bytes in the repo or any binary; disc-dependent tests skip when no disc is supplied

How the crates stack

The port is a stack of small crates with one rule running through it: the lower a crate sits, the fewer things it may link. Format parsers know nothing about engines; the VMs know nothing about GPUs or speakers; the simulation draws nothing; and only the hosts at the top touch a window, a browser or an audio device. That is what lets the browser run the same engine as the native window - it simply links a different top row.

Runtime architecture

One session, one world. A host hands the session a pad word and the camera azimuth each frame; the session runs the mode seat and the scene host; the scene host ticks the world; the world drives every VM by implementing its Host trait. Rendering and audio hang off the side: they consume what the world reports and never reach back into it.

The frame model

One world tick is one retail vsync, and retail never catches up: a slow frame makes a slow game. The hosts render at the display’s refresh instead, so the engine owns the rule that turns display frames into ticks (engine-core::frame_step): whole 1/60 s ticks with the remainder carried, at most four per display frame, and a backlog past four dropped rather than carried. Both hosts call the same kernel. The pause menu, the name-entry prompt and a movie consume ticks without ticking the world - under the pause menu that is retail’s own shape, since its mode handler runs no frame driver.

Goal and non-goals

Goal: a playable port of the NA release on modern systems via Rust + wgpu, with a WASM target; JP / EU follow once NA is solid. “Playable port” is grounded in retail, not bound by it: the traced dumps and oracles pin what the original does, the faithful mode reproduces it provably, and that is a measuring stick rather than a ceiling.

  • Not a decompilation. No byte-matching recompile is attempted and nothing is auto-translated from the MIPS; every line is fresh Rust written from format docs and the traced dumps, which stay reference material. Per-opcode tests use synthetic bytecode.
  • Never lose retail. Departures live behind toggles; the oracles keep “faithful” a testable claim. A quirk is preserved in the faithful mode and fair game to improve outside it.
  • No re-authored assets. Every texture, mesh, sample and sequence comes off your own disc at runtime.
  • Deterministic simulation. Seeded RNG, fixed timestep - the precondition for record / replay.

Modding and translation are shipped tracks, not exceptions: the randomizer (in-browser via the ROM patcher) and the translation tools patch a user-supplied disc without touching the engine, and what they prove out against retail - softlock fixes, tuning sliders - is expected to graduate into engine toggles.

Fidelity and enhancements

In the faithful mode no toggle changes damage, drops, AP costs, encounter rates or story flags, and every parity measurement runs against that mode. Enhancements are explicit toggles, bit-identical to retail when off, so flipping one never touches replays or oracles. Defaults follow the better experience: a knob still defaulting to retail marks an enhanced side that is maturing, not a policy of restraint.

  • Shading defaults to retail. Retail’s field mesh paths issue one GTE colour op - the depth cue - and no lighting op, so shading is baked into the mesh colour words as texel × colour / 128. The engine draws exactly that; enhanced lighting is layered over it and is an identity when off (every parity capture turns it off).
  • Rasterisation defaults to clean. The default image is sharper than a PlayStation’s; here faithfulness is opt-in.
  • Affine texturing is not gated. The PS1 has no perspective-correct texturing and neither does the mesh path; the swimming textures are the faithful behaviour on both hosts.
Why every minigame must be leavable

A mode the player can enter has to be one the player can leave on every host, or reaching it is a softlock. Retail has no single exit to port: each minigame quits through its own overlay’s state machine (the slot cabinet’s exit row, the duel’s decided-match confirm, the arena’s give-up arm). World::poll_minigame_escape is therefore an engine affordance: Start leaves whichever minigame is live through its own exit, so the cash-out or score matches a deliberate quit, and closes the round trip when the entry came through a door warp. It lives in the world tick, so both hosts inherit it.

The browser host

The WASM target runs the engine itself, not a second implementation of it: the play page holds a BootSession over its WebAudio output, built over a scene host it assembles in memory from the disc image. It reaches field and town scenes, live battles, the title and the opening chain, the pause menu and shops, the minigames and audio. Each screen is drawn from engine state through the shared engine-ui / engine-screens builders and the site’s WebGL renderer; per-feature parity between the two hosts is policed by the host-drift gates.

  • Seating. The cold-boot spawn is authored for town01 only; every other scene expects a door warp. A host that drops the player straight into a scene gets a resolved seat: the retail one if it stands inside the scene’s largest walkable region, otherwise a door-arrival tile or the region’s centroid.
  • Framing. Both hosts run the engine’s retail follow camera and neither culls geometry; a wall between the lens and the player is handled by the see-through-walls fade.

Details: the VRAM static mask

A save state’s VRAM is a live snapshot: two captures of the same scene differ across ~40% of the texture band (animation frames, battle leftovers), so no stateless pre-pass can be byte-exact against one snapshot. The VRAM test asserts against the static mask - the words identical across every same-scene capture - excluding the runtime-managed NPC palette band around row 479. Incompleteness is not flagged; a wrong texel on a static pixel is.

Two refinements the captures forced: the shared effect-texture band is history-dependent (a handful of pixels hold a boot-resident value until a battle re-uploads the disc bytes), so cells inside it must be static across all scenes; and the world map’s ocean palette rows 506 / 508 / 509 animate, so they are excluded for world-map scenes only.

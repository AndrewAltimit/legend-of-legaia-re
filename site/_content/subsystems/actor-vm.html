Actor / sprite VM

The interpreter that choreographs the game's UI windows: when the shop's gold box, vendor plate and Buy / Sell picker slide onto the screen together, that entrance is a tiny script, and this VM runs it. It is the simplest of Legaia's runtime VMs - 13 jump-table slots, fixed 4-byte instructions, no control flow. This page also covers the per-actor animation tick, a separate routine that shares the name "actor".

What it is not

Despite the name it inherited, this VM never moves characters. NPC pathing is the motion VM, animation programs are the move VM, and per-frame body animation is the separate anim tick below. This VM only ever moves windows.

How it works

A caller hands the VM a pointer to a program and the VM executes the whole thing in one call. It installs targets; the sliding itself happens over the following frames, in the window system's per-frame walker.

OpcodeWhat it does to the named window
00End of program
01Open (create if missing) and slide toward its home position; motion cleared if it is already there
02Open and slide toward the packed position in the operand
03Write the operand's low byte as the window's style byte
04Begin an animated close
05Close every window
06Clear the window's motion flag
07No-op
08Destroy immediately (free its buffers, unlink it)
09Open and snap to the packed position, or to home when the operand is zero
0ARe-create in place: remember its position, destroy, re-create, snap back there
0B..0DNo-op

A packed position is x = (w >> 7) & 0x1FE, y = w & 0xFF, so x is always even. The programs are data resident in the overlay itself, not a scene file: the shop's picker runs its open program (slide in the vendor plate, picker, gold box and two panels) on entry and the slide-away program on the Sell transition.

There is no branching and no cross-context targeting - a program is a flat command list. That contrast is the reason it is a separate VM from the field VM, a 43-opcode variable-length dispatcher with halt-acquire semantics and sub-dispatcher families: UI widgets at the presentation layer, scripts at the gameplay layer.

History: "lives in the title-screen overlay", and the helper names

An earlier reading placed the driver in an unindexed PROT.DAT gap after entry 0899. Recovering the menu overlay's base resolved the same image as PROT 0899 itself, which is why the shop, pause menu and save UI can all reach it. The same pass found the slide and snap helpers' names swapped (read off their tails, FUN_800357FC starts a slide and FUN_800358C0 snaps) and what had been called a "global tick" helper to be close-all.

The per-actor anim tick (a separate system)

FUN_80021DF4 is the per-actor animation and physics tick, related to the VM above only in that both touch actor records. It lives in the main executable and runs once per game tick for every active actor, laddering through a dispatch byte at actor+0x5A that selects which side-effects fire. It is also where the move VM gets stepped.

ByteNameWhat it drives
0x01PlainCommon stages only: plain kinematics, no extra arm (the ladder never tests 1)
0x02KeyframeAltPer-bone keyframe-style; shares logic with 0x06
0x03PathIntegrates a velocity triple and hands it to the CLUT-cell HSV cycler - the scripted colour pulses; skips the default motion
0x04VramScrollWrap-scrolls a VRAM texture rect (water, conveyors); installed by move-VM op 0x1E
0x05PathAlt / SFXPositional sound emitter: distance-based pan and volume; skips the default motion
0x06KeyframeThe dominant path: per-bone keyframe interpolation
0x07SplineSpline / curve-driven variant; installed by move-VM op 0x45

The tick reads three fixed fields: the record pointer at +0x4C, the dispatch byte at +0x5A, and the frame counter at +0x68 (seeded to 100 when an animation is registered). In the port it is engine-vm::actor_tick, a layered pipeline with a typed ActorPhysics struct; the keyframe arm is legaia_anm::AnimPlayer.

Per-arm physics

Every dispatch byte shares a common pre-update (timer drain, rotation accumulator) and late-update (envelope caps, optional move-VM kick, visibility cull, per-arm render); the arms differ in the middle.

  1. Pre-updateEvery byte: drain the per-frame timer at +0x54 and the rotation accumulator at +0x22.
  2. Arm0x02 / 0x06 fold acceleration into the shake envelopes; 0x05 runs the SFX emitter; 0x03 integrates the path velocity.
  3. Default movementEvery byte except 0x03 and 0x05: add the angular rates, the trig-LUT world update, and step render scale and depth-cue by their rates.
  4. Late-updateCap the envelopes; kick the move VM; cull; render the arm (line draws for 0x04, a triangle for 0x07, the keyframe pose for 0x06).
The arms field by field
  • Keyframe accel (0x02 / 0x06). Folds +0xC0..+0xCA × scalars >> 6 into the shake envelopes at +0xB4..+0xC8.
  • Positional SFX emitter (0x05). Ramps a fade between (+0x90, +0x92) and (+0x94 + +0x98, +0x96 + +0x9A) over +0xBC frames, or integrates the velocity pair. Issues SsAPI key-on (FUN_80065034), volume-only (FUN_800657D0) or release (FUN_800250D4) calls from listener distance.
  • Path (0x03). Velocity from +0x96..+0x9A into +0x90..+0x94, handed to the CLUT-cell HSV cycler FUN_80019D50.
  • VramScroll (0x04). StoreImage a band → MoveImage the remainder → LoadImage the band back at the far edge, on the actor's +0xD0 rect; the countdown at +0xC6 drains by the frame scalar and reloads from +0xC4.
  • +0xB4 aliases two arms: the SFX emitter reads it as an i32 release-pending flag, the keyframe arms as two i16 shake values. One actor never runs both, so the alias is benign.

One pointer, several meanings (actor+0x4C)

The field at +0x4C is a multi-purpose pointer whose meaning depends on the spawn path that created the actor. A morph actor spawned from a VDF record keeps its spawn bytes there (read once, at spawn, to size and fill the vertex pool); a keyframe-animated actor keeps its pose-output buffer there, read by the renderer's per-bone interpolator. Retail relies on the actor classes never colliding. The window VM above never reads +0x4C.
